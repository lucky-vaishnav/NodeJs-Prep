## 2.5 Asynchronous Error Handling in Production

We've already covered `try/catch`, Promise rejection, error-first callbacks, and how `await` propagates errors. We'll focus only on the remaining production-level gaps.

### 1. Fire-and-forget Promises

Consider an API that responds to the user while starting an analytics operation in the background.

JavaScript

```
app.post("/orders", async (req, res, next) => {
    try {
        const order = await createOrder(req.body);

        sendAnalytics(order); // Not awaited

        res.status(201).json(order);
    } catch (err) {
        next(err);
    }
});
```

What's the problem?

If `sendAnalytics()` returns a Promise that rejects, the surrounding `try/catch` won't catch that rejection because the Promise wasn't awaited or otherwise handled.

A simple fix is to handle the background failure explicitly:

JavaScript

```
sendAnalytics(order).catch(err => {
    logger.error({ err, orderId: order.id }, "Analytics failed");
});
```

Now the API can respond without waiting for analytics, and the rejection is handled.

However, logging alone is appropriate only if losing that analytics event is acceptable. If the operation is important, consider a durable queue or transactional outbox instead.

Senior-level takeaway: Fire-and-forget doesn't mean error-and-forget.

### 2. `try/catch` doesn't handle every asynchronous failure

Compare these examples.

Case A — Properly awaited

JavaScript

```
try {
    await saveOrder(order);
} catch (err) {
    logger.error(err);
}
```

The rejection from `saveOrder()` is caught.

Case B — Detached Promise

JavaScript

```
try {
    saveOrder(order);
} catch (err) {
    logger.error(err);
}
```

If `saveOrder()` returns a Promise that rejects later, this `catch` won't handle it.

Case C — Intentionally detached, but handled

JavaScript

```
saveOrder(order).catch(err => {
    logger.error(err);
});
```

The rejection is handled, although the calling function doesn't wait for the operation.

The rule is simple:

> Every Promise should have an intentional error-handling strategy, even if the caller doesn't need to await its completion.

### 3. Where should errors be handled?

A senior developer should distinguish between handling an error and passing it to the appropriate layer.

Consider this flow:

```
Database / External Service
           ↓
    Service Layer
           ↓
    Controller/API
           ↓
    Error Middleware
           ↓
    HTTP Response
```

Each layer has a different responsibility.

* Service layer: Propagate errors or recover when it has enough context to do so safely.

* Controller: Translate known application failures into suitable HTTP responses.

* Error middleware: Centralize response formatting, logging, and unexpected-error handling.

* Background worker: Handle failures through its own retry, dead-letter, or failure-reporting strategy.

For example, in Express:

JavaScript

```
app.post("/orders", async (req, res, next) => {
    try {
        const order = await createOrder(req.body);
        res.status(201).json(order);
    } catch (err) {
        next(err);
    }
});
```

An error-handling middleware can then format the response consistently.

Version note: Express 5 automatically forwards rejected Promises from route handlers to error middleware. With Express 4, rejected Promises generally need explicit forwarding or an async-handler wrapper.

### 4. Retry: when is it safe?

Retries are useful for transient failures, such as temporary network errors or rate limits. But retrying every error is dangerous.

Imagine:

JavaScript

```
await paymentProvider.chargeCustomer(paymentRequest);
```

The provider processes the payment, but the network connection times out before your application receives the response.

Your application doesn't know whether the payment succeeded.

Blindly retrying could charge the customer twice.

A safer approach is:

1. Determine whether the error is transient or permanent.

2. Use an idempotency key where the provider supports it.

3. Retry with bounded attempts and exponential backoff, optionally with jitter.

4. If the outcome remains unknown, query the provider or reconcile the transaction instead of assuming failure.

For example, a delay can grow like this:

```
Attempt 1 → immediately
Attempt 2 → after 1 second
Attempt 3 → after 2 seconds
Attempt 4 → after 4 seconds
```

These values are illustrative. Production backoff should have limits and account for provider guidance, deadlines, and rate limits.

Important: An idempotency key helps prevent duplicate effects only when the receiving system correctly supports and enforces it.

### 5. What about `unhandledRejection`?

Node.js provides a process-level event:

JavaScript

```
process.on("unhandledRejection", (reason, promise) => {
    logger.error({ reason }, "Unhandled Promise rejection");
});
```

This can help with diagnostics, but it should not replace proper error handling.

By the time a rejection reaches this handler, the application may not know which request or business operation should recover from it. Continuing to run after serious unhandled failures may also leave application state inconsistent.

For critical failures, use deliberate process-level failure policies, reliable logging, graceful shutdown where appropriate, and a process manager or orchestrator to restart unhealthy instances.

Node.js's unhandled-rejection behavior depends on its runtime configuration and version; don't assume this event is merely a harmless warning.

## What to add to your notes

You don't need to rewrite your existing Promise error-handling notes. Add these production-level points:

* Detached Promises need explicit rejection handling.

* `try/catch` doesn't catch a Promise rejection that isn't awaited or otherwise handled.

* Handle errors at the layer that has enough context to recover or translate them.

* Retry only when appropriate; consider idempotency, backoff, and unknown outcomes.

* Process-level rejection monitoring is a safety net, not the primary error-handling strategy.
