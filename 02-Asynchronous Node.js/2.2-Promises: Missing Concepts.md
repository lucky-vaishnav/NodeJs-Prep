## 2.2 Promises: Missing Concepts

We've already covered Promise creation, chaining, microtask scheduling, rejection handling, and `return` vs. `return await`. We'll skip those topics.

The next gap is Promise combinators: how to coordinate multiple asynchronous operations, what happens when one fails, and how to choose the right strategy in production.

## 1. `Promise.all()` — All results are required

Use it when several independent operations can run concurrently and you need every result.

JavaScript

```
const results = await Promise.all([
    getUser(1),
    getOrders(1),
    getNotifications(1)
]);
```

If all three Promises fulfill, `results` contains their values in the same order as the input Promises, not the order in which they finish.

If any Promise rejects, `Promise.all()` rejects with that failure.

Important: It does not automatically cancel the other operations. They may continue running.

Production example: loading independent data for a dashboard when the response requires every section.

## 2. `Promise.allSettled()` — Every outcome matters

Use it when you want to collect both successes and failures without failing the entire group because one operation rejected.

JavaScript

```
const results = await Promise.allSettled([
    sendEmail(user),
    updateAnalytics(user),
    syncExternalProfile(user)
]);

for (const result of results) {
    if (result.status === "fulfilled") {
        console.log("Success:", result.value);
    } else {
        console.error("Failure:", result.reason);
    }
}
```

Example output structure:

JavaScript

```
[
    { status: "fulfilled", value: "Email sent" },
    { status: "rejected", reason: Error("Analytics unavailable") },
    { status: "fulfilled", value: "Profile synced" }
]
```

Production example: running independent notification or best-effort synchronization tasks where partial success is acceptable.

Note that `allSettled()` waits for every input Promise to settle. It doesn't impose a timeout on slow operations.

## 3. `Promise.race()` — First settlement wins

`Promise.race()` settles as soon as the first input Promise settles, whether that outcome is fulfillment or rejection.

JavaScript

```
const result = await Promise.race([
    fetchData(),
    timeoutAfter(3000)
]);
```

This pattern can be used to implement a timeout, but there's an important catch:

Racing against a timeout does not cancel the original operation.

If the timeout wins, `fetchData()` might continue consuming resources in the background.

For an actual cancellable request, use an appropriate cancellation mechanism, such as `AbortController`, if the API supports it.

## 4. `Promise.any()` — First successful result wins

Use it when several alternatives are available and you only need one successful result.

JavaScript

```
const result = await Promise.any([
    fetchFromReplicaA(),
    fetchFromReplicaB(),
    fetchFromReplicaC()
]);
```

* The first fulfilled Promise determines the result.

* A rejection doesn't win while another Promise could still fulfill.

* If every input rejects, the result rejects with an `AggregateError` containing the failures.

Production example: querying redundant read replicas or equivalent service endpoints when any one successful response is sufficient.

Again, the losing operations are not automatically cancelled.

## 5. Comparison table

| Method                 | What determines the outcome?        | Typical use                    |
| ---------------------- | ----------------------------------- | ------------------------------ |
| `Promise.all()`        | All fulfill, or the first rejection | All results required           |
| `Promise.allSettled()` | Wait for every result to settle     | Partial success is acceptable  |
| `Promise.race()`       | First fulfillment or rejection      | Timeouts, competing operations |
| `Promise.any()`        | First fulfillment, or all reject    | Redundant alternatives         |

## 6. A subtle but important distinction: concurrency vs. cancellation

Consider:

JavaScript

```
const results = await Promise.all([
    chargeCustomer(),
    reserveParking()
]);
```

If `chargeCustomer()` rejects, `Promise.all()` rejects. But that does not guarantee `reserveParking()` stops.

This creates a production concern: asynchronous side effects can still happen after the caller sees a failure.

For operations involving payments or reservations, don't rely on Promise combinators alone to maintain consistency. Use explicit cancellation where supported, idempotency, compensation, and reconciliation where appropriate.

Also, `Promise.all()` doesn't itself start work in parallel. In this example, the function calls are evaluated before `Promise.all()` receives their returned Promises. They can proceed concurrently if the functions initiate asynchronous work independently.

## Checkpoint — Apply the concepts

Imagine an API needs data from three independent services:

* Service A returns successfully after 100 ms.

* Service B rejects after 200 ms.

* Service C returns successfully after 500 ms.

Answer these three questions in your own words:

1. With `Promise.all()`, what does the caller receive, and does Service C automatically stop?

2. Which combinator should you use if you need to inspect all three outcomes?

3. If you only need the first successful response from equivalent replicas, which combinator is the best fit?

After this, we'll move to the remaining gaps in 2.5 Error handling, then systematically cover 2.6 Concurrency vs. parallelism.

---

All three answers are correct — 3/3. ✅

1. `Promise.all()` — Rejects when Service B rejects. Service C continues unless it is independently cancelled.

2. `Promise.allSettled()` — Waits for all three Promises to settle and returns each outcome.

3. `Promise.any()` — Returns the first successful result; rejects with an `AggregateError` if all inputs reject.

One important senior-level detail: `Promise.all()` rejects when the first rejection is observed, but it doesn't cancel other operations or wait for all of them to finish before rejecting.
