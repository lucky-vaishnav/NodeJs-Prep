## 2.6 Concurrency vs. Parallelism

This is the last topic in Phase 2 that we need to cover systematically. We've already discussed the Event Loop, libuv Thread Pool, and Worker Threads, so we'll connect those concepts rather than repeat them.

## 1. Concurrency vs. parallelism

Concurrency means multiple tasks can make progress during overlapping periods. It doesn't necessarily mean they execute at the exact same time.

Parallelism means multiple tasks are actually executing simultaneously, typically on different CPU cores.

## Concurrency

Tasks make progress over overlapping periods

Task A

Task B

One task can wait for I/O while another progresses.

## Parallelism

Tasks execute at the same time

CPU core 1 · Task A

CPU core 2 · Task B

Both tasks execute simultaneously on separate cores.

The key distinction: concurrency is about coordinating multiple tasks; parallelism is about simultaneous execution.

## 2. How this applies to Node.js

Consider three database requests:

JavaScript

```
const results = await Promise.all([
    getUser(1),
    getOrders(1),
    getNotifications(1)
]);
```

Assuming these functions initiate independent asynchronous I/O, their operations can be in flight concurrently.

The main JavaScript thread doesn't sit idle waiting for each database response. It can execute other JavaScript while the I/O is pending.

However, this code alone does not mean the three JavaScript functions execute simultaneously on multiple CPU cores.

### The three models

1. Main JavaScript thread

JavaScript normally executes one piece of application code at a time on the main thread. Asynchronous I/O lets the thread do other work while waiting.

2. OS I/O and libuv Thread Pool

Network I/O can be coordinated through OS facilities. Certain filesystem, crypto, and other native operations can use libuv's worker pool. This enables concurrent work without running all of it on the main JS thread.

3. Worker Threads

Worker Threads can execute JavaScript in separate threads, allowing CPU-heavy JavaScript tasks to run in parallel when hardware resources permit.

## 3. Why `Promise.all()` doesn't guarantee parallelism

Compare these examples.

Example A — Asynchronous I/O

JavaScript

```
const [user, orders] = await Promise.all([
    fetchUser(),
    fetchOrders()
]);
```

If both functions initiate independent I/O operations, those operations can progress concurrently.

Example B — CPU-heavy JavaScript

JavaScript

```
const first = calculatePrimeNumbers(100_000);
const second = calculatePrimeNumbers(200_000);

const results = await Promise.all([first, second]);
```

If both functions are synchronous CPU-heavy calculations, they execute sequentially on the main thread before `Promise.all()` is even called.

The `async` keyword and Promise combinators do not automatically move CPU work to other threads.

To run CPU-heavy JavaScript in parallel, you could use Worker Threads.

## 4. When does concurrency become a problem?

Imagine an API receives 1,000 requests, each initiating several external service calls.

Concurrency can improve throughput because the application doesn't need to wait for each call to finish before starting the next.

But unlimited concurrency can cause:

* Database connection pool exhaustion.

* External API rate limiting.

* Excessive memory usage.

* Too many queued operations.

* Increased latency and timeouts.

For production systems, concurrency often needs to be bounded using techniques such as semaphores, worker queues, request limits, and backpressure.

Senior-level takeaway: Concurrency is not automatically faster. It improves utilization when tasks can make progress independently, but the system still needs capacity management.

## 5. Interview-ready answer

If an interviewer asks, "Is Node.js concurrent or parallel?", a strong answer is:

> "Node.js supports concurrency through its asynchronous, event-driven architecture. JavaScript application code normally executes on the main thread, while asynchronous I/O can progress through OS facilities and certain native operations can use the libuv Thread Pool. For parallel execution of JavaScript, Node.js provides Worker Threads. Therefore, concurrency and parallelism are distinct capabilities, and Node.js can support both depending on the workload and architecture."
