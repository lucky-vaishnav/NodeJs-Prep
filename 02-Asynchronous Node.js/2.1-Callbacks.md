## 2.1 Callbacks: Missing Concepts

We've already covered how callbacks are scheduled, how the Event Loop coordinates them, and how callback code executes on the Call Stack. We'll skip those fundamentals and focus on the gaps that matter in senior interviews and production code.

### 1. Error-first callbacks

In traditional Node.js APIs, callbacks commonly follow this convention:

JavaScript

```
fs.readFile("data.txt", "utf8", (err, data) => {
    if (err) {
        console.error(err);
        return;
    }

    console.log(data);
});
```

The convention is:

* First argument: `err` — contains an error if the operation failed; otherwise usually `null`.

* Remaining arguments: successful results, such as `data`.

Why put the error first?

It gives callers a consistent way to distinguish success from failure without relying on exceptions thrown asynchronously.

One important detail: this is a convention, not a rule enforced by JavaScript. Your own callback-based APIs should follow it when appropriate.

### 2. Callback hell and control-flow problems

Consider a workflow where each operation depends on the previous one:

JavaScript

```
getUser(userId, (err, user) => {
    if (err) return handleError(err);

    getOrders(user.id, (err, orders) => {
        if (err) return handleError(err);

        getPayment(orders[0].id, (err, payment) => {
            if (err) return handleError(err);

            console.log(payment);
        });
    });
});
```

As dependencies grow, nesting makes code harder to read, maintain, test, and handle errors in consistently.

Modern alternatives include Promises and `async/await`, which we've already studied.

However, callbacks remain useful for event handlers, stream APIs, and APIs that naturally use callback-based interfaces.

### 3. Why is `return` important inside a callback?

Look at this example:

JavaScript

```
function getUser(callback) {
    const user = null;

    if (!user) {
        callback(new Error("User not found"));
    }

    callback(null, user);
}
```

Problem: The callback can be invoked twice: first with an error, then with the result.

Correct version:

JavaScript

```
function getUser(callback) {
    const user = null;

    if (!user) {
        return callback(new Error("User not found"));
    }

    callback(null, user);
}
```

The `return` exits `getUser`, preventing the second invocation.

An equally valid style is:

JavaScript

```
function getUser(callback) {
    const user = null;

    if (!user) {
        callback(new Error("User not found"));
        return;
    }

    callback(null, user);
}
```

Senior-level takeaway: Calling a callback does not automatically stop the surrounding function. You must control the remaining execution flow.

### 4. Can a callback execute more than once?

Yes. JavaScript doesn't enforce exactly-once callback execution.

For example:

JavaScript

```
function doWork(callback) {
    setTimeout(() => callback(null, "first"), 100);
    setTimeout(() => callback(null, "second"), 200);
}

doWork((err, result) => {
    console.log(result);
});
```

Output:

```
first
second
```

That might be intentional for an event subscription, but it's usually a bug when the callback represents the completion of a single operation.

If your API promises a single completion callback, protect against accidental duplicate calls:

JavaScript

```
function once(callback) {
    let called = false;

    return (...args) => {
        if (called) return;

        called = true;
        callback(...args);
    };
}
```

Usage:

JavaScript

```
const done = once((err, result) => {
    console.log(result);
});

done(null, "first");
done(null, "second"); // ignored
```

This is a simple defensive pattern. It doesn't replace fixing the underlying bug, and it should not be applied to callbacks intended to fire repeatedly, such as event listeners.

### 5. Can `try/catch` handle errors from asynchronous callbacks?

Consider:

JavaScript

```
try {
    setTimeout(() => {
        throw new Error("Something failed");
    }, 100);
} catch (err) {
    console.log("Caught:", err.message);
}
```

The surrounding `try/catch` will not catch that error. The callback executes later, after the original synchronous `try` block has finished.

The error must be handled at the appropriate asynchronous boundary. For example, an Express error-handling pattern may look like:

JavaScript

```
setTimeout(() => {
    try {
        throw new Error("Something failed");
    } catch (err) {
        next(err);
    }
}, 100);
```

Here, `next(err)` forwards the error to Express error-handling middleware.

This example assumes `next` is available in the surrounding Express handler. In other contexts, use the relevant error-reporting or completion mechanism.

Remember that callback-based APIs don't all propagate errors in the same way. Some use error-first callbacks, some emit `'error'` events, and others require explicit handling.

## What you should remember for senior interviews

* Error-first callbacks: a common Node.js convention for reporting asynchronous errors.

* Callback hell: a control-flow and maintainability problem.

* `return callback(err)`: prevents execution from falling through into success logic.

* Duplicate callbacks: can cause duplicate writes, responses, or other side effects.

* Async errors: a synchronous `try/catch` doesn't automatically catch errors thrown later in a callback.

These are the missing callback concepts worth adding to your notes; the Event Loop material doesn't need to be repeated.
