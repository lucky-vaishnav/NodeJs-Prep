# Topic 4.1 — Performance

At senior level, Node.js performance is not just about making code execute faster. It's about improving throughput, latency, resource utilization, and stability under load.

## 1. What does performance mean?

| Metric          | Meaning                                     | Example                                    |
| --------------- | ------------------------------------------- | ------------------------------------------ |
| Latency         | Time taken to complete one request          | API responds in 120 ms                     |
| Throughput      | Requests processed per second               | 2,000 requests/second                      |
| CPU utilization | How much CPU capacity is being used         | CPU sustained at 95%                       |
| Memory usage    | Memory consumed by the process              | RSS growing from 300 MB to 1.5 GB          |
| Event Loop lag  | How late the Event Loop runs scheduled work | A callback runs 200 ms later than expected |
| Error rate      | Percentage of requests that fail            | 2% of requests return 5xx                  |

Two important latency measurements are p95 and p99. If p95 latency is 500 ms, approximately 95% of measured requests completed within 500 ms, while the slowest 5% took longer.

A system can have excellent average latency but still provide a poor experience if its p95 or p99 latency is high.

## 3. Common production scenarios

### Scenario A: High CPU usage

Possible causes:

- Expensive loops or calculations.
- Large JSON parsing/stringification operations.
- Complex transformations or regular expressions.
- Excessive synchronous processing.

Approach: Profile the CPU to find the actual hot path. Optimize the algorithm or reduce unnecessary work. Move genuinely CPU-intensive JavaScript into Worker Threads or use multiple processes where appropriate.

### Scenario B: High latency, but low CPU usage

Possible causes:

- Slow database queries.
- External API delays.
- Connection pool exhaustion.
- Lock contention or requests waiting in queues.

Approach: Measure time spent in each dependency, inspect query plans and pool metrics, and add appropriate timeouts and bounded concurrency. More CPU cores won't necessarily help.

### Scenario C: Performance degrades under load

Possible causes:

- Too many concurrent requests.
- Unbounded queues or memory growth.
- Thread-pool or database-pool saturation.
- Garbage collection pressure.
- Downstream services becoming overloaded.

Approach: Use load testing, monitor latency percentiles and resource metrics, and introduce backpressure, concurrency limits, caching, or capacity scaling as justified by measurements.

## 4. The senior engineer's approach

Use this sequence when investigating a production performance issue:

1. Measure: Establish a baseline for throughput, p95/p99 latency, errors, CPU, and memory.
2. Localize: Determine whether the bottleneck is JavaScript, the Event Loop, memory/GC, database, network, or a queue/pool.
3. Profile: Collect CPU profiles, heap snapshots, traces, and dependency timings as appropriate.
4. Optimize: Fix the measured bottleneck rather than making speculative changes.
5. Validate: Repeat the same workload and compare results, including tail latency and error rate.

One final principle: performance optimization is not complete until you measure the improvement under a representative workload.

| Operation          | Typical request | Slow request |
| ------------------ | --------------- | ------------ |
| Node.js processing | 20 ms           | 25 ms        |
| PostgreSQL         | 40 ms           | 2,400 ms     |

I'd start with distributed tracing or per-dependency timing, then investigate PostgreSQL query duration, connection-pool wait time, and external API latency/timeouts. Also check whether the two dependencies run sequentially or concurrently, since that affects total latency.

One subtle point: low CPU utilization doesn't completely rule out Event Loop issues or other resource bottlenecks, but it makes CPU saturation a less likely initial explanation.

Your reasoning is strong. Score: 9/10. You're correctly distinguishing between insufficient pool capacity and connections being held longer than necessary.

### What you got right

- Concurrent requests: Demand may exceed the number of available connections.
- Connections not released: A connection may remain checked out because of missing cleanup or a long-running operation.
- Database locks: Lock contention can slow queries and cause connections to remain occupied longer.
- Don't increase the pool blindly: A larger pool could hide the symptom while increasing PostgreSQL load and contention.

### How I'd investigate in production

1. Pool metrics: Check total, idle, and checked-out connections, plus acquisition wait time and timeout counts.
2. Connection lifecycle: Inspect transaction boundaries and ensure connections are released in `finally` blocks or through correctly managed transaction APIs.
3. PostgreSQL activity: Examine `pg_stat_activity` for long-running queries, idle-in-transaction sessions, and sessions waiting on locks.
4. Concurrency: Compare incoming request volume with connection acquisition and release rates.
5. Pool configuration: Check pool size, connection limits, and whether multiple Node.js processes each create their own pool.

For example, if you run four Cluster workers with a pool maximum of 20 connections per worker, the application could potentially request 80 PostgreSQL connections. Pool sizing must account for the total across all processes and other database clients.

One nuance: a database row lock doesn't always cause a connection acquisition delay directly. It can keep a checked-out connection occupied while a query waits for the lock, indirectly exhausting the pool.

### What you got right

- Long-running synchronous JavaScript prevents the main thread from executing other callbacks promptly.
- Optimizing the code should depend on the actual workload and functional requirements.
- You considered other operations that can affect responsiveness, including crypto, I/O, and timers.

### What I'd refine

High Event Loop lag with low overall CPU utilization does not necessarily mean the CPU is overloaded. A single JavaScript thread can be blocked while the overall machine still has plenty of unused CPU capacity.

Also, many I/O operations do not inherently slow the Event Loop. Node.js can handle substantial concurrent I/O efficiently. The concern is whether callbacks are expensive, queues are growing, or resources such as connection pools and the libuv thread pool are saturated.

### Senior-level investigation sequence

1. Measure Event Loop delay using `perf_hooks.monitorEventLoopDelay()`.
2. Capture a CPU profile to identify long-running JavaScript functions, synchronous APIs, expensive JSON processing, or pathological regular expressions.
3. Inspect callback duration and queueing to identify bursts of expensive callbacks or excessive microtask processing.
4. Check resource saturation such as libuv thread-pool queues, file descriptors, and connection pools where relevant.
5. Apply the right fix: optimize synchronous work, use Worker Threads for CPU-intensive JavaScript, or limit concurrency and improve resource management.

A useful production diagnostic is to correlate Event Loop delay with request latency, CPU profiles, and dependency metrics rather than relying on any single metric.
