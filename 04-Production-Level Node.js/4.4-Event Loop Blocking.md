## Topic 4.4 — Event Loop Blocking

You already understand that CPU-heavy synchronous JavaScript blocks Node.js. Now we'll go deeper into how to detect Event Loop blocking, recognize less obvious causes, and diagnose it in production.

## 1. What exactly is Event Loop blocking?

The Event Loop coordinates when Node.js executes callbacks for timers, I/O, and other asynchronous operations.

When the main JavaScript thread is busy executing synchronous code, it cannot execute other callbacks until that code yields control.

Notice that even if the database has already completed its work, the JavaScript callback may still be waiting for the main thread.

Important distinction: Event Loop blocking describes delayed JavaScript execution. It does not necessarily mean the entire operating system or every background operation is blocked.

## 2. Common causes beyond obvious CPU-heavy loops

Synchronous APIs

Examples: `fs.readFileSync()`, `crypto.pbkdf2Sync()`, and synchronous compression APIs. These can block the thread while performing their work.

Large JSON operations

`JSON.parse()` and `JSON.stringify()` execute synchronously. Processing very large payloads can cause significant delays.

Expensive regular expressions

Certain patterns can exhibit catastrophic backtracking on specific inputs, consuming excessive CPU time and blocking other callbacks.

Long callback or microtask chains

Expensive callbacks, recursive `process.nextTick()` scheduling, or continuously replenished Promise microtasks can delay normal Event Loop progress.

One common misconception: asynchronous syntax does not guarantee non-blocking execution.

```
async function processRequest() {
  const data = JSON.parse(veryLargePayload);
  return transformData(data);
}
```

The parsing and transformation still execute synchronously on the current JavaScript thread unless the work is explicitly offloaded or otherwise broken up.

## 3. How do you detect Event Loop blocking in production?

You should use multiple signals together.

### A. Measure Event Loop delay

Node.js provides `monitorEventLoopDelay()` through `node:perf_hooks`.

```
const {
  monitorEventLoopDelay
} = require("node:perf_hooks");

const histogram = monitorEventLoopDelay({
  resolution: 20
});

histogram.enable();

setInterval(() => {
  console.log({
    p99DelayMs: histogram.percentile(99) / 1e6,
    maxDelayMs: histogram.max / 1e6
  });

  histogram.reset();
}, 10_000);
```

This measures delays in the Event Loop's ability to run scheduled work. Values are in nanoseconds, so dividing by `1e6` converts them to milliseconds.

For production, also monitor the histogram's mean and max where useful, and export measurements to your monitoring system. Remember that a delay histogram measures event-loop delay, not the duration of a particular request.

### B. Compare with other metrics

| Observation                                  | Possible interpretation                                 |
| -------------------------------------------- | ------------------------------------------------------- |
| High Event Loop delay + high CPU             | Expensive JavaScript or other CPU-intensive work        |
| High Event Loop delay + low overall CPU      | One thread may be blocked while other cores are idle    |
| Low Event Loop delay + high API latency      | Database, network, queueing, or other wait time         |
| High latency + rising memory and GC activity | Allocation pressure or GC-related pauses may contribute |

These are clues, not definitive diagnoses.

### C. Profile the process

Use CPU profiles and targeted diagnostics to identify which functions consume execution time. For memory-related pauses, correlate GC metrics and heap behavior. For individual requests, distributed traces and per-operation timing can help isolate delays.

## 4. How do you prevent Event Loop blocking?

- Prefer asynchronous APIs when suitable, but verify whether the underlying operation actually runs asynchronously.
- Optimize algorithms and avoid repeatedly processing the same data.
- Offload CPU-intensive JavaScript to a bounded Worker Thread pool.
- Move long-running jobs to background workers when the product flow allows it.
- Limit input sizes and use safer regular expressions.
- Apply bounded concurrency and backpressure to prevent unbounded work from accumulating.

For example, replacing `readFileSync()` with `fs.promises.readFile()` avoids synchronously waiting for the file read on the main JavaScript thread. However, reading and parsing a huge file can still create memory pressure and expensive synchronous parsing afterward.

Your understanding is correct. High Event Loop delay means the main JavaScript thread is not getting opportunities to process scheduled callbacks on time. In this scenario, normal PostgreSQL and external API timings make those dependencies less likely to be the primary bottleneck.

One important nuance: 30% overall CPU utilization does not rule out a JavaScript-thread bottleneck. A single thread can be blocked or saturated while other CPU cores remain idle.

To investigate, I would:

1. Check Event Loop metrics — delay percentiles and timer drift confirm the impact and help establish when it occurs.
2. Capture a CPU profile — look for long-running synchronous functions, expensive loops, large `JSON.parse()`/`JSON.stringify()` operations, or costly regular expressions.
3. Investigate microtask starvation — check for recursively scheduled `process.nextTick()` callbacks or Promise microtasks that continuously replenish the microtask queue.
