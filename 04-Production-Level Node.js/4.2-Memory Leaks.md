## Topic 4.2 — Memory Leaks

For a senior Node.js developer, the goal isn't just to know what a memory leak is. It's to identify why memory is growing, prove what's retaining it, and fix the root cause without creating new production problems.

### 1. What is a memory leak?

A memory leak occurs when an application retains references to objects it no longer needs, preventing the garbage collector (GC) from reclaiming them.

Remember our earlier discussion: the garbage collector determines whether objects are reachable, not whether your application still logically needs them.
<img width="996" height="273" alt="Screenshot 2026-10-18 204938" src="https://github.com/user-attachments/assets/f1274761-d9b5-4f23-8e5b-1631926d6ab5" />

For example, a service that stores every request in a global array will continually retain data if that array is never cleared or bounded.

```
const requests = [];

app.use((req, res, next) => {
  requests.push({
    url: req.url,
    timestamp: Date.now()
  });

  next();
});
```

This is a potential leak if the array grows indefinitely. Even small objects can cause substantial memory growth when millions of them are retained.

## 3. How to detect a memory leak in production

Suppose your API starts at 300 MB RSS and grows to 1.5 GB after several hours.

Don't conclude immediately that there's a memory leak. First, understand the trend.

| Observation                                        | Possible explanation                                               |
| -------------------------------------------------- | ------------------------------------------------------------------ |
| `heapUsed` rises and remains high after GC         | Retained JavaScript objects or growing live data                   |
| `heapUsed` rises and falls repeatedly              | Normal allocation and garbage collection may be occurring          |
| RSS grows while `heapUsed` stays relatively stable | Buffers, native allocations, allocator behavior, or fragmentation  |
| `external` or `arrayBuffers` keeps growing         | Buffer or other external-memory allocation/retention               |
| Memory grows with traffic and doesn't stabilize    | Leak, unbounded cache, growing workload, or another capacity issue |

These are diagnostic clues, not definitive proof. For example, a legitimate cache may grow until it reaches a stable maximum, while a leak can involve native memory rather than JavaScript objects.

### Useful Node.js metrics

```
const v8 = require("node:v8");

setInterval(() => {
  console.log(process.memoryUsage());
  console.log(v8.getHeapStatistics());
}, 10_000);
```

Key `process.memoryUsage()` fields:

- `rss`: resident memory used by the whole process.
- `heapUsed`: V8 heap currently in use.
- `heapTotal`: V8 heap allocated by V8.
- `external`: memory associated with native objects linked to JavaScript objects.
- `arrayBuffers`: memory used by `ArrayBuffer` and `SharedArrayBuffer`, including Node.js Buffers; it is included in `external`.

Important: Don't force garbage collection repeatedly in production just to make memory graphs look better. Measure first, and use controlled diagnostic environments when explicit GC is necessary.

## 4. Heap snapshots: finding what retains memory

A heap snapshot helps you inspect the objects currently occupying the V8 heap and the references keeping them alive.

A practical investigation:

1. Reproduce the problem under a controlled workload, if possible.
2. Capture a baseline heap snapshot.
3. Apply representative traffic and allow the application to reach a comparable state.
4. Capture another snapshot and compare object counts, retained sizes, and retaining paths.
5. Identify the unexpected reference chain and fix its owner or lifecycle.

For example, you might discover that a global `Map` retains thousands of completed reservation objects. The key isn't simply that the objects are large; it's finding why they're still reachable.

Heap snapshots can pause the process and require substantial additional memory. Take them carefully in production, particularly when the service is already close to its memory limit.

## 5. Common interview question

How do you distinguish a memory leak from high memory usage caused by legitimate workload?

A strong answer:

> I monitor memory metrics over time and correlate them with traffic, workload, and garbage collection. If memory increases but stabilizes at a repeatable level, it may be normal allocation or bounded caching. If post-GC heap usage and retained objects keep increasing under a comparable workload, I investigate a potential leak. I compare heap snapshots, inspect retaining paths, and separately monitor RSS and external memory because not all memory growth occurs in the V8 heap.

## Your checkpoint

A Node.js API has been running for six hours.

- RSS has increased from 400 MB to 1.8 GB.
- `heapUsed` increases after each traffic spike but drops after GC.
- RSS keeps increasing even when `heapUsed` returns to approximately the same level.

What would you investigate next, and why would you not conclude immediately that this is a JavaScript heap memory leak?

### My Answer -
According to this scenario, first thing i will check is the external memory related code part because GC is working and heap memory is going down so need to check other memory part like eternal, native memory, arrayBuffer, sharedArrayBuffer etc.

Correct. Score: 9/10. You've identified the most important clue: RSS continues growing while `heapUsed` returns to roughly the same level after GC.

### What you got right

- Investigate memory outside the ordinary V8 heap.
- Check `external` and `arrayBuffers`, including memory associated with Node.js `Buffer` objects.
- Consider native allocations and `SharedArrayBuffer` usage.
- Don't assume that increasing RSS automatically means a JavaScript heap leak.

### One important refinement

GC working doesn't prove that the application has no JavaScript memory leak. It can reclaim unreachable objects while other objects remain reachable and accumulate.

For this specific scenario, I'd investigate in this order:

1. Trend all memory metrics: Compare RSS, `heapUsed`, `external`, and `arrayBuffers` over time.
2. Inspect Buffer and native-memory usage: Look for retained buffers, large binary payloads, native libraries, and shared-memory allocations.
3. Check allocator behavior and fragmentation: RSS can remain elevated even after objects are freed because the memory allocator may retain memory rather than immediately return it to the operating system.
4. Use targeted diagnostics: If the metrics don't identify the cause, investigate native allocations and compare controlled workload runs.

One nuance: `SharedArrayBuffer` memory may contribute to external/array-buffer accounting, but the exact accounting depends on the runtime and allocation. Don't assume all RSS growth will appear in those counters.

Senior-level takeaway: `heapUsed` measures only one part of process memory. Diagnose the memory category that is growing before choosing a fix.

## Practical example: Finding an unbounded cache

Suppose your reservation API caches reservation details in a global `Map`.

```
const reservationCache = new Map();

async function getReservation(id) {
  if (reservationCache.has(id)) {
    return reservationCache.get(id);
  }

  const reservation = await db.getReservation(id);
  reservationCache.set(id, reservation);

  return reservation;
}
```

Problem: If requests keep introducing new reservation IDs and entries are never removed, the cache can grow indefinitely.

### How you'd investigate

1. Observe `heapUsed` and RSS over time under representative traffic.
2. Take heap snapshots at comparable points in the workload.
3. Compare snapshots for growing `Map` entries and retained reservation objects.
4. Inspect the retaining path to confirm the global `Map` is keeping them alive.
5. Fix the root cause using a bounded cache, suitable eviction policy, TTL where appropriate, or no cache if it isn't needed.

A heap snapshot helps establish what is retained and why; memory metrics alone generally cannot prove the exact leak source.

### Common mistakes to remember

- Looking only at `heapUsed` and ignoring RSS and external memory.
- Assuming GC is broken whenever memory increases.
- Taking production heap snapshots without considering pause time and memory overhead.
- Increasing the memory limit without investigating the underlying cause.
- Adding a cache without defining its maximum size and eviction strategy.
