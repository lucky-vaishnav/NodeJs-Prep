## Phase 4.9 — PM2 (Node.js Process Manager)

PM2 is a process manager commonly used to run Node.js applications in production. It manages application processes, restarts crashed processes, collects logs, and supports running multiple instances.

Since your existing deployments use Node.js with PM2 and Nginx on EC2, this topic is directly relevant to understanding how your application runs and scales in production.

### 1. Why do we need PM2?

Suppose you start an Express application using:

```
node server.js
```

This starts a Node.js process, but you don't automatically get a complete production process-management setup.

If the process crashes, it won't automatically restart itself. If your SSH session or deployment environment is managed poorly, you may also have trouble keeping the service running reliably.

PM2 adds process supervision:

- Automatically restarts a process when it exits unexpectedly.
- Supports running multiple application instances.
- Provides log management and process monitoring.
- Supports reloads and deployment workflows.
- Runs applications in the background as a daemon.

Important: PM2 is not a replacement for Nginx, a load balancer, or infrastructure-level monitoring. Each solves a different problem.

### 2. PM2 fork mode vs. cluster mode

PM2 provides two common execution modes.

Example commands:

```
# Start one process
pm2 start server.js --name api

# Start four clustered instances
pm2 start server.js -i 4 --name api

# Let PM2 choose the number of instances
pm2 start server.js -i max --name api
```

`-i max` uses the available CPU-core count as the basis for the instance count. In production, don't blindly use every core: leave capacity for the OS and other workloads, and benchmark memory and CPU consumption.

### 3. A production ecosystem configuration

Instead of maintaining long commands, teams often define PM2 settings in an `ecosystem.config.js` file.

```
module.exports = {
  apps: [
    {
      name: "api",
      script: "./server.js",
      instances: 2,
      exec_mode: "cluster",

      autorestart: true,
      max_memory_restart: "500M",

      env: {
        NODE_ENV: "development",
      },

      env_production: {
        NODE_ENV: "production",
      },
    },
  ],
};
```

Start the application with:

```
pm2 start ecosystem.config.js --env production
```

Important configuration details:

- `instances`: Number of application processes.
- `exec_mode`: `cluster` for clustered instances or `fork` for a single process.
- `autorestart`: Restarts a process that exits unexpectedly.
- `max_memory_restart`: Requests a restart when PM2 detects memory exceeding the configured threshold.

The memory setting is a recovery safeguard, not a memory limit. It doesn't prevent an application from temporarily exceeding that amount, and restarts can interrupt work if the application isn't designed to handle them safely.

### 4. Graceful reloads and shutdowns

A production application should not abruptly terminate active requests whenever possible.

For example:

```
# Reload clustered application processes
pm2 reload api

# Restart application processes
pm2 restart api

# Inspect running processes
pm2 list

# View application logs
pm2 logs api

# Monitor resource usage
pm2 monit
```

The important distinction is:

- Reload: In cluster mode, PM2 can replace instances progressively to reduce downtime.
- Restart: Restarts processes and may interrupt requests, depending on how the application and process manager handle the operation.

A reload is not an absolute guarantee of zero downtime. It depends on application readiness, process startup, and shutdown behavior.

For graceful shutdown, your application should stop accepting new work, allow in-flight requests a reasonable period to finish, close database connections, and exit. Configure a shutdown timeout and make sure the application eventually terminates if draining gets stuck.

### 5. What happens internally when PM2 cluster mode is used?

Each clustered worker is a separate Node.js process with its own:

- V8 isolate and JavaScript heap.
- Event Loop.
- Application-level caches and global variables.
- Database connection pool, unless connections are managed differently through external infrastructure.

That last point is particularly important: four PM2 workers with a pool of 20 connections each can potentially create 80 database connections.

Similarly, in-memory sessions and caches are not automatically shared between workers. Use an appropriate shared store when multiple processes must see the same state.

### 6. Common production mistakes

- Running too many workers and exhausting RAM or database connections.
- Assuming PM2 cluster mode shares application memory.
- Relying on PM2 restarts instead of fixing recurring crashes or leaks.
- Assuming reloads are always zero-downtime.
- Failing to handle `SIGTERM` or other shutdown signals properly.
- Treating PM2 as a replacement for multi-instance high availability.

PM2 can supervise processes on one EC2 instance. If that instance fails entirely, PM2 on that machine cannot keep the service available; that requires another instance and an appropriate traffic-routing setup.

## Review of your answers

### 1. Some users are unexpectedly logged out

Your answer is correct.

If sessions are stored in process memory, a login request may reach worker 1, while a subsequent request reaches worker 3. Worker 3 may not have the session.

Production fix:

- Use a shared session store such as Redis when server-side sessions are required.
- Alternatively, use appropriately validated stateless authentication when suitable.
- Check whether deployment reloads are terminating processes that hold in-memory sessions.

One nuance: sticky sessions can help route a user to the same worker, but they are not a complete replacement for shared session storage when workers restart or fail.

### 2. PostgreSQL connections have doubled

Correct. Each worker typically creates its own database connection pool.

For example, if you previously had one process with a pool of 20 connections, and you now have four workers with the same pool configuration:

\\[ 4 \times 20 = 80 \text{ connections} \\]

Your connection count can quadruple, not merely double. If the previous configuration already had two processes, doubling to four would double the count.

Production fix:

- Calculate the total connection budget across all workers and instances.
- Reduce per-worker pool sizes as needed.
- Reserve capacity for migrations, administration, and other services.
- Consider a connection pooler such as PgBouncer where appropriate.

### 3. One worker periodically restarts due to high memory

You correctly want to investigate why, but uneven traffic distribution is only one possible explanation.

I'd investigate in this order:

1. Compare each worker's RSS, heap usage, external memory, request count, and restart history.
2. Check whether the affected worker receives larger payloads or handles particular endpoints.
3. Inspect for memory leaks, retained buffers, unbounded caches, or request-specific allocations.
4. Check whether PM2's `max_memory_restart` threshold is triggering the restart.
5. Review CPU-core allocation and worker count after investigating the memory issue.

The worker count being aligned with CPU cores may help CPU utilization, but it does not directly solve a memory leak.

## Senior-level takeaway

When moving from one Node.js process to PM2 cluster mode, remember three independent effects:

- State isolation: In-memory sessions and caches aren't shared.
- Resource multiplication: Database pools, caches, and other per-process resources multiply.
- Independent failure patterns: One worker can leak memory or receive unusually expensive requests even when other workers are healthy.
