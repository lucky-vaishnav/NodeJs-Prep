## Next: Phase 4.5 — Streams

### 1. Concept

In Node.js, a Stream is an abstraction for processing data incrementally, in chunks, rather than loading the entire dataset into memory at once.

Imagine downloading a 5 GB file.

- Without streaming: The application might load the entire file into memory before processing or sending it.
- With streaming: It processes and transfers chunks as they become available.

Without streams

Read entire 5 GB file into memory

Application processes or sends the file

With streams

Read a chunk → Process it → Send it

Chunks flow through the application, reducing the need to retain the entire file in memory.

### 2. The four types of streams

| Type      | Purpose                                           | Example                  |
| --------- | ------------------------------------------------- | ------------------------ |
| Readable  | Produces data                                     | `fs.createReadStream()`  |
| Writable  | Consumes data                                     | `fs.createWriteStream()` |
| Duplex    | Reads and writes data                             | TCP socket               |
| Transform | Reads data, transforms it, and outputs the result | Gzip compression         |

### 3. Practical example

Compress a file without loading it entirely into memory:

```javascript
const fs = require("node:fs");
const { pipeline } = require("node:stream/promises");
const { createGzip } = require("node:zlib");

async function gzipFile(inputPath, outputPath) {
  await pipeline(
    fs.createReadStream(inputPath),
    createGzip(),
    fs.createWriteStream(outputPath)
  );
}
```

Here, data flows through three stages:

1. `createReadStream()` reads the input incrementally.
2. `createGzip()` compresses the chunks.
3. `createWriteStream()` writes the compressed output incrementally.

`pipeline()` is generally preferable to manually connecting streams because it handles error propagation and stream cleanup more reliably.

### 4. Senior-level production implications

- Memory efficiency: Streams avoid retaining an entire large payload in memory, although buffers and internal queues still consume memory.
- Latency: Processing can begin before the entire input has been read.
- Error handling: Every stage must be considered; a failure in one stage should not leave other stages running unnecessarily.
- Data boundaries: A chunk is not necessarily a complete line, JSON record, or application message. You must handle records that span multiple chunks.
- Backpressure: If the destination consumes data more slowly than the source produces it, buffering can grow. Node.js provides mechanisms to control this.

We'll cover Backpressure separately in Phase 4.6, including `highWaterMark`, `.write()` returning `false`, and the `'drain'` event.

## 5. Consuming a readable stream

Node.js provides several ways to consume streams. Two useful approaches are event-based consumption and async iteration.

Event-based approach:

```javascript
const fs = require("node:fs");

const stream = fs.createReadStream("large.txt", {
  encoding: "utf8"
});

stream.on("data", (chunk) => {
  console.log("Received chunk:", chunk.length);
});

stream.on("end", () => {
  console.log("Reading completed");
});

stream.on("error", (err) => {
  console.error("Read failed:", err);
});
```

Async iteration approach:

```javascript
const fs = require("node:fs");

async function readFile() {
  const stream = fs.createReadStream("large.txt");

  try {
    for await (const chunk of stream) {
      await processChunk(chunk);
    }
  } catch (err) {
    console.error("Stream processing failed:", err);
  }
}

async function processChunk(chunk) {
  // Process this chunk.
}
```

Async iteration is often easier to read when processing must happen sequentially. If `processChunk()` performs asynchronous work, the loop waits for each call to finish before consuming the next chunk, naturally limiting how much work this particular loop has in flight.

## 6. Writable streams and `write()`

A writable stream accepts data from your application and writes it to a destination.

```javascript
const fs = require("node:fs");

const output = fs.createWriteStream("output.txt");

output.write("First line\n");
output.write("Second line\n");

output.end();
```

Important methods and events:

| API            | Purpose                                                        |
| -------------- | -------------------------------------------------------------- |
| `write(chunk)` | Writes a chunk                                                 |
| `end()`        | Signals that no more data will be written                      |
| `'finish'`     | Emitted after all data has been processed for writing          |
| `'error'`      | Reports a stream error                                         |
| `'drain'`      | Signals that writing can resume after buffering pressure eases |

One important distinction: `'finish'` does not necessarily mean the data has been physically persisted to disk storage. It means the writable stream has completed its writing process.

Also, `write()` returning `false` is not a failure. It indicates that the writable stream is applying flow control; we will examine this in the next topic on backpressure.

## 7. `pipe()` vs `pipeline()`

Both connect streams, but `pipeline()` is generally the safer choice for production pipelines.

```javascript
const fs = require("node:fs");
const { pipeline } = require("node:stream/promises");
const { createGzip } = require("node:zlib");

async function compress() {
  await pipeline(
    fs.createReadStream("input.txt"),
    createGzip(),
    fs.createWriteStream("output.txt.gz")
  );

  console.log("Compression completed");
}

compress().catch(console.error);
```

- `pipe()` connects a readable stream to a writable stream and handles basic flow control.
- `pipeline()` connects multiple streams while providing more reliable error propagation and cleanup when a stage fails.

For production file processing, compression, and data-transfer pipelines, prefer `pipeline()` unless you have a specific reason to manage the lifecycle yourself.

## 8. Common mistakes

- Loading a huge file with `readFile()` when incremental processing would be more appropriate.
- Assuming each chunk contains one complete record.
- Ignoring stream errors.
- Forgetting to call `end()` on a writable stream when writing is complete.
- Assuming streams eliminate memory pressure; internal buffers can still grow if flow control is mishandled.
- Performing expensive synchronous transformations on every chunk and blocking the Event Loop.

## Code implementation: Express + Axios + Streams

This example uses Axios to obtain the upstream response as a readable stream, then uses `pipeline()` to forward it to the client.

```javascript
const express = require("express");
const axios = require("axios");
const { pipeline } = require("node:stream/promises");

const app = express();

app.get("/download", async (req, res) => {
  let upstream;

  try {
    // Request the file as a stream, not as a buffered response.
    upstream = await axios.get(
      "https://example.com/large-file.zip",
      {
        responseType: "stream",
        timeout: 30_000,
      }
    );

    // Forward only the required response headers.
    res.status(upstream.status);

    if (upstream.headers["content-type"]) {
      res.setHeader(
        "Content-Type",
        upstream.headers["content-type"]
      );
    }

    if (upstream.headers["content-length"]) {
      res.setHeader(
        "Content-Length",
        upstream.headers["content-length"]
      );
    }

    // Stream chunks directly to the client.
    await pipeline(upstream.data, res);
  } catch (err) {
    console.error("Download streaming failed:", err.message);

    upstream?.data?.destroy();

    if (!res.headersSent && !res.destroyed) {
      res.status(502).json({
        message: "Unable to download the file",
      });
    } else if (!res.destroyed) {
      // Headers/body may already have been sent.
      res.destroy(err);
    }
  }
});

app.listen(3000, () => {
  console.log("Server running on port 3000");
});
```

### Production details to remember

1. Memory: You avoid buffering the entire file in application memory, although stream buffers still consume memory.
2. Backpressure: `pipeline()` coordinates flow control when the client is slower than the upstream source.
3. Errors: If streaming fails after response headers or body data have been sent, you generally cannot replace the response with a JSON error. The connection must be terminated.
4. Client disconnection: `pipeline()` coordinates stream teardown when the destination closes, helping stop unnecessary upstream transfer.
5. Security: In a real application, don't let users supply arbitrary upstream URLs without validation; that can create an SSRF vulnerability.

Interview takeaway: “I would use a readable stream for the upstream response and pipe it into the Express response using `pipeline()`. This avoids buffering the entire file, supports backpressure, and improves memory efficiency under concurrent load. I would also handle stream errors and client disconnections carefully.”
