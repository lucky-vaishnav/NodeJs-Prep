## Topic 4.3 — CPU-Heavy Operations

At senior level, the key is understanding why CPU-intensive work affects Node.js responsiveness, how to identify it, and how to handle it without degrading other requests.

## 1. What is a CPU-heavy operation?

A CPU-heavy operation requires substantial computation rather than waiting for an external resource.

Examples in a Node.js backend:

- Processing large JSON payloads.
- Generating PDFs or reports with complex calculations.
- Image processing or compression.
- Encrypting or hashing large amounts of data.
- Complex filtering, sorting, or data transformations.
- CPU-intensive loops, calculations, or regular expressions.

Not every expensive operation behaves the same way. For example, asynchronous cryptographic APIs may use libuv's thread pool, whereas ordinary synchronous JavaScript calculations execute on the current JavaScript thread.

## 2. Why is this a problem in Node.js?

Consider a Node.js server handling two requests:

Example:

```
app.get("/report", (req, res) => {
  let total = 0;

  for (let i = 0; i < 5_000_000_000; i++) {
    total += i;
  }

  res.json({ total });
});
```

This is an intentionally excessive example. The loop executes synchronously, so the main JavaScript thread cannot handle other requests until it finishes.

Even if another request's database query has already completed, its JavaScript callback must wait for the main thread to become available.

Important: Making a function `async` does not move its CPU work to another thread.

```
async function calculate() {
  // Still executes synchronously on the current JS thread
  expensiveCalculation();
}
```

An `async` function returns a Promise, but synchronous work inside it still blocks the thread.

## 4. A common senior interview distinction

| Workload                                 | Suitable approach                                          |
| ---------------------------------------- | ---------------------------------------------------------- |
| Slow PostgreSQL query                    | Optimize the query and connection usage                    |
| CPU-intensive JavaScript calculation     | Optimize the algorithm or use Worker Threads               |
| Long-running report generation           | Background job with bounded concurrency                    |
| High volume of independent HTTP requests | Cluster or horizontal scaling, after measuring bottlenecks |
| Asynchronous filesystem operation        | Use the asynchronous API where appropriate                 |

For cryptographic operations, compression, and similar native operations, first determine whether the API is synchronous or asynchronous and whether it uses libuv's thread pool. Moving such work to Worker Threads isn't automatically the best solution.

## 5. Production considerations

When offloading CPU-intensive work, remember:

- Bound concurrency: Too many workers can cause CPU contention and memory pressure.
- Bound queues: Reject, defer, or throttle work when capacity is exhausted.
- Measure latency: Track p95/p99 response times as well as CPU utilization.
- Handle failures: Set suitable timeouts, handle worker failures, and make background jobs retry-safe.
- Protect the main thread: Avoid expensive synchronous parsing, serialization, or regular expressions on large inputs.

### One important correction

High CPU usage does not automatically make Cluster a better choice than Worker Threads.

Both can use the same machine's CPU resources. Cluster creates separate processes, but it doesn't create extra CPU capacity. If all cores are saturated, adding more Cluster workers may not solve the problem.

For this particular scenario, I'd consider the options in this order:

| Situation                                                                       | Preferred approach                                            |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| PDF generation blocks the main thread, but the workload is moderate             | Worker Thread pool                                            |
| PDF generation takes seconds and doesn't need to finish during the HTTP request | Background job queue                                          |
| PDF library is primarily native code or already uses asynchronous operations    | Profile the library and its execution model first             |
| The entire service is CPU-saturated                                             | Optimize, control concurrency, and consider more CPU capacity |
| Need to scale independent HTTP requests across cores                            | Cluster or multiple instances                                 |

### What I'd choose for your scenario

For production PDF reports that take several seconds, I'd generally lean toward a background job queue if the product requirements allow asynchronous completion.

1. API validates the request and creates a job.
2. The job is queued.
3. Separate workers generate PDFs with bounded concurrency.
4. The result is stored, and the client receives a job ID or notification when it's ready.

This isolates report-generation workload from ordinary API handling. However, it still requires CPU capacity planning; background processing doesn't make computation free.

If the PDF must be returned immediately, a bounded Worker Thread pool may be more appropriate, depending on the PDF library.
