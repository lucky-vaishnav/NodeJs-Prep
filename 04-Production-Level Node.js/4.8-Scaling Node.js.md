## Phase 4.8 — Scaling Node.js

At a senior-engineer level, scaling Node.js isn't just about adding more CPU or running more processes. It's about increasing request-handling capacity while maintaining acceptable latency, reliability, and resource usage.

There are two primary approaches:

- Vertical scaling: Give an existing server more resources.
- Horizontal scaling: Run more application instances or processes and distribute requests among them.

Horizontal scaling

Add more application instances or processes and distribute requests between them.

- Increases aggregate capacity.
- Can improve availability when deployed across independent failure domains.
- Requires attention to shared state, session management, and downstream capacity.

For a production Node.js backend, these approaches can be combined. For example, use appropriately sized EC2 instances and run multiple application processes across multiple instances.

## 2. Why one Node.js process may not use all CPU cores

Node.js executes ordinary JavaScript callbacks on its main JavaScript thread. If a server has eight CPU cores, one CPU-intensive Node.js process generally cannot execute ordinary JavaScript on all eight cores simultaneously.

However, Node.js can still handle many concurrent I/O operations because much of the waiting happens outside the main JavaScript thread.

For example:

- Requests waiting for PostgreSQL don't necessarily keep the JavaScript thread busy.
- A synchronous CPU-heavy loop blocks the main JavaScript thread.
- Worker Threads can execute CPU-intensive JavaScript in separate threads.
- Multiple Node.js processes can run JavaScript on separate cores.

Important: Adding more processes helps only when the bottleneck can benefit from additional execution capacity. It won't automatically solve a saturated database connection pool, a slow external API, or an inefficient query.

## 4. Production scaling: what you must get right

### A. Keep the application stateless where possible

Imagine a user logs in and the server stores their session in process memory.

- Request 1 reaches process A, which stores the session.
- Request 2 reaches process B, which doesn't know about that session.
- The request may fail authentication or behave inconsistently.

Prefer shared session storage, such as Redis, or appropriately designed stateless authentication using validated tokens.

The same principle applies to uploaded files, in-memory caches, and background-job state. If another instance needs the data, don't assume it can access one process's memory.

### B. Watch database connection multiplication

Suppose you run:

- 4 EC2 instances
- 4 Node.js processes per instance
- 20 PostgreSQL connections per process

The theoretical maximum is:

\\[ 4 \times 4 \times 20 = 320 \\]

That's 320 potential application database connections, before counting other services and operational connections.

Scaling application processes without accounting for database capacity can overwhelm PostgreSQL. Configure connection pools based on the total deployment, not just one process.

### C. Scale based on the actual bottleneck

| Observed bottleneck                   | Possible response                                            |
| ------------------------------------- | ------------------------------------------------------------ |
| CPU saturation from application logic | Optimize code; add processes or instances                    |
| Event Loop blocking                   | Remove blocking work or offload CPU-heavy operations         |
| Memory pressure                       | Investigate leaks, bound memory use, adjust instance sizing  |
| Database saturation                   | Optimize queries, pool usage, and database capacity          |
| External API latency                  | Use timeouts, bounded concurrency, caching where appropriate |
| Traffic spikes                        | Add instances, use autoscaling, and apply admission control  |

Adding instances is not always the correct first action. If all instances overload the same database, horizontal scaling may make the incident worse.

### D. Make scaling safe during deployments and failures

A production setup should also include:

- Health checks so unhealthy instances stop receiving traffic.
- Graceful shutdown so an instance stops accepting new work and finishes or safely cancels in-flight requests.
- Centralized logs and metrics across all processes.
- Bounded queues and rate limiting to prevent overload.
- Multiple independent instances or failure domains when availability requirements justify them.

## What you got right

- High CPU + high Event Loop delay: You correctly suspect CPU-intensive JavaScript or other work blocking the main thread.
- Worker Threads: A good choice for CPU-heavy tasks that can be moved off the main JavaScript thread.
- Bounded concurrency: Important for preventing too many simultaneous tasks from overwhelming CPU and memory.
- Multiple EC2 instances: A sensible next step when one machine's capacity is insufficient or you need more deployment-level resilience.

## Three important refinements

### 1. First, confirm what is consuming CPU

High CPU and high Event Loop delay strongly suggest CPU contention, but they don't prove that one synchronous function is responsible.

Use CPU profiling to distinguish a long-running JavaScript function from multiple competing workloads, excessive microtask scheduling, or other CPU-intensive activity.

### 2. Cluster and Worker Threads solve different problems

| Option                               | Best fit                                                                                          |
| ------------------------------------ | ------------------------------------------------------------------------------------------------- |
| Worker Threads                       | Offloading CPU-intensive JavaScript from a process's main thread                                  |
| Cluster / multiple Node.js processes | Distributing incoming requests across independent processes and CPU cores                         |
| Multiple EC2 instances               | Increasing total capacity beyond one machine and improving resilience when deployed appropriately |

For example, if every API request performs expensive synchronous calculations, multiple processes may increase request-handling capacity. Worker Threads may be better if the calculation can be isolated and the main process needs to remain responsive.

A bounded Worker Thread pool is usually preferable to creating a new worker for every request.

### 3. You don't necessarily need to wait before adding instances

If profiling shows that a single EC2 instance has reached its CPU capacity, adding instances behind a load balancer may be the most direct solution. You can optimize CPU-heavy work and scale horizontally in parallel.

Also, background jobs are appropriate only when the operation can be moved out of the synchronous request-response path. They aren't a substitute for handling CPU-heavy work that must complete before the API responds.

## A stronger senior-interview answer

“I would first profile the application to identify the CPU hotspot and verify why Event Loop delay is high. If CPU-intensive JavaScript is blocking the main thread, I would optimize the algorithm or move the work to a bounded Worker Thread pool. If the issue is request-handling capacity, I would consider multiple Node.js processes on the existing instance, subject to available CPU and memory. If one instance is still insufficient or we need greater resilience, I would scale horizontally behind a load balancer. Before increasing process or instance counts, I would verify that PostgreSQL, connection pools, and other shared dependencies can handle the additional load.”
