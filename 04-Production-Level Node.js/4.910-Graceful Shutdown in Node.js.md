# Phase 4.10 — Graceful Shutdown in Node.js

This is the final topic in Phase 4: Production-Level Node.js. The goal is to understand how a production Node.js service should terminate safely during deployments, PM2 restarts, server replacements, or infrastructure shutdowns.

## 1. What is graceful shutdown?

A graceful shutdown means stopping a Node.js application without abruptly interrupting work that is already in progress.

Imagine your Express API is processing a payment request when a deployment starts. If the process exits immediately, the request may fail midway, the client may retry, or the payment workflow may end up in an uncertain state.

A graceful shutdown attempts to:

1. Stop accepting new work.
2. Allow in-flight HTTP requests to finish.
3. Finish or safely release background jobs.
4. Close database, Redis, and other connections.
5. Exit before the platform's termination deadline.

## 2. What triggers a graceful shutdown?

| Trigger                         | Typical signal or event                                                |
| ------------------------------- | ---------------------------------------------------------------------- |
| Terminal interruption           | `SIGINT`                                                               |
| EC2 or container termination    | Often `SIGTERM`                                                        |
| PM2 restart or deployment       | Depends on PM2 configuration and shutdown behavior                     |
| Container orchestration rollout | Usually `SIGTERM`, followed by forced termination after a grace period |

The important point is that your application should not assume it will always receive enough time to shut down. The platform may eventually forcefully terminate it.

## 4. Implementing graceful shutdown

Here is a practical Express + PostgreSQL example.

```javascript
const http = require("node:http");
const express = require("express");
const { Pool } = require("pg");

const app = express();
const server = http.createServer(app);
const pool = new Pool();

let shuttingDown = false;

app.get("/health/ready", (_req, res) => {
  if (shuttingDown) {
    return res.status(503).send("Shutting down");
  }

  res.status(200).send("OK");
});

const shutdown = async (signal) => {
  // Prevent duplicate shutdown attempts.
  if (shuttingDown) return;
  shuttingDown = true;

  console.log(`${signal} received. Starting shutdown.`);

  // Emergency deadline if shutdown hangs.
  const forceExitTimer = setTimeout(() => {
    console.error("Shutdown deadline exceeded.");

    server.closeAllConnections?.();
    process.exit(1);
  }, 10_000);

  forceExitTimer.unref();

  try {
    // Stop accepting new connections and drain HTTP requests.
    const serverClosed = new Promise((resolve, reject) => {
      server.close((err) => {
        if (err) reject(err);
        else resolve();
      });
    });

    // Close idle keep-alive connections where supported.
    server.closeIdleConnections?.();

    await serverClosed;

    // Close the PostgreSQL pool after requests have drained.
    await pool.end();

    clearTimeout(forceExitTimer);
    console.log("Graceful shutdown completed.");
    process.exitCode = 0;
  } catch (error) {
    console.error("Graceful shutdown failed:", error);

    // Keep the deadline active as a final safety net.
    process.exitCode = 1;
  }
};

process.on("SIGTERM", () => void shutdown("SIGTERM"));
process.on("SIGINT", () => void shutdown("SIGINT"));

server.listen(3000);
```

Important: `10_000` is just an example deadline. Choose one that fits your platform's termination grace period. The forced `process.exit(1)` is reserved for the emergency deadline; don't use immediate `process.exit()` during a normal shutdown because it can interrupt pending work.

This example handles HTTP connections and a PostgreSQL pool. A production service must also account for its other resources.

## 5. What happens to in-flight requests?

Suppose your API receives three requests:

- Request A is halfway through a database transaction.
- Request B is waiting for a database query.
- Request C arrives after shutdown begins.

The desired behavior is:

- A and B: Allow them to finish within the shutdown deadline.
- C: Stop accepting new connections or route it to a healthy instance.
- Database: Keep it available while A and B finish, then close the pool.

Returning `503` from a readiness endpoint helps indicate that the instance is shutting down, but it doesn't automatically remove the instance from a load balancer. Your deployment or infrastructure must handle deregistration and connection draining too.

Also, `server.close()` alone does not solve every case. WebSockets, Server-Sent Events, upgraded connections, and background jobs need their own shutdown logic.

## 6. Background jobs and message queues

Consider a service consuming jobs from a queue.

When shutdown starts:

1. Stop fetching new jobs.
2. Let the current job finish if there is enough time.
3. If it cannot finish, safely release or abandon it according to the queue's retry and acknowledgement rules.
4. Close the consumer connection.

For jobs that have external side effects—such as issuing refunds—design for idempotency. A forced termination can happen at any point, even with graceful-shutdown logic, so retries must not cause duplicate side effects.

## 7. Common mistakes

| Mistake                              | Why it is dangerous                                                  |
| ------------------------------------ | -------------------------------------------------------------------- |
| Calling `process.exit()` immediately | Can interrupt active work and pending operations.                    |
| Never setting a shutdown deadline    | The process may hang indefinitely.                                   |
| Closing the DB pool too early        | In-flight requests may fail when they need the database.             |
| Forgetting queue consumers           | New jobs may start while the service is shutting down.               |
| Only changing the readiness endpoint | The load balancer may still route requests to the instance.          |
| Assuming every request will finish   | Long-running requests can exceed the available shutdown window.      |
| Ignoring retries and idempotency     | Interrupted work may be repeated and produce duplicate side effects. |

## 8. Senior interview questions

Q1. Why is graceful shutdown important in a Node.js application running under PM2 or Docker?

It reduces failed requests and interrupted work during restarts, deployments, and termination events.

Q2. Does `server.close()` immediately terminate existing requests?

No. It stops accepting new connections and waits for existing connections to close. Idle connections and long-lived connections may require additional handling.

Q3. What if an HTTP request takes longer than the shutdown deadline?

The service needs a defined policy: allow it to finish if time permits, otherwise terminate the connection and rely on safe client retries and idempotent processing where appropriate.

Q4. Is graceful shutdown sufficient to guarantee that no work is lost?

No. A process can be killed unexpectedly or lose power. Durable queues, transaction design, acknowledgements, retries, and idempotency are also necessary.

## 1. Does `process.exitCode = 1` terminate Node.js?

No. Setting `process.exitCode = 1` sets the exit status Node.js should return when the process eventually exits naturally. It does not immediately terminate the process.

Compare these:

| Code                           | Meaning                                                       |
| ------------------------------ | ------------------------------------------------------------- |
| `process.exitCode = 1`         | Set the eventual exit status to failure; execution continues. |
| `process.exit(1)`              | Terminate the process immediately with failure status.        |
| `clearTimeout(forceExitTimer)` | Cancel the emergency shutdown timer.                          |
| `forceExitTimer.unref()`       | Prevent the timer alone from keeping the event loop alive.    |

In the earlier example:

```
catch (error) {
  console.error("Graceful shutdown failed:", error);

  // Set the eventual exit status.
  process.exitCode = 1;
}
```

The catch block records the failure and sets the exit status. The emergency timer remains active because we did not call `clearTimeout(forceExitTimer)`.

If shutdown hangs, the timer can eventually run:

```
const forceExitTimer = setTimeout(() => {
  console.error("Shutdown deadline exceeded.");
  process.exit(1);
}, 10_000);
```

One subtle but important detail: because the timer uses `.unref()`, it does not keep an otherwise idle process alive by itself. However, if an open connection or another resource keeps Node.js running, the timer can still fire. If the process becomes idle and exits naturally first, the timer won't keep it alive just to run.

The distinction: `process.exitCode` sets the result; `process.exit()` forces termination.

## 2. Does `server.close()` guarantee requests have drained before `pool.end()`?

For ordinary HTTP connections, it provides the key drain mechanism—but there are limits.

Consider this sequence:

```javascript
await new Promise((resolve, reject) => {
  server.close((error) => {
    if (error) reject(error);
    else resolve();
  });
});

await pool.end();
```

What happens:

1. `server.close()` stops the HTTP server from accepting new connections.
2. Its callback completes when the server has closed its connections.
3. The `await` pauses the shutdown function until that callback completes.
4. Only then does execution reach `await pool.end()`.

So, yes: the PostgreSQL pool is closed after the HTTP server's normal connection-draining step completes.

But `server.close()` is not a universal guarantee that all application work has finished. For example:

- A request handler may start background work without awaiting it.
- A queue consumer may still be using PostgreSQL.
- WebSockets or upgraded connections need separate handling.
- A request may not finish before the shutdown deadline.

Therefore, the safe rule is:

> Stop new HTTP and queue work, drain existing HTTP requests and active queue jobs, then close shared resources such as PostgreSQL.

The queue must also finish using the database before you call `pool.end()`.

  if (shutdownPromise) return shutdownPromise;

    console.error("Shutdown deadline exceeded");

    // Force-close ordinary HTTP connections where supported.
    server.closeAllConnections?.();

    // Emergency exit; active work may be interrupted.
    process.exit(1);

  shutdownPromise = (async () => {
    try {
      // 1. Stop accepting new HTTP connections.
      const httpDrain = closeHttpServer();

      // 2. Stop fetching new queue jobs.
      await queueConsumer.stopFetching();

      // 3. Drain both HTTP requests and active queue jobs.
      await Promise.all([
        httpDrain,
        queueConsumer.waitForActiveJobs(),

      await queueConsumer.close();

      await pool.end();

      // Cancel the hard deadline only after success.
      clearTimeout(forceExitTimer);

      console.error("Graceful shutdown failed:", error);

      // Do not clear the deadline. It remains the final safety net.
      process.exitCode = 1;
    }
  })();

  return shutdownPromise;
}

process.on("SIGINT", () => void shutdown("SIGINT"));

## 4. Important production caveats

This is a reusable starting template, not a complete drop-in solution for every application.

- Readiness and load balancers: Marking readiness as false is only one step. Your load balancer or deployment system must stop routing new traffic, with sufficient time for propagation.
- Queue semantics: The queue library must stop fetching new jobs and safely finish, release, or retry active jobs. Confirm how its acknowledgement and shutdown APIs work.
- Deadline behavior: The example's 30-second timer starts when shutdown begins. In real deployments, reserve time for forced termination and keep the deadline within the platform's own grace period.
- Forced termination: `server.closeAllConnections()` does not handle every upgraded connection, such as WebSockets. Handle those separately if your application uses them.
- Payment safety: A connection closing does not prove whether a payment succeeded. Use idempotency keys and durable transaction/payment states to recover safely.

### The mental model to remember

Signal received → mark unready → stop new HTTP/queue work → drain HTTP and active jobs → close queue and database resources → exit.

If the deadline expires, force termination and recover safely on retry.

## 1. What does this code actually do?

```javascript
return new Promise((resolve, reject) => {
  server.close((error) => {
    if (error) reject(error);
    else resolve();

});
```

There are three possible outcomes to understand:

| Situation                              | What happens                                                                                                                                  |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| No active connections                  | The server closes, and the callback normally calls `resolve()`.                                                                               |
| Active HTTP requests/connections exist | The server stops accepting new connections and waits for existing connections to close. Once closed, the callback normally calls `resolve()`. |
| An actual closing error occurs         | The callback receives an error, and the Promise rejects, sending execution to `catch`.                                                        |

Active connections are not, by themselves, an error.

## 3. The key distinction

- `resolve()` means the server has completed closing.
- `reject()` means the closing operation reported an error.
- Timeout means the closing operation hasn't completed within the allowed time; the separate timer handles that situation.

One additional nuance: on modern Node.js versions, `server.close()` has version-dependent behavior around idle keep-alive connections, and it does not cover every kind of upgraded connection. That's why production shutdown code may need additional connection handling.
