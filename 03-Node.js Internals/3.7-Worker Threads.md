# Topic 3.7 — Worker Threads

## 1. What are Worker Threads?

Node.js `worker_threads` allows JavaScript to execute in separate threads within the same process. Each worker has its own JavaScript execution environment, allowing CPU-intensive JavaScript tasks to run in parallel.

Worker Threads are particularly useful for CPU-heavy work, not as a default replacement for asynchronous I/O.

## 2. How do they work?

The main thread can delegate work to workers and continue handling other operations. Workers execute their own JavaScript, and the application can communicate with them through messages or shared memory mechanisms.

Worker Threads have their own V8 isolates and JavaScript heaps. They are threads, not separate operating-system processes.

## 3. Basic implementation

Main file — `main.js`

```
const { Worker } = require("node:worker_threads");

const worker = new Worker("./worker.js");

worker.on("message", (result) => {
  console.log("Result:", result);
});

worker.on("error", (error) => {
  console.error("Worker failed:", error);
});

worker.on("exit", (code) => {
  if (code !== 0) {
    console.error("Worker stopped with exit code", code);
  }
});
```

Worker file — `worker.js`

```
const { parentPort } = require("node:worker_threads");

let total = 0;

for (let i = 0; i < 100_000_000; i++) {
  total += i;
}

parentPort.postMessage(total);
```

The calculation runs on the worker thread rather than blocking the main JavaScript thread.

Production code should also handle worker lifecycle management, task failures, timeouts, and unexpected exits.

## 4. When should you use Worker Threads?

| Workload                                                        | Preferred approach                                             |
| --------------------------------------------------------------- | -------------------------------------------------------------- |
| HTTP requests and ordinary asynchronous database queries        | Async I/O on the main thread                                   |
| CPU-heavy calculations                                          | Worker Threads                                                 |
| Image processing or computational transformations in JavaScript | Worker Threads may be appropriate                              |
| Large numbers of short CPU tasks                                | Consider a worker pool to avoid creating a new thread per task |
| Independently scalable or isolated background jobs              | Consider separate processes or a worker service                |

Important: Worker Threads introduce overhead from scheduling, communication, and transferring data. A worker pool is often better than creating a new worker for every request.

## 5. Worker Threads vs libuv Thread Pool

| Feature                   | Worker Threads                         | libuv Thread Pool                                       |
| ------------------------- | -------------------------------------- | ------------------------------------------------------- |
| Main purpose              | Run application JavaScript in parallel | Perform selected native asynchronous operations         |
| Executes your JavaScript? | Yes                                    | Generally no; pool work is native                       |
| Controlled through        | `node:worker_threads` API              | libuv runtime and settings such as `UV_THREADPOOL_SIZE` |
| Typical use               | CPU-heavy JS calculations              | Filesystem, selected crypto and other native operations |

Don't confuse these two mechanisms in interviews.

## 6. Interview-ready answer

> Worker Threads allow Node.js to execute JavaScript in parallel using separate threads and V8 isolates within the same process. They're useful for CPU-intensive JavaScript because they prevent long computations from blocking the main thread. For production workloads, I would generally consider a bounded worker pool, handle worker failures, and measure the overhead of transferring data between threads.

## Do Worker Threads have their own Event Loop?

Yes. Each Worker Thread has its own JavaScript execution environment and its own Event Loop.

A Worker Thread isn't simply a background function running inside the main thread. It has its own V8 isolate, JavaScript Call Stack, and Event Loop.

### Why does this matter?

Suppose Worker 1 performs a CPU-heavy calculation that takes two seconds.

- Worker 1's JavaScript thread is blocked by that calculation.
- Worker 1's own Event Loop cannot process ordinary callbacks while its thread is blocked.
- The main thread's Event Loop can continue handling requests, provided the main thread isn't blocked by other work.
- Worker 2 can execute its work independently, subject to available CPU resources.

So a worker's Event Loop doesn't make CPU-heavy JavaScript non-blocking within that worker. The benefit is that the computation no longer blocks the main JavaScript thread.

### Interview-ready answer

> Each Node.js Worker Thread has its own V8 isolate, JavaScript Call Stack, and Event Loop. CPU-heavy synchronous JavaScript blocks that worker's thread, but it doesn't inherently block the main thread or other workers. Workers can communicate through message passing or shared memory.

One final distinction: Worker Threads have their own Event Loops, but they share the same operating-system process. They aren't equivalent to Cluster workers, which run in separate processes.

## 1. What happens if you create too many Worker Threads?

Suppose your server has 8 logical CPU cores and you create 100 workers, all performing CPU-intensive calculations simultaneously.

- CPU contention: Many runnable threads compete for a limited number of CPU cores.
- Context-switching overhead: The operating system spends time switching between threads.
- Memory overhead: Each worker has its own V8 isolate and associated runtime resources.
- Higher latency: Main-thread request processing can become slower because it competes for CPU resources with workers.
- Reduced throughput: Adding more workers beyond the useful capacity can make the system slower rather than faster.

One important nuance: CPU contention doesn't mean every thread is literally blocked. Threads may be runnable but waiting for CPU time.

Logical CPU count is only a starting point. Container CPU quotas, other workloads on the host, task duration, and the main thread's workload all affect the appropriate pool size.

## 3. How should a production worker pool behave?

A good pool should generally have:

- A fixed or configurable maximum number of workers.
- A bounded task queue, with backpressure or rejection when overloaded.
- Worker error handling and replacement when necessary.
- Graceful shutdown and task timeouts where appropriate.
- Metrics for queue depth, wait time, execution time, failures, and CPU utilization.

If every worker is busy, new tasks should wait within controlled limits or be rejected gracefully rather than causing unlimited resource growth.

## 4. Senior interview answer

> I would use a bounded Worker Thread pool rather than creating a worker for every request. Too many CPU-intensive workers cause CPU contention, scheduling overhead, and increased memory usage, potentially degrading the main thread's latency. I would start with the available CPU resources as a baseline, account for the main thread and deployment limits, and benchmark pool sizes using throughput, tail latency, CPU, and queue metrics. I would also bound the task queue to prevent overload.

Rephrased question: Does the same CPU contention problem apply to Node.js Cluster when we create too many worker processes?

Yes, exactly. The same principle applies to Cluster, but Cluster uses separate OS processes, whereas Worker Threads use separate threads within one process.

| Aspect               | Worker Threads                                        | Cluster                                                             |
| -------------------- | ----------------------------------------------------- | ------------------------------------------------------------------- |
| Execution unit       | Thread                                                | OS process                                                          |
| JavaScript execution | Separate thread per worker                            | Separate process per worker                                         |
| Memory               | Separate V8 isolates/heaps; shared memory is possible | Separate process memory                                             |
| Too many workers     | CPU contention, context switching, memory overhead    | CPU contention, context switching, generally higher memory overhead |
| Main use             | CPU-intensive JavaScript tasks                        | Scaling a Node.js server across CPU cores                           |

### Example

Suppose your server has 4 available CPU cores.

- 4 Cluster workers: A reasonable starting point for a CPU-bound workload, subject to benchmarking.
- 20 Cluster workers: They compete for the same CPU resources. This can increase context switching, memory consumption, and request latency without improving throughput.
- 2 Cluster workers: May be sufficient if the workload is mostly I/O-bound, or if the machine is shared with other services.

These are starting points, not fixed rules. Also, CPU quotas in containers may mean that the number of available cores differs from the host's physical CPU count.

### Senior-level takeaway

Cluster improves multi-core utilization; it does not create additional CPU capacity. Start with a sensible worker count, then benchmark throughput, CPU utilization, memory usage, and p95/p99 latency.

One important distinction: if one Cluster worker gets blocked by CPU-heavy synchronous JavaScript, the other workers can continue serving requests independently. However, if all workers are overloaded—or the machine runs out of CPU capacity—the whole service can still suffer.
