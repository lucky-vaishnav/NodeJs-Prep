## Topic 3.4: Garbage Collection (GC)

You already understand the key prerequisite: V8 can reclaim objects that are no longer reachable, but it generally cannot reclaim objects that remain reachable through references.

Now we'll go deeper into how garbage collection works, how V8 handles objects with different lifetimes, and why GC matters for production latency and memory leaks.

## 1. What is garbage collection?

Garbage collection is the process of identifying memory that is no longer needed by the JavaScript program and reclaiming it for reuse.

Consider:

```
function processRequest() {
  let user = {
    name: "Ava",
    details: {
      role: "Developer"
    }
  };

  user = null;
}

processRequest();
```

After `user = null`, the local variable no longer references the object. If no other references point to that object or its nested data, those objects become eligible for garbage collection.

Two important terms:

- Unreachable: The object cannot be reached through the program's live references.
- Eligible for collection: The object can be reclaimed, but collection is not necessarily immediate.

JavaScript developers generally don't manually free ordinary objects. V8 manages their memory automatically.

## 2. How does V8 know what can be collected?

V8 uses reachability analysis. Conceptually, it starts from GC roots and follows references to determine which objects are still reachable.

Common roots include active execution state, global references, and runtime-held references.

Notice that Object B can remain reachable even if your application doesn't directly reference it. A reference from Object A is enough to keep it reachable.

This is why a single long-lived reference can retain a large object graph.

## 3. Why does V8 use generational garbage collection?

A useful observation about application memory is that many objects have short lifetimes, while a smaller number survive for a long time.

For example, in an API server:

- Temporary objects created while parsing a request may become unreachable shortly afterward.
- A cached configuration object may remain reachable for the entire lifetime of the process.
- A long-lived in-memory cache may retain objects for hours or days.

V8 uses generational strategies to take advantage of this pattern.

The exact heap organization and collection strategies are implementation details that can evolve between V8 versions.

### Minor GC vs major GC

| Concept  | General purpose                                                                          |
| -------- | ---------------------------------------------------------------------------------------- |
| Minor GC | Collects the young generation, where many short-lived objects are allocated.             |
| Major GC | Performs collection work involving the old generation and typically has a broader scope. |

These are useful conceptual terms for interviews. Modern V8 uses several cooperating collection mechanisms, so don't assume every collection is a single, simple stop-the-world operation.

## 4. What algorithms does garbage collection use?

You should recognize these names and their purpose.

Marking: V8 identifies objects that remain reachable from GC roots.

Sweeping: Memory associated with unreachable objects is reclaimed for reuse.

Compaction: Live objects may be moved closer together to reduce fragmentation and make memory allocation more efficient.

Incremental collection: Some GC work is split into smaller steps to reduce the duration of individual pauses.

Concurrent collection: Some GC work can run concurrently with application JavaScript on other threads.

Parallel collection: Multiple threads perform parts of GC work together.

These approaches can be combined. V8 uses different strategies depending on the type of collection and the memory region involved.

The important performance trade-off is that GC requires resources. V8 must balance the cost of collection against memory consumption and application responsiveness.

## 5. Does garbage collection cause API latency?

Yes, it can contribute to latency, although it is not the only possible cause.

Imagine a Node.js service receiving hundreds of requests per second. Each request creates many temporary objects:

```
app.get("/report", async (req, res) => {
  const rows = await loadRows();

  const result = rows.map((row) => ({
    id: row.id,
    amount: row.amount,
    formatted: formatAmount(row.amount)
  }));

  res.json(result);
});
```

If this endpoint creates large amounts of temporary data, it can increase allocation and GC work.

Potential consequences include:

- Increased CPU consumption.
- GC pauses or other GC-related execution delays.
- Higher request latency, particularly at the tail of the latency distribution.
- Greater memory pressure when objects survive longer than expected.

However, don't conclude that `map()` or object creation is inherently a problem. You need profiling evidence. Large database results, expensive formatting, serialization, slow dependencies, and synchronous CPU work can also contribute to latency.

## 6. How do you investigate GC and memory issues in production?

Use a combination of metrics and profiling.

1. Monitor memory trends. Track `heapUsed`, `heapTotal`, `rss`, `external`, and `arrayBuffers` using `process.memoryUsage()`.
2. Inspect GC behavior. Use supported Node.js diagnostics, GC tracing in a controlled environment, or profiling tools to examine collection frequency and duration.
3. Compare heap snapshots. When safe, capture snapshots at different points and identify object types that accumulate or remain retained.
4. Inspect retaining references. Determine whether objects are held by caches, closures, event listeners, global collections, or pending operations.
5. Measure application impact. Correlate memory and GC metrics with request latency, CPU utilization, traffic volume, and errors.

Production warning: Heap snapshots can temporarily consume substantial memory and pause execution. On a memory-constrained production instance, capturing one can worsen an existing problem. Prefer a controlled reproduction or a carefully planned diagnostic procedure.

Also, forcing GC with `--expose-gc` during diagnosis can sometimes help compare retained heap usage, but it is not a fix for a leak and should not be treated as normal production memory management.

## 7. Interview-ready answer

If asked, “How does garbage collection work in V8?”, you could say:

> V8 uses reachability analysis to determine which JavaScript objects are still accessible from live roots. Unreachable objects become eligible for collection. V8 uses generational strategies because many objects have short lifetimes, and it employs different collection techniques depending on the memory region and workload. Garbage collection can consume CPU and contribute to latency, so in production I would monitor heap and process memory, examine GC behavior, and use heap snapshots to investigate retained objects rather than assuming that every increase in memory is a leak.

Good attempt.You've identified the likely direction of both scenarios, but there's one important correction about garbage collection.

## Scenario A — Memory remains high

Your answer: memory leak; GC cannot reclaim memory to reuse.

Partially correct. A memory leak is a strong possibility, but GC may be working correctly and still be unable to reclaim the memory.

For example, a global cache might retain objects even after requests finish. Those objects remain reachable, so V8 cannot collect them.

What I'd investigate:

- Track `heapUsed` and RSS after traffic returns to normal.
- Compare heap snapshots to identify accumulating objects.
- Inspect retaining references, especially unbounded caches, closures, and event listeners.

Key correction: GC reclaims unreachable objects; it doesn't decide whether reachable objects are still useful to your business logic.

## Scenario B — Memory rises, then drops

Your answer: GC works, but the API uses a lot of memory.

Mostly correct. The pattern is consistent with a workload creating many temporary objects that GC later reclaims.

However, occasional latency spikes might be related to GC activity, but you need profiling evidence to establish that relationship.

What I'd investigate:

- GC frequency and duration.
- Request latency, particularly p95 and p99.
- Allocation rate and the volume of temporary objects.
- Whether CPU-heavy work or slow external dependencies also contribute to the latency.

## Remember the distinction

| Observation                                        | Possible explanation                                        |
| -------------------------------------------------- | ----------------------------------------------------------- |
| Heap keeps growing and objects remain retained     | Memory leak or unintended retention                         |
| Heap rises during traffic and falls after GC       | Temporary allocation pressure                               |
| RSS grows while heap remains stable                | Native or external memory growth, among other possibilities |
| Latency spikes coincide with expensive GC activity | GC may be contributing to latency                           |

These are diagnostic clues, not definitive proof.
