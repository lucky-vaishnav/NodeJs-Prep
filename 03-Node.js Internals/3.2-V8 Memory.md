## Topic 3.2: V8 Memory

The goal of this topic is to understand how V8 manages JavaScript memory, why a Node.js process can consume increasing amounts of RAM, and how memory behavior affects production performance.

Since you already understand that V8 executes JavaScript and manages JavaScript memory, we'll focus on the internals and production implications rather than repeat the basics.

## 1. What does V8 memory management mean?

When your Node.js application creates objects, arrays, functions, and strings, those values require memory.

For example:

```
const user = {
  id: 101,
  name: "Lucky",
  roles: ["admin", "developer"]
};
```

V8 manages the memory required by JavaScript values and objects. It tracks objects that are still reachable and can reclaim memory occupied by objects that are no longer needed.

At a high level, think of memory management as three responsibilities:

An important distinction: an object being unnecessary to your business logic does not automatically mean V8 can reclaim it. If your program still holds a reference to that object, it may remain reachable.

We'll study garbage collection algorithms and pauses in Topic 3.4. For now, focus on how memory is organized and what V8 needs to manage.

## 2. What kinds of memory does a Node.js process use?

A common mistake is to assume that all memory consumed by Node.js belongs to the V8 JavaScript heap. It doesn't.

<img width="988" height="625" alt="Screenshot 2026-10-18 135459" src="https://github.com/user-attachments/assets/074262aa-81cf-49d7-9b0b-5456b94db7bb" />

These categories are conceptual and can overlap in accounting. For example, an ArrayBuffer's backing memory may be accounted for as external memory even though a JavaScript object references it.

### Why this matters in production

Imagine your Node.js service has these metrics:

- V8 heap usage: 400 MB
- Process RSS: 1.2 GB

This does not automatically mean that V8 has a 1.2 GB JavaScript memory leak. The difference may include native allocations, Buffer backing stores, code, stacks, and other process memory.

You need to identify which memory category is growing before deciding how to investigate.

## 3. How to inspect Node.js memory

Node.js exposes `process.memoryUsage()`:

```
const memory = process.memoryUsage();

console.log({
  rss: memory.rss,
  heapTotal: memory.heapTotal,
  heapUsed: memory.heapUsed,
  external: memory.external,
  arrayBuffers: memory.arrayBuffers
});
```

The returned sizes are in bytes.

| Metric         | What it tells you                                                                           |
| -------------- | ------------------------------------------------------------------------------------------- |
| `rss`          | Resident Set Size: physical memory currently resident for the whole process.                |
| `heapTotal`    | Memory allocated for the V8 heap.                                                           |
| `heapUsed`     | Portion of the V8 heap currently being used.                                                |
| `external`     | Memory associated with native objects bound to JavaScript objects, outside the V8 heap.     |
| `arrayBuffers` | Memory used by ArrayBuffer and SharedArrayBuffer backing stores, including Node.js Buffers. |

`arrayBuffers` is included in `external`, so do not add those two numbers together when estimating memory consumption.

Also, `heapTotal` is not the same as the maximum heap limit. V8 may grow its heap as needed, subject to its limits and the available system resources.

### Example: interpreting a trend

Suppose you observe this pattern over several hours:

| Metric     | At startup | After several hours |
| ---------- | ---------- | ------------------- |
| `heapUsed` | 150 MB     | 700 MB              |
| `rss`      | 300 MB     | 950 MB              |

This suggests that JavaScript heap usage is growing substantially, but it doesn't prove a memory leak. The application may be retaining legitimate data, experiencing a temporary workload increase, or accumulating objects that should have been released.

The next step is to investigate the trend after garbage collection and, when appropriate, compare heap snapshots.

## 4. Why can memory usage keep increasing?

Consider this example:

```
const cache = new Map();

function handleRequest(userId, userData) {
  cache.set(userId, userData);
}
```

Every request adds an entry to `cache`, and nothing removes old entries.

Even if the request has finished and the user is no longer active, the cached objects remain reachable through the global `Map`.

V8 cannot reclaim those objects while they remain reachable.

This is a common source of memory leaks in long-running Node.js applications.

Other common causes include:

- Unbounded caches: Data accumulates without a size limit or expiration policy.
- Global references: Objects are retained longer than intended.
- Event listeners: Listeners retain closures or related objects after they are no longer needed.
- Unfinished asynchronous work: Pending operations retain their associated state.
- Large request or response buffers: Buffers remain referenced after processing should have finished.

The important principle is that a memory leak is not simply “an object that exists for a long time.” It is memory retained unnecessarily, often causing usage to grow over time.

## 5. How V8 memory management affects performance

V8 doesn't wait until the entire process runs out of RAM before doing any garbage collection. It manages its heap and performs collection as needed.

At a high level, V8 uses different allocation and collection strategies for objects with different lifetimes. It can reclaim unreachable objects and compact or reorganize memory where appropriate.

We'll study the specific garbage collection behavior in Topic 3.4.

For now, understand these production implications:

- Creating many short-lived objects can increase allocation and garbage-collection work.
- Retaining large objects unnecessarily increases memory pressure.
- Garbage collection can consume CPU time and may contribute to latency spikes.
- Excessive memory use can lead to out-of-memory failures or the operating system terminating the process.
- Restarting a process may temporarily clear accumulated memory, but it does not fix the underlying leak.

For an API service managed by PM2, for example, repeatedly restarting a process that consumes increasing amounts of memory may reduce the immediate impact, but the application still needs investigation.

## 6. Interview-ready answer

If asked, “How does Node.js manage memory?”, you could say:

> Node.js uses V8 to manage JavaScript memory. V8 allocates memory for JavaScript values and tracks object reachability so that garbage collection can reclaim memory occupied by unreachable objects. However, the total Node.js process memory includes more than the V8 heap; it also includes native allocations, Buffer backing memory, stacks, and other runtime resources. In production, I would monitor heap usage alongside RSS and external memory, look for sustained growth, and use heap snapshots or other profiling tools to investigate suspected leaks.

## 1. Why can't V8 reclaim the objects?

Your answer is correct: objects that remain reachable through references generally cannot be reclaimed by garbage collection.

For example, a global cache might retain data from thousands of API requests. Even when each request finishes, its data remains reachable through the cache.

One refinement: it isn't necessarily because code is still executing. Objects can remain reachable even when no function is actively using them—for example, through a global variable, a `Map`, or an event listener.

## 2. How would you investigate the leak?

You're right that we shouldn't monitor only `heapUsed`. We should monitor the overall process memory and its different components.

A stronger investigation would be:

1. Track memory trends: Compare `heapUsed`, `heapTotal`, `rss`, `external`, and `arrayBuffers` over time.
2. Check sustained growth: Determine whether memory keeps increasing under a stable workload, rather than temporarily rising during a traffic spike.
3. Investigate heap retention: Compare heap snapshots to identify objects that accumulate and inspect their retaining references.
4. Check external memory: If RSS increases but heap usage stays relatively stable, investigate Buffer allocations and native memory as well.

Remember: increasing memory usage alone doesn't prove a leak. The key question is whether memory that should have been released is being retained unnecessarily.
