## Topic 3.6: Single-Threaded Model

You've already learned that Node.js executes JavaScript primarily on a main JS thread, while asynchronous I/O and certain native operations can progress outside that thread. Now let's understand exactly what “single-threaded” means, its advantages, and its limitations in production.

## 1. What does single-threaded actually mean?

In the normal Node.js execution model, application JavaScript executes on the main JavaScript thread.

Consider:

```
console.log("A");

setTimeout(() => {
  console.log("B");
}, 1000);

console.log("C");
```

The main JS thread executes `A`, schedules the timer, and then executes `C`. After the timer becomes eligible and Node.js can process its callback, the main JS thread executes `B`.

The timer's waiting period does not require the main JS thread to sit idle.

But consider this:

```
console.log("A");

while (true) {
  // Infinite synchronous loop
}

console.log("B");
```

The main JS thread is stuck in the loop. The Event Loop cannot make progress on ordinary JavaScript callbacks, and `B` never executes.

The key distinction: asynchronous waiting allows other JavaScript to run; synchronous CPU-heavy work keeps the main JS thread occupied.

## 2. If Node.js is single-threaded, where does concurrency come from?

Node.js combines the main JS thread with facilities provided by the runtime and operating system.

For example, a server may have hundreds of requests waiting on database or network responses. Node.js doesn't need a dedicated JavaScript thread for each request.

While one request waits for I/O, the main JS thread can execute JavaScript associated with another request.

This is concurrency, not necessarily parallel execution of application JavaScript.

## 3. What are the advantages and limitations?

| Advantages                                                                                             | Limitations                                                                        |
| ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| No need to coordinate shared JavaScript state across multiple application threads in the default model | CPU-heavy synchronous work can block all other JavaScript callbacks on that thread |
| Efficient handling of many I/O-bound requests                                                          | Long-running callbacks increase request latency                                    |
| Asynchronous APIs allow the main thread to work while operations wait                                  | Thread-pool saturation can delay operations that depend on the pool                |
| A simpler execution model for ordinary application code                                                | Scaling CPU-heavy JavaScript may require Worker Threads or multiple processes      |

One clarification: single-threaded JavaScript doesn't mean the application is free from race conditions. Asynchronous operations can still interleave in ways that create logical races, such as two requests trying to reserve the same parking space.

## 4. What if the application needs CPU parallelism?

Suppose your API needs to perform expensive image processing or a large calculation.

Making the function `async` doesn't move its CPU work to another thread:

```
async function calculate() {
  let total = 0;

  for (let i = 0; i < 1_000_000_000; i++) {
    total += i;
  }

  return total;
}
```

The loop still executes synchronously on the main JS thread. The `async` keyword makes the function return a Promise; it does not automatically offload the computation.

For CPU-heavy JavaScript, consider:

- Worker Threads: execute JavaScript on separate threads and can use multiple CPU cores.
- Child processes or cluster workers: run separate processes, each with its own JavaScript execution environment.
- External worker services: useful when CPU-heavy jobs need independent scaling or durable background processing.

We'll cover Worker Threads and Cluster separately in the upcoming roadmap topics.

## 5. Interview-ready answer

> Node.js is commonly described as single-threaded because application JavaScript normally executes on one main JavaScript thread. It achieves high I/O concurrency through its event-driven runtime, operating-system asynchronous I/O facilities, and libuv's thread pool for selected native operations. When an asynchronous operation completes, its JavaScript callback executes on the main thread. This works well for I/O-bound workloads, but CPU-heavy synchronous JavaScript blocks that thread. Worker Threads or separate processes can be used when parallel CPU execution is required.
