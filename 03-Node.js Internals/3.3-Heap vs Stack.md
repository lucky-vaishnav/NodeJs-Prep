# Topic 3.3 — Heap vs Stack

This is the next topic in your roadmap. We'll focus on the memory model and its implications, without repeating the full V8 introduction.

## 1. What is the difference?

## Call Stack

- Tracks active function calls and execution state.
- Uses stack frames as functions execute.
- Deep or unbounded recursion can cause a stack overflow.

## V8 Heap

- Holds dynamically allocated JavaScript objects and related data.
- Objects may remain in memory after the function that created them returns.
- Garbage collection can reclaim unreachable objects.

A key distinction: the Call Stack is primarily about execution, while the Heap is primarily about memory allocation for objects and other data.

## 2. Trace this example

```
function createUser() {
  const user = {
    name: "Lucky",
    role: "Developer"
  };

  return user;
}

const result = createUser();

console.log(result.name);
```

Conceptually:

- `createUser()` begins executing, creating a stack frame.
- The `user` variable holds a reference to an object managed by V8.
- The function returns that reference.
- The `createUser()` stack frame is removed.
- `result` still references the returned object, so the object remains reachable.

Important: Don't memorize that every local variable lives on the physical stack or that every object has a simplistic, fixed location. V8 can optimize how values are represented and stored. The stack-versus-heap distinction is a useful conceptual model, not a complete description of every implementation detail.

### 1. Why can `getName()` access `user.name`?

Because of a closure.

The `inner` function retains access to the lexical environment in which it was created. That environment contains the binding for `user`, so `getName()` can still access it after `outer()` returns.

### 2. Can the object be garbage-collected when `outer()` returns?

No, not while it remains reachable through the returned function.

The key distinction is that `outer()`'s stack frame has finished, but the data needed by the closure can remain alive.

One senior-level nuance: closures retain the necessary lexical bindings, not necessarily a complete copy of every local variable in the outer function. Also, if the returned function and its references become unreachable, the captured data may eventually be reclaimed.

Production connection: Closures are useful for maintaining state, but long-lived callbacks, timers, or event listeners can unintentionally retain large objects and contribute to memory leaks.
