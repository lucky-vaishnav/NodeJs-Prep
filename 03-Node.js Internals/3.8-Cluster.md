# Topic 3.8 — Cluster

## 1. What is Cluster?

Node.js Cluster allows you to run multiple Node.js worker processes that can share a server port, such as port `3000`.

By default, a Node.js application’s JavaScript runs on one main thread. Even if your server has eight CPU cores, a single Node.js process won't automatically execute its JavaScript request handlers across all eight cores.

Cluster lets you run multiple processes so the application can use multiple cores.

Each worker is a separate process with its own JavaScript execution environment, Event Loop, and memory space. Workers don't automatically share ordinary JavaScript objects or in-memory variables.

## 2. Example implementation

```
const cluster = require("node:cluster");
const os = require("node:os");
const http = require("node:http");

const workerCount =
  os.availableParallelism?.() ?? os.cpus().length;

if (cluster.isPrimary) {
  console.log(`Primary PID: ${process.pid}`);

  for (let i = 0; i < workerCount; i++) {
    cluster.fork();
  }

  cluster.on("exit", (worker, code, signal) => {
    console.log(`Worker ${worker.process.pid} exited`);
  });
} else {
  const server = http.createServer((req, res) => {
    res.end(`Handled by worker PID: ${process.pid}`);
  });

  server.listen(3000);
}
```

How it works:

1. The primary process starts and creates multiple workers using `cluster.fork()`.
2. Each worker starts its own copy of the Node.js application.
3. Workers call `server.listen(3000)`. Cluster coordinates the shared server port and distributes connections according to its scheduling strategy.
4. Requests can be handled by different worker processes, each with its own PID and memory.
5. If a worker exits, the primary can detect the exit. Production applications need a controlled restart strategy, including restart limits and backoff.

This example demonstrates the basic mechanism, not a complete production deployment.

## 3. Cluster vs Worker Threads

| Feature               | Cluster                          | Worker Threads                                                                                             |
| --------------------- | -------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Isolation             | Separate OS processes            | Separate threads in one process                                                                            |
| Memory                | Independent process memory       | Separate V8 isolates; optional shared memory                                                               |
| Startup/resource cost | Generally higher                 | Generally lower                                                                                            |
| Typical purpose       | Scale HTTP servers across cores  | Run CPU-intensive JavaScript tasks in parallel                                                             |
| Failure isolation     | Stronger process-level isolation | A worker failure does not necessarily crash the process, but process-level failures can affect all threads |
| Communication         | Inter-process messaging (IPC)    | Message passing; `SharedArrayBuffer` is also possible                                                      |

Both can utilize multiple cores. Neither automatically makes a single synchronous JavaScript operation parallel—you must distribute the work appropriately.

## 4. Production considerations

- Worker count: Start with a sensible number based on available CPU capacity, memory, and workload. Benchmark rather than blindly matching the physical core count.
- State: Don't rely on process-local variables for shared sessions, counters, or reservation state. Use shared infrastructure such as Redis or a database where appropriate.
- Failures: Add health checks, controlled restarts, graceful shutdown, and monitoring.
- Scaling: Cluster scales processes within one machine. Multiple machines or containers behind a load balancer provide another level of horizontal scaling.
- Deployment: PM2 supports cluster mode and can manage multiple application processes. We'll cover PM2 in Phase 4.

## 5. Interview-ready answer

> Node.js Cluster allows an application to run multiple worker processes, enabling it to use multiple CPU cores for handling requests. Each worker has its own V8 isolate, Event Loop, and memory space. The primary process manages workers, and Cluster coordinates connections to the shared server port. Unlike Worker Threads, Cluster provides process-level isolation but generally has higher memory overhead. In production, we need to manage worker count, failures, graceful shutdown, shared state, and monitoring.

An important distinction: Node.js can use multiple cores for other work even without Cluster. For example:

- The libuv thread pool can run certain filesystem, crypto, and other native operations on background threads.
- The operating system can handle asynchronous network I/O.
- Native libraries may use additional threads.

Senior-level takeaway: Cluster is one way to scale JavaScript execution across CPU cores using multiple processes. Worker Threads are another option, particularly for CPU-intensive JavaScript tasks. Neither is automatically necessary for every application.

## 2. Do Worker Threads have separate heaps and garbage collectors?

Rephrased question: Like Cluster processes, do Worker Threads have their own memory, heap, and garbage collection?

Yes, mostly — but there's an important distinction between an isolate and a process.

| Feature                        | Cluster workers                      | Worker Threads                                                   |
| ------------------------------ | ------------------------------------ | ---------------------------------------------------------------- |
| Separate execution environment | Yes                                  | Yes, separate V8 isolate                                         |
| Separate JavaScript heap       | Yes                                  | Yes                                                              |
| Garbage collection             | Each process manages its own V8 heap | Each isolate manages its own V8 heap                             |
| Separate OS process            | Yes                                  | No                                                               |
| Shared JavaScript objects      | Not directly                         | Not normally; shared memory is possible with `SharedArrayBuffer` |
| Native/process resources       | Separate process resources           | Some resources belong to the overall process and may be shared   |

### How GC works in Worker Threads

Each Worker Thread has its own V8 isolate, so its JavaScript heap and garbage collection are managed separately from the main thread's isolate.

For example:

```
// main.js
const { Worker } = require("node:worker_threads");

const worker = new Worker("./worker.js");

const user = { name: "Lucky" };
```

```
// worker.js
const { parentPort } = require("node:worker_threads");

const data = { items: new Array(100_000) };

parentPort.postMessage("Work completed");
```

Here, `user` belongs to the main thread's JavaScript environment, while `data` belongs to the worker's environment. They are not automatically part of one shared JavaScript heap.

A few nuances:

- Garbage collection is isolate-specific, but don't assume every GC operation is always completely independent of every other thread or shared process resource.
- A worker can consume substantial memory even if the main thread's heap usage looks low.
- `process.memoryUsage()` reports process-level memory information, not simply the main thread's heap. Use appropriate heap statistics and per-worker monitoring when investigating memory.
- With `SharedArrayBuffer`, threads can access shared memory, but the shared memory is not an ordinary JavaScript object graph managed like each isolate's private heap.

Interview-ready answer:

> Worker Threads run JavaScript in separate V8 isolates, each with its own JavaScript heap and garbage collection. Unlike Cluster, they share the same OS process, so they have lower process-level overhead in many cases, but they don't share ordinary JavaScript objects automatically. Shared memory can be used explicitly through mechanisms such as SharedArrayBuffer.
