# Phase 7.1 — CommonJS vs ES Modules: Deep Dive

This is an important senior Node.js topic because module systems affect application startup, dependency loading, package compatibility, testing, circular dependencies, and production deployments.

Our goal isn't just to know the syntax difference between `require()` and `import`. We want to understand how Node.js loads, resolves, caches, and executes modules, and what can go wrong in a real backend application.

## 1. What are CommonJS and ES Modules?

Node.js supports two module systems:

- CommonJS (CJS): Node.js's traditional module system, using `require()` and `module.exports`.
- ES Modules (ESM): The official JavaScript module standard, using `import` and `export`.

Example:

CommonJS

```jsx
// userService.js
const userRepository = require("./userRepository");

function getUser(id) {
  return userRepository.findById(id);
}

module.exports = { getUser };
```

```jsx
// app.js
const { getUser } = require("./userService");
```

ES Modules

```jsx
// userService.js
import userRepository from "./userRepository.js";

export function getUser(id) {
  return userRepository.findById(id);
}
```

```jsx
// app.js
import { getUser } from "./userService.js";
```

The syntax looks similar in purpose, but the underlying loading and execution models are different.

## 2. How CommonJS works internally

When Node.js loads a CommonJS file, it approximately:

1. Resolves the requested module path.
2. Checks whether the module is already in the module cache.
3. If cached, returns its existing exports.
4. Otherwise, creates a new module object.
5. Wraps the file in a function.
6. Executes that function.
7. Stores the module in the cache and returns its exports.

Node.js conceptually wraps every CommonJS module like this:

```jsx
(function (
  exports,
  require,
  module,
  __filename,
  __dirname
) {
  // Your module code runs here
});
```

This explains why these variables are available without importing them:

```jsx
console.log(__dirname);
console.log(__filename);
console.log(module);
console.log(require);
```

They are provided through the CommonJS module wrapper.

### 2.1 `module.exports` vs `exports`

This is a common interview question.

Initially:

```jsx
exports === module.exports; // true
```

Both reference the same object.

This works:

```jsx
exports.getUser = () => {};
exports.createUser = () => {};
```

Because you're adding properties to the shared object.

But this behaves differently:

```jsx
exports = {
  getUser: () => {}
};
```

You have reassigned the local `exports` variable. You haven't changed `module.exports`.

Correct way to replace the exported value:

```jsx
module.exports = {
  getUser: () => {},
  createUser: () => {}
};
```

Senior takeaway: `module.exports` is what `require()` returns. `exports` is just an initially provided reference to it.

## 3. CommonJS module caching and singleton behavior

CommonJS caches modules after their first successful load.

Consider:

```jsx
// counter.js
let count = 0;

function increment() {
  count++;
}

function getCount() {
  return count;
}

module.exports = { increment, getCount };
```

Two other modules import it:

```jsx
// serviceA.js
const counter = require("./counter");

counter.increment();

module.exports = counter;
```

```jsx
// serviceB.js
const counter = require("./counter");

counter.increment();

module.exports = counter;
```

Both receive the same cached module instance when they resolve to the same module file.

```jsx
const a = require("./serviceA");
const b = require("./serviceB");

console.log(a.getCount()); // 2
console.log(b.getCount()); // 2

console.log(a === b); // true
```

This is why a module can behave like a singleton within a Node.js process.

Production implications:

This is useful for:

- Shared configuration.
- Database connection managers.
- Logger instances.
- In-memory registries.

But it can also cause problems:

- Mutable global state shared between requests.
- Tests affecting one another.
- Configuration being initialized before environment variables are loaded.
- Accidental state sharing between modules.

Remember: module caching is per Node.js process, not across multiple PM2 instances, cluster workers, or containers. Each process has its own module instances.

## 4. How ES Modules work internally

ES Modules use a different model.

Instead of executing `import` as an ordinary function call, Node.js processes the module graph.

The simplified lifecycle is:

1. Resolution: Identify the imported module.
2. Loading: Obtain the module source.
3. Linking/instantiation: Connect imports to exports and establish bindings.
4. Evaluation: Execute module code in dependency order.

The important difference is that ESM has a static module structure.

For example:

```jsx
import { getUser } from "./userService.js";

console.log(getUser());
```

The import declaration is known before normal execution of the module body.

This enables static analysis by JavaScript engines and development tools.

### 4.1 Static imports vs dynamic imports

Static import:

```jsx
import { getUser } from "./userService.js";
```

You cannot place this inside an ordinary conditional block:

```jsx
if (process.env.USE_USER_SERVICE) {
  import { getUser } from "./userService.js"; // Syntax error
}
```

For conditional loading, use dynamic import:

```jsx
if (process.env.USE_USER_SERVICE === "true") {
  const userModule = await import("./userService.js");

  userModule.getUser();
}
```

Dynamic `import()` returns a Promise.

It is useful for:

- Lazy-loading large modules.
- Loading optional integrations.
- Loading modules based on runtime configuration.
- Splitting application startup work.

### 4.2 ESM live bindings

This is one of the most important differences.

Consider:

```jsx
// counter.js
export let count = 0;

export function increment() {
  count++;
}
```

```jsx
// app.js
import { count, increment } from "./counter.js";

console.log(count); // 0

increment();

console.log(count); // 1
```

The imported `count` is a live binding to the exported variable.

It is not simply a copied value.

However, the importing module cannot reassign the imported binding:

```jsx
count = 10; // TypeError
```

The exporting module owns the binding.

This is different from importing a CommonJS object, where you receive an object reference and can mutate its properties.

### 4.3 ESM has strict mode by default

Every ESM module executes in strict mode.

Also:

```jsx
console.log(this);
```

At the top level of an ESM module, `this` is `undefined`.

CommonJS behaves differently because top-level code runs inside a wrapper function, where `this` is initially associated with `module.exports`.

ESM also does not automatically provide:

- `require`
- `module`
- `exports`
- `__filename`
- `__dirname`

You need alternatives for these.

## 5. How to define the module type in Node.js

Node.js determines whether a file is CommonJS or ESM using its extension and package configuration.

| File/configuration | Module system |
| --- | --- |
| `.cjs` | CommonJS |
| `.mjs` | ES Modules |
| `.js` with `"type": "commonjs"` | CommonJS |
| `.js` with `"type": "module"` | ES Modules |

Example project:

```
my-app/
├── package.json
├── app.js
├── userService.js
└── config.cjs
```

`package.json`:

```
{
  "name": "my-app",
  "type": "module"
}
```

Now `.js` files in this package scope are treated as ESM.

But `config.cjs` remains CommonJS.

Important: The `"type"` setting applies according to package scope, not simply to the entire computer or Node.js process. A nested `package.json` can establish another package scope.

### Which should you use?

For a new Node.js backend, I generally recommend ESM unless you have a specific compatibility reason to use CommonJS.

For an existing production application, don't migrate just for syntax preference. Evaluate dependency compatibility, test tooling, deployment scripts, and the cost of migration.

## 6. Module resolution differences

One practical difference you'll notice when migrating from CommonJS to ESM is file resolution.

### CommonJS

```jsx
const userService = require("./userService");
```

CommonJS can resolve certain extensions and directory entry points using its resolution rules.

### ESM

```jsx
import userService from "./userService.js";
```

For relative and absolute file imports, Node.js ESM generally requires the file extension to be specified.

This is a frequent migration issue.

For example:

```jsx
// May work in CommonJS
const config = require("./config");

// In Node.js ESM, prefer:
import config from "./config.js";
```

Don't assume that changing `require` to `import` is enough.

### 6.1 Replacing `__dirname` and `__filename`

In ESM, use `import.meta.url`.

```jsx
import path from "node:path";
import { fileURLToPath } from "node:url";

const __filename = fileURLToPath(import.meta.url);

const __dirname = path.dirname(__filename);

console.log(__filename);
console.log(__dirname);
```

Why?

ESM uses URL-based module identification. `import.meta.url` provides the current module's URL.

This also means you can work with file URLs directly:

```jsx
const fileUrl = new URL("./config.json", import.meta.url);
```

### 6.2 Using CommonJS `require()` inside ESM

Sometimes you migrate an application to ESM but one dependency or legacy file still requires CommonJS-style loading.

You can use `createRequire()`:

```jsx
import { createRequire } from "node:module";

const require = createRequire(import.meta.url);

const legacyModule = require("./legacyModule.cjs");
```

This is useful during gradual migrations.

Alternatively, use dynamic import when appropriate:

```jsx
const legacyModule = await import("./legacyModule.cjs");
```

The exact shape of the returned module namespace depends on interoperability behavior, which we'll cover next.

## 7. CommonJS and ESM interoperability

This is particularly important for production Node.js applications because dependencies don't always use the same module system.

### 7.1 Importing CommonJS from ESM

Suppose you have:

```jsx
// legacyService.cjs
module.exports = {
  getUser() {
    return "User found";
  }
};
```

You can import it from ESM:

```jsx
// app.js
import legacyService from "./legacyService.cjs";

console.log(legacyService.getUser());
```

The CommonJS `module.exports` value is available as the default export.

You may also encounter:

```jsx
import { getUser } from "./legacyService.cjs";
```

Node.js attempts to detect named exports from CommonJS source using static analysis. However, this detection is heuristic and is not reliable for every dynamic export pattern.

For predictable interoperability, prefer the default import when consuming CommonJS.

### 7.2 Requiring ESM from CommonJS

Traditionally, CommonJS couldn't synchronously load ESM using `require()`.

The standard compatibility approach is dynamic import:

```jsx
// app.cjs
async function start() {
  const userModule = await import("./userService.mjs");

  console.log(userModule.getUser());
}

start();
```

Modern Node.js has introduced support for `require()` loading certain synchronous ESM graphs, but this depends on Node.js version and module graph characteristics. In particular, an ESM graph involving top-level `await` cannot be synchronously loaded this way.

For portable application code, use dynamic `import()` when loading ESM from CommonJS.

Senior takeaway: Don't assume module interoperability is symmetric. ESM importing CommonJS and CommonJS loading ESM have different constraints.

## 8. Circular dependencies

A circular dependency occurs when two or more modules depend on each other.

Example:

```
userService.js → orderService.js
orderService.js → userService.js
```

### 8.1 CommonJS circular dependencies

Consider:

```jsx
// a.js
console.log("A start");

exports.name = "A";

const b = require("./b");

console.log("B name:", b.name);

exports.done = true;
```

```jsx
// b.js
console.log("B start");

const a = require("./a");

console.log("A name:", a.name);

exports.name = "B";
```

When Node.js detects a circular dependency, it can return the partially initialized exports object rather than waiting for the module to finish executing.

This can lead to surprising results.

For example, if module B reads a property before module A has assigned it, that property may be `undefined`.

### 8.2 ESM circular dependencies

ESM uses live bindings and links the module graph before evaluation.

This does not automatically eliminate circular dependency problems.

For example, accessing a `let`, `const`, or `class` export before its initialization can produce a `ReferenceError` due to the temporal dead zone.

Production recommendation:

Circular dependencies often indicate unclear module boundaries.

Instead of relying on initialization order, consider:

- Moving shared functionality into a third module.
- Introducing an interface or abstraction.
- Using dependency injection.
- Separating domain logic from infrastructure logic.

For example:

```
userService.js
orderService.js
sharedDomainService.js
```

Both services can depend on the shared module rather than depending directly on each other.

## 9. Advanced package configuration: `exports` and `imports`

This is especially useful when building reusable Node.js libraries or managing larger backend repositories.

Consider a package:

```
my-library/
├── package.json
├── index.js
├── internal/
│   ├── database.js
│   └── validation.js
└── utils/
    └── date.js
```

Without an export map, consumers may attempt to import internal files directly:

```jsx
import database from "my-library/internal/database.js";
```

This creates unwanted coupling to your internal structure.

### 9.1 The `exports` field

You can control which package entry points are publicly accessible:

```jsx
{
  "name": "my-library",
  "type": "module",
  "exports": {
    ".": "./index.js",
    "./utils/date": "./utils/date.js"
  }
}
```

Now consumers can use:

```jsx
import library from "my-library";
import dateUtils from "my-library/utils/date";
```

But they cannot access an unexported internal path through normal package subpath resolution.

Why this matters:

You can refactor internal files without breaking consumers, as long as the public API stays stable.

### 9.2 Conditional exports

A package can expose different implementations for CommonJS and ESM:

```jsx
{
  "name": "my-library",
  "exports": {
    ".": {
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    }
  }
}
```

Now:

```jsx
import library from "my-library";
```

uses the ESM entry point, while:

```jsx
const library = require("my-library");
```

uses the CommonJS entry point.

This is useful for libraries that support both module systems.

### 9.3 The `imports` field

The `imports` field defines private package-level import aliases. These aliases must start with `#`.

Example:

```jsx
{
  "type": "module",
  "imports": {
    "#utils/*": "./src/utils/*.js",
    "#config": "./src/config.js"
  }
}
```

Usage:

```jsx
import config from "#config";
import { formatDate } from "#utils/date";
```

Unlike `exports`, which controls package entry points for consumers, `imports` provides aliases for code within the package itself.

## 10. The dual-package hazard

This is a genuinely senior-level module-system issue.

Suppose a package provides both CommonJS and ESM entry points:

```jsx
{
  "exports": {
    ".": {
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    }
  }
}
```

Imagine both files maintain their own in-memory state.

```jsx
// index.js (ESM)
export const registry = new Map();
```

```jsx
// index.cjs (CommonJS)
const registry = new Map();

module.exports = { registry };
```

Now an application loads the package through both module systems:

```jsx
import { registry as esmRegistry } from "my-library";

import { createRequire } from "node:module";

const require = createRequire(import.meta.url);

const { registry: cjsRegistry } = require("my-library");

console.log(esmRegistry === cjsRegistry); // false
```

You now have two separate registry instances.

This can cause:

- Duplicate event listeners.
- Separate caches.
- Multiple singleton instances.
- Inconsistent state.
- Class identity problems, where objects created by one copy fail `instanceof` checks against the other copy's class.

This is called the dual-package hazard.

Possible solutions include:

- Keeping a shared implementation behind both entry points.
- Avoiding mixed loading of the same stateful package.
- Designing the package to be stateless where possible.
- Using a carefully tested shared CommonJS implementation when appropriate.

The key lesson: two entry points don't necessarily mean one shared module instance.

## 11. Module caching in ESM

CommonJS and ESM both avoid repeatedly evaluating the same resolved module under normal circumstances, but their caching mechanisms differ.

| CommonJS | ESM |
| --- | --- |
| Uses `require.cache` | Uses an internal ESM module map |
| CommonJS cache is inspectable through `require.cache` | No equivalent public ESM cache API |
| Cache identity is based on resolved module filenames | Module identity is URL-based |
| `require()` returns the cached exports | Imports use the existing module instance and its bindings |

One interesting detail:

```jsx
import "./config.js?version=1";
import "./config.js?version=2";
```

These are different module URLs, so Node.js can load them as separate ESM module instances.

This is not a recommended way to manage configuration. It demonstrates that module identity matters.

Also, don't confuse these caches with application-level caching such as Redis or an in-memory data cache. Module caching is about loaded code and its module instance.

## 12. JSON imports and built-in modules

### 12.1 Importing JSON in ESM

CommonJS:

```jsx
const config = require("./config.json");
```

In modern Node.js ESM, JSON modules use import attributes:

```jsx
import config from "./config.json" with { type: "json" };
```

This is worth remembering because older Node.js examples may show the previous `assert` syntax.

For application configuration, another practical approach is to read the file using `node:fs` and parse it explicitly when you need more control over loading or validation.

### 12.2 Importing built-in Node.js modules

You can use:

```jsx
import fs from "node:fs";
import path from "node:path";
import { readFile } from "node:fs/promises";
import { randomUUID } from "node:crypto";
```

The `node:` prefix explicitly identifies a Node.js built-in module and avoids ambiguity with packages of the same name.

It is a good convention in modern Node.js projects.

## 13. Migrating a production application from CommonJS to ESM

Let's say you have an existing Express application using CommonJS:

```
src/
├── app.js
├── server.js
├── config/
│   └── database.js
├── routes/
│   └── userRoutes.js
├── controllers/
│   └── userController.js
└── services/
    └── userService.js
```

A migration is more than replacing `require()` with `import`.

### Migration checklist

1. Update package configuration

```jsx
{
  "type": "module"
}
```

2. Convert imports and exports

```jsx
// Before
const express = require("express");

module.exports = app;
```

```jsx
// After
import express from "express";

export default app;
```

3. Add extensions to relative imports

```jsx
import userRoutes from "./routes/userRoutes.js";
```

4. Replace CommonJS globals

Use `import.meta.url` and `fileURLToPath()` for paths.

5. Check third-party dependencies

Verify that dependencies support the way you intend to import them. Don't assume every package has identical CJS/ESM support.

6. Check configuration and startup scripts

Review:

- PM2 ecosystem configuration.
- Test runner configuration.
- Build and deployment scripts.
- CLI scripts.
- Migration and seed scripts.
- Development tools such as nodemon.

7. Test the complete application

Pay particular attention to:

- Startup and initialization order.
- Circular dependencies.
- Dynamic imports.
- Package resolution.
- Database initialization.
- Background workers.

### My recommendation for your existing backend projects

Since you already work with Node.js, Express, NestJS, and production deployments, don't migrate a working application just to use ESM.

First understand the module system used by the project. If starting a new project, choose ESM deliberately and maintain consistency.

For a gradual migration, `.cjs` and `.mjs` allow both systems to coexist.

## 14. Common mistakes to avoid

| Mistake | Correct understanding |
| --- | --- |
| `exports = {}` exports an object | It only reassigns the local variable; use `module.exports` |
| CJS and ESM are interchangeable | Their loading and execution models differ |
| ESM imports are ordinary function calls | Static imports are linked as part of module processing |
| ESM can use `__dirname` directly | Use `import.meta.url` and convert it |
| ESM always prevents circular dependencies | Cycles still exist and can cause initialization errors |
| Named imports from CJS always work | Node's named-export detection has limitations |
| `require()` can always load ESM | Synchronous loading has restrictions |
| All imports create new instances | Module caching generally reuses instances for the same module identity |
| Both CJS and ESM entry points share singleton state | They may create separate instances |
| Migration only requires syntax changes | Resolution, dependencies, scripts, and initialization must also be checked |
