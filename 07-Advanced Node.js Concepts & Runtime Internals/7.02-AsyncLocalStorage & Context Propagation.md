# Phase 7.2 — AsyncLocalStorage & Context Propagation

This topic is particularly useful in real backend applications.

Imagine your Express application receives 100 concurrent requests. Each request has its own:

- Request ID
- Authenticated user ID
- Tenant ID
- Correlation ID
- Logging context

Now imagine a service deep inside your application needs the request ID for logging.

How do you access it without passing the request object through every function?

One approach is to pass context explicitly:

```jsx
async function getUser(userId, context) {
  return userRepository.findById(userId, context);
}
```

Then every function must pass that context further:

```jsx
async function getUserProfile(userId, context) {
  return getUser(userId, context);
}
```

As the application grows, this creates unnecessary parameter passing throughout the codebase.

AsyncLocalStorage solves this problem by allowing context to be stored and accessed across asynchronous execution within the same asynchronous chain.

It is built on Node.js's `async_hooks` infrastructure.

Let's understand how it works and how to use it properly.

## 1. What is AsyncLocalStorage?

`AsyncLocalStorage` is a Node.js API that provides asynchronous context propagation.

It allows us to store data for a particular asynchronous execution context and retrieve that data later, even when execution moves through Promises, callbacks, timers, and other asynchronous operations.

Import:

```jsx
import { AsyncLocalStorage } from "node:async_hooks";

const asyncLocalStorage = new AsyncLocalStorage();
```

Basic example:

```jsx
asyncLocalStorage.run(
  { requestId: "req-123" },
  async () => {
    console.log(
      asyncLocalStorage.getStore()
    );

    await someAsyncOperation();

    console.log(
      asyncLocalStorage.getStore()
    );
  }
);
```

Output:

```jsx
{ requestId: 'req-123' }
{ requestId: 'req-123' }
```

Notice that the context remains accessible after `await`.

This is the key benefit.

Without AsyncLocalStorage, you would generally need to pass the context manually through function arguments.

## 2. How does AsyncLocalStorage work internally?

To understand this properly, we need to understand one Node.js concept: asynchronous execution context.

Consider:

```jsx
async function processOrder() {
  console.log("Step 1");

  await fetchOrder();

  console.log("Step 2");

  await processPayment();

  console.log("Step 3");
}
```

This function executes across multiple asynchronous operations.

The JavaScript call stack doesn't remain active throughout the entire operation. After an `await`, execution resumes later.

So how does Node.js know which context belongs to which asynchronous operation?

Node.js uses its asynchronous resource tracking infrastructure, exposed through `async_hooks`.

### 2.1 Async resources

An asynchronous resource is an object associated with an asynchronous operation.

Examples include:

- Promise execution.
- Timers such as `setTimeout`.
- I/O operations.
- TCP connections.
- Some callback-based APIs.

When an asynchronous resource is created within an existing asynchronous context, Node.js can associate it with that context.

AsyncLocalStorage uses this mechanism to propagate its store.

The important point is that the context follows the asynchronous execution chain, not just the current JavaScript function call.

### 2.2 Does AsyncLocalStorage create a separate thread?

No.

This is a common misconception.

AsyncLocalStorage:

- Does not create a thread.
- Does not execute JavaScript in parallel.
- Does not create a separate event loop.
- Does not replace Promises or async/await.

It provides context tracking within Node.js asynchronous execution.

It is a context-management API, not a concurrency API.

## 3. Important AsyncLocalStorage methods

Let's understand the methods you should know.

| Method | Purpose |
| --- | --- |
| `run(store, callback)` | Executes a callback with a specified context |
| `getStore()` | Retrieves the current context |
| `enterWith(store)` | Sets the context for the remainder of the current synchronous execution and its associated async operations |
| `exit(callback)` | Executes a callback outside the current context |
| `disable()` | Disables the AsyncLocalStorage instance |

### 3.1 `run()` — the most important method

```jsx
const storage = new AsyncLocalStorage();

storage.run(
  { userId: 101 },
  () => {
    console.log(storage.getStore());
  }
);
```

Output:

```jsx
{ userId: 101 }
```

The store is available inside the callback and asynchronous operations created within that context.

When the callback finishes, the previous context is restored.

For normal request-scoped context, `run()` is the preferred approach.

### 3.2 `getStore()`

Used to retrieve the current store.

```jsx
function getCurrentRequestId() {
  return storage.getStore()?.requestId;
}
```

If the current execution is not inside a context established by that instance, `getStore()` returns `undefined`.

Therefore, avoid assuming context always exists.

### 3.3 `enterWith()`

Example:

```jsx
storage.enterWith({
  requestId: "req-123"
});
```

This changes the context for the remainder of the current synchronous execution and subsequent asynchronous operations created within it.

Why not use it everywhere?

Because its scope can be less obvious, especially when used inside event handlers or shared synchronous execution paths.

For example, a context established in one event listener can unexpectedly influence later listeners executing in the same synchronous event dispatch.

For Express request middleware, prefer `run()` because its boundary is clearer.

### 3.4 `exit()`

Runs a callback outside the current context:

```jsx
storage.run(
  { requestId: "req-123" },
  () => {
    console.log(storage.getStore()); // req-123

    storage.exit(() => {
      console.log(storage.getStore()); // undefined
    });

    console.log(storage.getStore()); // req-123
  }
);
```

This is useful in specialized cases where you deliberately want an operation to execute without the current context.

### 3.5 `disable()`

```jsx
storage.disable();
```

Disables the AsyncLocalStorage instance and exits its current contexts.

It is generally relevant when an instance is no longer needed, rather than something you call for every request.

Practical rule: In most application code, you will primarily use `run()` and `getStore()`.

## 4. Practical implementation: Request context in Express

Now let's implement something useful for a real backend.

Suppose an Express application has:

```
Request
  ↓
Middleware
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
Database
```

You want every log entry from the same request to include:

- Request ID
- User ID
- Tenant ID
- Request method
- Request path

Without passing these values through every service function.

### Step 1: Create a request context module

`requestContext.js`

```jsx
import { AsyncLocalStorage } from "node:async_hooks";

export const requestContext = new AsyncLocalStorage();

export function getRequestContext() {
  return requestContext.getStore();
}

export function getRequestId() {
  return getRequestContext()?.requestId;
}

export function getUserId() {
  return getRequestContext()?.userId;
}
```

We keep one shared AsyncLocalStorage instance for the application.

Why one shared instance?

Because middleware, controllers, services, and repositories must all access the same context store.

If each module creates its own AsyncLocalStorage instance, they will not automatically share context.

### Step 2: Create Express middleware

`requestContextMiddleware.js`

```jsx
import { randomUUID } from "node:crypto";

import { requestContext } from "./requestContext.js";

export function requestContextMiddleware(
  req,
  res,
  next
) {
  const requestId = randomUUID();

  requestContext.run(
    {
      requestId,
      method: req.method,
      path: req.path,
      userId: undefined,
      tenantId: undefined
    },
    () => {
      res.setHeader("X-Request-ID", requestId);

      next();
    }
  );
}
```

Register it early in your Express application:

```jsx
app.use(requestContextMiddleware);

app.use(express.json());

app.use(authMiddleware);

app.use("/api", apiRoutes);
```

Now all asynchronous operations started within this request chain can access its context.

### Step 3: Add authenticated user information

Authentication runs after the request context middleware.

Once authentication succeeds, we can update the existing store:

```jsx
import { getRequestContext } from "./requestContext.js";

export function authMiddleware(req, res, next) {
  const user = req.user;

  const context = getRequestContext();

  if (context && user) {
    context.userId = user.id;
    context.tenantId = user.tenantId;
  }

  next();
}
```

Here, we're mutating the existing store object.

This works because the same object is available throughout that request's asynchronous context.

Be careful not to replace the context object casually, because different operations may already hold a reference to the original store.

### Step 4: Access context from any service

`userService.js`

```jsx
import { getRequestId } from "./requestContext.js";

export async function getUser(userId) {
  const requestId = getRequestId();

  console.log({
    requestId,
    message: "Fetching user",
    userId
  });

  return userRepository.findById(userId);
}
```

Notice that `getUser()` doesn't receive `requestId` as an argument.

It gets it directly from the asynchronous context.

### Step 5: Use it in a logger

This is where the approach becomes especially useful.

```jsx
import { getRequestContext } from "./requestContext.js";

export function logInfo(message, metadata = {}) {
  const context = getRequestContext();

  console.log({
    timestamp: new Date().toISOString(),
    level: "info",
    message,
    requestId: context?.requestId,
    userId: context?.userId,
    ...metadata
  });
}
```

Any service can now use:

```jsx
logInfo("Payment initiated", {
  paymentId: "PAY-1001"
});
```

The logger automatically includes request information.

For production, use a structured logger such as Pino rather than building a custom logger with `console.log`. Pino supports child loggers and structured fields, which integrate naturally with this pattern.

Important ordering detail: Request context middleware must run before authentication if authentication is going to enrich that context. If you also want to capture errors from earlier middleware, place the context middleware before those components too.

## 5. The most important benefit: isolating concurrent requests

Let's understand why this is powerful.

Imagine two requests arrive almost simultaneously:

- Request A belongs to user 101.
- Request B belongs to user 202.

Both execute the same service function.

```jsx
import { AsyncLocalStorage } from "node:async_hooks";

const storage = new AsyncLocalStorage();

async function processRequest(userId) {
  await new Promise(resolve => setTimeout(resolve, 100));

  console.log({
    userId,
    context: storage.getStore()
  });
}

async function main() {
  await Promise.all([
    storage.run(
      { requestId: "req-A" },
      () => processRequest(101)
    ),

    storage.run(
      { requestId: "req-B" },
      () => processRequest(202)
    )
  ]);
}

main();
```

Expected output:

```jsx
{
  userId: 101,
  context: { requestId: "req-A" }
}

{
  userId: 202,
  context: { requestId: "req-B" }
}
```

Even though both operations run concurrently, each sees its own context.

This is the central reason AsyncLocalStorage is useful in backend applications.

### What would happen with a global variable?

Imagine implementing the same thing using:

```jsx
let currentRequestId;

async function processRequest(requestId) {
  currentRequestId = requestId;

  await someAsyncOperation();

  console.log(currentRequestId);
}
```

If requests overlap, one request can overwrite the value before another request reads it.

That causes context contamination.

AsyncLocalStorage avoids this by associating the store with the asynchronous execution chain rather than using one shared mutable global variable.

## 6. Production use cases

Request IDs are only one use case. There are several other valuable applications.

| Use case | Example |
| --- | --- |
| Request correlation | Attach a request ID to every log |
| Distributed tracing | Associate trace and span identifiers with logs |
| User context | Access authenticated user ID in services |
| Multi-tenancy | Access tenant ID for tenant-aware operations |
| Audit logging | Record who initiated a business operation |
| Transaction context | Associate operations with a transaction context, with careful lifecycle management |
| Performance measurement | Record request-level timing information |

### 6.1 Request correlation and distributed tracing

Suppose a user initiates a parking reservation.

The request passes through:

```
API → Reservation Service → Payment Service → Database
```

You want logs to look like:

```
requestId=req-123
Reservation initiated

requestId=req-123
Payment initiated

requestId=req-123
Payment completed

requestId=req-123
Reservation confirmed
```

Now all logs can be searched using the same request ID.

This makes production debugging considerably easier.

One distinction:

- A request ID identifies a particular incoming request.
- A trace ID identifies a distributed trace that may span several services and requests.
- A span ID identifies an individual operation within that trace.

AsyncLocalStorage can carry these identifiers locally. It does not automatically propagate them to another service. You must forward the appropriate tracing headers or use an observability library such as OpenTelemetry.

### 6.2 Multi-tenant context

Consider a SaaS application where users belong to different organizations.

A request might have:

```jsx
{
  requestId: "req-123",
  userId: "user-101",
  tenantId: "tenant-55"
}
```

A service can access the tenant:

```jsx
export async function getOrders() {
  const tenantId = getRequestContext()?.tenantId;

  return orderRepository.findByTenantId(tenantId);
}
```

This reduces repeated parameter passing.

However, an important security point:

Never treat AsyncLocalStorage as an authorization mechanism.

It is a way to carry context, not to verify that the user is allowed to access a resource.

Authorization must still validate the authenticated identity and permissions. Also, never allow an untrusted client-supplied tenant ID to become trusted context without validation.

## 7. Important edge cases and limitations

This is where senior-level understanding matters. AsyncLocalStorage is very useful, but it is not magic.

### 7.1 Context propagation is not universal across every boundary

Context generally propagates through asynchronous resources created within the active context.

But consider:

```jsx
let callback;

storage.run(
  { requestId: "req-123" },
  () => {
    callback = () => {
      console.log(storage.getStore());
    };
  }
);

callback();
```

The callback is invoked after the original context has ended, outside that context.

You should not assume that simply retaining a callback preserves its original context forever.

The context depends on where asynchronous work is created and how it is executed.

For unusual callback integrations, Node.js provides APIs such as `AsyncResource` to associate custom asynchronous resources with the correct context.

### 7.2 Custom callback-based libraries

Most modern Promise-based APIs work naturally with AsyncLocalStorage.

But older libraries or custom callback systems can sometimes lose context if they manage asynchronous execution in unusual ways.

For example, a library may create a callback or resource outside the intended context and invoke it later.

When this happens, investigate the library's asynchronous resource lifecycle.

`AsyncResource` can help:

```jsx
import { AsyncResource } from "node:async_hooks";

class MyAsyncResource extends AsyncResource {
  constructor() {
    super("MyAsyncResource");
  }

  execute(callback) {
    this.runInAsyncScope(callback);
  }

  close() {
    this.emitDestroy();
  }
}
```

Here, `runInAsyncScope()` executes the callback in the resource's associated asynchronous context.

This is a lower-level integration tool. Most Express applications should not need to create custom AsyncResources themselves.

### 7.3 Context does not automatically cross worker threads

Worker Threads have separate JavaScript execution environments.

You should not expect an AsyncLocalStorage context from the main thread to automatically appear inside a worker.

Pass the required context explicitly:

```jsx
worker.postMessage({
  requestId: getRequestId(),
  task: "generate-report"
});
```

The worker can establish its own context if required.

Similarly, a separate Node.js process or microservice needs explicit context propagation.

### 7.4 Background jobs and queues

This is particularly important for your backend work.

Suppose an HTTP request creates a BullMQ job:

```jsx
await queue.add("send-email", {
  userId: 101
});
```

The worker may execute that job several seconds or minutes later, possibly in another process.

The HTTP request's AsyncLocalStorage context does not automatically travel with the job.

If the worker needs correlation information, include it in the job payload:

```jsx
const context = getRequestContext();

await queue.add("send-email", {
  userId: 101,
  correlationId: context?.requestId
});
```

Then establish a new context in the worker:

```jsx
await requestContext.run(
  {
    requestId: job.data.correlationId,
    jobId: job.id
  },
  async () => {
    await sendEmail(job.data.userId);
  }
);
```

This creates a new context for the background job.

Important distinction: A job's correlation ID may be inherited from the original request, but its execution is a separate lifecycle. Don't blindly carry request-specific information such as an HTTP response object or assume the original request is still active.

### 7.5 Avoid storing large objects

Don't put the entire Express request or response object into AsyncLocalStorage.

Avoid:

```jsx
requestContext.run(
  {
    req,
    res,
    user: req.user
  },
  next
);
```

Prefer a small, intentional store:

```jsx
{
  requestId,
  userId,
  tenantId,
  traceId
}
```

Why?

- Large objects can retain unnecessary memory.
- They can contain sensitive information.
- They create hidden dependencies between application layers.
- They make debugging more difficult.

### 7.6 Be careful with mutable context

The context store is an ordinary JavaScript object.

This means it can be mutated:

```jsx
const context = getRequestContext();

context.tenantId = "tenant-55";
```

That is useful in controlled middleware stages.

But avoid uncontrolled mutation from multiple parts of the application.

A good practice is to define which middleware owns each context field and when it may be populated.

## 8. AsyncLocalStorage vs dependency injection

This is an important architectural decision.

You already studied Dependency Injection in Phase 6. Let's connect the two concepts.

Explicit dependency injection:

```jsx
async function createReservation(data, context) {
  return reservationRepository.create(data, context);
}
```

AsyncLocalStorage:

```jsx
async function createReservation(data) {
  const context = getRequestContext();

  return reservationRepository.create(data, context);
}
```

Which is better?

| Dependency injection / explicit parameters | AsyncLocalStorage |
| --- | --- |
| Dependencies are visible | Context dependency is implicit |
| Easy to understand from function signature | Less parameter passing |
| Easier to test in isolation | Requires context setup in tests |
| Good for business-critical inputs | Good for cross-cutting metadata |
| More explicit | More convenient for logging and tracing |

My recommendation:

Use explicit parameters for important business data and dependencies.

Use AsyncLocalStorage for cross-cutting execution metadata such as:

- Request ID
- Trace ID
- User ID for logging
- Tenant context, after validation
- Operation correlation metadata

Don't use AsyncLocalStorage to hide every dependency in your application.

For example, a payment service should still receive the payment amount, reservation ID, and payment provider explicitly. Those are core business inputs, not incidental request metadata.

## 9. What about NestJS?

NestJS applications often use dependency injection and request-scoped providers.

You might ask: if NestJS already supports request-scoped providers, why use AsyncLocalStorage?

They solve related but different problems.

- Request-scoped providers allow NestJS to create provider instances associated with a request lifecycle.
- AsyncLocalStorage allows context to be accessed throughout asynchronous execution without passing it through every function.

A common approach in NestJS is to use a CLS (continuation-local storage) integration that builds on AsyncLocalStorage.

This is useful when you want request IDs, tenant context, or tracing metadata to be available throughout services without making every provider request-scoped.

Request-scoped providers can introduce additional dependency-resolution and lifecycle overhead, so don't make every service request-scoped just to access a request ID.

## 10. Testing AsyncLocalStorage

Because the context is implicit, tests should establish it explicitly when testing code that depends on it.

Example:

```jsx
import { describe, it, expect } from "vitest";

import { requestContext } from "./requestContext.js";
import { getRequestId } from "./requestContext.js";

describe("request context", () => {
  it("returns the current request ID", async () => {
    await requestContext.run(
      { requestId: "test-123" },
      async () => {
        await Promise.resolve();

        expect(getRequestId()).toBe("test-123");
      }
    );
  });
});
```

Also test concurrency isolation:

```jsx
it("isolates concurrent contexts", async () => {
  const readContext = (requestId) =>
    requestContext.run(
      { requestId },
      async () => {
        await new Promise(resolve =>
          setTimeout(resolve, 10)
        );

        return getRequestId();
      }
    );

  const results = await Promise.all([
    readContext("request-A"),
    readContext("request-B")
  ]);

  expect(results).toEqual([
    "request-A",
    "request-B"
  ]);
});
```

This is particularly useful for catching accidental global-state implementations.

## 11. Performance considerations

Does AsyncLocalStorage have performance overhead?

Yes. Node.js needs to maintain asynchronous context information as asynchronous resources are created and executed.

However, for normal backend use cases, the overhead is generally acceptable.

A few recommendations:

1. Create one shared AsyncLocalStorage instance rather than creating instances per request.
2. Keep the store small.
3. Avoid storing large objects or unnecessary data.
4. Don't create custom `async_hooks` instrumentation unless you genuinely need it.
5. Measure performance under realistic load if your application has very high asynchronous operation volume.

Also, don't confuse AsyncLocalStorage with manually implementing `async_hooks`.

You generally shouldn't use low-level hooks such as `init`, `before`, `after`, and `destroy` to implement request context yourself. AsyncLocalStorage already provides a higher-level abstraction for this purpose.

## 13. Final revision notes

What to remember

- AsyncLocalStorage provides asynchronous context propagation.
- It is built on Node.js asynchronous resource tracking.
- `run()` establishes a context.
- `getStore()` retrieves the current context.
- It isolates context across concurrent asynchronous execution chains.
- It is useful for request IDs, logging, tracing, and tenant metadata.
- It does not automatically propagate across processes, workers, or distributed services.
- Queue jobs need explicit context propagation.
- Use explicit dependency injection for core business data.
- Keep the context small and avoid using it as an authorization mechanism.

## 14. How this applies to your backend work

For an Express backend with integrations such as parking reservations, payments, and background jobs, I would recommend this implementation:

- Establish a request ID in the first middleware.
- Add authenticated user and validated tenant information after authentication.
- Make the structured logger automatically include the context.
- Forward correlation IDs when calling external services where useful.
- Include correlation metadata in background job payloads.
- Establish a new context inside each worker execution.

This provides much better log correlation and troubleshooting without passing request metadata through every service method.

#### Question- Will context will auto destroy after async execution flow completed or it will keep in memory as you don't mentioned about this point in examples , short answer ->  

Yes. The context is automatically no longer active once its asynchronous execution scope completes.

- `run()` establishes the context for that execution chain.
