# Phase 7.3 — Node.js Diagnostics & Profiling

This topic is about something senior backend engineers regularly need to do: investigate what is happening inside a running Node.js application when something goes wrong.

You already covered performance fundamentals in Phase 4, including event-loop blocking, memory leaks, CPU-heavy operations, and scaling.

We won't repeat those concepts. Instead, we'll focus on the diagnostic tools and techniques that help you find the actual cause.

Imagine these production situations:

1. Your API response time suddenly increases, but CPU utilization looks normal.
2. One Node.js process consumes 90% CPU.
3. Memory usage increases continuously and eventually the process crashes.
4. The event loop is delayed, even though the application isn't doing much visible work.
5. Your application crashes unexpectedly, and you need evidence about its state.
6. You need to identify which function is consuming most of the execution time.

Node.js provides several built-in tools for these situations.

## 1. The Node.js diagnostic toolkit

First, understand which tool helps with which problem.

| Tool | Primary purpose |
| --- | --- |
| Node.js Inspector | Debugging and runtime inspection |
| CPU profiling | Find CPU-intensive functions |
| Heap snapshots | Investigate memory retention |
| Diagnostic reports | Capture process and system information |
| `perf_hooks` | Measure performance and event-loop delay |
| Trace events | Inspect runtime activity over time |
| Process signals and reports | Collect information during failures |

We will cover each one and connect them to real production investigations.

## 2. Node.js Inspector

The Node.js Inspector allows you to inspect and debug a running Node.js process.

It supports:

- Breakpoints.
- Step-by-step execution.
- Variable inspection.
- Call stack inspection.
- CPU profiling.
- Heap profiling.
- Runtime debugging.

### 2.1 Starting the Inspector

Start your application with:

```jsx
node --inspect app.js
```

By default, the Inspector listens on port `9229`.

You may see output similar to:

```jsx
Debugger listening on ws://127.0.0.1:9229/...
```

You can connect using Chrome DevTools:

```jsx
chrome://inspect
```

Or use the Node.js debugging integration in VS Code.

For debugging an application that should wait until a debugger connects:

```jsx
node --inspect-brk app.js
```

The difference:

- `-inspect`: Starts normally and allows a debugger to attach.
- `-inspect-brk`: Pauses execution at the beginning until debugging proceeds.

### 2.2 Debugging a running process

Suppose an application is already running:

```jsx
node app.js
```

You can send it `SIGUSR1` on supported Node.js platforms to activate the Inspector:

```jsx
kill -USR1 <PID>
```

This is useful when you need to investigate a process that wasn't originally started with `--inspect`.

However, activating the Inspector in production requires security controls.

Important security warning:

Never expose the Inspector port publicly.

The Inspector provides powerful access to the process, including the ability to execute JavaScript in its context. An unauthorized connection could compromise the application.

Prefer localhost binding and secure tunneling when remote debugging is necessary.

For example:

```jsx
node --inspect=127.0.0.1:9229 app.js
```

For a production EC2 instance, you could use an SSH tunnel rather than exposing port `9229` through the public network.

## 3. CPU profiling — finding CPU-intensive functions

Suppose your Node.js API suddenly becomes slow.

You check monitoring and notice:

- CPU utilization is high.
- Requests are taking longer.
- One Node.js process is consuming most of the CPU.

You suspect a CPU-intensive function, but you don't know which one.

This is where CPU profiling helps.

A CPU profile records where the JavaScript execution time is being spent.

### 3.1 Generate a CPU profile using Node.js

You can start your application with:

```jsx
node --cpu-prof app.js
```

Node.js collects CPU profiling data and writes a `.cpuprofile` file when the process exits.

You can inspect that file using Chrome DevTools.

Alternatively, you can use the Inspector:

1. Start the application with `-inspect`.
2. Open Chrome DevTools.
3. Go to the Performance panel.
4. Start recording.
5. Reproduce the slow operation.
6. Stop recording.
7. Inspect the CPU profile.

### 3.2 Understanding the CPU profile

Imagine this application:

```jsx
function calculateTotal(items) {
  let total = 0;

  for (const item of items) {
    for (let i = 0; i < 100000; i++) {
      total += item.price * Math.random();
    }
  }

  return total;
}

app.get("/report", (req, res) => {
  const result = calculateTotal(largeDataset);

  res.json({ result });
});
```

The CPU profile might show:

```
calculateTotal       85%
Array iteration       8%
Other functions       7%
```

This tells you that `calculateTotal()` is responsible for most of the sampled CPU time.

You now have a specific function to investigate rather than guessing based on API response times.

### 3.3 What is a flame graph?

A flame graph is a visualization of sampled function activity.

[An Introduction to Profiling in Node.js | AppSignal Blog](https://images.openai.com/static-rsc-4/h8vtJXETk3P9YUfzsxfjzVgdzLwIYJfAfgtnk4z5BEu4SKOWCgGPr3_m82M972LnOVuX4IvHOK5V_NBCwQZnAceFxPJZfGxzHDpEHVKjxfqnmIoYkgjzKADHc_N0DcKF-JcLr5l7OxYmuz7lE-eLUlC--uZQnreshtwBZH6oLO4?purpose=inline)


How to interpret it:

- The horizontal width represents the amount of sampled activity attributed to a function and its descendants.
- The vertical axis represents call-stack depth.
- Wider stacks generally indicate more CPU activity.
- A function with a wide block may deserve investigation.

One important distinction: a flame graph is not a timeline of exact function execution durations. It is based on samples collected during profiling.

Also, distinguish:

- Self time: Time attributed to the function itself, excluding its children.
- Total time: Time attributed to the function and its descendants.

If a function has high total time but low self time, its child functions may be the actual bottleneck.

### 3.4 Production considerations

CPU profiling itself introduces overhead.

Therefore:

- Profile a representative workload.
- Avoid running intensive profiling continuously without a reason.
- Keep profiles secure because they can reveal internal application behavior.
- Reproduce the issue under realistic traffic where possible.
- Compare profiles before and after a code change.

Senior takeaway: Don't optimize a function just because it looks complicated. Use CPU profiling to identify where the CPU is actually spending time.

## 4. Heap snapshots — investigating memory leaks

Now imagine a different problem.

Your Node.js application starts with:

```
Memory: 250 MB
```

After several hours:

```
Memory: 700 MB
```

After another few hours:

```
Memory: 1.4 GB
```

Eventually, the process crashes with an out-of-memory error.

You need to identify which objects are being retained.

This is where heap snapshots help.

### 4.1 What is a heap snapshot?

A heap snapshot is a representation of objects currently allocated in the V8 JavaScript heap.

It helps you investigate:

- Which objects are consuming memory.
- How many instances of an object exist.
- Which objects retain other objects.
- Why objects are not being garbage-collected.
- Which references prevent memory from being released.

Example:

```jsx
const users = [];

setInterval(() => {
  users.push({
    id: Date.now(),
    data: Buffer.alloc(1024 * 100)
  });
}, 1000);
```

This code continuously retains objects in the `users` array.

Even if an object is no longer needed by the business logic, the array still references it.

Therefore, garbage collection cannot reclaim it.

### 4.2 Generating a heap snapshot

One approach is using the Inspector:

1. Start the application with `-inspect`.
2. Open Chrome DevTools.
3. Select the Memory panel.
4. Choose Heap snapshot.
5. Capture a snapshot.
6. Repeat after reproducing the memory growth.
7. Compare the snapshots.

Another approach is using Node.js:

```jsx
import { writeHeapSnapshot } from "node:v8";

const fileName = writeHeapSnapshot();

console.log("Heap snapshot:", fileName);
```

This writes a `.heapsnapshot` file.

### 4.3 Comparing heap snapshots

Suppose you take two snapshots:

<img width="1014" height="537" alt="Screenshot 2026-11-14 191906" src="https://github.com/user-attachments/assets/31e25b56-314f-490c-86a1-c8da9a3dd1a5" />

The user objects have increased dramatically.

Now inspect their retaining paths.

A retaining path explains why an object is still reachable.

For example:

```
Global variable
    ↓
users array
    ↓
User object
    ↓
Large data object
```

This helps identify the reference preventing garbage collection.

### 4.4 Important heap snapshot concepts

Shallow size: Memory directly occupied by an object.

Retained size: Memory that could potentially be reclaimed if the object and the objects exclusively retained through it became unreachable.

Retainers: References keeping an object alive.

When investigating a memory leak, retained size and retaining paths are often more useful than simply looking at object count.

### 4.5 Heap snapshots are expensive

This is extremely important in production.

Creating a heap snapshot can:

- Pause the application.
- Consume significant CPU.
- Require substantial additional memory.
- Temporarily affect request processing.
- Cause an already memory-constrained process to crash.

A heap snapshot can be comparable in size to the heap itself, and the generation process needs additional resources.

My recommendation: Don't casually generate a heap snapshot on a production instance already approaching its memory limit.

Prefer a controlled reproduction in staging or a replica with representative traffic. If production evidence is essential, plan the capture carefully.

## 5. Diagnostic reports — investigating crashes and process failures

CPU profiles and heap snapshots are specialized tools.

But sometimes you need a broader picture of the process at a particular moment.

For example:

- The application is approaching its memory limit.
- The process crashes unexpectedly.
- A native module causes a failure.
- You need runtime and operating-system information.
- You need to understand the environment in which a failure occurred.

Node.js provides the `process.report` API.

### 5.1 Generate a diagnostic report

```jsx
import process from "node:process";

const fileName = process.report.writeReport();

console.log("Report generated:", fileName);
```

This creates a diagnostic report, usually as a JSON file.

It can contain information such as:

- Node.js version and runtime information.
- Operating-system details.
- Process and resource information.
- JavaScript stack information.
- Native stack information.
- Loaded native modules.
- Heap and memory-related information.
- libuv handle information.

This is particularly useful when investigating failures involving native code, handles, or process state.

### 5.2 Automatically generate reports on failures

You can enable diagnostic reports through command-line options:

```jsx
node \
  --report-on-fatalerror \
  --report-uncaught-exception \
  app.js
```

These options help capture reports for fatal errors and uncaught exceptions.

You can also configure a report on a signal:

```jsx
node --report-on-signal app.js
```

By default, this uses `SIGUSR2` on supported platforms.

You can request a report while the process is running:

```jsx
kill -USR2 <PID>
```

This is useful because you don't necessarily need to restart the application to capture a diagnostic report.

### 5.3 Example production setup

For a PM2-managed application, you could configure the Node.js startup arguments through the PM2 ecosystem configuration:

```jsx
module.exports = {
  apps: [
    {
      name: "parking-api",
      script: "./server.js",
      node_args: [
        "--report-on-fatalerror",
        "--report-on-uncaught-exception"
      ]
    }
  ]
};
```

The exact PM2 configuration should be validated against the version and deployment setup you're using.

### 5.4 Diagnostic report vs heap snapshot

This distinction is important.

| Diagnostic report | Heap snapshot |
| --- | --- |
| Broad process-level information | Detailed JavaScript heap objects |
| Useful for crashes and runtime failures | Useful for memory leak investigations |
| Includes process/runtime details | Includes object references and retaining paths |
| Usually easier to capture as an incident artifact | Potentially expensive to generate and analyze |

Think of a diagnostic report as a broad health and failure snapshot, while a heap snapshot is a detailed investigation of the JavaScript heap.

## 6. `perf_hooks` — measuring performance inside Node.js

Now let's move to a tool you'll probably use more frequently in application development.

Node.js provides the `perf_hooks` module.

It exposes performance measurement APIs, including:

- High-resolution timing.
- Performance marks and measures.
- Event-loop delay monitoring.
- Event-loop utilization.
- Performance observers.

Import:

```jsx
import { performance } from "node:perf_hooks";
```

### 6.1 Measure how long a function takes

```jsx
import { performance } from "node:perf_hooks";

async function processPayment() {
  const start = performance.now();

  await paymentProvider.charge();

  const end = performance.now();

  console.log(
    `Payment took ${end - start} ms`
  );
}
```

`performance.now()` provides a high-resolution timestamp in milliseconds relative to the performance time origin.

It is more appropriate for measuring elapsed duration than using `Date.now()`.

Why?

`Date.now()` represents wall-clock time and can be affected by system clock adjustments.

`performance.now()` is monotonic for elapsed-time measurement.

### 6.2 Performance marks and measures

For more structured measurements:

```jsx
import { performance } from "node:perf_hooks";

async function createReservation() {
  performance.mark("reservation-start");

  await validateReservation();

  performance.mark("validation-complete");

  await processPayment();

  performance.mark("payment-complete");

  performance.measure(
    "validation-duration",
    "reservation-start",
    "validation-complete"
  );

  performance.measure(
    "payment-duration",
    "validation-complete",
    "payment-complete"
  );
}
```

Read the measurements:

```jsx
const measures = performance.getEntriesByType("measure");

for (const measure of measures) {
  console.log({
    name: measure.name,
    duration: measure.duration
  });
}
```

For a long-running application, remember to clear marks and measures after collecting them, or use a `PerformanceObserver` and a suitable cleanup strategy. Otherwise, performance entries themselves can accumulate.

### 6.3 Using PerformanceObserver

Instead of manually reading performance entries, you can observe them:

```jsx
import {
  performance,
  PerformanceObserver
} from "node:perf_hooks";

const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log({
      name: entry.name,
      duration: entry.duration
    });
  }
});

observer.observe({
  entryTypes: ["measure"]
});
```

Now when a measure is created, the observer receives it.

This is useful for instrumenting application operations.

## 7. Event-loop delay monitoring

This is one of the most useful diagnostic capabilities for a Node.js backend.

You already learned what event-loop blocking means in Phase 4.

Now let's learn how to measure it.

Node.js provides:

```jsx
monitorEventLoopDelay()
```

Example:

```jsx
import { monitorEventLoopDelay } from "node:perf_hooks";

const histogram = monitorEventLoopDelay({
  resolution: 20
});

histogram.enable();

setInterval(() => {
  console.log({
    min: histogram.min / 1e6,
    max: histogram.max / 1e6,
    mean: histogram.mean / 1e6,
    p99: histogram.percentile(99) / 1e6
  });

  histogram.reset();
}, 10000);
```

Why divide by `1e6`?

The histogram values are in nanoseconds.

We divide by one million to convert nanoseconds to milliseconds.

### 7.1 Understanding the metrics

| Metric | Meaning |
| --- | --- |
| `min` | Minimum observed delay |
| `max` | Maximum observed delay |
| `mean` | Average observed delay |
| `p99` | 99th percentile delay |
| `stddev` | Standard deviation |

Suppose your monitoring shows:

```
Event loop delay p99: 250 ms
```

This indicates that 99% of the recorded delay observations were at or below 250 ms during that measurement period.

A high event-loop delay can indicate:

- Synchronous CPU-heavy work.
- Large JSON serialization or parsing.
- Excessive garbage collection pauses.
- Heavy callback processing.
- Other long-running JavaScript execution.

But don't immediately conclude that the event loop is blocked by your business logic. Investigate CPU profiles and runtime behavior to identify the cause.

### 7.2 Event-loop delay vs event-loop utilization

These two metrics are related but different.

Node.js also exposes:

```jsx
performance.eventLoopUtilization()
```

Example:

```jsx
import { performance } from "node:perf_hooks";

let previous = performance.eventLoopUtilization();

setInterval(() => {
  const current = performance.eventLoopUtilization();

  const interval = performance.eventLoopUtilization(
    current,
    previous
  );

  previous = current;

  console.log({
    utilization: interval.utilization,
    active: interval.active,
    idle: interval.idle
  });
}, 10000);
```

Event-loop utilization (ELU) measures the proportion of observed time that the event loop was active rather than idle.

For example:

```
ELU = 0.85
```

Approximately 85% of the measured interval was spent in the event loop's active state.

Important distinction:

- High ELU means the event loop is busy.
- High event-loop delay means scheduling or execution is experiencing significant delays.

They are not interchangeable.

An application can have high ELU because it is processing a large number of requests efficiently. High delay suggests responsiveness problems and deserves further investigation.

## 8. Trace events — understanding runtime activity

Sometimes CPU profiling is not enough.

You may need to understand the sequence of runtime activities over time.

Node.js supports trace events.

They can help capture information about:

- Node.js runtime activity.
- V8 operations.
- Garbage collection activity.
- Asynchronous execution-related events.
- Other supported runtime categories.

### 8.1 Enabling trace events

Example:

```jsx
node \
  --trace-event-categories v8,node.async_hooks \
  --trace-event-file-pattern trace-%pid.json \
  app.js
```

This generates trace files that can be inspected using compatible tracing viewers.

The exact available categories depend on the Node.js version and runtime build.

### 8.2 What can you investigate?

Suppose your application experiences occasional latency spikes.

A trace can help you examine:

- Whether garbage collection happened during the spike.
- What runtime operations were occurring.
- Whether asynchronous activity changed around the same time.
- Whether a specific operation coincided with the slowdown.

### CPU profile vs trace events

| CPU profile | Trace events |
| --- | --- |
| Focuses on where CPU time is spent | Focuses on runtime activity over time |
| Helps identify expensive functions | Helps understand event sequences |
| Useful for CPU bottlenecks | Useful for timing and runtime investigations |

You generally don't need trace events running continuously in every production application. Use them when you need deeper runtime-level evidence.

## 9. Monitoring process memory alongside diagnostics

You already studied Node.js memory in Phase 4 and Buffer/ArrayBuffer memory in Phase 5.11, so we'll connect that knowledge to diagnostics rather than repeat it.

Use:

```jsx
import process from "node:process";

function getMemoryUsage() {
  const memory = process.memoryUsage();

  return {
    rss: memory.rss,
    heapUsed: memory.heapUsed,
    heapTotal: memory.heapTotal,
    external: memory.external,
    arrayBuffers: memory.arrayBuffers
  };
}

console.log(getMemoryUsage());
```

The key metrics:

| Metric | What it tells you |
| --- | --- |
| `rss` | Total resident memory used by the process |
| `heapUsed` | JavaScript heap currently used |
| `heapTotal` | JavaScript heap allocated by V8 |
| `external` | Native/external memory associated with JavaScript objects |
| `arrayBuffers` | Memory used by ArrayBuffers and SharedArrayBuffers, including Node.js Buffers |

### How to use these metrics during investigation

Scenario A: `heapUsed` keeps increasing

Investigate:

- Retained JavaScript objects.
- Global collections.
- Unbounded caches.
- Event listeners.
- Closures retaining unnecessary data.

A heap snapshot can help.

Scenario B: `rss` increases, but `heapUsed` remains relatively stable

Investigate:

- Buffer allocations.
- Native memory.
- External libraries.
- Memory fragmentation.
- Other native allocations.

A JavaScript heap snapshot alone may not explain this.

Scenario C: `external` and `arrayBuffers` increase

Investigate:

- Buffer accumulation.
- Large ArrayBuffers.
- Buffer slices retaining larger backing allocations.
- Unbounded queues containing binary payloads.

This is where your Phase 5.11 knowledge becomes useful.

## 10. A real production investigation workflow

Now let's combine the tools.

Imagine your Express API is running on EC2 under PM2.

Your monitoring shows:

- API response time increases.
- CPU usage is around 90%.
- Memory is increasing.
- The process hasn't crashed yet.

How should a senior engineer investigate?

Don't randomly restart the service or immediately increase EC2 resources.

Use a structured approach.

Production investigation workflow

1. Identify the affected process
    
    Check PM2 process status, PID, restart count, uptime, CPU and memory.
    
2. Check runtime metrics
    
    Capture RSS, heap usage, external memory, event-loop delay and ELU.
    
3. Investigate CPU
    
    Generate a CPU profile and identify functions consuming the most CPU time.
    
4. Investigate memory
    
    Compare heap snapshots in a safe environment and inspect retaining paths.
    
5. Capture process diagnostics
    
    Generate a diagnostic report if you need broader runtime, native or process information.
    
6. Correlate with application behavior
    
    Check request IDs, logs, database latency, external API latency, job queues and deployment changes.
    
7. Fix and verify
    
    Reproduce the issue, implement the fix, run the same workload and compare measurements.
    

### Which tool would you choose?

| Observed problem | First useful diagnostic |
| --- | --- |
| High CPU | CPU profile |
| Increasing JavaScript heap | Heap snapshots |
| Process crashes unexpectedly | Diagnostic report |
| Event-loop responsiveness issues | `monitorEventLoopDelay()` |
| Need to measure a particular function | `perf_hooks` |
| Need to inspect runtime activity over time | Trace events |
| Need to debug execution step by step | Inspector |

These tools complement each other. One tool rarely explains every production issue.

## 11. Production considerations for your PM2/EC2 environment

Since you work with PM2-managed Node.js services, there are some practical points worth knowing.

### 11.1 Identify the correct process

```jsx
pm2 list
```

Find the process ID:

```
pm2 pid parking-api
```

Then inspect its operating-system process:

```
ps -p <PID> -o pid,%cpu,%mem,rss,etime,cmd
```

You can also inspect system resource usage:

```
top -p <PID>
```

Remember that PM2 itself is a separate process. Make sure you are inspecting the actual application worker rather than the PM2 daemon.

### 11.2 Don't expose diagnostic ports publicly

For remote debugging, prefer SSH tunneling.

For example, from your local machine:

```
ssh -L 9229:127.0.0.1:9229 ubuntu@YOUR_EC2_HOST
```

Then connect your local Chrome DevTools to:

```
localhost:9229
```

The remote Inspector should be bound to loopback on the EC2 instance.

### 11.3 Protect diagnostic artifacts

CPU profiles, heap snapshots, and diagnostic reports may contain:

- Application function names.
- Internal paths.
- Request-related data.
- Environment and runtime details.
- Potentially sensitive object contents in heap snapshots.

Treat these files as sensitive production artifacts.

Don't upload them to public storage or share them casually.

### 11.4 Be careful with production profiling

A practical order of investigation is:

1. Start with lightweight metrics and logs.
2. Capture a diagnostic report if broader process information is needed.
3. Use CPU profiling if CPU is the suspected bottleneck.
4. Use heap snapshots when memory retention is suspected, preferably in a controlled reproduction.
5. Use trace events for deeper runtime analysis.

This avoids introducing unnecessary diagnostic overhead into an already struggling service.
