# Phase 5.10 — Node.js `child_process`

This topic is about running external programs from Node.js safely and reliably—for example, running FFmpeg to process videos, a PDF utility to generate documents, or a CLI command to perform a deployment task.

For senior-level interviews, the important part isn't just knowing the four APIs. You should understand which API to choose, how output is handled, how to prevent command injection, and how to manage failures and child processes in production.

## 1. What is `child_process`?

Node.js provides the built-in `node:child_process` module to start and communicate with other operating-system processes.

```javascript
const {
  exec,
  execFile,
  spawn,
  fork
} = require('node:child_process');
```

A child process has its own process-level resources and, for Node.js children, its own V8 instance and JavaScript heap. It is different from a Worker Thread, which runs in the same OS process but in a separate JavaScript execution thread.

Typical use cases:

- Generate PDFs or process images and videos using external tools.
- Run Git, database utilities, or other CLI programs.
- Execute deployment and maintenance scripts.
- Isolate a tool that can crash or consume substantial resources.
- Run a separate Node.js service or task processor.

### The key difference

| API        | Shell by default?             | Output handling                 | Best fit                         |
| ---------- | ----------------------------- | ------------------------------- | -------------------------------- |
| `exec`     | Yes                           | Buffered                        | Small command output             |
| `execFile` | No                            | Buffered                        | Known executable, bounded output |
| `spawn`    | No                            | Streams                         | Large/continuous output          |
| `fork`     | No shell for the child launch | IPC plus optional stdout/stderr | Separate Node.js program         |

Remember: `execFile()` can be configured to use a shell, and `spawn()` can also use one if requested. Avoid enabling a shell unnecessarily.

## 3. `exec()` — convenient, but has two important risks

Example:

```javascript
const { exec } = require('node:child_process');

exec('git --version', (error, stdout, stderr) => {
  if (error) {
    console.error('Command failed:', error.message);
    return;
  }

  console.log(stdout.trim());
});
```

Here, Node.js invokes a shell, the shell runs the command, and Node.js collects the output.

### Risk A: Command injection

Suppose an API accepts a user-supplied filename:

```javascript
const filename = req.query.filename;

exec(`some-tool ${filename}`);
```

If untrusted input is inserted into a shell command, an attacker may be able to alter what the shell executes. This is command injection.

Preferred approach: avoid building shell command strings from user input.

```javascript
const { execFile } = require('node:child_process');

execFile(
  '/usr/bin/some-tool',
  ['--input', validatedFilename],
  { timeout: 10_000 },
  (error, stdout, stderr) => {
    if (error) {
      console.error('Tool failed:', error.message);
      return;
    }

    console.log(stdout);
  }
);
```

The arguments are supplied as an array rather than being parsed as a shell command. You must still validate the filename, constrain it to permitted files/directories, and use a trusted executable path. Avoid allowing users to choose arbitrary executables or command options.

### Risk B: Output is buffered in memory

`exec()` collects the command's output. A command producing hundreds of megabytes can consume significant memory or exceed `maxBuffer`, causing the operation to fail.

For large or continuous output, prefer `spawn()` and consume the output as streams.

## 4. `spawn()` — streaming and process lifecycle

Suppose a backend runs a video conversion command. It may produce progress output for several minutes.

```javascript
const { spawn } = require('node:child_process');

const child = spawn(
  'ffmpeg',
  ['-i', 'input.mp4', 'output.mp4'],
  { shell: false }
);

child.stdout.on('data', chunk => {
  console.log('stdout:', chunk.toString());
});

child.stderr.on('data', chunk => {
  console.log('stderr:', chunk.toString());
});

child.on('error', error => {
  console.error('Failed to start process:', error);
});

child.on('close', (code, signal) => {
  if (code === 0) {
    console.log('Conversion completed');
  } else {
    console.error('Conversion failed:', { code, signal });
  }
});
```

A couple of practical details:

- Many CLI tools write progress and diagnostic information to stderr, even when the operation is working normally. Don't treat every stderr chunk as a failure.
- A process can start successfully but later exit with a non-zero code. Handle both startup errors and process completion.

### `exit` versus `close`

This is an important interview detail:

- `exit` fires when the process has exited.
- `close` fires when the process has ended and its associated stdio streams have closed.

If your application needs to finish consuming stdout/stderr before deciding that a command is fully finished, `close` is generally the more useful completion event.

Do not rely on the order of independent event handlers as a substitute for understanding their lifecycle.

## 5. How do you handle large output safely?

`spawn()` gives you readable streams for stdout and stderr. You still need to consume them properly.

For example, this is risky:

```javascript
child.stdout.on('data', chunk => {
  allOutput += chunk.toString();
});
```

Although it streams from the child, this code accumulates the entire output in memory. Streaming at the source does not help much if your application stores everything in one giant string.

Better options include:

- Pipe output to a file or another writable stream.
- Process each chunk incrementally.
- Use `stream.pipeline()` where appropriate so stream errors are handled correctly.
- Avoid unbounded arrays, strings, and queues.
- Respect backpressure when forwarding output to another stream.

For instance, to send a child process's stdout to a file:

```javascript
const { spawn } = require('node:child_process');
const { createWriteStream } = require('node:fs');
const { pipeline } = require('node:stream/promises');

async function runCommand() {
  const child = spawn('some-tool', ['--export'], {
    shell: false,
    stdio: ['ignore', 'pipe', 'pipe']
  });

  // Consume stderr too, so diagnostics don't accumulate in memory.
  child.stderr.on('data', chunk => {
    process.stderr.write(chunk);
  });

  const output = createWriteStream('./export.bin');

  try {
    await Promise.all([
      pipeline(child.stdout, output),
      new Promise((resolve, reject) => {
        child.once('error', reject);
        child.once('close', (code, signal) => {
          if (code === 0) resolve();
          else reject(new Error(`Command failed: code=${code}, signal=${signal}`));
        });
      })
    ]);
  } catch (error) {
    child.kill();
    throw error;
  }
}
```

This demonstrates the idea, but production code needs a little more care: coordinate cleanup, avoid competing error handlers, drain stderr safely, and delete or quarantine partial output on failure. A non-zero exit should not leave an incomplete export looking like a valid final artifact.

## 6. `fork()` — running another Node.js program

Use `fork()` when the child itself is a JavaScript file running under Node.js and you want a built-in IPC channel.

Parent:

```javascript
const { fork } = require('node:child_process');

const child = fork('./report-worker.js');

child.send({
  type: 'GENERATE_REPORT',
  jobId: 'job-123'
});

child.on('message', message => {
  console.log('Child response:', message);
});
```

Child — `report-worker.js`:

```javascript
process.on('message', async message => {
  if (message?.type !== 'GENERATE_REPORT') return;

  try {
    // Generate the report here.
    process.send?.({
      type: 'COMPLETED',
      jobId: message.jobId
    });
  } catch (error) {
    process.send?.({
      type: 'FAILED',
      jobId: message.jobId
    });
  }
});
```

This is a simple illustration; a real implementation should validate messages, handle disconnects, and serialize error details safely.

### `fork()` versus Worker Threads

| Consideration   | `fork()`                  | Worker Threads                                |
| --------------- | ------------------------- | --------------------------------------------- |
| OS process      | Separate                  | Same process                                  |
| JavaScript heap | Separate                  | Separate per worker isolate                   |
| Communication   | IPC messages              | Messages; transferable/shared memory options  |
| Isolation       | Stronger process boundary | Less isolation than a separate process        |
| Overhead        | Generally higher          | Generally lower for many data-intensive tasks |

Use `fork()` when you need a separate Node.js process or process-level isolation. Use Worker Threads when you need parallel JavaScript execution within the same application process and the workload benefits from it.

Neither automatically solves workload management. Both can overload the machine if you create too many concurrent tasks.

## 7. Timeouts, cancellation, and process cleanup

Starting a child process is only half the job. You also need to decide what happens if it hangs, takes too long, or your API request is cancelled.

```javascript
const { spawn } = require('node:child_process');

const child = spawn('some-tool', ['--process', 'input.dat'], {
  shell: false,
  stdio: 'ignore'
});

const timeout = setTimeout(() => {
  child.kill('SIGTERM');
}, 30_000);

child.once('error', error => {
  clearTimeout(timeout);
  console.error('Could not start process:', error);
});

child.once('close', (code, signal) => {
  clearTimeout(timeout);
  console.log({ code, signal });
});
```

This requests termination after 30 seconds. It does not guarantee that the process has stopped by that exact time.

For production use, consider:

- Start with graceful termination where supported.
- Use a bounded grace period, then escalate if the process is still running.
- Handle child errors and non-zero exit codes.
- On API cancellation, terminate the associated task if safe.
- Clean up temporary files and partial results.
- Avoid orphan processes when a command launches grandchildren.
- Ensure shutdown logic accounts for active child processes.

Important: Killing the direct child does not necessarily kill its descendants. Process groups, signals, and termination behavior differ across operating systems. On Windows, you may need platform-specific process-tree handling or a dedicated process-management approach.

Also, a child process timing out doesn't mean it had no side effects. A command might have already written a file, updated a database, or triggered a remote action. Retrying such work requires idempotency or reconciliation.

## 8. Production design: running external tools from an API

Imagine your backend accepts a request to convert an uploaded document to PDF.

A production-oriented flow might look like this:

For a task that takes minutes, don't keep an HTTP request open by default. Return a job ID, process the task asynchronously, and let the client poll or receive a notification when it finishes.

Other production safeguards include:

- Concurrency limits: Bound how many processes run at once.
- Queue limits: Reject or defer new jobs when capacity is exhausted.
- Resource limits: Restrict CPU, memory, execution time, and file sizes where the OS/container supports it.
- Observability: Record job ID, executable, duration, exit code, timeout count, queue wait time, and failure category.
- Security: Use least-privilege accounts, controlled executable paths, validated arguments, and isolated temporary directories.
- Reliability: Make jobs retry-safe and keep job status durable when processing must survive application restarts.

## 9. Common mistakes to avoid

| Mistake                                  | Better approach                                                           |
| ---------------------------------------- | ------------------------------------------------------------------------- |
| Interpolating user input into `exec()`   | Prefer `execFile()` or `spawn()` with argument arrays and validated input |
| Using `exec()` for huge output           | Stream output with `spawn()`                                              |
| Treating every stderr message as failure | Determine success from exit status and the tool's documented behavior     |
| Handling only the `exit` event           | Understand `close`, startup errors, and non-zero exit codes               |
| Killing only the direct child            | Consider descendant processes and platform-specific cleanup               |
| Starting unlimited child processes       | Use bounded concurrency and queue limits                                  |
| Assuming a timeout means no side effects | Use idempotency, durable job status, and reconciliation                   |
| Trusting a successful exit code alone    | Validate the resulting artifact before publishing it                      |

## 10. Senior-level interview answers

Q: When would you use `exec` versus `spawn`?

I use `exec` for trusted commands with small, bounded output because it buffers the result. For large or continuous output, I prefer `spawn` because it exposes streams and avoids buffering the entire output in memory.

Q: How do you prevent command injection?

I avoid constructing shell commands from user input. I prefer `execFile` or `spawn` with a trusted executable and an argument array, keep shell execution disabled, validate inputs against an allowlist, and restrict filesystem access and process privileges.

Q: How do you handle a child process that hangs?

I set a timeout, request termination, and escalate if necessary after a grace period. I also handle process errors and completion events, clean up temporary resources, and account for descendant processes. For retriable jobs, I track execution state and make side effects idempotent.

Q: Why use a child process instead of a Worker Thread?

A child process provides a separate OS process and stronger process-level isolation, making it useful for external CLI tools or tasks that need independent process resources. Worker Threads are often better for CPU-intensive JavaScript within one application process, especially when their lower communication overhead or shared-memory capabilities are useful.

Each process has its own execution environment and memory space. One process cannot ordinarily access the other's memory directly; they communicate through mechanisms such as IPC or pipes.

### Why do we use child processes?

Suppose your API needs to convert a video using FFmpeg.

- Without a child process: You would need a suitable library or implementation inside your application.
- With a child process: Your Node.js API launches FFmpeg, which performs the conversion independently.

Other uses include running Git commands, generating PDFs, and executing operating-system utilities.

A child process can also isolate crashes or resource-heavy work from your main process, although it still shares the machine's overall CPU and memory capacity.

### Why does `exec()` need a shell?

A shell is a program such as Bash that understands commands, pipes (`|`), redirection (`>`), and command chaining (`&&`).

For example:

```
cat report.txt | grep error > errors.txt
```

`exec()` invokes a shell to interpret this command. In contrast, `execFile()` and `spawn()` normally launch a specified executable directly.

In short: Use a shell when you genuinely need shell features. Otherwise, direct execution is generally simpler and safer, especially when handling user input.

## 2. `fork()` vs Worker Threads — when should you use each?

You're right that they are similar in purpose: both can run work separately from your main request-handling code. But their execution environments differ.

| Feature              | Worker Threads                         | `fork()`                                 |
| -------------------- | -------------------------------------- | ---------------------------------------- |
| OS process           | Same process as parent                 | Separate process                         |
| JavaScript execution | Separate worker thread and V8 isolate  | Separate Node.js process and V8 instance |
| CPU-heavy JavaScript | Yes                                    | Yes                                      |
| Communication        | Messages; can transfer or share memory | IPC messages                             |
| Isolation            | Thread-level; shares the OS process    | Stronger process-level isolation         |
| Overhead             | Usually lower                          | Usually higher                           |

### Can `fork()` handle CPU-heavy tasks?

Yes. Absolutely. Both Worker Threads and child processes can execute CPU-heavy JavaScript without blocking the parent's event loop.

For example, if your API needs to calculate a large report:

- Worker Thread: A good choice when the task is CPU-intensive JavaScript and you want lower communication overhead or shared-memory options.
- `fork()`: A good choice when you want a separate Node.js process, stronger isolation, or an independently managed task processor.

One important distinction: a forked child has its own main JavaScript thread and event loop. A Worker Thread has its own JavaScript execution thread and event loop inside the same OS process.

### A practical rule for interviews

- Need to execute an external tool such as FFmpeg? Use `spawn()` or `execFile()`.
- Need CPU-intensive JavaScript with lower overhead? Consider Worker Threads.
- Need a separate Node.js process for isolation or independent process management? Consider `fork()`.

Remember: Neither Worker Threads nor `fork()` magically creates more CPU capacity. Both need sensible concurrency limits and resource monitoring.

## 3. What does “separate OS process” mean?

Your Node.js application itself runs as an OS process. If it starts a child process, the OS manages two distinct processes.

## 2. Does Cluster also use separate OS processes?

Yes! Node.js Cluster creates multiple Node.js worker processes.

| Approach               | OS processes | JavaScript execution               |
| ---------------------- | ------------ | ---------------------------------- |
| Normal Node.js app     | 1            | Main thread                        |
| Worker Threads         | 1            | Multiple JavaScript threads        |
| `child_process.fork()` | 2 or more    | Separate process per child         |
| Cluster                | 2 or more    | Separate worker process per worker |

- Worker Threads: multiple JavaScript threads inside one OS process.
