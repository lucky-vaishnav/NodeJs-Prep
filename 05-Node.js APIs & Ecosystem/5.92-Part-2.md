Let's continue with Phase 5.11 — ArrayBuffer, SharedArrayBuffer & Typed Arrays.

We've covered the fundamentals. Now we'll focus on practical Worker Threads integration, memory ownership, and performance trade-offs.

## 1. ArrayBuffer: copying vs transferring

When sending an `ArrayBuffer` to a worker, you have two main choices.

Option A: Copy using structured cloning

Parent thread:

```javascript
const { Worker } = require('worker_threads');

const buffer = new ArrayBuffer(4);
const data = new Uint8Array(buffer);
data.set([10, 20, 30, 40]);

const worker = new Worker('./worker.js');

worker.postMessage(buffer); // Copies the data
console.log(buffer.byteLength); // 4 — still usable
```

The worker receives its own copy. Changes made by the worker won't affect the original buffer.

Option B: Transfer ownership

```javascript
worker.postMessage(buffer, [buffer]);

console.log(buffer.byteLength); // 0 — detached
```

The worker receives ownership of the original memory. The parent can no longer access it.

Worker (`worker.js`):

```javascript
const { parentPort } = require('worker_threads');

parentPort.on('message', (buffer) => {
  const data = new Uint8Array(buffer);

  const total = data.reduce((sum, value) => sum + value, 0);

  parentPort.postMessage({ total });
});
```

Key difference: Copying preserves the original but consumes additional memory. Transferring avoids the data copy but gives up access in the sender.

## 2. SharedArrayBuffer: sharing memory between two workers

Unlike transferring an `ArrayBuffer`, a `SharedArrayBuffer` allows multiple workers to access the same memory.

Let's build a simple example where two workers increment one shared counter.

Parent thread (`main.js`):

```javascript
const { Worker } = require('node:worker_threads');

const sharedBuffer = new SharedArrayBuffer(
  Int32Array.BYTES_PER_ELEMENT
);

const counter = new Int32Array(sharedBuffer);

const workers = [
  new Worker('./shared-worker.js', { workerData: sharedBuffer }),
  new Worker('./shared-worker.js', { workerData: sharedBuffer })
];

Promise.all(
  workers.map(worker =>
    new Promise((resolve, reject) => {
      worker.once('error', reject);
      worker.once('exit', code => {
        code === 0
          ? resolve()
          : reject(new Error(`Worker exited: ${code}`));
      });
    })
  )
).then(() => {
  console.log(Atomics.load(counter, 0));
});
```

Worker (`shared-worker.js`):

```javascript
const { workerData } = require('node:worker_threads');

const counter = new Int32Array(workerData);

for (let i = 0; i < 100000; i++) {
  Atomics.add(counter, 0, 1);
}
```

Expected result

```
200000
```

Both workers increment the same memory location 100,000 times.

### Why do we need Atomics?

Consider this operation:

```javascript
counter[0]++;
```

It looks like one operation, but conceptually it involves:

1. Read the current value.
2. Add one.
3. Write the updated value.

Two workers can interleave these steps and overwrite each other's updates. This is a race condition.

Instead:

```javascript
Atomics.add(counter, 0, 1);
```

performs the increment atomically, preventing lost updates.

Other useful operations include:

```javascript
Atomics.load(counter, 0);
Atomics.store(counter, 0, 100);
Atomics.add(counter, 0, 5);
Atomics.compareExchange(counter, 0, 100, 200);
```

`compareExchange` updates a value only if its current value matches the expected value.

Important: `SharedArrayBuffer` shares memory between threads in the same process. It does not automatically share memory between separate processes created using `child_process.fork()` or Cluster.

## 3. Using Buffer with Worker Threads

In Node.js, `Buffer` is a subclass of `Uint8Array`. However, be careful when transferring its underlying `ArrayBuffer`.

A Buffer can use pooled memory, meaning its underlying `buffer.buffer` may be larger than the visible Buffer data. Blindly transferring it can have unexpected copying or ownership consequences.

A safe approach is to create an exact standalone `ArrayBuffer`:

```javascript
const input = Buffer.from([10, 20, 30, 40]);

const arrayBuffer = input.buffer.slice(
  input.byteOffset,
  input.byteOffset + input.byteLength
);

worker.postMessage(arrayBuffer, [arrayBuffer]);
```

This creates an exact copy first, then transfers that copy to the worker.

For large binary workloads, if performance matters, consider allocating an `ArrayBuffer` at the beginning and writing data into it directly. That avoids the extra copy needed to convert an existing Buffer.

## 4. Copy vs Transfer vs Share

| Approach | Memory behavior                                    | Sender access | Best suited for                              |
| -------- | -------------------------------------------------- | ------------- | -------------------------------------------- |
| Copy     | Creates another copy                               | Retained      | Small data, independent ownership            |
| Transfer | Moves ownership without copying the backing memory | Detached      | Large data passed to one worker              |
| Share    | Multiple threads access the same memory            | Retained      | Shared counters and coordinated numeric data |

A useful way to decide:

- Copy: Choose simplicity and independent ownership.
- Transfer: Choose efficient ownership handoff.
- Share: Choose only when multiple threads genuinely need access to the same memory.

Sharing is not automatically faster overall. Synchronization, contention, and debugging complexity can outweigh the memory savings.

## 5. Production considerations

A few important points for senior-level Node.js development:

1. Memory monitoring: Large ArrayBuffers and typed arrays can consume substantial memory even when V8's `heapUsed` looks healthy. Monitor `rss`, `external`, and `arrayBuffers` through `process.memoryUsage()`.
2. Validate binary input: Check lengths and offsets before reading with `DataView` or typed arrays. Malformed input can cause out-of-bounds errors or incorrect parsing.
3. Avoid unnecessary conversions: Repeatedly converting Buffer → ArrayBuffer → Buffer creates unnecessary allocations and copies.
4. Don't share everything: Prefer message passing and ownership transfer unless shared memory is justified.
5. Avoid blocking the main thread: `Atomics.wait()` blocks the calling thread. Don't use it on the main event loop.
6. Remember ownership: After transferring an ArrayBuffer, the sender's buffer is detached. Don't attempt to reuse it.

## 6. When should you use these APIs?

| Scenario                                 | Recommended approach                                |
| ---------------------------------------- | --------------------------------------------------- |
| Reading files and handling HTTP payloads | `Buffer` and streams                                |
| Parsing a custom binary protocol         | `Buffer` or `DataView`                              |
| Processing large binary data in a worker | `ArrayBuffer` transfer                              |
| Sharing counters between workers         | `SharedArrayBuffer` + `Atomics`                     |
| Processing image/audio data              | Typed Arrays, often with workers                    |
| Normal Express CRUD APIs                 | Usually no need for manual binary memory management |

The important distinction is that these APIs are not mandatory for every Node.js application. They become useful when working with binary data, high-volume processing, or memory-intensive worker workloads.
