# Phase 5.7 — Node.js `crypto` module

## 1. What is the `crypto` module?

Node.js provides the built-in `node:crypto` module for cryptographic operations such as:

- Hashing data.
- Verifying data integrity.
- Generating secure random values.
- Creating and verifying digital signatures.
- Encrypting and decrypting sensitive data.
- Deriving keys from passwords.
- Generating message authentication codes (HMACs).

```
const crypto = require('node:crypto');
```

You don't need to install a separate npm package to use these core APIs.

Important distinction: Cryptography is not one operation. Hashing, encryption, password hashing, and digital signatures solve different problems. Choosing the wrong one can create serious security vulnerabilities.

## 2. Hashing

A cryptographic hash function converts input data into a fixed-length digest.

For example, SHA-256 produces a 256-bit digest regardless of the input's size.

```javascript
const crypto = require('node:crypto');

const hash = crypto
  .createHash('sha256')
  .update('hello')
  .digest('hex');

console.log(hash);
```

The same input produces the same digest, but even a small input change should produce a very different digest.

### Production use cases

- Checking file integrity after downloading a file.
- Creating content fingerprints to detect duplicate content.
- Verifying that a downloaded artifact matches a trusted digest.
- Building internal data-integrity checks.

### What hashing does not do

Hashing is one-way in the practical cryptographic sense: you don't decrypt a hash to recover the original data.

It also doesn't authenticate the sender by itself. If an attacker can replace both a file and its expected hash, a plain hash won't establish trust.

Password storage is a separate case: don't store passwords using plain SHA-256. Use a password-hashing algorithm designed to resist brute-force attacks, such as Argon2id, scrypt, or appropriately configured PBKDF2.

## 3. HMAC: verifying integrity and authenticity

HMAC stands for Hash-based Message Authentication Code. It combines a cryptographic hash function with a secret key to authenticate a message.

```javascript
const crypto = require('node:crypto');

const secret = process.env.WEBHOOK_SECRET;
const payload = '{"event":"payment.completed","id":"p123"}';

const signature = crypto
  .createHmac('sha256', secret)
  .update(payload)
  .digest('hex');

console.log(signature);
```

The receiver, which also knows the shared secret, can independently calculate and verify the HMAC.

### Where you'll use HMAC in production

- Verifying payment-provider webhooks.
- Authenticating requests between internal services.
- Signing payloads for integrations that specify HMAC authentication.
- Detecting tampering with messages when the secret remains protected.

### Important webhook detail

If an external provider signs the raw request body, verify the exact raw bytes it signed. Parsing JSON and serializing it again may change whitespace, key ordering, or escaping and cause verification to fail.

Also, compare signatures using `crypto.timingSafeEqual()` where applicable, after validating that both inputs have the same length. This avoids a common class of timing-based comparison leaks.

```javascript
const expected = Buffer.from(expectedSignature, 'hex');
const received = Buffer.from(receivedSignature, 'hex');

const valid =
  expected.length === received.length &&
  crypto.timingSafeEqual(expected, received);
```

This example assumes both strings use valid hexadecimal encoding and that the expected signature was calculated correctly. Real webhook implementations must follow the provider's precise signature format and validation rules.

## 4. Secure random values

Use `crypto.randomBytes()` to generate cryptographically secure random bytes.

```javascript
const crypto = require('node:crypto');

const token = crypto.randomBytes(32).toString('hex');

console.log(token);
```

This generates 32 random bytes represented as 64 hexadecimal characters.

### Production use cases

- Generating secure session identifiers.
- Creating password-reset tokens.
- Generating random salts.
- Creating cryptographic keys or other security tokens when the required size and format are appropriate.

For a password-reset token, store a hash of the token when practical, set an expiry, and invalidate it after use. Otherwise, someone who gains read access to the token table may be able to use unexpired tokens directly.

Avoid: `Math.random()` for security-sensitive tokens. It is not a cryptographically secure random-number generator.

## 5. Password hashing and key derivation

Passwords should not be stored as plaintext or as ordinary fast hashes such as SHA-256.

A password-hashing algorithm deliberately makes guessing expensive. Each password should have a unique salt, and the algorithm should use appropriate parameters.

Node.js includes `crypto.scrypt()` for password-based key derivation.

```javascript
const crypto = require('node:crypto');
const { promisify } = require('node:util');

const scrypt = promisify(crypto.scrypt);

async function hashPassword(password) {
  const salt = crypto.randomBytes(16);

  const derivedKey = await scrypt(password, salt, 64);

  return {
    salt: salt.toString('hex'),
    hash: derivedKey.toString('hex')
  };
}
```

This demonstrates deriving a key from a password and a random salt. A production password-storage format should also identify the algorithm and its parameters so they can be changed over time. During login, derive the candidate key using the stored salt and parameters, then compare the results safely.

For a production authentication system, a well-maintained password-hashing library implementing Argon2id or scrypt is often preferable to inventing a custom storage format.

### Senior-level distinction

- Hashing: produces a digest; not reversible.
- Password hashing: deliberately expensive to make guessing harder.
- Key derivation: derives cryptographic key material from a password or other secret.
- Encryption: transforms data so it can be recovered with the appropriate key.

These are related, but they are not interchangeable.

## 6. Encryption and decryption

Encryption protects confidentiality: someone without the required key should not be able to read the protected data.

For symmetric encryption, the same secret key is used for encryption and decryption. AES-256-GCM is a common choice because it provides both confidentiality and integrity authentication.

```javascript
const crypto = require('node:crypto');

function encrypt(plaintext, key) {
  const iv = crypto.randomBytes(12);

  const cipher = crypto.createCipheriv('aes-256-gcm', key, iv);

  const ciphertext = Buffer.concat([
    cipher.update(plaintext, 'utf8'),
    cipher.final()
  ]);

  const authTag = cipher.getAuthTag();

  return {
    iv: iv.toString('hex'),
    ciphertext: ciphertext.toString('hex'),
    authTag: authTag.toString('hex')
  };
}
```

Here, `key` must be exactly 32 bytes for AES-256. The example omits decryption to keep the encryption flow clear.

To decrypt, initialize the matching decipher with the same key and IV, set the authentication tag, and call `final()`. If authentication fails, decryption must fail rather than returning untrusted plaintext.

### Important production rules

- Generate a fresh, unpredictable IV for each encryption under the same key. For GCM, IV uniqueness is critical; 12-byte IVs are the standard choice.
- Never hardcode encryption keys in source code or commit them to Git.
- Store and manage keys using an appropriate secret-management or key-management system.
- Store the IV and authentication tag with the ciphertext; neither needs to be secret.
- Plan key rotation and access control.
- Don't release decrypted plaintext as trusted data until authentication has succeeded.

### Where encryption is used

- Encrypting sensitive application fields at rest.
- Protecting confidential files.
- Encrypting data before storing it in object storage, where application-level encryption is required.
- Protecting sensitive payloads shared between systems.

Use HTTPS/TLS for data in transit. Application-level encryption is an additional design choice, not a replacement for properly configured TLS.

## 7. Digital signatures and asymmetric cryptography

Asymmetric cryptography uses a public/private key pair.

- The private key must remain protected.
- The public key can be shared.
- A digital signature can be created using the private key and verified using the corresponding public key.

Node.js provides `crypto.sign()` and `crypto.verify()`.

```javascript
const crypto = require('node:crypto');

// privateKey and publicKey are appropriately generated/imported keys.
const message = Buffer.from('payment:123:completed');

const signature = crypto.sign(
  'sha256',
  message,
  privateKey
);

const valid = crypto.verify(
  'sha256',
  message,
  publicKey,
  signature
);
```

The keys must be compatible with the selected signature algorithm and options. This example illustrates the API rather than a complete key-management system.

### Production use cases

- Verifying signed webhooks when a provider uses asymmetric signatures.
- Validating signed software releases or artifacts.
- Signing tokens or documents.
- Establishing trust in messages without sharing a symmetric signing secret.

Don't confuse digital signatures with encryption. Signing establishes authenticity and integrity; it doesn't automatically make the message confidential.

## 9. Does crypto block the Node.js event loop?

This is an important senior-level topic.

Not all crypto operations execute in the same way.

- Some APIs are synchronous and block the JavaScript thread while they execute.
- Some APIs provide asynchronous versions, which can avoid blocking the JavaScript thread during the expensive operation.
- Certain asynchronous crypto operations use libuv's thread pool, depending on the API.
- Large numbers of expensive operations can still saturate CPU or the thread pool, increasing latency for unrelated work.

For example, synchronous key derivation or expensive password hashing in a request handler can harm API responsiveness.

Prefer asynchronous variants for expensive operations in a server request path, and use appropriate concurrency limits. Asynchronous APIs do not make computation free; they change where and how the work is scheduled.

Also distinguish cryptographic operations from TLS networking: Node's HTTPS stack handles TLS through its underlying networking and cryptographic implementations.

## 10. Production security mistakes

| Mistake                                                     | Better approach                                                             |
| ----------------------------------------------------------- | --------------------------------------------------------------------------- |
| Storing plaintext passwords                                 | Use a suitable password-hashing algorithm                                   |
| Using SHA-256 alone for password storage                    | Use Argon2id, scrypt, or appropriately configured PBKDF2                    |
| Using `Math.random()` for reset tokens                      | Use `crypto.randomBytes()` or `crypto.randomUUID()` as appropriate          |
| Hardcoding encryption keys                                  | Use secret/key management and access controls                               |
| Reusing a GCM IV with the same key                          | Generate a unique IV for each encryption                                    |
| Treating Base64 as encryption                               | Use a proper encryption scheme when confidentiality is required             |
| Trusting a webhook without verifying its signature          | Verify according to the provider's protocol and validate replay protections |
| Comparing sensitive signatures carelessly                   | Use timing-safe comparison for equal-length byte sequences                  |
| Performing expensive synchronous crypto in request handlers | Use asynchronous APIs and control concurrency                               |
| Logging secrets, keys, or plaintext sensitive data          | Redact sensitive values and restrict log access                             |

### Webhook security: one more production consideration

A valid signature proves that the signed payload was produced by someone with the relevant signing secret or key. It does not necessarily prove the event is new.

For payment webhooks, also validate timestamps or other replay protections where the provider supports them, and make event processing idempotent. A provider may legitimately retry a webhook.

## 11. Short senior-level interview answers

Q: What is the difference between hashing and encryption?

Hashing produces a digest and is not designed to be reversed. Encryption protects confidentiality and allows recovery of the original data with the appropriate key.

Q: How would you store passwords securely?

I would use a password-hashing algorithm such as Argon2id or scrypt with a unique salt and suitable parameters. I would store the algorithm and parameters with the hash and never store plaintext passwords.

Q: How would you generate a secure password-reset token?

I would generate it using `crypto.randomBytes()`, store a hash of the token where practical, set a short expiry, and invalidate it after use. I would also rate-limit requests and avoid revealing whether an account exists.

Q: How would you verify a payment webhook?

I would verify the provider's signature using the exact payload format required by its protocol, use safe comparison where appropriate, validate timestamps or replay protection, and make event processing idempotent.

Q: How would you encrypt sensitive database fields?

I would use authenticated encryption such as AES-256-GCM with a securely managed key, a unique IV for every encryption under that key, and appropriate storage for the authentication tag. I would plan for key rotation and access control.

Q: Why can crypto operations affect Node.js performance?

Some operations block the JavaScript thread, while certain asynchronous operations use the libuv thread pool. Expensive cryptographic work can also saturate CPU or the pool, so I would prefer asynchronous APIs where appropriate and limit concurrency.

## 1. Public key, private key, signing, and verification

Yes, your understanding is correct.

- Private key: Kept secret. Used to create a digital signature.
- Public key: Can be shared publicly. Used to verify that signature.

The two keys are mathematically related, but knowing the public key should not allow someone to practically derive the private key when a secure algorithm is used correctly.

### How it works

Step 1: Sender signs the data

The sender uses their private key to generate a signature for the data.

Step 2: Sender sends both

The original data and its digital signature are sent to the receiver. The public key is shared separately or through a trusted certificate.

Step 3: Receiver verifies

The receiver uses the sender's public key to verify the signature. If verification succeeds, the data matches what was signed and the signature was created by someone holding the corresponding private key.

### What if the public key leaks?

That is expected. A public key is designed to be shared. Someone who obtains it can verify signatures, but should not be able to create valid signatures for that key without the private key.

One important detail: a valid signature does not automatically prove the sender's real-world identity. Your application must also trust that the public key actually belongs to the claimed sender.

### Node.js example

```javascript
const {
  generateKeyPairSync,
  sign,
  verify,
} = require('node:crypto');

const { publicKey, privateKey } = generateKeyPairSync('ed25519');

const data = Buffer.from('Payment ID: PAY-123');

const signature = sign(null, data, privateKey);

const isValid = verify(null, data, publicKey, signature);

console.log(isValid); // true
```

If the data changes, verification fails. If the private key is compromised, an attacker may create valid signatures, so protecting the private key is critical.

Interview-ready answer: A private key signs data, and the corresponding public key verifies the signature. The public key can be distributed safely, while the private key must remain secret.

## 2. What is an IV, and why do we need key rotation?

These are separate concepts used in symmetric encryption, such as AES-256-GCM.

### A. What is an IV?

IV stands for Initialization Vector. It is an input supplied to an encryption algorithm alongside the secret key.

Think of it this way:

- Key: The secret used to protect the data.
- IV: A value that helps make each encryption operation unique, even when the same key is used.

For AES-256-GCM, a typical setup is:

- Key: 32 bytes (256 bits).
- IV: 12 bytes (96 bits), generated securely and uniquely for each encryption under the same key.
- Authentication tag: Used to detect tampering with the encrypted data.

Example:

```javascript
const crypto = require('node:crypto');

const key = crypto.randomBytes(32);

const iv1 = crypto.randomBytes(12);
const iv2 = crypto.randomBytes(12);

// Use key + iv1 to encrypt one record.
// Use key + iv2 to encrypt another record.
```

For AES-GCM, never reuse the same IV with the same key. Random 12-byte IVs are common, but if your system performs very large numbers of encryptions, you need a deliberate strategy to prevent collisions.

The IV is generally stored alongside the ciphertext. It does not need to be secret.

For example, your database could store:

| Field        | Purpose                                  |
| ------------ | ---------------------------------------- |
| `ciphertext` | The encrypted data                       |
| `iv`         | The IV used for encryption               |
| `authTag`    | Detects tampering                        |
| `keyId`      | Identifies which encryption key was used |

To decrypt, the application retrieves the correct key, IV, authentication tag, and ciphertext.

### B. What is key rotation?

Key rotation means replacing an encryption key periodically or when necessary, such as after a security incident, according to a security policy, or when a key reaches its intended lifetime.

Your concern is correct: if you encrypt data with Key A, you cannot normally decrypt it with an unrelated Key B.

There are two common approaches.

Approach 1: Keep old keys for decryption

- Encrypt new data with Key B.
- Keep Key A available for decrypting older records.
- Store a `keyId` with each encrypted record.
- Select the appropriate key when decrypting.

This is useful when you have a large amount of historical data.

Approach 2: Re-encrypt existing data

- Decrypt old data using Key A.
- Encrypt it using Key B and a fresh IV.
- Update the stored ciphertext and key ID.
- Retire Key A once all required data has been safely migrated and verified.

This is useful when the goal is to eliminate reliance on an old key, but migration must be carefully managed.

### C. A production example

Suppose your application stores encrypted bank account details.

Initially:

| Record    | Key ID   | Encryption key |
| --------- | -------- | -------------- |
| Account A | `key-v1` | Key A          |
| Account B | `key-v1` | Key A          |

You rotate to Key B.

| Record        | Key ID   | Encryption key |
| ------------- | -------- | -------------- |
| Account A     | `key-v1` | Key A          |
| Account B     | `key-v2` | Key B          |
| New Account C | `key-v2` | Key B          |

The application uses `keyId` to retrieve the right key for each record. Key A remains available for old records, but it is no longer used to encrypt new data.

Once Account A is re-encrypted with Key B, Key A may be retired after verifying that no remaining data or dependent systems need it.

In production, services such as AWS KMS can manage encryption keys and key versions. Your application should use stable key identifiers and a controlled rotation/migration process rather than hardcoding secret keys in source code.

One additional pattern is envelope encryption: data is encrypted using a data-encryption key (DEK), and that DEK is protected by a key-encryption key (KEK). Rotating the KEK can often be done by rewrapping the DEK rather than re-encrypting all the original data, depending on the system's requirements.

Interview-ready answer: An IV is a usually non-secret value used during encryption; with AES-GCM, it must be unique for each encryption under a given key. Key rotation replaces the encryption key, so systems retain old keys for decryption or re-encrypt existing data. A key ID lets the application select the correct key for each record.

The key point is: with AES-GCM, reusing an IV with the same secret key is a security vulnerability, not simply an error that makes encryption fail. The encryption may appear to work normally, but it can expose sensitive information and undermine data integrity.

Let's understand why.

## 1. If the secret key is already secure, why do we need an IV?

The key and IV have different purposes.

- Secret key: Controls who can decrypt the data.
- IV (Initialization Vector): Helps ensure that each encryption operation is cryptographically distinct when using the same key.

Different IVs allow safe reuse of the same key, within the algorithm's security limits.

You can reuse the secret key for many encryption operations. You should not reuse the IV with that key when using AES-GCM.

## 2. What happens if the IV is reused?

Suppose both records use the same key K and the same IV 101.

Security risk

AES-GCM's encryption process reuses the same underlying keystream. This can expose relationships between the plaintexts, and IV reuse can also compromise GCM's authentication guarantees, potentially allowing forged messages.

An attacker generally does not automatically obtain both complete plaintexts just because an IV was reused. However, the reuse creates serious cryptographic weaknesses, and the exact impact depends on the data and attacker's capabilities.

Important: AES-GCM usually will not throw an error just because you reused an IV. It does not automatically detect that you reused one. Preventing reuse is your application's responsibility.

## 3. Is the IV required to be unique, or will encryption fail otherwise?

For AES-GCM, the IV must be unique for every encryption under a particular key.

| Situation                              | Result                                                |
| -------------------------------------- | ----------------------------------------------------- |
| Same key, different IVs                | Normal, intended use                                  |
| Different keys, same IV                | Not the same reuse violation, because the key differs |
| Same key, same IV reused               | Serious security risk                                 |
| Random IV generated for each operation | Common approach, but collisions are possible          |

A 12-byte random IV has \\(2^{96}\\) possible values, so accidental collisions are unlikely at ordinary volumes. But the probability increases as the number of encryptions grows. High-volume systems may need a carefully designed nonce-generation strategy and must respect AES-GCM usage limits.

## 4. What should you do in Node.js?

Generate a fresh IV for each encryption operation:

```javascript
const crypto = require('node:crypto');

const key = crypto.randomBytes(32); // Store securely
const iv = crypto.randomBytes(12);  // Fresh for this encryption

const cipher = crypto.createCipheriv('aes-256-gcm', key, iv);

const ciphertext = Buffer.concat([
  cipher.update('Sensitive bank details', 'utf8'),
  cipher.final(),
]);

const authTag = cipher.getAuthTag();

// Store ciphertext, iv, authTag, and keyId.
// The IV and authentication tag are not secret.
```

In production, the key would normally come from secure key management rather than being generated every time the application starts. The IV, however, is newly generated for each encryption operation.

Senior-level takeaway: The key provides secrecy, while the IV helps ensure safe cryptographic operation. With AES-GCM, IV uniqueness is a security requirement, not a validation check that the encryption library will necessarily enforce.
