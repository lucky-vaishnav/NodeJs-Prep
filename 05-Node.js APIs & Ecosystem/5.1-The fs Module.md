# Phase 5.1 — The `fs` Module

## 1. What is the `fs` module?

The `fs` module stands for File System. It is a built-in Node.js module used to interact with files and directories.

Common use cases in backend applications include:

- Reading configuration files and templates.
- Writing logs or generated reports.
- Uploading, moving, and deleting files.
- Processing CSV, JSON, or other files.
- Managing files temporarily during data imports or exports.

You don't need to install a package to use it.

```javascript
const fs = require("node:fs");
const fsPromises = require("node:fs/promises");
```

`node:fs` makes it clear that you're importing a built-in Node.js module.

## 2. Three ways to work with files

The most important distinction is between synchronous, callback-based, and Promise-based APIs.

### 1. Synchronous API

Blocks the event loop

```javascript
const fs = require("node:fs");

const data = fs.readFileSync("config.json", "utf8");
console.log(data);
```

Execution waits for the file read to finish. Other JavaScript callbacks on that thread cannot run while the synchronous operation is blocking.

### 2. Callback API

```javascript
const fs = require("node:fs");

fs.readFile("config.json", "utf8", (err, data) => {
  if (err) {
    console.error(err);
    return;
  }

  console.log(data);
});
```

The function returns without waiting for the file read to complete. The callback handles the result or error later.

### 3. Promise API

Good default for async code

```javascript
const fs = require("node:fs/promises");

async function readConfig() {
  try {
    const data = await fs.readFile(
      "config.json",
      "utf8"
    );

    console.log(data);
  } catch (err) {
    console.error(err);
  }
}

readConfig();
```

Supports `async/await`, making control flow and error handling easier to follow.

Senior-level takeaway: For typical asynchronous backend file operations, Promise-based APIs are a good default. Synchronous APIs can be reasonable for small, one-time operations during startup, but avoid blocking the event loop on request paths.

## 3. How does `fs` work internally?

When you call an asynchronous file operation such as:

```
fs.readFile("report.csv", callback);
```

Node.js coordinates the operation with the operating system and its native runtime. Many filesystem operations use libuv's thread pool.

A key distinction from our earlier event-loop lessons:

- Asynchronous file I/O does not mean JavaScript runs in parallel on multiple threads.
- File operations may use libuv's thread pool, while JavaScript callbacks normally execute on the main JavaScript thread.
- Synchronous filesystem calls block that JavaScript thread until the operation completes.

Not every operation follows precisely the same internal path; the operating system and operation type matter.

## 4. Common methods you should know

| Method                | Purpose                            |
| --------------------- | ---------------------------------- |
| `readFile()`          | Read an entire file into memory    |
| `writeFile()`         | Create or overwrite a file         |
| `appendFile()`        | Append data to a file              |
| `mkdir()`             | Create a directory                 |
| `readdir()`           | List directory entries             |
| `stat()`              | Retrieve file metadata             |
| `rename()`            | Rename or move a file              |
| `unlink()`            | Delete a file                      |
| `access()`            | Check accessibility or permissions |
| `createReadStream()`  | Read a file incrementally          |
| `createWriteStream()` | Write data incrementally           |

For large files, streams are particularly important. We'll cover them in depth in the next phases, so we won't repeat the full streams lesson here.

## 5. Production scenario: reading a large CSV

Suppose an Express API must process a CSV file of several hundred megabytes.

This approach is risky:

```
const data = await fs.readFile(filePath, "utf8");
```

Why? `readFile()` loads the entire file into memory. Under concurrent requests, multiple large files can create substantial memory pressure and potentially exhaust the process's memory.

A better design is to use `createReadStream()` and process the file incrementally, applying backpressure and appropriate parsing logic.

Also remember:

- Validate the file path and restrict access to permitted directories.
- Handle errors such as `ENOENT` (file not found) and `EACCES` (permission denied).
- Don't assume an `access()` check guarantees the file will still exist or be accessible when you subsequently open it; the state can change between operations.
- Avoid using a user-supplied path directly without validation, because that can expose files outside the intended directory.
