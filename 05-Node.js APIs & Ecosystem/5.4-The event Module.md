# Phase 5.4 — Node.js `events` Module

## 1. What is the `events` module?

Node.js provides a built-in `node:events` module that allows objects to emit named events and other parts of the application to listen and respond to them.

```javascript
const EventEmitter = require('node:events');

const emitter = new EventEmitter();

emitter.on('userCreated', (user) => {
  console.log('User created:', user.name);
});

emitter.emit('userCreated', { id: 1, name: 'Alice' });
```

Output:

```
User created: Alice
```

Here:

- `on()` registers a listener.
- `emit()` triggers the event.
- The object passed to `emit()` is provided to the listener as an argument.

### Where is it useful?

Imagine a user registers in your application. After creating the user, you might want to trigger several independent actions:

- Send a welcome email.
- Record an audit event.
- Update application metrics.

An event emitter can help separate the code that creates the user from the code that responds to the event.

## 2. How `EventEmitter` works internally

Consider this example:

```javascript
const EventEmitter = require('node:events');
const emitter = new EventEmitter();

emitter.on('paymentCompleted', () => {
  console.log('Listener 1');
});

emitter.on('paymentCompleted', () => {
  console.log('Listener 2');
});

console.log('Before emit');

emitter.emit('paymentCompleted');

console.log('After emit');
```

Output:

```
Before emit
Listener 1
Listener 2
After emit
```

Important: EventEmitter listeners run synchronously by default, in registration order.

The event emitter does not automatically move listeners to another thread, schedule them on the event loop, or make them asynchronous.

`emit('paymentCompleted')`

Listener 1 executes

Listener 2 executes

Execution continues after `emit()`

If a listener performs expensive synchronous work, it blocks the JavaScript thread just like any other synchronous function.

### What if a listener is asynchronous?

```javascript
emitter.on('paymentCompleted', async () => {
  await sendEmail();
  console.log('Email sent');
});

emitter.emit('paymentCompleted');

console.log('Emit finished');
```

Assuming `sendEmail()` yields asynchronously, the output begins with:

```
Emit finished
```

The email listener starts synchronously, reaches `await`, and suspends. The emitter does not wait for its returned Promise to finish.

This is a critical production detail: `emit()` is not a Promise-based workflow manager. If you need to await completion, coordinate the asynchronous operations explicitly.

## 3. Important EventEmitter methods

| Method                            | Purpose                                    |
| --------------------------------- | ------------------------------------------ |
| `on(event, listener)`             | Register a listener                        |
| `once(event, listener)`           | Register a listener that runs at most once |
| `emit(event, ...args)`            | Invoke listeners for an event              |
| `off(event, listener)`            | Remove a specific listener                 |
| `removeListener(event, listener)` | Alias for removing a listener              |
| `removeAllListeners(event?)`      | Remove listeners; use carefully            |
| `listenerCount(event)`            | Count listeners for an event               |
| `listeners(event)`                | Retrieve listener functions                |
| `setMaxListeners(n)`              | Configure the listener warning threshold   |

Example of `once()`:

```javascript
emitter.once('connected', () => {
  console.log('Connected for the first time');
});

emitter.emit('connected');
emitter.emit('connected');
```

The message appears only once.

`setMaxListeners()` deserves special attention: exceeding the default threshold typically triggers a warning, not a hard limit. Increasing it may be appropriate in some designs, but it shouldn't be used to hide a listener leak.

## 4. The special `error` event

One of the most important Node.js EventEmitter rules:

If an EventEmitter emits `'error'` without an appropriate registered error listener, Node.js throws the error. If it remains uncaught, the process can terminate.

```javascript
const EventEmitter = require('node:events');
const emitter = new EventEmitter();

emitter.on('error', (err) => {
  console.error('Handled error:', err.message);
});

emitter.emit('error', new Error('Something failed'));
```

Output:

```
Handled error: Something failed
```

For production code, register the appropriate error handling before starting an operation that may emit errors.

Also, a normal `try/catch` around `emit()` is not a substitute for handling errors emitted later by an asynchronous operation. Error propagation depends on how that operation reports its failure.

## 5. EventEmitter vs Event Loop

These concepts are related but different.

| EventEmitter                                             | Event loop                                                                                  |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| A mechanism for publishing and listening to named events | Node.js mechanism for scheduling and executing callbacks as work becomes ready              |
| `emit()` invokes listeners synchronously by default      | Executes queued callbacks in its phases and processes microtasks according to runtime rules |
| Does not automatically make work asynchronous            | Coordinates asynchronous callback execution                                                 |
| Can be used entirely synchronously                       | Supports Node's asynchronous execution model                                                |

For example, `emitter.emit('done')` directly calls its listeners. By contrast, a timer callback runs when the timer mechanism schedules it for execution.

Senior-level takeaway: EventEmitter is an event-dispatch mechanism, not a message broker, thread pool, or automatic asynchronous task runner.

### What if you need to wait for the email?

You must coordinate the asynchronous work explicitly. For example, you could call an async function directly and await it:

```javascript
await sendEmail();
```

Or design a separate async workflow that awaits all required tasks. Simply using `await emitter.emit(...)` won't work because `emit()` returns a boolean, not a Promise.

In production, if sending the email is a critical side effect of a payment, consider a durable queue or an outbox-based workflow rather than relying on an in-memory event alone.

## 3. Next: listener cleanup and memory leaks

One important senior-level issue is repeatedly registering listeners without removing them.

```javascript
function handleRequest() {
  emitter.on('paymentCompleted', () => {
    console.log('Payment completed');
  });
}
```

If `handleRequest()` runs thousands of times, it adds thousands of listeners. This can cause duplicate processing, retain references to objects in memory, and eventually trigger a `MaxListenersExceededWarning`.

A better approach is to register long-lived listeners once where possible, or explicitly remove listeners when their lifecycle ends.

## 6. Listener leaks and cleanup

Consider this example:

```javascript
const EventEmitter = require('node:events');
const emitter = new EventEmitter();

function handleRequest(userId) {
  emitter.on('paymentCompleted', () => {
    console.log('Payment completed for user:', userId);
  });
}

handleRequest(101);
handleRequest(102);

emitter.emit('paymentCompleted');
```

Output:

```
Payment completed for user: 101
Payment completed for user: 102
```

Each call to `handleRequest()` registers another listener. If this function runs for every HTTP request, the listeners keep accumulating.

This can cause three problems:

1. Duplicate work: one event triggers many handlers, including handlers you didn't intend to retain.
2. Memory retention: listeners can retain references to objects and data they close over.
3. Performance degradation: emitting an event becomes more expensive as the listener count grows.

Node.js typically warns when more than 10 listeners are registered for a single event on an emitter. This is a warning threshold, not a hard limit; exceeding it doesn't automatically mean a leak, but it is a reason to investigate.

### How to fix it

Approach A: Register a long-lived listener once.

```javascript
emitter.on('paymentCompleted', (payment) => {
  console.log('Payment completed:', payment.id);
});

function handleRequest(userId) {
  // Handle the request; don't register the same
  // application-wide listener on every request.
}
```

Approach B: Remove a listener when its lifecycle ends.

```javascript
function onPaymentCompleted(payment) {
  console.log('Payment completed:', payment.id);
}

emitter.on('paymentCompleted', onPaymentCompleted);

// Later, when this listener is no longer needed:
emitter.off('paymentCompleted', onPaymentCompleted);
```

You must pass the same function reference to `off()` that you passed to `on()`. Creating a new anonymous function won't remove the original listener.

Approach C: Use `once()` for one-time events.

```javascript
emitter.once('connected', () => {
  console.log('Connected');
});
```

After the first matching event, Node removes that listener automatically.

### A subtle production issue

Suppose a listener captures a large object:

```javascript
function registerListener(requestContext) {
  emitter.on('paymentCompleted', () => {
    console.log(requestContext.userId);
  });
}
```

The listener may keep `requestContext` reachable for as long as the listener remains registered. If the emitter is long-lived, this can retain memory long after the request finishes.

This is why listener lifecycle matters—not just listener count.

## 7. `EventEmitter` versus a message queue

An in-process event emitter is useful for coordinating components inside one Node.js process. But it isn't a durable messaging system.

Use `EventEmitter` for lightweight, in-process notifications—for example, refreshing local metrics or notifying components in the same process.

Use a durable queue or transactional outbox when work must survive process restarts, be retried, or be processed by separate services. Remember that a queue alone doesn't make the database update and message publication atomic; an outbox pattern can help close that gap.

## 8. Async listener errors: a common production trap

Consider this code:

```javascript
emitter.on('paymentCompleted', async () => {
  throw new Error('Email service failed');
});

emitter.emit('paymentCompleted');
```

The listener returns a rejected Promise. A normal `try/catch` around `emit()` won't catch that rejection, because `emit()` doesn't await the Promise.

This can lead to an unhandled rejection if nothing handles it.

One option is to handle the error inside the listener:

```javascript
emitter.on('paymentCompleted', async () => {
  try {
    await sendEmail();
  } catch (err) {
    console.error('Email failed:', err);
  }
});
```

Another option for `EventEmitter` is `captureRejections`, which routes rejected listener Promises to the emitter's error-handling mechanism. That still requires appropriate error handling, and it doesn't make `emit()` wait for listeners.

Senior-level rule: Don't assume EventEmitter manages the lifecycle, completion, or failures of asynchronous work for you.

### Q1. How do you prevent EventEmitter listener leaks?

Repeatedly registering listeners inside an HTTP request handler can cause duplicate executions, memory retention, and performance issues. I would register long-lived listeners once and remove temporary listeners using `off()` when their lifecycle ends. I would use `once()` for one-time events where appropriate.

### Q2. Why isn't EventEmitter reliable for critical background tasks?

EventEmitter works only within the current process and doesn't persist events. If the process crashes before a listener completes its work, the task can be lost. For critical tasks such as payment receipts, I would use a durable queue or a transactional outbox pattern, with retries and idempotent processing.

### Q3. Does `try/catch` around `emit()` catch errors from async listeners?

No, not reliably. EventEmitter doesn't await the Promise returned by an async listener, so a rejected Promise won't be caught by the caller's `try/catch`. I would handle errors inside the listener or explicitly manage the returned Promise. For multiple async tasks that must complete, I would use an approach that awaits and handles their results.
