# Phase 5.5 — Node.js Streams

## 1. What are streams, and why do we need them?

A stream is an abstraction for processing data incrementally rather than requiring the entire dataset to be available in memory.

For example, if an API generates a 1.5 GB CSV report, building the entire report in a string or array before sending it can cause high memory usage, particularly when multiple requests run concurrently.

Using streams, the application can read, process, and write smaller chunks of data as it becomes available.

Key benefits

- Lower memory consumption for large datasets.
- Incremental processing and faster time to first byte.
- Backpressure to coordinate producers and consumers.
- Composition of processing stages, such as reading, transforming, compressing, and writing.

Streams do not automatically guarantee low memory usage. Unbounded buffering, excessive concurrency, or accumulating chunks manually can still cause memory problems.

## 2. The four types of streams

| Type        | Purpose                                 | Examples                 |
| ----------- | --------------------------------------- | ------------------------ |
| `Readable`  | Produces data                           | `fs.createReadStream()`  |
| `Writable`  | Consumes data                           | `fs.createWriteStream()` |
| `Duplex`    | Reads and writes independently          | TCP socket               |
| `Transform` | Reads data and outputs transformed data | Gzip compression         |

A `Transform` is a specialized `Duplex` stream.

## 3. How streams work internally

Node.js streams coordinate data production and consumption through internal buffers and events.

For a readable-to-writable pipeline:

1. The readable produces chunks.
2. Data enters the downstream stream's internal buffer.
3. The writable processes or sends the data.
4. If the consumer is slower than the producer, buffering increases.
5. Backpressure signals that the producer should slow down or stop temporarily.
6. Production resumes when the downstream stream can accept more data.

This coordination prevents an uncontrolled producer from continuously overwhelming a slower consumer.

### `highWaterMark`

`highWaterMark` determines the buffering threshold at which a stream starts applying backpressure.

- In byte mode, it is generally measured in bytes.
- In object mode, it counts objects.
- It is a threshold, not a strict maximum buffer size or total process-memory limit.

A transform can also have separate readable and writable buffering thresholds.

## 4. Backpressure: the essential production concept

Consider a service that reads database records quickly but sends them to a slow external destination. Without backpressure, the application may keep accumulating data in memory.

When manually writing to a writable stream:

```javascript
const canContinue = writable.write(chunk);

if (!canContinue) {
  writable.once('drain', () => {
    // Resume writing
  });
}
```

If `write()` returns `false`, stop writing additional chunks until `drain` fires. The chunk passed to `write()` has already been accepted into the stream's buffering mechanism; don't resend it.

For connected streams, prefer `pipeline()` or `pipe()` when appropriate, because they handle flow control without requiring you to manually coordinate every chunk.

Senior-level distinction: Backpressure controls the rate of data flowing between stream stages. It does not automatically limit the number of concurrent requests, the size of an individual chunk, or memory allocated elsewhere in the application.

## 5. `pipe()` vs. `pipeline()`

Both connect streams and support flow control, but they differ in error handling and lifecycle management.

| Feature                                   | `pipe()`                 | `pipeline()`                        |
| ----------------------------------------- | ------------------------ | ----------------------------------- |
| Connect streams                           | Yes                      | Yes                                 |
| Backpressure                              | Yes                      | Yes                                 |
| Error propagation across the entire chain | Requires additional care | Built in                            |
| Coordinated cleanup on failure            | Requires additional care | Built in                            |
| Promise-based usage                       | Not directly             | Supported by `node:stream/promises` |

For production pipelines, `pipeline()` is generally the better default.

```javascript
const fs = require('node:fs');
const zlib = require('node:zlib');
const { pipeline } = require('node:stream/promises');

async function compressFile() {
  await pipeline(
    fs.createReadStream('large.csv'),
    zlib.createGzip(),
    fs.createWriteStream('large.csv.gz')
  );
}

compressFile().catch(err => {
  console.error('Compression failed:', err);
});
```

This reads the file incrementally, compresses chunks, and writes the compressed output incrementally. If a stage fails, the Promise rejects and the pipeline handles coordinated stream cleanup.

Important: Cleanup does not mean the destination file is automatically deleted or restored to its original state. If the output must be all-or-nothing, use a temporary file and publish it only after the pipeline completes successfully.

## 6. Consuming streams

Node.js offers several common ways to consume readable streams.

### A. Event-based consumption

```javascript
const fs = require('node:fs');

const stream = fs.createReadStream('large.csv');

stream.on('data', chunk => {
  // Process chunk
});

stream.on('end', () => {
  console.log('Reading completed');
});

stream.on('error', err => {
  console.error('Reading failed:', err);
});
```

Adding a `data` listener generally puts a readable stream into flowing mode, where chunks are delivered as they become available.

### B. Async iteration

```javascript
const fs = require('node:fs');

async function processFile() {
  for await (const chunk of fs.createReadStream('large.csv')) {
    // Process chunk
  }
}
```

Async iteration is useful when you want to process chunks sequentially using `async/await`. If processing is awaited inside the loop, the consumer naturally requests the next chunk only as it advances through the iteration.

### C. `Readable.from()`

Use `Readable.from()` to expose an iterable or async iterable as a readable stream.

```javascript
const { Readable } = require('node:stream');

async function* generateRows() {
  yield 'id,name\n';
  yield '1,Alice\n';
  yield '2,Bob\n';
}

const readable = Readable.from(generateRows());
```

This pattern is useful for generating report rows incrementally from an async database cursor or another async data source.

## 7. Readable stream modes

Readable streams have two commonly discussed consumption modes:

- Flowing mode: Chunks are delivered automatically, commonly through `data` events.
- Paused mode: The consumer requests data, commonly through `read()`, or uses another consumption pattern that controls when it advances.

A stream can transition between modes based on how it is consumed. Avoid mixing `data` listeners, manual `read()` calls, and piping without understanding the resulting flow behavior; doing so can make data handling and flow control harder to reason about.

## 8. Creating a custom `Transform` stream

A transform stream is useful when data must be processed incrementally.

For example, this transform converts text chunks to uppercase:

```javascript
const { Transform } = require('node:stream');

const uppercase = new Transform({
  transform(chunk, encoding, callback) {
    callback(null, chunk.toString().toUpperCase());
  }
});
```

The `transform()` method receives a chunk and a callback. Calling `callback(null, output)` supplies the transformed output; calling `callback(error)` reports a failure.

If a transform needs to produce output asynchronously, it must still respect the stream's callback and buffering contract. Do not launch unlimited asynchronous operations and call their callbacks whenever they finish: that can cause unbounded concurrency, out-of-order results, or memory growth.

### Object mode

Streams normally handle byte-oriented data. In object mode, they can carry JavaScript values, such as individual records.

```javascript
const { Transform } = require('node:stream');

const filterActiveUsers = new Transform({
  objectMode: true,

  transform(user, encoding, callback) {
    if (user.active) {
      callback(null, user);
    } else {
      callback();
    }
  }
});
```

Object mode is useful for processing database records or parsed application data. Its buffers count objects rather than bytes, so a small number of objects can still consume substantial memory if each object is large.

## 9. Chunk boundaries and encoding

A stream chunk is a transport or buffering unit, not necessarily a complete application record.

For example, a CSV row might be split across two chunks:

```
Chunk 1: 101,Alex
Chunk 2: ander,alex@example.com\n
```

Processing each chunk as a complete row would produce incorrect results.

The same issue applies to multi-byte character encodings: a character can span chunk boundaries.

For CSV or other structured formats, use a streaming parser that maintains the necessary state between chunks. If implementing your own parser, preserve incomplete records and handle encoding boundaries correctly.

## 10. Production use cases

| Use case                   | Recommended approach                                       |
| -------------------------- | ---------------------------------------------------------- |
| Large file download        | File readable → HTTP response writable                     |
| Large file upload          | HTTP request readable → file/storage writable              |
| Compression                | Readable → gzip transform → writable                       |
| Large CSV export           | Incremental data source → row formatter → response or file |
| Data transformation        | Readable → custom transform → writable                     |
| Database record processing | Cursor or async iterator → bounded processing pipeline     |

For an Express application, you can stream through `req` and `res` directly. You do not need to switch to the built-in `http` module merely to use streams.

For large uploads, use a streaming multipart parser when needed. For large JSON payloads, consider a streaming JSON parser if the payload must be processed incrementally; `express.json()` normally buffers and parses the body before your route handler runs.

## 11. Stream events and completion

Know the difference between these events:

| Event    | Meaning                                          |
| -------- | ------------------------------------------------ |
| `data`   | A readable emits a chunk                         |
| `end`    | A readable has no more data                      |
| `finish` | A writable has completed its writes              |
| `error`  | A stream operation failed                        |
| `close`  | The stream or its underlying resource has closed |

`end` does not mean a writable has finished, and `finish` does not mean a readable has reached its end. The events apply to different stream lifecycles.

For a production pipeline, use `pipeline()` where possible instead of relying only on individual event handlers. For other stream workflows, `finished()` from `node:stream` can help detect completion or failure.

## 12. Error handling, cancellation, and partial files

Streams can fail because of disk errors, client disconnects, network problems, or failures in a transform.

A production design should:

1. Handle pipeline failures and log useful context.
2. Stop or cancel upstream work when the downstream operation can no longer continue.
3. Clean up temporary resources and partial output.
4. Retry only when safe and supported by the workflow.
5. Avoid treating incomplete output as a successful result.

`pipeline()` supports an `AbortSignal`, allowing the pipeline to be aborted when appropriate:

```javascript
const { pipeline } = require('node:stream/promises');

const controller = new AbortController();

await pipeline(
  source,
  transform,
  destination,
  { signal: controller.signal }
);
```

Call `controller.abort()` when cancellation is required. In a real application, handle the resulting rejection and clean up resources. Also remember that aborting a stream does not automatically undo external side effects that have already happened.

For a file-compression job, a robust pattern is to write to a temporary destination, wait for successful completion, and then rename or publish the file. A failed job should not leave a partial file at the final published path.

## 13. Common mistakes to avoid

- Reading an entire large file into memory instead of streaming it.
- Ignoring the `false` return from `write()` and continuing to send data.
- Assuming `highWaterMark` is a hard memory limit.
- Assuming every chunk contains a complete CSV row or character.
- Starting unlimited asynchronous work inside a transform.
- Forgetting to handle errors or remove partial output.
- Assuming `pipeline()` automatically makes every destination operation transactional.
- Assuming streams alone solve memory issues caused by excessive concurrent requests.

## 14. Short interview answers

Q: What are Node.js streams?

Streams allow data to be processed incrementally rather than loading the entire dataset into memory. They are useful for large files, HTTP transfers, and data pipelines.

Q: What is backpressure?

Backpressure coordinates the producer and consumer when data is produced faster than it can be consumed. For writable streams, a `false` return from `write()` signals the producer to wait for `drain`.

Q: What is the difference between `pipe()` and `pipeline()`?

Both connect streams and support backpressure. `pipeline()` also provides coordinated error propagation and cleanup across the stream chain, making it a strong default for production pipelines.

Q: What is `highWaterMark`?

It is the buffering threshold that controls when a stream applies backpressure. It is not a strict cap on total memory usage.

Q: How do you process a large CSV file safely?

I would stream the file through a streaming CSV parser, process records incrementally, handle errors, and keep concurrency and buffering bounded. I would avoid accumulating the entire file or all parsed records in memory.

Q: How do you handle a failed stream pipeline?

I would use `pipeline()` to propagate failures and clean up the stream chain. For file outputs, I would use temporary files and publish them only after successful completion, with retry and cleanup logic appropriate to the workflow.

What to improve

## Concise senior-level interview answers

Q1. How would you handle a 1.5 GB report?

“I would process database records incrementally using a cursor or pagination and stream the generated rows to the response or a file. This avoids loading the entire report into memory. I would rely on backpressure and limit concurrent report-generation jobs to control resource usage.”

Q2. How would you handle a slow downstream consumer?

“I would use backpressure to coordinate the producer and consumer. When `write()` returns `false`, I would wait for `drain` before writing more. For connected streams, I would prefer `pipeline()` and monitor memory usage and throughput.”

Q3. How would you handle a failed compression pipeline?

“I would use `pipeline()` for error propagation and cleanup, write output to a temporary file, and publish it only after successful completion. On failure, I would remove the partial output and retry from the beginning or a safe checkpoint, depending on the workflow.”
