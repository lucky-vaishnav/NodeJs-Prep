# Phase 5.3 — Node.js `http` Module

## 1. What is the `http` module?

Node.js provides a built-in `node:http` module for creating HTTP servers and making HTTP requests without requiring an external package.

```javascript
const http = require('node:http');

const server = http.createServer((req, res) => {
  res.statusCode = 200;
  res.setHeader('Content-Type', 'application/json');

  res.end(JSON.stringify({
    message: 'Hello from Node.js'
  }));
});

server.listen(3000);
```

You can test it by opening `http://localhost:3000`.

### How does it relate to Express?

Express does not replace Node.js HTTP. It builds on top of it.

<img width="1004" height="526" alt="Screenshot 2026-10-25 222145" src="https://github.com/user-attachments/assets/3eb94eaa-243d-4ec8-b803-8d8e7411ede5" />

For example:

```javascript
const http = require('node:http');
const express = require('express');

const app = express();

app.get('/health', (req, res) => {
  res.json({ status: 'ok' });
});

const server = http.createServer(app);
server.listen(3000);
```

Express can also start its own HTTP server with `app.listen()`. You usually use `http.createServer(app)` when you need direct access to the underlying server—for example, to configure server timeouts or attach WebSocket handling.

Senior-level takeaway: Even when you use Express or NestJS, understanding the underlying HTTP server helps you debug connection issues, timeouts, streaming, and graceful shutdown.

## 2. Understand `req` and `res`

When a request reaches the server, Node gives your handler two important objects.

| Object | Node.js class          | Purpose                     |
| ------ | ---------------------- | --------------------------- |
| `req`  | `http.IncomingMessage` | Read the incoming request   |
| `res`  | `http.ServerResponse`  | Build and send the response |

### The request lifecycle

<img width="1021" height="484" alt="Screenshot 2026-10-25 222226" src="https://github.com/user-attachments/assets/a03fc512-537c-493f-99a7-3a90cf1433f9" />

These are conceptual steps, not a guarantee that Node buffers the entire body before your handler runs. Request bodies can arrive in chunks, and your application can process them as a stream.

Example:

```javascript
const http = require('node:http');

const server = http.createServer((req, res) => {
  console.log('Method:', req.method);
  console.log('URL:', req.url);
  console.log('Headers:', req.headers);

  res.writeHead(200, {
    'Content-Type': 'application/json'
  });

  res.end(JSON.stringify({
    method: req.method,
    url: req.url
  }));
});

server.listen(3000);
```

Important details:

- `req.method` gives the HTTP method, such as `GET` or `POST`.
- `req.url` contains the request target, such as `/users?id=10`; it is not automatically a parsed URL object.
- `req.headers` contains normalized header names. Some headers can have special handling, so don't assume it preserves the original header formatting.
- `res.writeHead()` sends the status and headers.
- `res.end()` signals that the response is complete. It can also send the final body chunk.

### `res.write()` vs `res.end()`

```javascript
res.write('Hello ');
res.write('world');
res.end('!');
```

The client receives `Hello world!` as the response body.

- `res.write()` sends a chunk but does not finish the response.
- `res.end()` finishes the response, optionally sending a final chunk.
- Once the response has ended, you must not attempt to send more body data.

A common production bug is trying to send a second response after an error:

```javascript
if (!user) {
  res.statusCode = 404;
  res.end('User not found');
}

// Bug: code may continue and try to send another response.
res.end('Success');
```

Return after sending the error:

```javascript
if (!user) {
  res.statusCode = 404;
  return res.end('User not found');
}

res.end('Success');
```

In a real application, make sure asynchronous branches also cannot attempt to finish the same response twice.

## 3. Request bodies are streams

This is one of the most important production concepts in the HTTP module.

`req` is a readable stream. For a POST or PUT request, its body may arrive in multiple chunks.

A basic example for a small JSON request body:

```javascript
const http = require('node:http');

const server = http.createServer((req, res) => {
  if (req.method !== 'POST') {
    res.writeHead(405);
    return res.end('Method not allowed');
  }

  let body = '';

  req.setEncoding('utf8');

  req.on('data', chunk => {
    body += chunk;
  });

  req.on('end', () => {
    try {
      const data = JSON.parse(body);

      res.writeHead(200, {
        'Content-Type': 'application/json'
      });

      res.end(JSON.stringify({ received: data }));
    } catch {
      res.writeHead(400);
      res.end('Invalid JSON');
    }
  });

  req.on('error', () => {
    if (!res.destroyed) {
      res.destroy();
    }
  });
});

server.listen(3000);
```

This illustrates the mechanics, but it is not production-ready as written. It doesn't enforce a body-size limit, and concatenating chunks can consume excessive memory. Production code also needs to account for aborted requests and robust error handling.

### Why can this implementation be dangerous?

Imagine an API accepting file uploads or JSON payloads. A client sends a 500 MB body, or many clients send large bodies concurrently.

If your server accumulates each body into a string, memory usage can grow substantially. A size limit checked only after the full body has arrived is too late.

For large payloads, prefer streaming to a destination or through a parser with bounded buffering. Enforce limits while reading, and handle stream errors and client disconnects.

### Backpressure

Suppose the request produces data faster than your application or destination can consume it.

Streams use backpressure to prevent producers from overwhelming consumers. When writing to a writable stream, `write()` can return `false`; the producer should wait for the writable stream's `drain` event before continuing.

For a real file-upload pipeline, Node's `stream.pipeline()` is generally preferable to manually wiring stream events because it coordinates errors and stream cleanup.

Senior-level takeaway: streaming doesn't automatically guarantee low memory usage. Your downstream consumer, buffering, parser, and concurrency limits all matter.

## 4. Headers, status codes, and response state

HTTP headers communicate metadata about a request or response.

```javascript
res.statusCode = 201;
res.setHeader('Content-Type', 'application/json');
res.setHeader('Cache-Control', 'no-store');

res.end(JSON.stringify({ id: 123 }));
```

Common methods and properties:

| API                              | Purpose                              |
| -------------------------------- | ------------------------------------ |
| `res.statusCode`                 | Set the response status              |
| `res.setHeader(name, value)`     | Set a header before it is sent       |
| `res.getHeader(name)`            | Read a response header               |
| `res.removeHeader(name)`         | Remove a header before it is sent    |
| `res.headersSent`                | Check whether headers have been sent |
| `res.writeHead(status, headers)` | Set status and headers, sending them |
| `res.end([data])`                | Finish the response                  |

Remember these status codes:

- `200 OK` — successful request.
- `201 Created` — a resource was created.
- `204 No Content` — successful response with no body.
- `400 Bad Request` — invalid request.
- `401 Unauthorized` — authentication is missing or invalid.
- `403 Forbidden` — the caller isn't permitted to perform the operation.
- `404 Not Found` — resource or route not found.
- `429 Too Many Requests` — rate limit exceeded.
- `500 Internal Server Error` — unexpected server error.
- `502 Bad Gateway` / `504 Gateway Timeout` — often seen when a proxy cannot obtain a valid upstream response or the upstream takes too long.

Security point: Don't copy untrusted input directly into response headers. Validate header values and use Node's APIs rather than constructing raw HTTP response text. Also validate request `Host` values when your application relies on them for tenant routing, redirects, or absolute URL generation.

## 5. Connection management and timeouts

This is particularly important for senior backend interviews because many production issues aren't caused by the business logic itself.

### Keep-alive

HTTP keep-alive allows a TCP connection to be reused for multiple HTTP requests, rather than opening a new connection every time.

Benefits include fewer connection handshakes and reduced overhead.

However, keep-alive settings on Node's server, Node's outbound HTTP client, a load balancer, and a reverse proxy are separate configurations. Their timeout values need to work together.

### Important server settings

| Setting                   | What it controls                                                                   |
| ------------------------- | ---------------------------------------------------------------------------------- |
| `server.keepAliveTimeout` | How long a connection can remain idle waiting for another request after a response |
| `server.headersTimeout`   | How long Node allows the client to send complete request headers                   |
| `server.requestTimeout`   | How long Node allows the client to send the entire incoming request                |
| `server.timeout`          | Socket inactivity timeout; distinct from a total request deadline                  |

Exact defaults and behavior can depend on the Node.js version. For production configuration, check the documentation for the version you're running.

Example:

```javascript
const http = require('node:http');

const server = http.createServer((req, res) => {
  res.end('OK');
});

// Illustrative values; choose based on your workload.
server.headersTimeout = 15_000;
server.requestTimeout = 60_000;
server.keepAliveTimeout = 5_000;

server.listen(3000);
```

These values are examples, not universal recommendations.

### Why are timeouts necessary?

Consider an API that receives a request but waits indefinitely for an external service. Without an appropriate deadline and cancellation strategy, resources may remain occupied longer than expected.

For an API calling a database or another service, consider:

1. A timeout for receiving the incoming request.
2. A deadline for the application operation.
3. A timeout for outbound calls.
4. A database query or statement timeout.
5. A load-balancer or proxy timeout compatible with the application.
6. Cleanup or cancellation when the client disconnects.

A timeout at one layer doesn't automatically cancel work in every other layer. For example, stopping an HTTP response doesn't guarantee that an already-started database query has stopped.

### Client disconnects

Relevant signals include:

- `req.aborted` — indicates the incoming request was aborted.
- `req.destroyed` — indicates the request stream has been destroyed.
- `res.close` — indicates the response has closed; it can occur after normal completion too.
- `res.writableEnded` — indicates `res.end()` has been called.

If a client disconnects while an expensive report is being generated, the application may be able to cancel the underlying work rather than continue wasting resources. You need to wire cancellation to the actual database, HTTP client, or task API; detecting a disconnect alone doesn't cancel everything automatically.

## 6. Graceful shutdown

You've already covered graceful shutdown in Phase 4, so we'll connect that knowledge to the HTTP server rather than repeat the full lesson.

```javascript
server.close(err => {
  if (err) {
    console.error('Error closing HTTP server:', err);
    return;
  }

  console.log('HTTP server closed');
});
```

`server.close()` stops the server from accepting new connections and waits for existing connections to finish before its callback runs. Long-lived connections, such as WebSockets, may need additional handling.

In a production deployment, combine this with readiness changes, a shutdown deadline, and cleanup for databases and queues. This is especially important when using PM2 cluster mode or running behind a load balancer.

## 7. Making outbound HTTP requests

The `node:http` module can also act as an HTTP client.

```javascript
const http = require('node:http');

const req = http.get('http://localhost:3000/health', res => {
  let body = '';

  res.setEncoding('utf8');

  res.on('data', chunk => {
    body += chunk;
  });

  res.on('end', () => {
    console.log('Status:', res.statusCode);
    console.log('Body:', body);
  });
});

req.on('error', err => {
  console.error('Request failed:', err.message);
});
```

For a request with a body, headers, or a specific HTTP method, use `http.request()`.

Important distinctions:

- The response callback receives an `IncomingMessage`; the response body is a stream.
- Attach an error handler to the client request. Network errors can occur before a response arrives.
- Receiving an HTTP `500` or `404` is not the same as a network error. The server returned an HTTP response, so check `res.statusCode`.
- For production outbound calls, configure connection reuse, deadlines, cancellation, response-size limits, and retry policies as appropriate.

Node also provides a built-in global `fetch()` API in modern versions. It uses a different API from `node:http`, so don't assume their request and response handling are identical.

## 8. Handling malformed requests

Node's HTTP server exposes a `clientError` event for certain errors encountered while parsing incoming HTTP traffic.

```javascript
server.on('clientError', (err, socket) => {
  if (socket.writable) {
    socket.end(
      'HTTP/1.1 400 Bad Request\r\n' +
      'Connection: close\r\n' +
      '\r\n'
    );
  } else {
    socket.destroy();
  }
});
```

This is a low-level handler: it operates on the socket because a normal `req`/`res` pair may not have been created.

Production considerations:

- Handle malformed traffic without crashing the process.
- Don't expose internal error details to clients.
- Avoid logging sensitive request data.
- Keep request header and body limits reasonable.
- Configure proxy and application HTTP parsing consistently to reduce HTTP request-smuggling risks.

## 9. Common mistakes to remember

| Mistake                                                        | Better approach                                                     |
| -------------------------------------------------------------- | ------------------------------------------------------------------- |
| Buffering huge request bodies into memory                      | Stream the data and enforce size limits                             |
| Sending a response twice                                       | Return after completing a response; handle async branches carefully |
| Treating HTTP `500` as a network error                         | Inspect the response status separately from request errors          |
| Assuming a timeout cancels all downstream work                 | Propagate cancellation to the relevant operation                    |
| Ignoring keep-alive and proxy timeout differences              | Align settings across the network path                              |
| Assuming `server.close()` instantly terminates all connections | Drain active work and handle long-lived connections                 |
| Treating `req.url` as a parsed URL                             | Parse and validate it explicitly when needed                        |
| Relying only on application-level validation for large bodies  | Apply limits while receiving data                                   |

## 2. Large requests: You can still use Express

This is the important correction to your understanding: you do not need to switch to the `http` module directly for streaming.

Express sits on top of Node's HTTP server, and the original request stream is still available.

For example, you could stream an uploaded file to disk using Express and Node's stream APIs:

```javascript
const express = require('express');
const fs = require('node:fs');
const { pipeline } = require('node:stream/promises');

const app = express();

app.post('/upload', async (req, res, next) => {
  try {
    // Illustrative only: production code also needs
    // upload limits, validation, and safe file naming.
    await pipeline(
      req,
      fs.createWriteStream('/tmp/upload.bin')
    );

    res.status(201).json({ message: 'Upload completed' });
  } catch (err) {
    next(err);
  }
});

app.listen(3000);
```

This example assumes the route receives the raw upload body. Don't register body-parsing middleware that consumes this request first, and don't use a client-controlled filename directly as a filesystem path.

For production uploads, also enforce a maximum size while streaming, handle client disconnects, validate the content, and remove incomplete files when necessary.

#### `res` is also a stream?

Yes! `res` is also a stream, but it's a writable stream, whereas `req` is a readable stream.

In Node.js HTTP:

- `req` (`http.IncomingMessage`) → Readable stream: reads incoming request data.
- `res` (`http.ServerResponse`) → Writable stream: writes outgoing response data.

## Example

```javascript
const http = require('node:http');

const server = http.createServer((req, res) => {
  // req: readable stream
  req.on('data', chunk => {
    console.log('Received:', chunk);
  });

  req.on('end', () => {
    // res: writable stream
    res.write('Hello ');
    res.write('client!');
    res.end();
  });
});

server.listen(3000);
```

## How they differ

| Feature            | `req`                               | `res`                             |
| ------------------ | ----------------------------------- | --------------------------------- |
| Stream type        | Readable                            | Writable                          |
| Direction          | Client → Server                     | Server → Client                   |
| Main purpose       | Read request data                   | Send response data                |
| Key methods/events | `on('data')`, `on('end')`, `pipe()` | `write()`, `end()`, `writeHead()` |
| Backpressure       | When reading data from the client   | When sending data to the client   |

### Senior-level detail: response backpressure

When sending a large response, `res.write()` can return `false`. This means the writable buffer is full enough that you should pause producing data until the `drain` event fires.

```javascript
const canContinue = res.write(chunk);

if (!canContinue) {
  // Pause producing data until res emits 'drain'.
}
```

For stream-to-stream transfers, prefer `pipeline()` where appropriate because it handles stream errors and cleanup.

Remember: `req` is readable, `res` is writable, and both are stream-based objects. Express's `req` and `res` wrap the same underlying Node.js HTTP request and response objects, adding framework-specific functionality.

#### then client side needed to be handled according if csv sent in chunks?

Yes, but it depends on how the client consumes the CSV. The client doesn't necessarily need to handle chunks manually.

When your Node.js server sends a CSV using `res.write()` and `res.end()`, HTTP delivers a response body that may arrive in multiple chunks. The client can either process those chunks as they arrive or let its HTTP library collect the complete response.

## 1. If the client downloads the CSV as a file

For a normal CSV download, the browser can handle the chunks automatically. You don't need to write custom chunk-handling code.

Your server might send:

```
res.setHeader('Content-Type', 'text/csv');
res.setHeader(
  'Content-Disposition',
  'attachment; filename="report.csv"'
);

res.write('id,name\n');
res.write('1,Alice\n');
res.write('2,Bob\n');
res.end();
```

The browser downloads the file as `report.csv`.

## 2. If the client needs to process a large CSV

For example, if an Angular application must process a very large CSV without loading the entire response into memory, it should use a streaming-capable approach.

The client can process chunks incrementally, but it must also handle:

- CSV rows split across chunks.
- A row that begins in one chunk and finishes in another.
- Character encoding boundaries.
- Errors or an interrupted connection.

A chunk is not guaranteed to contain complete CSV rows. The client needs a CSV parser that supports streaming rather than simply splitting each chunk by newline.

## 3. What about a normal Angular HTTP request?

With Angular's standard `HttpClient` usage, the response is generally collected before your application receives the complete body. It doesn't automatically expose a streaming CSV parser just because the server used `res.write()`.

So the key distinction is:

| Use case                                | Does the client need custom chunk handling?    |
| --------------------------------------- | ---------------------------------------------- |
| Browser downloading a CSV file          | Usually no                                     |
| Small CSV read into memory              | Usually no                                     |
| Very large CSV processed incrementally  | Yes, use a streaming-capable client and parser |
| Live updates using a streaming protocol | Yes, depending on the protocol                 |

Senior-level takeaway: Server-side streaming reduces the need to buffer the entire response on the server. To get the same memory benefit on the client, the client must also consume the response incrementally. Otherwise, the client may still buffer the entire CSV.

Yes. A browser can receive and consume an HTTP response incrementally, but whether it does so depends on how you access the response.

There are two common scenarios.

## 1. Normal browser CSV download

If the server sends a CSV as a downloadable file:

```javascript
res.setHeader('Content-Type', 'text/csv');

  'Content-Disposition',

res.write('id,name\n');
res.write('1,Alice\n');

// More rows...
res.end();
```

The browser can receive the data progressively and write the downloaded file without requiring your JavaScript application to store the entire CSV in a string.

You generally don't need to implement chunk handling yourself for a normal download.

## 2. Consume the response in JavaScript

If you want your application to process the data while it arrives, the browser Fetch API supports readable response streams.

```javascript
async function downloadCsv() {
  const response = await fetch('/api/report.csv');

  if (!response.ok) {
    throw new Error(`HTTP error: ${response.status}`);
  }

  const reader = response.body.getReader();
  const decoder = new TextDecoder();

  while (true) {
    const { value, done } = await reader.read();

    if (done) break;

    const chunk = decoder.decode(value, { stream: true });

    console.log('Received chunk:', chunk);

    // Process this chunk incrementally.
  }

  // Flush any remaining bytes held by the decoder.
  const remaining = decoder.decode();

  if (remaining) {
    console.log('Final chunk:', remaining);
  }
}
```

Here, `response.body` is a readable stream. The browser exposes chunks as they become available.

Important: These chunks are arbitrary byte sequences, not guaranteed to correspond to complete CSV rows. A production CSV processor must handle rows split across chunks, ideally using a streaming CSV parser.

One distinction to remember: receiving data progressively is not the same as rendering or processing it progressively. The browser may receive chunks incrementally, but your code must use a streaming API to process them incrementally. A regular `response.text()` call, for example, waits for the full response body to be read before returning the text.
