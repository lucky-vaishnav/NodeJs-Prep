# Phase 5.9 — `worker_threads`: Advanced APIs and Production Usage

We'll cover only the details that add to your earlier Worker Threads and Cluster lessons. No repetition of the basic architecture or event-loop concepts.

The focus is on how to build, communicate with, manage, and safely reuse workers in a production Node.js service.

## 1. Worker lifecycle and communication APIs

The core APIs are:

| API                    | Purpose                                          |
| ---------------------- | ------------------------------------------------ |
| `new Worker()`         | Starts a worker executing a JS file or module    |
| `workerData`           | Supplies initial data when the worker starts     |
| `parentPort`           | Allows the worker to communicate with its parent |
| `worker.postMessage()` | Sends data from the parent to the worker         |
| `message` event        | Receives messages from the other side            |
| `error` event          | Reports an uncaught worker error                 |
| `exit` event           | Reports that the worker has exited               |
| `worker.terminate()`   | Requests worker termination                      |

### Example: Worker with input and output

Parent file — `main.js`:

```javascript
const { Worker } = require('node:worker_threads');

const worker = new Worker('./worker.js', {
  workerData: { number: 10 },
});

worker.on('message', result => {
  console.log('Result:', result);
});

worker.on('error', error => {
  console.error('Worker failed:', error);
});

worker.on('exit', code => {
  console.log('Worker exited:', code);
});
```

Worker file — `worker.js`:

```javascript
const { workerData, parentPort } =
  require('node:worker_threads');

const result = workerData.number * workerData.number;

parentPort.postMessage(result);
```

Output:

```
Result: 100
Worker exited: 0
```

Here, `workerData` provides initial input, while `parentPort.postMessage()` sends the result back.

Production detail: These event handlers are important, but they are not a complete worker manager. A production implementation must also handle unexpected exits, task failures, timeouts, worker replacement, and shutdown.

## 2. `workerData` vs `postMessage()`

Both pass data to a worker, but they serve different purposes.

- `workerData`: Initial data provided when the worker is created.
- `postMessage()`: Data exchanged after the worker exists, including task requests and results.

Use `workerData` for configuration or initialization. Use messages for ongoing communication.

For example, a worker pool may start workers with configuration once, then send hundreds of individual jobs through `postMessage()` without recreating the worker each time.

### A common mistake

Creating a new worker for every small task:

```javascript
async function calculate(input) {
  const worker = new Worker('./worker.js', {
    workerData: input,
  });

  // Wait for result, then terminate worker...
}
```

This adds worker startup and initialization overhead for every task.

For frequent tasks, a worker pool is generally better: create a bounded number of workers and reuse them.

## 3. Copying versus transferring data

This is an important detail when processing large buffers, files, images, or binary payloads.

By default, messages use structured cloning. Data is copied or cloned according to the supported data type; the sender's original object generally remains usable.

For large binary payloads, copying can increase CPU and memory pressure. An `ArrayBuffer` can instead be transferred to the worker.

```javascript
// main.js
const { Worker } = require('node:worker_threads');

const worker = new Worker('./process-buffer.js');

const buffer = new ArrayBuffer(1024 * 1024);
const bytes = new Uint8Array(buffer);

bytes[0] = 42;

worker.postMessage(buffer, [buffer]);

// The ArrayBuffer has been transferred.
// The sender's buffer is now detached.
console.log(buffer.byteLength); // 0
```

Worker file — `process-buffer.js`:

```javascript
const { parentPort } = require('node:worker_threads');

parentPort.on('message', buffer => {
  const bytes = new Uint8Array(buffer);

  // Process the bytes here.
  parentPort.postMessage({
    size: bytes.length,
    firstByte: bytes[0],
  });
});
```

The transfer list transfers ownership of the underlying `ArrayBuffer` rather than copying its contents.

### When should you transfer?

- Small objects: Structured cloning is often simpler.
- Large binary payloads: Consider transferring an `ArrayBuffer`.
- Data needed by both threads: Copy it, or consider shared memory if concurrent access is genuinely needed.

Be careful when transferring a `Buffer` in Node.js. Its underlying `ArrayBuffer` may be pooled or shared with other views. Do not assume you can safely transfer every `Buffer`'s backing memory directly. If necessary, create a dedicated `ArrayBuffer` or an independent copy.

## 4. Shared memory: `SharedArrayBuffer` and `Atomics`

Transferring an `ArrayBuffer` gives ownership to the receiver. `SharedArrayBuffer`, by contrast, lets multiple threads access the same underlying memory.

This can avoid copying, but it introduces synchronization concerns.

Example:

```javascript
const shared = new SharedArrayBuffer(4);
const counter = new Int32Array(shared);

// In code that has access to this same shared memory:
Atomics.add(counter, 0, 1);

console.log(Atomics.load(counter, 0));
```

`Atomics.add()` performs an atomic update on the shared integer. If several workers update the same counter, this avoids the lost-update problem that could occur with an ordinary read-modify-write sequence.

### When is shared memory useful?

- High-throughput numerical processing.
- Shared counters or coordination state.
- Specialized binary processing where copying is expensive.

For ordinary API tasks, shared memory is often unnecessary. It makes synchronization, debugging, and correctness more difficult. Prefer message passing unless profiling shows that sharing memory provides a meaningful benefit.

## 5. Worker pools: the production pattern

A worker pool manages a fixed number of workers and distributes tasks to them.

A production pool needs to manage:

1. Fixed concurrency: Limit workers to the available CPU and memory budget.
2. Bounded queue: Reject or defer tasks when capacity is exhausted.
3. Task correlation: Associate each result or error with its original task.
4. Failure handling: Detect crashes, reject affected tasks, and replace workers if appropriate.
5. Timeouts and cancellation: Avoid allowing stuck work to occupy a worker forever.
6. Graceful shutdown: Stop accepting jobs, drain accepted work within a deadline, then terminate remaining workers if necessary.
7. Observability: Track queue depth, task duration, worker restarts, errors, and utilization.

A queue with no maximum size can become a memory leak under load. A pool with unlimited worker creation can overwhelm the container or cause CPU contention.

### Why not write a pool from scratch every time?

For production, consider a maintained library such as `piscina`, which provides worker pooling and task scheduling features. Still configure limits, error behavior, and shutdown deliberately; a library does not remove the need for capacity planning.

## 6. Worker failure, timeouts, and task reliability

A worker is not a durable job system. If a worker crashes while processing a task, Node.js does not automatically guarantee that the task will be retried or completed.

Suppose a worker generates a report:

1. The parent submits task `report-123`.
2. The worker begins processing.
3. The worker crashes before returning the result.
4. The parent must decide what happens to `report-123`.

A reliable task manager should track the task state and determine whether retry is safe.

Important distinction: A worker crash does not necessarily mean the task failed before doing any work. If the task made external changes before crashing, blindly retrying can duplicate those changes. Use idempotency or durable task state for side-effecting operations.

For expensive CPU tasks, also consider:

- A task deadline or timeout.
- A strategy for replacing crashed workers.
- A maximum number of retries.
- Backoff to avoid rapid crash/restart loops.
- A separate durable queue if jobs must survive application restarts.

If a worker is stuck in synchronous computation, it may not process a cancellation message. Termination may be necessary, but it can interrupt the work without a clean application-level rollback.

## 7. Production mistakes to avoid

| Mistake                                                | Better approach                                                    |
| ------------------------------------------------------ | ------------------------------------------------------------------ |
| Creating one worker per request                        | Reuse a bounded worker pool                                        |
| Accepting unlimited queued jobs                        | Set queue capacity and overload behavior                           |
| Copying huge binary payloads unnecessarily             | Consider transferable `ArrayBuffer` objects                        |
| Using shared memory without synchronization            | Use `Atomics` correctly or prefer message passing                  |
| Retrying every failed task automatically               | Check idempotency and whether side effects occurred                |
| Ignoring worker errors and exits                       | Track task ownership and manage worker replacement                 |
| Assuming workers increase API throughput automatically | Profile first; account for CPU, memory, and downstream bottlenecks |

## 8. Short senior-level interview answers

When should you use Worker Threads?

Use them for CPU-intensive JavaScript work that would otherwise block the main event loop. They are generally unnecessary for ordinary asynchronous I/O that Node.js already handles efficiently.

Why use a worker pool?

Creating workers has overhead. A bounded pool reuses workers, limits CPU and memory consumption, and controls task concurrency.

When would you use transferable objects?

When large binary data would otherwise incur significant copying overhead. Transferring an `ArrayBuffer` moves ownership to the receiving thread, detaching it from the sender.

When would you use `SharedArrayBuffer`?

When multiple threads genuinely need access to the same memory and avoiding copies matters. Synchronization using `Atomics` is essential where concurrent access can cause race conditions.

How do you make worker processing reliable?

Track task state, handle worker errors and exits, enforce deadlines and queue limits, and retry only when the operation is safe to repeat. Use durable storage or a persistent queue when work must survive process restarts.

## 1. Task disappears after a worker crash — 8/10

What you got right

- Writing to a temporary file and renaming it to the final filename is a good way to avoid exposing a partially generated PDF.
- Checking whether the output already exists can help prevent duplicate work.

What is missing

A final file's existence alone does not prove that the entire job succeeded. For example, the PDF might exist while the corresponding PostgreSQL record was never committed.

I'd improve your design with a durable job state and an idempotent workflow:

1. Give each job a stable `jobId`.
2. Generate the PDF into a unique temporary file.
3. Validate the PDF, then atomically rename it into its final location when supported by the filesystem.
4. Record the final result in PostgreSQL using an idempotent transaction or unique constraint.
5. If a retry occurs, inspect the job state and validate the existing artifact before deciding whether to reuse or regenerate it.

File operations and a PostgreSQL transaction are not one atomic operation, so you still need recovery logic for failures between those steps.

Senior-level interview answer:

> I would give each job a stable idempotency key and track its state in PostgreSQL. The worker would generate and validate the PDF in a temporary file, then publish it under a deterministic final name. On retry, the system would inspect the durable job state and validate any existing artifact instead of blindly regenerating it. I would also handle failures between file publication and the database commit through reconciliation or retry-safe recovery logic.

What you got right: You identified `ArrayBuffer` as a possible solution, but choosing it alone doesn't address the memory problem.

What is missing

First, investigate where memory is growing:

- Are payloads copied when sent to workers?
- Are multiple 100 MB payloads retained simultaneously?
- Is the worker queue growing without a limit?
- Are results copied back to the parent?
- Is memory retained after tasks finish?

Transferring an `ArrayBuffer` can avoid copying its underlying bytes when ownership moves to the worker. The sender's transferred buffer becomes detached and can no longer be used normally.

Also, if requests arrive faster than workers process them, transferring buffers won't solve the growing queue by itself.

Senior-level interview answer:

> I would profile RSS, heap, external memory and queue depth, then check whether payloads are copied or retained across requests and workers. For large binary data, I would consider transferring a dedicated `ArrayBuffer` to avoid an additional copy, keeping in mind that the sender loses access to the transferred buffer. I would also bound task concurrency and queue capacity so memory remains controlled under load.

## 3. Worker pool overload — 9/10

What you got right

- You recognized that concurrency must be limited.
- You connected capacity planning with load testing.
- You identified RSS, heap and external memory as useful diagnostics.

These are strong production-level instincts.

What is missing

Rate limiting and worker-pool queue limits solve related but different problems:

- Rate limiting controls how frequently requests are accepted.
- Concurrency limits control how many tasks run simultaneously.
- Queue limits cap the number of waiting tasks.
- Backpressure or rejection prevents the system from accepting more work than it can handle.

Even if request rate is limited, a queue can still grow if tasks take longer than expected. So explicitly bound the queue and define what happens when it is full—for example, reject with HTTP `429` or `503`, or defer the work through a durable queue.

Monitor queue depth, task wait time, processing time, worker utilization, rejection rate, RSS, heap, external memory, and CPU usage.

Senior-level interview answer:

> I would use load testing to establish safe throughput and concurrency, then enforce a bounded worker pool and bounded queue. When capacity is exhausted, I would apply backpressure or reject requests rather than accumulating unbounded work. I would monitor queue depth, queue wait time, task latency, worker utilization, rejection rates, CPU and memory metrics to identify whether the bottleneck is worker capacity or the workload itself.

## Key takeaway

Your strongest answer was the third one. For senior-level interviews, remember this distinction:

Limiting concurrency controls active work; bounding the queue controls waiting work; monitoring tells you whether the chosen limits are sufficient.
