## 5.11.1 — First, understand the problem these APIs solve

Imagine your Node.js application receives binary data rather than ordinary text:

- An image contains pixel bytes.
- An audio file contains encoded audio data.
- A network protocol sends binary messages.
- A Worker Thread needs to process millions of numeric values.
- Two threads need to access the same numeric data efficiently.

JavaScript strings and ordinary arrays aren't always the best representation for this data. That's where `ArrayBuffer`, Typed Arrays, and related APIs become useful.

### The basic relationship

These are related, but they solve different problems.

- `ArrayBuffer` stores raw bytes. It doesn't provide ordinary array operations by itself.
- A Typed Array, such as `Uint8Array` or `Float64Array`, interprets memory as elements of a particular numeric type.
- `DataView` provides flexible reading and writing of binary values, including explicit byte order.
- `SharedArrayBuffer` enables shared access to memory between threads; synchronization may be needed when they access the same data concurrently.

## 5.11.2 — `ArrayBuffer` and Typed Arrays in practice

Let's create a buffer containing four bytes.

```javascript
const buffer = new ArrayBuffer(4);

console.log(buffer.byteLength); // 4
```

This allocates four bytes. But how do we access those bytes?

We create a view:

```javascript
const bytes = new Uint8Array(buffer);

bytes[0] = 10;
bytes[1] = 20;
bytes[2] = 30;
bytes[3] = 40;

console.log(bytes[0]); // 10
console.log([...bytes]); // [10, 20, 30, 40]
```

Here, `Uint8Array` interprets each byte as an unsigned 8-bit integer, so each element can represent values from `0` to `255`.

Notice that `Uint8Array` does not allocate a second four-byte data block in this example. It creates a view over the existing buffer.

## 5.11.3 — Why are there different Typed Arrays?

Different types interpret the same memory differently.

| Type           | Size per element | Example use                   |
| -------------- | ---------------- | ----------------------------- |
| `Uint8Array`   | 1 byte           | Raw bytes, pixel channels     |
| `Int16Array`   | 2 bytes          | Signed 16-bit samples         |
| `Uint32Array`  | 4 bytes          | Unsigned 32-bit values        |
| `Float32Array` | 4 bytes          | Numeric and signal processing |
| `Float64Array` | 8 bytes          | Double-precision calculations |

For example:

```javascript
const buffer = new ArrayBuffer(8);

const integers = new Uint32Array(buffer);
const floats = new Float32Array(buffer);

integers[0] = 1065353216;

console.log(floats[0]); // 1
```

Both views refer to the same eight bytes. The first interprets the first four bytes as an unsigned integer; the second interprets those bytes as an IEEE 754 floating-point number.

This example assumes the platform's native Typed Array byte order, so it is best used to illustrate reinterpretation, not as a portable binary protocol format.

### When do you actually need these APIs?

For a typical Express endpoint that receives JSON and queries PostgreSQL or MongoDB, you usually don't need to create an `ArrayBuffer` manually.

They become useful when you need precise control over binary memory, numeric data representation, or efficient communication between threads.
