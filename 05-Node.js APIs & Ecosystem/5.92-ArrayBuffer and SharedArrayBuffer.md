## 5.11.1 — First, understand the problem these APIs solve

Imagine your Node.js application receives binary data rather than ordinary text:

- An image contains pixel bytes.
- An audio file contains encoded audio data.
- A network protocol sends binary messages.
- A Worker Thread needs to process millions of numeric values.
- Two threads need to access the same numeric data efficiently.

JavaScript strings and ordinary arrays aren't always the best representation for this data. That's where `ArrayBuffer`, Typed Arrays, and related APIs become useful.

### The basic relationship

<img width="998" height="432" alt="Screenshot 2026-10-31 161400" src="https://github.com/user-attachments/assets/ee85c72c-ff3f-40a7-a5ea-8087358e4915" />

These are related, but they solve different problems.

- `ArrayBuffer` stores raw bytes. It doesn't provide ordinary array operations by itself.
- A Typed Array, such as `Uint8Array` or `Float64Array`, interprets memory as elements of a particular numeric type.
- `DataView` provides flexible reading and writing of binary values, including explicit byte order.
- `SharedArrayBuffer` enables shared access to memory between threads; synchronization may be needed when they access the same data concurrently.

## 5.11.2 — `ArrayBuffer` and Typed Arrays in practice

Let's create a buffer containing four bytes.

```javascript
const buffer = new ArrayBuffer(4);

console.log(buffer.byteLength); // 4
```

This allocates four bytes. But how do we access those bytes?

We create a view:

```javascript
const bytes = new Uint8Array(buffer);

bytes[0] = 10;
bytes[1] = 20;
bytes[2] = 30;
bytes[3] = 40;

console.log(bytes[0]); // 10
console.log([...bytes]); // [10, 20, 30, 40]
```

Here, `Uint8Array` interprets each byte as an unsigned 8-bit integer, so each element can represent values from `0` to `255`.

Notice that `Uint8Array` does not allocate a second four-byte data block in this example. It creates a view over the existing buffer.

### Try it yourself

This is the basic idea behind binary data manipulation: memory contains bytes, and views provide a convenient way to interpret and modify them.

## 5.11.3 — Why are there different Typed Arrays?

Different types interpret the same memory differently.

| Type           | Size per element | Example use                   |
| -------------- | ---------------- | ----------------------------- |
| `Uint8Array`   | 1 byte           | Raw bytes, pixel channels     |
| `Int16Array`   | 2 bytes          | Signed 16-bit samples         |
| `Uint32Array`  | 4 bytes          | Unsigned 32-bit values        |
| `Float32Array` | 4 bytes          | Numeric and signal processing |
| `Float64Array` | 8 bytes          | Double-precision calculations |

For example:

```javascript
const buffer = new ArrayBuffer(8);

const integers = new Uint32Array(buffer);
const floats = new Float32Array(buffer);

integers[0] = 1065353216;

console.log(floats[0]); // 1
```

Both views refer to the same eight bytes. The first interprets the first four bytes as an unsigned integer; the second interprets those bytes as an IEEE 754 floating-point number.

This example assumes the platform's native Typed Array byte order, so it is best used to illustrate reinterpretation, not as a portable binary protocol format.

### When do you actually need these APIs?

For a typical Express endpoint that receives JSON and queries PostgreSQL or MongoDB, you usually don't need to create an `ArrayBuffer` manually.

They become useful when you need precise control over binary memory, numeric data representation, or efficient communication between threads.

## 5.11.4 — `DataView`: Reading and writing binary data

So far, we have used Typed Arrays such as `Uint8Array` and `Uint32Array`.

But imagine an external system sends you a binary message containing:

- 2 bytes for a message type.
- 4 bytes for a user ID.
- 4 bytes for a price.

You need to read different numeric types from specific byte positions.

This is where `DataView` is useful.

Unlike Typed Arrays, `DataView` lets you choose the data type and byte order for each read or write.

### Example

```javascript
const buffer = new ArrayBuffer(10);

const view = new DataView(buffer);

// Write a 16-bit unsigned integer
view.setUint16(0, 100, false);

// Write a 32-bit unsigned integer
view.setUint32(2, 12345, false);

// Write a 32-bit floating-point number
view.setFloat32(6, 99.5, false);

// Read values
console.log(view.getUint16(0, false)); // 100
console.log(view.getUint32(2, false)); // 12345
console.log(view.getFloat32(6, false)); // 99.5
```

The third argument controls byte order:

- `false` = big-endian.
- `true` = little-endian.

Big-endian stores the most significant byte first; little-endian stores the least significant byte first.

Why does this matter?

Binary protocols and file formats often specify a particular byte order. If you read the bytes using the wrong order, you may get completely incorrect values.

### Typed Array vs DataView

| Feature             | Typed Array           | DataView                          |
| ------------------- | --------------------- | --------------------------------- |
| Data interpretation | One type per view     | Multiple types per view           |
| Byte order          | Native platform order | Explicitly configurable           |
| Access              | Array-like indexing   | Getter/setter methods             |
| Best for            | Numeric arrays        | Binary protocols and file formats |

For example, use `Float32Array` for a large collection of floating-point values. Use `DataView` when parsing a binary file with different fields and offsets.

## 5.11.5 — Node.js `Buffer` vs `ArrayBuffer`

This is particularly important because you've already studied Node.js `Buffer`.

Let's distinguish them.

| Feature      | `Buffer`                             | `ArrayBuffer`                |
| ------------ | ------------------------------------ | ---------------------------- |
| Available in | Node.js                              | JavaScript runtime           |
| Purpose      | Convenient binary data handling      | Raw fixed-size binary memory |
| Common usage | Files, streams, network data, crypto | Typed Arrays, binary memory  |
| API          | Node-specific                        | Standard JavaScript          |

In Node.js, `Buffer` is a subclass of `Uint8Array`.

```javascript
const buffer = Buffer.from([10, 20, 30, 40]);

console.log(buffer instanceof Uint8Array); // true
console.log(buffer.length); // 4
console.log(buffer.byteLength); // 4
```

This means a Buffer can be used with many APIs that accept Typed Arrays.

### Buffer and ArrayBuffer share memory

Consider:

```javascript
const buffer = Buffer.from([10, 20, 30, 40]);

const arrayBuffer = buffer.buffer;

console.log(arrayBuffer.byteLength);
```

One important warning: `buffer.buffer` returns the underlying ArrayBuffer, which may be larger than the visible Buffer region.

Node.js can allocate small Buffers from a shared internal memory pool. Therefore, you should not assume that the returned ArrayBuffer contains only your four bytes.

If you need an exact, independent ArrayBuffer:

```javascript
const buffer = Buffer.from([10, 20, 30, 40]);

const exactArrayBuffer = buffer.buffer.slice(
  buffer.byteOffset,
  buffer.byteOffset + buffer.byteLength
);
```

Now you have an independent ArrayBuffer containing exactly the visible Buffer data.

### When should you use which?

- Use `Buffer` for normal Node.js file, network, stream, and crypto operations.
- Use `ArrayBuffer` and Typed Arrays when an API expects those types or you need typed numeric views.
- Use `DataView` when parsing structured binary formats with different field types and byte orders.

You don't need to replace Buffer with ArrayBuffer in ordinary backend development.

## 5.11.6 — Practical use case: Parsing a binary message

Let's combine what we've learned.

Suppose a device sends a binary message with this structure:

| Field        | Size    |
| ------------ | ------- |
| Message type | 1 byte  |
| User ID      | 4 bytes |
| Temperature  | 4 bytes |

Total = 9 bytes.

We can parse it like this:

```javascript
const buffer = new ArrayBuffer(9);
const view = new DataView(buffer);

// Simulate incoming binary message
view.setUint8(0, 1);
view.setUint32(1, 12345, false);
view.setFloat32(5, 36.5, false);

// Parse the message
const messageType = view.getUint8(0);
const userId = view.getUint32(1, false);
const temperature = view.getFloat32(5, false);

console.log({
  messageType,
  userId,
  temperature
});
```

Output:

```javascript
{
  messageType: 1,
  userId: 12345,
  temperature: 36.5
}
```

This kind of approach is useful for:

- IoT device communication.
- Custom TCP or UDP protocols.
- Parsing binary file formats.
- Audio and image processing.
- Hardware and sensor data.

## 5.11.7 — Important distinction: `ArrayBuffer` vs `SharedArrayBuffer`

Now let's move to the most interesting part.

Suppose you have a large numeric dataset and want two Worker Threads to process it.

With a normal `ArrayBuffer`, you can:

1. Copy the data to another worker.
2. Transfer ownership of the underlying ArrayBuffer to another worker.

With a `SharedArrayBuffer`, multiple workers can access the same memory.

<img width="1019" height="608" alt="Screenshot 2026-10-31 162801" src="https://github.com/user-attachments/assets/92eb9598-22b7-4a06-91fd-795c9830b7ba" />

### Example: SharedArrayBuffer

```javascript
const shared = new SharedArrayBuffer(4);

const numbers = new Int32Array(shared);

numbers[0] = 100;

console.log(numbers[0]); // 100
```

This looks similar to ArrayBuffer, but the important difference is that the underlying memory can be shared across threads.

However, sharing memory introduces a new problem: race conditions.

Imagine two workers both incrementing the same counter:

```javascript
numbers[0] = numbers[0] + 1;
```

This operation is not guaranteed to be atomic. Both workers could read the same value before either writes the incremented result, causing an update to be lost.

That's why JavaScript provides `Atomics`.

### Using Atomics

```javascript
const shared = new SharedArrayBuffer(4);
const numbers = new Int32Array(shared);

Atomics.store(numbers, 0, 100);

Atomics.add(numbers, 0, 1);

console.log(Atomics.load(numbers, 0)); // 101
```

`Atomics.add()` performs the increment atomically, so concurrent increments won't overwrite each other.

Other useful operations include:

- `Atomics.load()`
- `Atomics.store()`
- `Atomics.add()`
- `Atomics.compareExchange()`
- `Atomics.wait()` and `Atomics.notify()` (for supported integer typed-array views; `wait()` cannot be used on the main browser thread, but is available in Node.js workers).

### When should you use SharedArrayBuffer?

Consider it when:

- Multiple workers need access to a large shared dataset.
- Copying or transferring data repeatedly becomes expensive.
- You need shared counters or coordination between workers.
- You're implementing high-performance numeric processing.

For ordinary Express APIs, database queries, and JSON processing, it is usually unnecessary. Shared memory adds synchronization complexity and the possibility of race conditions.
