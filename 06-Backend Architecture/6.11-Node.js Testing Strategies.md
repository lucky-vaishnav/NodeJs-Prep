## 1. Testing tools in the Node.js ecosystem

There are several testing libraries in the Node.js ecosystem.

| Tool | Purpose |
| --- | --- |
| Jest | Test runner, assertions, mocks, coverage |
| Vitest | Modern test runner with Jest-like APIs |
| Mocha | Test runner |
| Chai | Assertion library |
| Sinon | Spies, stubs, and mocks |
| Supertest | HTTP/API testing |
| Nock | HTTP request mocking |
| mongodb-memory-server | In-memory MongoDB for tests |

For our examples, we'll primarily use Jest + Supertest.

Why?

- Jest provides a complete testing environment.
- Supertest makes Express API testing convenient.
- Jest supports asynchronous tests, mocks, spies, and coverage.
- These tools are commonly encountered in Node.js projects.

Vitest is also a good choice, particularly in modern JavaScript and TypeScript projects.

## 2. Unit testing

Unit testing means testing an individual function or small unit of application logic independently.

Consider a service:

```jsx
// services/user.service.js

function calculateDiscount(amount, percentage) {
  return amount * percentage / 100;
}

module.exports = {
  calculateDiscount
};
```

We want to test whether this function returns the expected result.

```jsx
// tests/user.service.test.js

const {
  calculateDiscount
} = require('../services/user.service');

describe('calculateDiscount', () => {
  test('should calculate discount correctly', () => {
    const result = calculateDiscount(1000, 10);

    expect(result).toBe(100);
  });

  test('should return zero for zero discount', () => {
    const result = calculateDiscount(1000, 0);

    expect(result).toBe(0);
  });
});
```

Important Jest functions:

| Function | Purpose |
| --- | --- |
| `describe()` | Groups related tests |
| `test()` / `it()` | Defines a test case |
| `expect()` | Defines an assertion |
| `beforeEach()` | Runs before every test |
| `afterEach()` | Runs after every test |
| `beforeAll()` | Runs once before the test group |
| `afterAll()` | Runs once after the test group |

### What makes a good unit test?

A good unit test should:

- Test one meaningful behavior.
- Be independent of other tests.
- Produce predictable results.
- Avoid unnecessary external dependencies.
- Cover important edge cases.

For a senior developer, the important skill is identifying the right unit to test—not simply writing more test cases.

## 3. Mocking, stubbing, and spying

This is one of the most important areas of Node.js testing.

Consider a user service:

```jsx
// services/user.service.js

const userRepository = require('../repositories/user.repository');

async function getUser(userId) {
  const user = await userRepository.findById(userId);

  if (!user) {
    throw new Error('User not found');
  }

  return user;
}

module.exports = { getUser };
```

When testing `getUser()`, we don't necessarily want to connect to a real database.

We only want to test the service logic.

So we mock the repository.

```jsx
const userRepository = require('../repositories/user.repository');
const userService = require('../services/user.service');

jest.mock('../repositories/user.repository');

describe('getUser', () => {
  afterEach(() => {
    jest.clearAllMocks();
  });

  test('should return user when found', async () => {
    userRepository.findById.mockResolvedValue({
      id: 1,
      name: 'John'
    });

    const result = await userService.getUser(1);

    expect(result.name).toBe('John');

    expect(userRepository.findById)
      .toHaveBeenCalledWith(1);
  });

  test('should throw error when user not found', async () => {
    userRepository.findById.mockResolvedValue(null);

    await expect(
      userService.getUser(1)
    ).rejects.toThrow('User not found');
  });
});
```

### Difference between mock, stub, and spy

These terms are related but have different meanings.

| Technique | Meaning |
| --- | --- |
| Stub | Replaces behavior with a controlled response |
| Mock | Provides controlled behavior and often verifies expected interactions |
| Spy | Observes calls to a function, including arguments and call count |

For example:

Stub

```jsx
jest.spyOn(userRepository, 'findById')
  .mockResolvedValue({ id: 1 });
```

Spy

```jsx
const spy = jest.spyOn(console, 'log');

console.log('Hello');

expect(spy).toHaveBeenCalledWith('Hello');
```

Mock

```jsx
const sendEmail = jest.fn()
  .mockResolvedValue(true);

await sendEmail('test@example.com');

expect(sendEmail).toHaveBeenCalledWith(
  'test@example.com'
);
```

One important distinction: `jest.fn()` creates a mock function. `jest.spyOn()` creates a spy that calls the original implementation by default unless you override it.

### Why is this important?

Suppose your application has:

```
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

When unit testing the service, you can mock the repository.

When unit testing the controller, you can mock the service.

This allows each layer to be tested independently.

## 4. Testing asynchronous Node.js code

Node.js applications heavily use Promises and `async/await`.

Jest needs to know when an asynchronous operation has completed.

Consider:

```jsx
async function getUser() {
  return {
    id: 1,
    name: 'John'
  };
}
```

Correct test:

```jsx
test('should return user', async () => {
  const result = await getUser();

  expect(result.name).toBe('John');
});
```

### Testing rejected Promises

```jsx
async function getUser() {
  throw new Error('Database unavailable');
}
```

Test:

```jsx
test('should throw error', async () => {
  await expect(getUser())
    .rejects
    .toThrow('Database unavailable');
});
```

### Common mistake

Incorrect:

```jsx
test('should return user', () => {
  getUser().then(user => {
    expect(user.name).toBe('John');
  });
});
```

The test doesn't return or await the Promise.

Jest might finish the test before the assertion executes.

Correct:

```jsx
test('should return user', async () => {
  const user = await getUser();

  expect(user.name).toBe('John');
});
```

Or:

```jsx
test('should return user', () => {
  return getUser().then(user => {
    expect(user.name).toBe('John');
  });
});
```

Interview point: Always return or await asynchronous operations in your tests.

## 5. Testing Express APIs using Supertest

This is particularly relevant to your daily Express development.

Suppose we have an Express application:

```jsx
// app.js

const express = require('express');
const userService = require('./services/user.service');

const app = express();

app.use(express.json());

app.get('/users/:id', async (req, res, next) => {
  try {
    const user = await userService.getUser(req.params.id);

    res.status(200).json(user);
  } catch (error) {
    next(error);
  }
});

module.exports = app;
```

Notice that we export the Express app separately instead of starting the HTTP server inside this file.

Why?

Because we want to test the application without binding it to a specific port.

Our actual server entry point can be separate:

```jsx
// server.js

const app = require('./app');

app.listen(3000, () => {
  console.log('Server started');
});
```

### Install Supertest

```
npm install --save-dev supertest jest
```

### API test

```jsx
const request = require('supertest');
const app = require('../app');

const userService = require('../services/user.service');

jest.mock('../services/user.service');

describe('GET /users/:id', () => {
  afterEach(() => {
    jest.clearAllMocks();
  });

  test('should return user', async () => {
    userService.getUser.mockResolvedValue({
      id: 1,
      name: 'John'
    });

    const response = await request(app)
      .get('/users/1');

    expect(response.status).toBe(200);

    expect(response.body.name).toBe('John');
  });

  test('should handle service failure', async () => {
    userService.getUser.mockRejectedValue(
      new Error('Database error')
    );

    const response = await request(app)
      .get('/users/1');

    // Assumes the application has error middleware
    // that converts this error into HTTP 500.
    expect(response.status).toBe(500);
  });
});
```

Supertest can invoke your Express app directly and manage the HTTP test request.

You don't need to manually start a server on port 3000 for this example.

### What should we test in Express APIs?

- Correct HTTP status codes.
- Response structure.
- Request validation.
- Authentication and authorization.
- Missing resources.
- Business rule failures.
- Database or service failures.
- Middleware behavior.
- Invalid request payloads.

For a senior developer, testing the negative scenarios is just as important as testing the successful response.

## 6. Database integration testing

Unit tests usually mock database dependencies.

But mocking alone cannot verify that your actual database queries work correctly.

For that, we need integration tests.

Example:

```jsx
describe('User repository integration', () => {
  beforeAll(async () => {
    await connectTestDatabase();
  });

  afterAll(async () => {
    await disconnectTestDatabase();
  });

  beforeEach(async () => {
    await User.deleteMany({});
  });

  test('should create and retrieve user', async () => {
    const createdUser = await User.create({
      name: 'John',
      email: 'john@example.com'
    });

    const user = await User.findById(createdUser._id);

    expect(user.name).toBe('John');
  });
});
```

Here, we're testing actual database operations rather than mocking them.

### MongoDB integration testing

One option is `mongodb-memory-server`.

It starts a temporary MongoDB instance for testing.

```
npm install --save-dev mongodb-memory-server
```

Example:

```jsx
const mongoose = require('mongoose');
const { MongoMemoryServer } = require('mongodb-memory-server');

let mongoServer;

beforeAll(async () => {
  mongoServer = await MongoMemoryServer.create();

  await mongoose.connect(mongoServer.getUri());
});

afterAll(async () => {
  await mongoose.disconnect();

  await mongoServer.stop();
});
```

This allows database integration tests without connecting to your actual development or production database.

Note: `mongodb-memory-server` may download a MongoDB binary, so CI environments need the appropriate binary availability and permissions.

### PostgreSQL integration testing

For PostgreSQL, common options include:

- Dedicated test database.
- Docker-based PostgreSQL instance.
- Testcontainers.
- Transaction rollback between tests, where appropriate.

A good practice is to isolate test data so one test cannot affect another.

## 7. Testing external APIs

Imagine your service integrates with an external payment provider.

```jsx
async function processPayment(paymentData) {
  const response = await axios.post(
    'https://payment-provider.com/payments',
    paymentData
  );

  return response.data;
}
```

We don't want unit tests to make actual payment requests.

Instead, mock the external dependency.

```jsx
jest.mock('axios');

test('should process payment', async () => {
  axios.post.mockResolvedValue({
    data: {
      paymentId: 'PAY123',
      status: 'SUCCESS'
    }
  });

  const result = await processPayment({
    amount: 1000
  });

  expect(result.status).toBe('SUCCESS');
});
```

This gives predictable test behavior and prevents accidental external transactions.

For HTTP-level request interception, tools such as Nock are also useful.

### Important production-testing distinction

Mocking an external API doesn't verify that your actual integration still matches the provider's API contract.

For that, consider:

- Contract tests.
- Provider sandbox environments.
- Controlled end-to-end tests.

Don't rely entirely on mocks for third-party integrations.

## 8. Testing timers and scheduled operations

Node.js applications sometimes use:

- `setTimeout()`
- `setInterval()`
- Delayed retries
- Scheduled jobs
- Token expiration logic

Waiting for real time in tests is inefficient.

Jest provides fake timers.

Example:

```jsx
function scheduleTask(callback) {
  setTimeout(callback, 5000);
}
```

Test:

```jsx
test('should execute callback after 5 seconds', () => {
  jest.useFakeTimers();

  const callback = jest.fn();

  scheduleTask(callback);

  expect(callback).not.toHaveBeenCalled();

  jest.advanceTimersByTime(5000);

  expect(callback).toHaveBeenCalledTimes(1);

  jest.useRealTimers();
});
```

This allows you to control time without actually waiting five seconds.

Be careful with async timers and Promise scheduling: advancing timers and flushing microtasks are separate concerns. Use the asynchronous fake-timer APIs when the scheduled callbacks themselves perform asynchronous work.

## 9. Test isolation and cleanup

One common problem in Node.js test suites is tests interfering with each other.

For example:

- Test A creates a user.
- Test B expects an empty database.
- Test B fails because Test A's data still exists.

Use proper setup and cleanup.

| Hook | Common purpose |
| --- | --- |
| `beforeAll` | Initialize database or test server |
| `afterAll` | Close database connections |
| `beforeEach` | Reset test data |
| `afterEach` | Clear mocks and restore spies |

### Difference between Jest mock cleanup methods

This is a useful senior-level detail.

| Method | Behavior |
| --- | --- |
| `jest.clearAllMocks()` | Clears call history and results |
| `jest.resetAllMocks()` | Clears history and resets mock implementations |
| `jest.restoreAllMocks()` | Restores original implementations for spies and replaced properties |

Don't use these interchangeably.

For example, `clearAllMocks()` does not remove a mock implementation that you configured earlier.

### Test isolation and parallel execution

Jest can execute test files in parallel.

That can create issues if multiple test files share:

- The same database records.
- The same Redis queue.
- The same fixed port.
- Global mutable state.

Possible solutions:

- Use unique test data.
- Give test suites isolated databases or schemas.
- Use unique queue names.
- Avoid shared global state.
- Control test execution when isolation cannot be guaranteed.

## 10. Code coverage

Code coverage tells you how much of your code is executed by tests.

Jest supports:

```
npx jest --coverage
```

It reports metrics such as:

| Metric | Meaning |
| --- | --- |
| Statements | Executable statements executed |
| Branches | Conditional branches executed |
| Functions | Functions called |
| Lines | Source lines executed |

For example, consider:

```jsx
function getDiscount(amount) {
  if (amount > 1000) {
    return 10;
  }

  return 0;
}
```

If your tests only use `amount = 2000`, you've covered the true branch but not the false branch.

A branch-coverage report helps identify that missing case.

Important: High code coverage does not automatically mean good tests.

A test can execute a function without actually verifying meaningful behavior.

Focus on testing important business behavior and edge cases, not simply maximizing a percentage.

## 11. A practical Node.js testing structure

For a medium-sized Express application, you could organize tests like this:

```
src/
  controllers/
  services/
  repositories/
  routes/
  models/
  app.js
  server.js

tests/
  unit/
    services/
    utilities/

  integration/
    repositories/
    database/

  api/
    users.test.js
    reservations.test.js

  mocks/
    user.repository.mock.js

  setup/
    database.js
    test-environment.js
```

A useful distinction:

- Unit tests: Test individual business logic units.
- Integration tests: Test interaction between components, such as repository and database.
- API tests: Test actual HTTP behavior through Express.
- End-to-end tests: Test a complete user or business flow across multiple real components.

We don't need to write an end-to-end test for every function. Choose the test level based on what could realistically fail.

## 12. Common mistakes in Node.js testing

| Mistake | Problem |
| --- | --- |
| Not awaiting Promises | Tests may finish before assertions execute |
| Mocking everything | Real integration problems remain undetected |
| Sharing test database state | Tests become order-dependent |
| Not closing DB connections | Jest may hang after tests finish |
| Testing only successful cases | Error handling and edge cases remain untested |
| Overusing implementation-specific assertions | Refactoring becomes unnecessarily difficult |
| Using real external APIs | Tests become slow, expensive, and unpredictable |
| Ignoring timer behavior | Time-dependent logic may fail unexpectedly |
| Treating code coverage as test quality | High coverage can still miss important bugs |
| Excessive mocking | Tests can become disconnected from actual behavior |

## 14. Key takeaways for your notes

- Use Jest or Vitest for Node.js testing.
- Use unit tests to validate isolated business logic.
- Mock repositories when testing services independently.
- Always await or return asynchronous operations in tests.
- Use Supertest for Express API testing.
- Use a dedicated test database for integration tests.
- Mock external APIs in unit tests; use sandbox or contract tests for integration confidence.
- Use fake timers for scheduled and time-dependent logic.
- Keep test data and external resources isolated.
- Close database connections, workers, and servers after testing.
- Code coverage is useful, but meaningful assertions matter more.
