# Phase 6.1 — Node.js Backend Architecture Fundamentals

## 1. What do we mean by backend architecture?

Backend architecture is how we organize the application so that different responsibilities are handled by appropriate components.

For example, consider an API:

```
POST /api/orders
```

It needs to:

1. Receive the HTTP request.
2. Validate the request data.
3. Authenticate and authorize the user.
4. Execute business logic.
5. Interact with the database.
6. Return an appropriate response.
7. Handle errors consistently.

The important question is:

Should all this logic live inside the route handler?

No. As the application grows, putting everything in one place makes the code difficult to maintain, test, debug, and extend.

We need clear separation of responsibilities.

## 2. Common architectural layers

A typical Node.js backend application can be divided into these layers:

Let's understand the responsibility of each layer.

| Layer      | Main responsibility                       |
| ---------- | ----------------------------------------- |
| Routes     | Define API endpoints and connect handlers |
| Middleware | Handle cross-cutting request processing   |
| Controller | Handle HTTP input and output              |
| Service    | Implement business rules and workflows    |
| Repository | Encapsulate database operations           |
| Database   | Persist application data                  |

These are logical boundaries. They don't necessarily need to be separate servers, packages, or even files in a small application.

## 3. Practical implementation using Express

Let's implement a simple order creation API.

### Suggested project structure

```
src/
├── config/
│   └── database.js
│
├── modules/
│   └── order/
│       ├── order.routes.js
│       ├── order.controller.js
│       ├── order.service.js
│       └── order.repository.js
│
├── middleware/
│   ├── auth.middleware.js
│   └── error.middleware.js
│
├── utils/
│   └── AppError.js
│
├── app.js
└── server.js
```

Notice that we are organizing the application by feature/module, rather than keeping all controllers in one folder, all services in another, and so on.

We'll discuss project organization and its trade-offs in more detail later.

### A. Route layer

`order.routes.js`

```javascript
const express = require('express');
const router = express.Router();

const orderController = require('./order.controller');

router.post('/', orderController.createOrder);

module.exports = router;
```

The route only defines the endpoint and delegates the request.

It should not contain database queries or business rules.

### B. Controller layer

`order.controller.js`

```javascript
const orderService = require('./order.service');

exports.createOrder = async (req, res, next) => {
  try {
    const result = await orderService.createOrder({
      userId: req.user.id,
      items: req.body.items
    });

    return res.status(201).json({
      success: true,
      data: result
    });
  } catch (error) {
    next(error);
  }
};
```

The controller:

- Reads HTTP request data.
- Passes the required information to the service.
- Converts the result into an HTTP response.
- Passes errors to Express error handling.

It should not decide how the order is created internally.

### C. Service layer

`order.service.js`

```javascript
const orderRepository = require('./order.repository');

exports.createOrder = async ({ userId, items }) => {
  if (!items || items.length === 0) {
    throw new Error('Order must contain at least one item');
  }

  const totalAmount = items.reduce(
    (total, item) => total + item.price * item.quantity,
    0
  );

  const order = await orderRepository.create({
    userId,
    items,
    totalAmount
  });

  return order;
};
```

The service contains business logic.

For example:

- Checking whether an order can be created.
- Calculating the total amount.
- Applying discounts.
- Checking business rules.
- Coordinating multiple operations.

In a real application, we would use proper domain errors and validate prices against trusted product data rather than trusting prices supplied by the client.

### D. Repository layer

`order.repository.js`

```javascript
const Order = require('../../models/order.model');

exports.create = async (orderData) => {
  return Order.create(orderData);
};
```

The repository encapsulates database operations.

The service doesn't need to know whether the data is stored using Mongoose, Sequelize, Prisma, or a raw SQL query.

That separation can make testing and database changes easier.

## 4. How does the request flow work?

For this API, the request lifecycle looks like this:

1. Express receives `POST /api/orders`.
2. The route matches the endpoint.
3. Authentication and other middleware run.
4. The controller extracts the required data.
5. The service executes the business logic.
6. The repository interacts with the database.
7. The result travels back to the controller.
8. The controller sends the HTTP response.

If an error occurs, it should travel to centralized error handling rather than every layer independently formatting HTTP responses.

## 5. Important architectural decisions

### Should the controller contain business logic?

Generally, no. Keep controllers thin so that HTTP concerns remain separate from business rules.

### Should services directly query the database?

They can, especially in smaller applications. A separate repository layer is useful when it creates a meaningful boundary, but it is not mandatory for every service.

### Should every API have its own service?

Not necessarily. Services should represent meaningful application operations or business capabilities, not just exist to satisfy a folder structure.

### Does this architecture apply to NestJS?

Yes. NestJS provides more built-in structure:

| Express                  | NestJS                         |
| ------------------------ | ------------------------------ |
| Routes                   | Controllers and decorators     |
| Middleware               | Middleware                     |
| Controller functions     | Controller classes             |
| Services                 | Injectable providers           |
| Manual dependency wiring | Dependency injection container |
| Error middleware         | Exception filters              |

The underlying separation-of-responsibility principles are similar.

## 6. Common mistakes

1. Putting database queries and business logic directly in controllers.
2. Creating unnecessary layers for every small operation.
3. Making services depend heavily on Express `req` and `res` objects.
4. Duplicating business rules across multiple controllers.
5. Making repositories responsible for business decisions.
6. Building a complex folder structure without clear responsibility boundaries.

Senior-level takeaway: Good architecture is not about having the maximum number of layers. It is about keeping responsibilities clear and dependencies manageable without introducing unnecessary complexity.
