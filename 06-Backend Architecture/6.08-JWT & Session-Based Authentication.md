## 6.7 — JWT & Session-Based Authentication

This is one of the most important topics for a senior Node.js backend developer. You'll encounter JWT and sessions in Express, NestJS, microservices, mobile applications, and enterprise authentication systems.

We'll cover both approaches, their internal working, implementation, security, production trade-offs, and common interview scenarios.

### 1. Why do we need JWT or sessions?

After a user logs in, the backend needs a way to recognize that user on subsequent API requests.

HTTP is stateless. Each request is independent, so the server doesn't automatically remember who made the previous request.

For example:

1. User logs in with email and password.
2. Backend verifies credentials.
3. User requests `/api/profile`.
4. Backend needs to identify the user without asking for their password again.

Two common approaches solve this:

- Session-based authentication: The server stores authentication state and gives the client a session identifier.
- Token-based authentication: The server issues a signed token that the client presents on subsequent requests.

The key architectural difference: a traditional session requires server-side session state, whereas a self-contained JWT can be validated without looking up a session on every request.

### 2. JWT — JSON Web Token

A JWT is a compact token format used to securely transmit claims between parties.

A JWT typically consists of three parts:

```
xxxxx.yyyyy.zzzzz
  |      |      |
Header Payload Signature
```

Example decoded structure:

Header

```
{
  "alg": "HS256",
  "typ": "JWT"
}
```

- `alg`: Signing algorithm.
- `typ`: Token type.

Payload

```jsx
{
  "sub": "user_123",
  "email": "user@example.com",
  "role": "ADMIN",
  "iat": 1794052800,
  "exp": 1794056400
}
```

Common claims:

| Claim | Meaning |
| --- | --- |
| `sub` | Subject, usually user ID |
| `iat` | Issued at |
| `exp` | Expiration time |
| `iss` | Token issuer |
| `aud` | Intended audience |
| `jti` | Unique token identifier |

Signature

The signature is generated using the header, payload, and signing key.

Conceptually:

```jsx
signature = Sign(
    base64url(header) + "." + base64url(payload),
    secretKey
)
```

The server verifies this signature to determine whether the token has been modified and whether it was signed by a trusted issuer.

### 3. Important: JWT is signed, not encrypted

This is a very common interview question.

A standard signed JWT provides integrity and authenticity, not confidentiality.

Anyone who obtains the token can decode its header and payload.

For example, this is unsafe:

```jsx
{
  "email": "user@example.com",
  "password": "myPassword123",
  "creditCard": "..."
}
```

Never put passwords, payment credentials, or other sensitive information inside a normal JWT payload.

If you need confidentiality, use an appropriate encryption mechanism such as JWE, or preferably keep sensitive information on the server.

### 5. JWT implementation in Express

Let's implement a simplified example using the `jsonwebtoken` package.

Install:

```jsx
npm install jsonwebtoken
```

Generate an access token

```jsx
const jwt = require('jsonwebtoken');

function generateAccessToken(user) {
    return jwt.sign(
        {
            role: user.role
        },
        process.env.JWT_SECRET,
        {
            subject: user.id.toString(),
            expiresIn: '15m',
            issuer: 'my-api',
            audience: 'my-application'
        }
    );
}
```

Here:

- `subject` identifies the user.
- `expiresIn` sets the expiration.
- `issuer` identifies the token issuer.
- `audience` identifies the intended recipient.

Verify the token

```jsx
function authenticate(req, res, next) {
    try {
        const authHeader = req.headers.authorization;

        const token = authHeader?.startsWith('Bearer ')
            ? authHeader.slice(7)
            : null;

        if (!token) {
            return res.status(401).json({
                message: 'Authentication required'
            });
        }

        const decoded = jwt.verify(
            token,
            process.env.JWT_SECRET,
            {
                algorithms: ['HS256'],
                issuer: 'my-api',
                audience: 'my-application'
            }
        );

        req.user = {
            id: decoded.sub,
            role: decoded.role
        };

        next();

    } catch (error) {
        if (
            error instanceof jwt.TokenExpiredError ||
            error instanceof jwt.JsonWebTokenError
        ) {
            return res.status(401).json({
                message: 'Invalid or expired token'
            });
        }

        next(error);
    }
}
```

Use it in routes:

```jsx
app.get('/api/profile', authenticate, getProfile);
```

One production consideration: if you use multiple services or different token issuers, validate the expected algorithm, issuer, and audience explicitly. Never trust the algorithm specified by an untrusted token without enforcing your own allowed algorithms.

### 6. Access token vs refresh token

This is one of the most important JWT topics.

A common mistake is generating a JWT with a long expiration, such as 30 days, and using it for every API request.

If that token is stolen, the attacker may have access for the entire validity period.

A better architecture uses two tokens.

Access token

- Used to access protected APIs.
- Short-lived.
- Usually valid for 5–15 minutes, depending on risk and application requirements.
- Sent with normal API requests.

Refresh token

- Used to obtain a new access token.
- Longer-lived.
- Should be protected more carefully.
- Should be revocable and rotated.

Example:

```
Login
  |
  v
Access Token  → 15 minutes
Refresh Token → 7 days
```

These durations are examples, not universal requirements.

### 7. Refresh token rotation and reuse detection

Suppose a refresh token is stolen.

If the attacker and legitimate user both use the same refresh token, both may be able to obtain new access tokens unless the system has additional protections.

Refresh token rotation addresses this.

Example:

```
Initial login
    |
    v
Refresh Token A
    |
    | Used to refresh
    v
Access Token B + Refresh Token B
    |
    | Refresh Token A is invalidated
    v
Next refresh
    |
    v
Access Token C + Refresh Token C
```

The backend maintains the state of the refresh-token family.

If an already-used refresh token is presented again, it may indicate token theft or replay.

The server can then revoke the active token family and require the user to authenticate again.

This is particularly useful for applications handling sensitive operations.

### 8. JWT revocation — what happens when a token is stolen?

A common interview question:

If JWT is stateless, how can we invalidate it before expiration?

This is a major trade-off.

A JWT remains cryptographically valid until its expiry unless the server has an additional revocation mechanism.

Possible approaches:

| Approach | How it works |
| --- | --- |
| Short-lived access tokens | Reduce the exposure window |
| Token denylist | Store revoked token IDs |
| Token version | Compare token version against user state |
| Session-based refresh control | Revoke refresh sessions |
| Signing key rotation | Invalidate tokens signed by old keys, depending on key strategy |

For example, a token might contain:

```
{
  "sub": "user_123",
  "tokenVersion": 2
}
```

The server compares the claim against the user's current token version.

If the database says the current version is `3`, the token is rejected.

However, this requires a database or cache lookup, so authentication is no longer completely stateless.

Senior-level takeaway: Stateless JWT validation improves independent verification, but immediate revocation requires some server-side state or key-management action.

## 9. Session-based authentication

Now let's understand the other approach.

In session-based authentication, the server maintains the user's authentication state.

After login:

1. Backend verifies the credentials.
2. Backend creates a session.
3. Session data is stored server-side.
4. Client receives a session ID in a cookie.
5. Client sends that cookie with subsequent requests.
6. Server looks up the session and identifies the user.

Example session data:

```jsx
{
  "sessionId": "abc123",
  "userId": "user_123",
  "role": "ADMIN",
  "createdAt": "2026-11-07T10:00:00Z",
  "expiresAt": "2026-11-07T18:00:00Z"
}
```

The session ID is just an identifier. The actual session data stays on the server.

### 10. Express session implementation

Install:

```
npm install express-session
```

Basic configuration:

```jsx
const session = require('express-session');

app.use(session({
    name: 'app.sid',
    secret: process.env.SESSION_SECRET,
    resave: false,
    saveUninitialized: false,
    cookie: {
        httpOnly: true,
        secure: true,
        sameSite: 'lax',
        maxAge: 60 * 60 * 1000
    }
}));
```

After successful login:

```jsx
app.post('/login', async (req, res, next) => {
    try {
        const user = await authService.login(req.body);

        req.session.regenerate(error => {
            if (error) return next(error);

            req.session.userId = user.id;

            req.session.save(error => {
                if (error) return next(error);

                res.json({
                    message: 'Login successful'
                });
            });
        });

    } catch (error) {
        next(error);
    }
});
```

The session ID is automatically managed through the session cookie.

For logout:

```jsx
app.post('/logout', (req, res, next) => {
    req.session.destroy(error => {
        if (error) return next(error);

        res.clearCookie('app.sid');
        res.json({ message: 'Logged out' });
    });
});
```

Important production warning: Express's default `MemoryStore` is not suitable for production. It doesn't provide a scalable, durable shared session store and can cause memory growth.

Use a shared session store such as Redis or a supported database-backed store.

### 11. How session storage works in a distributed application

Imagine you have three Node.js instances behind a load balancer.

```
              Load Balancer
              /     |     \
             /      |      \
           App 1   App 2   App 3
             \      |      /
              \     |     /
                Redis
             Session Store
```

Why Redis?

Suppose the user logs in through App 1 and their session is stored only in App 1's memory.

Their next request may go to App 2.

App 2 won't know about the session.

A shared Redis session store solves this by allowing every application instance to access the same session data.

Sticky sessions can route requests to the same instance, but they don't provide the same resilience and shared-state benefits.

### 12. Cookie security

Both JWT and session identifiers can be delivered through cookies, although the security considerations differ.

Important cookie attributes:

| Attribute | Purpose |
| --- | --- |
| `HttpOnly` | Prevents JavaScript from reading the cookie |
| `Secure` | Sends cookie only over HTTPS |
| `SameSite` | Controls cross-site cookie sending |
| `Max-Age` | Controls cookie lifetime |
| `Path` | Restricts cookie path |
| `Domain` | Controls eligible domains |

A common secure session cookie:

```jsx
cookie: {
    httpOnly: true,
    secure: true,
    sameSite: 'lax',
    maxAge: 3600000
}
```

Important details:

- `HttpOnly` helps reduce cookie theft through JavaScript, but doesn't prevent XSS itself.
- `Secure` should be enabled in HTTPS production environments.
- `SameSite` helps reduce CSRF risk, but is not a universal CSRF solution.
- For cross-site cookie use cases, `SameSite=None` generally requires `Secure`.

### 13. CSRF vs XSS

These are frequently confused.

CSRF — Cross-Site Request Forgery

An attacker tricks a user's browser into sending an authenticated request to a website where the user is already logged in.

For example, the browser automatically sends a session cookie with a malicious cross-site request.

Protection includes:

- Appropriate `SameSite` cookie settings.
- CSRF tokens where required.
- Origin/Referer validation as an additional defense.
- Avoiding state-changing GET requests.

XSS — Cross-Site Scripting

An attacker injects malicious JavaScript into a page viewed by another user.

That script may steal data or perform actions using the user's browser privileges.

Protection includes:

- Context-aware output encoding.
- Safe rendering of user-controlled HTML.
- Content Security Policy (CSP).
- Avoiding unsafe DOM operations.
- Using `HttpOnly` cookies to reduce direct cookie theft.

Quick comparison

CSRF

Abuses browser credentials

Tricks the browser into sending an authenticated request.

XSS

Injects malicious script

Executes attacker-controlled JavaScript in a trusted page.

## 14. JWT vs Session — Detailed comparison

This is an important interview and architecture discussion.

| Area | JWT | Session |
| --- | --- | --- |
| Authentication state | Often carried in token | Stored server-side |
| Server-side lookup | Not required for basic verification | Required |
| Revocation | Requires additional mechanism or expiry | Usually straightforward |
| Horizontal scaling | Easy signature verification across instances | Requires shared session store or affinity |
| Token/session size | Claims travel with requests | Usually a small session ID |
| User role changes | Existing claims can become stale | Can reflect updated session/user state |
| Logout | Requires token/session strategy | Destroy server-side session |
| Best fit | Distributed API authentication | Server-managed browser authentication |

Neither is universally better.

For example:

- A traditional web application may benefit from server-side sessions.
- A mobile API may use short-lived access tokens and refresh-token rotation.
- An enterprise application may delegate identity to an OIDC provider and maintain its own authorization rules.

### 15. Symmetric vs asymmetric JWT signing

Another important senior-level topic.

Symmetric signing — HS256

The same secret is used for signing and verification.

```
Service A ── Secret Key ── Service B
```

Advantages:

- Simple.
- Fast.
- Suitable for applications with a shared trusted boundary.

Disadvantage:

- Every service that can verify the token also has the secret needed to create valid tokens.

Asymmetric signing — RS256 / ES256

There is a private key and a public key.

```
Identity Service
   |
   | Signs using private key
   v
JWT
   |
   v
Backend Services
   |
   | Verify using public key
   v
Valid / Invalid
```

Advantages:

- Only the trusted issuer needs the private key.
- Other services can verify using public keys.
- Public keys can be distributed through a JWKS endpoint.

This is particularly useful in microservice and enterprise authentication architectures.

For a distributed system, asymmetric signing is often preferable when multiple independent services need to verify tokens but should not be able to issue them.

## 16. Production security checklist

Before deploying JWT or session-based authentication, consider:

| Area | Recommendation |
| --- | --- |
| Passwords | Argon2id or bcrypt |
| Access token | Short lifetime |
| Refresh token | Secure storage, rotation and revocation |
| JWT signing | Strong keys and explicit algorithm validation |
| JWT claims | Validate expiry, issuer and audience |
| Cookies | HttpOnly, Secure, appropriate SameSite |
| Sessions | Shared production store such as Redis |
| Logout | Revoke session or refresh-token state |
| CSRF | Appropriate CSRF defenses for cookie-authenticated requests |
| XSS | Output encoding, CSP, safe rendering |
| HTTPS | Required for sensitive authentication traffic |
| Monitoring | Detect suspicious login and token reuse patterns |

### 17. Common production mistakes

1. Using long-lived access tokens without a revocation strategy.
2. Storing JWTs in browser localStorage without considering XSS exposure.
3. Assuming JWT payloads are encrypted.
4. Using the same secret across unrelated environments.
5. Not validating issuer and audience.
6. Keeping refresh tokens indefinitely valid.
7. Using Express MemoryStore in production.
8. Forgetting to regenerate session IDs after login.
9. Assuming logout automatically invalidates an already-issued JWT.
10. Not implementing CSRF protection for cookie-based authentication where required.

A useful additional point: browser-based applications should carefully evaluate whether tokens need to be accessible to JavaScript at all. An HttpOnly cookie-based design can reduce token exposure to XSS, but requires appropriate CSRF defenses and cookie configuration.

## 18. Which approach would you choose?

Consider these scenarios:

| Scenario | Possible choice |
| --- | --- |
| Traditional server-rendered web application | Session-based |
| Mobile application with backend APIs | Short-lived JWT + refresh-token mechanism |
| Multiple backend services verifying identity | Asymmetric JWT / OIDC |
| Enterprise SSO | OIDC or SAML integration |
| Internal application with centralized session control | Session-based with Redis |
| Public API for external integrations | OAuth 2.0 or scoped API credentials |

A senior developer should not choose JWT just because it is popular or because the application uses microservices.

Choose based on:

- Revocation requirements.
- Security requirements.
- Application clients.
- Number of services.
- Operational complexity.
- User experience.

## 19. Senior-level interview questions

Q1. Why is JWT considered stateless?

Because a service can validate a self-contained signed token using its trusted key without looking up session state for basic authentication. However, adding token revocation or version checks introduces server-side state.

Q2. What happens if an access token is stolen?

An attacker may use it until it expires or is otherwise rejected. Short-lived access tokens, refresh-token rotation, secure storage, and revocation mechanisms reduce the risk.

Q3. Why do we need refresh tokens?

They allow clients to obtain new access tokens without repeatedly asking users to enter credentials. They should be protected and managed with rotation and revocation.

Q4. Why use Redis for session storage?

Redis provides a shared session store accessible by multiple application instances, avoiding reliance on individual process memory.

Q5. What is the difference between JWT and encryption?

A standard JWT is generally signed, not encrypted. Its signature protects integrity and establishes authenticity, but its payload can be decoded.

Q6. Can we immediately invalidate a JWT?

Not with signature verification alone. You need additional state, such as a denylist, token version, or refresh-session revocation, or a key rotation strategy that invalidates the relevant tokens.

Q7. What is the difference between HS256 and RS256?

HS256 uses one shared secret for signing and verification. RS256 uses a private key for signing and a corresponding public key for verification.

Q8. Why is storing JWT in localStorage risky?

JavaScript can access localStorage. If an attacker exploits XSS, they may steal the token. HttpOnly cookies reduce direct JavaScript access, though they introduce CSRF considerations.

Q9. Why regenerate a session ID after login?

To prevent session fixation, where an attacker attempts to make a victim authenticate using a session identifier already known to the attacker.

Q10. Is JWT always better for microservices?

No. JWT can simplify independent verification, but session-based or centralized identity approaches can also work. The decision depends on service trust boundaries, revocation needs, and operational requirements.
