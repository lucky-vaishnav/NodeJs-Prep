# Phase 6.10 — Background Jobs & Queue Implementation in Node.js

This topic is about implementing background processing in Node.js applications.

You've already studied event-driven architecture, asynchronous programming, Worker Threads, and `child_process`. We'll build on those concepts rather than repeat them.

We'll use BullMQ + Redis for practical examples because BullMQ is widely used in Node.js applications.

## 1. Why do we need background jobs?

Imagine your Express application receives a request to create a parking reservation.

After creating the reservation, it also needs to:

- Send a confirmation email.
- Generate a PDF receipt.
- Notify another service.
- Update an analytics record.

A simple implementation might look like this:

```jsx
app.post('/reservations', async (req, res) => {
  const reservation = await createReservation(req.body);

  await sendConfirmationEmail(reservation);
  await generateReceipt(reservation);
  await notifyExternalService(reservation);

  res.status(201).json(reservation);
});
```

The problem is that the HTTP response waits for all these operations.

If the email provider takes 3 seconds and the PDF generation takes 2 seconds, the request can remain open much longer than necessary.

Instead, we can move non-immediate work into background jobs.

```jsx
app.post('/reservations', async (req, res) => {
  const reservation = await createReservation(req.body);

  await emailQueue.add('send-confirmation', {
    reservationId: reservation.id
  });

  res.status(201).json(reservation);
});
```

Now the request doesn't need to wait for the email to be sent.

A separate worker processes the job.

## 2. How background job processing works

<img width="995" height="676" alt="Screenshot 2026-11-08 230142" src="https://github.com/user-attachments/assets/b94022bb-4041-4be9-ae86-136707ebc836" />

There are three important components:

1. Producer: Creates and submits jobs.
2. Queue: Holds jobs until they are processed.
3. Worker: Executes the job's business logic.

The producer and worker don't need to run in the same Node.js process. They can be separate applications or processes.

This separation is useful because API traffic and background processing can be managed independently.

## 3. Background jobs vs Promises vs Worker Threads

These concepts are related, but they solve different problems.

| Technology | Main purpose |
| --- | --- |
| Promise / `async-await` | Manage asynchronous operations |
| Background queue | Persist and process work outside the request lifecycle |
| Worker Threads | Execute CPU-intensive JavaScript in separate threads |
| `child_process` | Run external programs or separate processes |
| BullMQ | Manage persistent jobs and worker processing using Redis |

An important distinction:

A Promise does not make work durable.

Consider:

```jsx
sendEmail().catch(console.error);
```

If the Node.js process crashes before the operation finishes, the work may be lost.

A queue provides a persisted job record that can be picked up by a worker after a restart, subject to the queue's Redis persistence and recovery configuration.

Also, background processing doesn't automatically mean CPU work is executed in parallel. A BullMQ worker running JavaScript on the main thread can still block its own event loop.

For CPU-intensive tasks, consider Worker Threads or separate processes.

## 4. BullMQ — basic implementation

Install the packages:

```jsx
npm install bullmq ioredis
```

We'll organize the implementation like this:

```
src/
  config/
    redis.js

  queues/
    email.queue.js

  workers/
    email.worker.js

  services/
    email.service.js

  app.js
```

### Step 1: Redis connection

`config/redis.js`

```jsx
const IORedis = require('ioredis');

const connection = new IORedis({
  host: process.env.REDIS_HOST,
  port: Number(process.env.REDIS_PORT),
  maxRetriesPerRequest: null
});

module.exports = connection;
```

BullMQ workers require an appropriate Redis connection configuration. In particular, `maxRetriesPerRequest: null` is commonly used for worker connections.

For production, also configure authentication, TLS where needed, connection lifecycle handling, and environment-specific settings.

### Step 2: Create a queue

`queues/email.queue.js`

```jsx
const { Queue } = require('bullmq');
const connection = require('../config/redis');

const emailQueue = new Queue('email-queue', {
  connection,
  defaultJobOptions: {
    attempts: 3,
    backoff: {
      type: 'exponential',
      delay: 2000
    },
    removeOnComplete: 1000,
    removeOnFail: 5000
  }
});

module.exports = emailQueue;
```

Let's understand the important options.

| Option | Meaning |
| --- | --- |
| `attempts` | Maximum processing attempts |
| `backoff` | Delay strategy between retries |
| `exponential` | Increases delay between attempts |
| `removeOnComplete` | Retains a limited number of completed jobs |
| `removeOnFail` | Retains a limited number of failed jobs |

With three attempts and a 2-second exponential backoff, the retry delays are approximately 2 seconds and 4 seconds before subsequent attempts.

The exact job lifecycle and retry behavior are managed by BullMQ.

### Step 3: Add a job from Express

```jsx
const emailQueue = require('./queues/email.queue');

app.post('/reservations', async (req, res, next) => {
  try {
    const reservation = await createReservation(req.body);

    await emailQueue.add('send-confirmation', {
      reservationId: reservation.id,
      email: reservation.email
    });

    res.status(201).json({
      success: true,
      reservation
    });
  } catch (error) {
    next(error);
  }
});
```

Notice that we pass identifiers and the data needed by the worker, rather than passing functions or complex application objects.

The worker can retrieve the latest reservation data from the database using its ID.

### Step 4: Create a worker

`workers/email.worker.js`

```jsx
const { Worker } = require('bullmq');
const connection = require('../config/redis');
const sendEmail = require('../services/email.service');

const worker = new Worker(
  'email-queue',
  async (job) => {
    if (job.name === 'send-confirmation') {
      await sendEmail({
        email: job.data.email,
        reservationId: job.data.reservationId
      });
    }
  },
  {
    connection,
    concurrency: 5
  }
);

worker.on('completed', (job) => {
  console.log(`Job ${job.id} completed`);
});

worker.on('failed', (job, error) => {
  console.error(`Job ${job?.id} failed`, error);
});

module.exports = worker;
```

The worker listens for jobs in `email-queue` and executes the processor function.

`concurrency: 5` means this worker can process up to five jobs concurrently using its asynchronous processing model.

It does not create five JavaScript threads.

## 5. Understanding job concurrency

Suppose a worker receives 100 email jobs.

With:

```
concurrency: 5
```

It can have up to five jobs actively executing at a time.

For I/O-heavy jobs such as:

- Sending emails.
- Calling external APIs.
- Waiting for database queries.
- Uploading files.

Concurrency can improve throughput because the worker can make progress on other jobs while waiting for I/O.

However, setting concurrency too high can cause:

- Database connection pool exhaustion.
- External API rate limits.
- Excessive memory usage.
- Increased Redis and application load.

For CPU-heavy jobs, concurrency on the same Node.js event loop can actually make performance worse.

A practical distinction:

| Workload | Recommended approach |
| --- | --- |
| Email sending | Async BullMQ worker |
| External API calls | Async BullMQ worker |
| Database updates | Async BullMQ worker |
| Large PDF generation | Separate process or Worker Thread if CPU-heavy |
| Image processing | Worker Thread or separate processing service depending on library |
| Large data transformation | Worker Thread or separate process |

BullMQ also supports sandboxed processors and worker thread/process-based processing options for certain workloads.

The important thing is to understand the actual bottleneck before choosing the execution model.

## 6. Job lifecycle and states

A BullMQ job moves through different states during its lifetime.

<img width="999" height="369" alt="Screenshot 2026-11-08 230205" src="https://github.com/user-attachments/assets/6a0d5f4d-4d89-46c4-8476-00ad0c137aa5" />

Other useful states include:

- Delayed: Job is scheduled to run later.
- Waiting-children: A parent job is waiting for its child jobs to finish.
- Paused: Queue processing is paused.
- Stalled: A worker stopped renewing its job lock, so BullMQ may return the job to waiting for another worker to process it.

### Why does the stalled state matter?

Imagine a worker picks up a job and then crashes.

The job was marked active, but it never completed.

BullMQ uses job locks and stalled-job detection to identify jobs that are no longer being processed properly.

The job can be returned to the waiting state and picked up by another worker, subject to the configured stalled-job limits.

This gives us an important reliability property:

A job can execute more than once.

Never assume a background job executes exactly once.

## 7. Retry handling and exponential backoff

External services can fail temporarily.

For example, your email provider might return:

- Network timeout.
- HTTP 503.
- Temporary connection failure.
- Rate-limit response.

Instead of immediately marking every job as permanently failed, we can configure retries.

```jsx
await emailQueue.add(
  'send-confirmation',
  {
    reservationId: 123
  },
  {
    attempts: 5,
    backoff: {
      type: 'exponential',
      delay: 1000
    }
  }
);
```

Conceptually, the retry delays increase:

| Attempt | Approximate delay before retry |
| --- | --- |
| 1st retry | 1 second |
| 2nd retry | 2 seconds |
| 3rd retry | 4 seconds |
| 4th retry | 8 seconds |

The actual number of processing attempts is bounded by `attempts`.

### Custom retry decisions

Not every error should be retried.

For example:

| Error | Retry? |
| --- | --- |
| Temporary network timeout | Usually yes |
| HTTP 503 | Usually yes |
| HTTP 429 | Usually yes, respecting retry guidance |
| Invalid email address | No |
| Missing reservation | Usually no; investigate the business condition |
| Invalid authentication credentials | Usually no until configuration is corrected |

You can implement this decision inside your processor by throwing an error for retryable failures and handling permanent failures separately.

```jsx
async function processEmail(job) {
  try {
    await sendEmail(job.data);
  } catch (error) {
    if (error.code === 'INVALID_EMAIL') {
      // Permanent failure: don't retry.
      // Record the failure or move to a review workflow.
      return;
    }

    // Retryable failure: let BullMQ handle the retry.
    throw error;
  }
}
```

Be careful: swallowing an error marks the job as successfully completed. If you handle a permanent failure this way, you should also record that business outcome somewhere.

## 8. Idempotency — one of the most important concepts

Suppose a worker sends a confirmation email.

1. The worker sends the email successfully.
2. The process crashes before BullMQ records the job as completed.
3. The job gets picked up again.
4. The worker sends the same email again.

The customer receives two emails.

This is why background jobs should be designed to be idempotent.

An idempotent operation produces the same intended business result when executed multiple times.

### Example: Avoid duplicate email sending

One implementation is to maintain a notification record in the database.

```jsx
async function sendReservationEmail(job) {
  const { reservationId } = job.data;

  const notification = await Notification.findOne({
    reservationId,
    type: 'CONFIRMATION'
  });

  if (notification?.status === 'SENT') {
    return;
  }

  // Send the email.
  await emailProvider.send({
    to: job.data.email,
    subject: 'Reservation confirmed'
  });

  await Notification.updateOne(
    {
      reservationId,
      type: 'CONFIRMATION'
    },
    {
      $set: { status: 'SENT' }
    },
    { upsert: true }
  );
}
```

This illustrates the idea, but it has a race condition: two workers could both read the notification as unsent and send the email.

A stronger implementation uses a unique database constraint and a notification state machine or atomic claim operation.

Also, there is an unavoidable failure window between the email provider accepting the email and your database recording `SENT`. If the provider supports idempotency keys, use them. Otherwise, duplicate delivery may still be possible.

### BullMQ job IDs

BullMQ also allows custom job IDs:

```jsx
await emailQueue.add(
  'send-confirmation',
  {
    reservationId: 123
  },
  {
    jobId: 'reservation-confirmation-123'
  }
);
```

This can prevent adding another job with the same ID while the existing job is retained in the queue.

However, it is not a replacement for business-level idempotency:

- Completed jobs may eventually be removed.
- A job can be retried.
- A worker can crash after performing an external side effect.
- Two different jobs can still represent the same business operation.

Interview takeaway: Queue-level deduplication and business-level idempotency solve related but different problems.

## 9. Handling failed jobs

BullMQ provides events to observe job outcomes.

```jsx
worker.on('completed', (job) => {
  console.log('Completed:', job.id);
});

worker.on('failed', (job, error) => {
  console.error('Failed:', job?.id, error.message);
});

worker.on('error', (error) => {
  console.error('Worker error:', error);
});
```

There are two useful distinctions:

- `failed`: A particular job failed.
- `error`: A worker-level error occurred.

A failed job can be retried according to its configured attempts. Once attempts are exhausted, it remains failed until you take further action.

### Inspecting failed jobs

```jsx
const failedJobs = await emailQueue.getFailed();

for (const job of failedJobs) {
  console.log({
    id: job.id,
    name: job.name,
    data: job.data,
    reason: job.failedReason
  });
}
```

For production systems, consider:

- Retaining a limited number of completed and failed jobs.
- Monitoring failed-job counts.
- Alerting on repeated failures.
- Providing a controlled retry or replay mechanism.
- Avoiding sensitive information in job payloads and logs.

Do not automatically retry every permanently failed job forever.

## 10. Delayed jobs and scheduled processing

Sometimes a job should run later rather than immediately.

For example:

- Send a reminder 24 hours before a reservation.
- Retry an operation after a specified delay.
- Send a follow-up notification after a period of inactivity.

BullMQ supports delayed jobs:

```jsx
await emailQueue.add(
  'reservation-reminder',
  {
    reservationId: 123
  },
  {
    delay: 60 * 60 * 1000
  }
);
```

This schedules the job to become eligible for processing after approximately one hour.

For recurring work, BullMQ also provides scheduling capabilities. The exact APIs depend on the BullMQ version, so use the current Job Scheduler API rather than copying older repeatable-job examples blindly.

A useful distinction:

- Delayed job: Execute once in the future.
- Recurring job: Execute repeatedly according to a schedule.

## 12. Queueing jobs safely after database operations

Consider this implementation:

```jsx
const reservation = await Reservation.create(data);

await emailQueue.add('send-confirmation', {
  reservationId: reservation.id
});
```

What happens if:

1. The database successfully creates the reservation.
2. Redis becomes unavailable.
3. Adding the job fails.

Now the reservation exists, but the confirmation job was never queued.

This is a common reliability gap.

The general solution is the Transactional Outbox Pattern, which you've already studied in System Design.

The Node.js implementation perspective is:

1. Save the reservation.
2. Save an outbox record in the same database transaction.
3. A background publisher reads pending outbox records.
4. It publishes jobs to BullMQ.
5. It marks records as published.
6. Duplicate publication is handled through idempotent job processing.

We won't repeat the architecture lesson here. The important implementation point is that a successful database operation and a successful Redis queue submission are not automatically one atomic operation.

## 13. Separating API and worker processes

For a real application, I recommend keeping the API and worker entry points separate.

```
src/
  app.js

  config/
    redis.js
    database.js

  queues/
    email.queue.js

  workers/
    email.worker.js

  services/
    email.service.js
```

API entry point:

```jsx
// api.js

const app = require('./app');

app.listen(3000, () => {
  console.log('API started');
});
```

Worker entry point:

```jsx
// worker.js

require('./workers/email.worker');

console.log('Background worker started');
```

Then you can run them independently:

```
node api.js
node worker.js
```

Or manage them separately using PM2:

```
pm2 start api.js --name api
pm2 start worker.js --name email-worker
```

This gives you more control over deployment and resource usage.

For example:

- API processes can scale according to HTTP traffic.
- Worker processes can scale according to queue backlog.
- A worker crash does not necessarily take down the API.
- CPU-heavy worker processes can be isolated from API processes.

This separation is particularly useful in production Node.js applications.

## 14. Graceful worker shutdown

A worker should not be terminated abruptly while processing jobs.

For example, if PM2 restarts a worker while it is sending an email or generating a report, we want the worker to finish its active jobs where possible.

BullMQ provides `worker.close()`.

```jsx
const worker = require('./workers/email.worker');

async function shutdown() {
  console.log('Shutting down worker...');

  try {
    await worker.close();
    console.log('Worker closed successfully');
    process.exit(0);
  } catch (error) {
    console.error('Worker shutdown failed:', error);
    process.exit(1);
  }
}

process.on('SIGTERM', shutdown);
process.on('SIGINT', shutdown);
```

`worker.close()` stops taking new jobs and waits for active jobs to finish. It does not impose its own timeout, so production deployments should have an overall shutdown deadline.

Also, avoid registering multiple shutdown handlers that independently close the same resources.

## 15. Common mistakes in Node.js background processing

| Mistake | Why it's problematic |
| --- | --- |
| Sending large objects in job payloads | Increases Redis storage and serialization overhead |
| Assuming exactly-once execution | Jobs can execute more than once |
| No retry strategy | Temporary failures become permanent failures |
| Retrying every error | Wastes resources on permanent failures |
| No idempotency | Duplicate payments, emails, or updates |
| Excessive concurrency | Can exhaust DB connections or external API limits |
| CPU-heavy work on the main event loop | Blocks other jobs handled by that worker |
| No failed-job monitoring | Failures can remain unnoticed |
| Putting secrets in job data | Sensitive information can be exposed through queue storage |
| No worker shutdown handling | Active work can be interrupted during deployment |
| Assuming Redis queue submission is atomic with DB commit | Can leave business records without corresponding jobs |

## 16. When should you use BullMQ vs a simple asynchronous function?

Not every operation needs a queue.

| Scenario | Appropriate approach |
| --- | --- |
| Small operation needed immediately | Normal `await` |
| Non-critical in-process operation | Background Promise, if losing it on crash is acceptable |
| Email sending that must survive process restarts | BullMQ |
| Large report generation | BullMQ worker |
| Scheduled notifications | BullMQ delayed/scheduled jobs |
| CPU-heavy processing | BullMQ with separate worker execution, Worker Threads, or processes |
| Long-running retryable external API operation | BullMQ |

A useful rule:

If the work needs persistence, retry handling, independent execution, or recovery after process restarts, a queue is usually worth considering.

## 18. Key takeaways for your notes

- Producer adds jobs; queue stores them; worker processes them.
- BullMQ uses Redis to manage job state and processing.
- A Promise is not a durable background job.
- Worker concurrency is not the same as JavaScript thread count.
- Use retries with appropriate backoff for temporary failures.
- Design jobs to be idempotent because duplicate execution is possible.
- Use separate worker processes for better isolation and independent scaling.
- Keep job payloads small; use database IDs where possible.
- Use Worker Threads or processes for CPU-heavy operations.
- Handle stalled and failed jobs.
- Use graceful worker shutdown.
- Understand the DB-to-queue reliability gap and the Outbox Pattern.
