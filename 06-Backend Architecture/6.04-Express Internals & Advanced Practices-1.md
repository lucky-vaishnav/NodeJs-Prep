## 6.4.1 — How Express handles an incoming request

When a request reaches your Express application, Express doesn't immediately execute the controller. It passes the request through its internal middleware and routing mechanisms.

Consider:

```javascript
const express = require('express');

const app = express();

app.use(express.json());

app.use((req, res, next) => {
  console.log('Request received');
  next();
});

app.get('/users/:id', (req, res) => {
  res.json({ userId: req.params.id });
});

app.listen(3000);
```

### What happens internally?

1\. Node.js HTTP server receives the request

Express uses Node.js's built-in HTTP server functionality. When you call:

```javascript
app.listen(3000);
```

Express creates an HTTP server and delegates incoming requests to the Express application.

Conceptually, this is similar to:

```javascript
const server = require('http').createServer(app);
server.listen(3000);
```

2\. Express processes the middleware stack

Express maintains an ordered stack of middleware and routing layers.

Each applicable layer gets an opportunity to process the request.

For example:

```javascript
app.use(requestLogger);
app.use(express.json());
app.use('/api', apiRouter);
```

The order matters. A middleware registered later cannot process a request before an earlier matching middleware.

3\. Express matches the route

For:

```
GET /users/123
```

Express matches:

```javascript
app.get('/users/:id', handler);
```

Then it makes the route parameter available through:

```javascript
req.params.id;
```

4\. Response is sent

Once the handler calls:

```
res.json({ success: true });
```

Express serializes the response and sends it through Node.js's HTTP response object.

The response is now completed, and the request lifecycle ends.

### Important senior-level detail

Express does not create a separate thread for each incoming request.

Requests are handled through Node.js's event-driven execution model. While one request is waiting for asynchronous I/O, other requests can continue to be processed.

This is why blocking the event loop with CPU-heavy synchronous work can affect unrelated requests.

## 6.4.1 — What you should remember

- Express is built on top of Node.js HTTP functionality.
- `app.listen()` creates and starts an HTTP server.
- Express processes matching middleware and route layers in registration order.
- Routing determines which handler processes the request.
- Response completion ends the normal request lifecycle.
- Blocking synchronous operations can affect all requests sharing the event loop.

### 6.4 Express Internals & Advanced Practices

6.4.2 — Middleware and Router Stack: How Express Controls Request Flow

In the previous lesson, we covered how a request enters Express. Now let's look at how Express decides which middleware and route handlers execute.

### 1. Express executes middleware in registration order

Express maintains an ordered stack of middleware and route layers. When a request arrives, Express moves through that stack and executes the matching layers.

Consider this example:

```javascript
app.use(requestLogger);

app.use('/api', authenticate);

app.get('/api/users', getUsers);

app.use(errorHandler);
```

For `GET /api/users`, the execution order is:

1. `requestLogger`
2. `authenticate`
3. `getUsers`
4. Response is sent

The important point: middleware order matters. If authentication is registered after a protected route, that route may execute before authentication.

### 2. Understanding `next()`

`next()` tells Express to continue processing the request.

```javascript
function requestLogger(req, res, next) {
    console.log(`${req.method} ${req.originalUrl}`);
    next();
}
```

Without `next()`, the request doesn't move forward.

A middleware must do one of two things:

- Send or otherwise complete the response.
- Call `next()` to pass control onward.

If it does neither, the request remains pending until it times out or the connection is closed.

### 3. Understanding `next('route')`

This is useful when a route has multiple handlers and you want to skip the remaining handlers for the current route.

```javascript
app.get(
    '/users/:id',
    (req, res, next) => {
        if (req.params.id === 'admin') {
            return next('route');
        }

        next();
    },
    (req, res) => {
        res.send('Regular user');
    }
);

// Another matching route
app.get('/users/:id', (req, res) => {
    res.send('Alternative user handler');
});
```

For `/users/admin`, Express skips the remaining callbacks of the first route and looks for another matching route.

Important: `next('route')` is intended for route handlers. It is not a general way to skip arbitrary application middleware.

### 4. Understanding `next(error)`

This tells Express that an error occurred and switches processing to error-handling middleware.

```javascript
app.get('/users', (req, res, next) => {
    const error = new Error('Something went wrong');
    next(error);
});

app.use((err, req, res, next) => {
    console.error(err);

    res.status(500).json({
        message: 'Internal server error'
    });
});
```

An Express error-handling middleware has four parameters:

```
(err, req, res, next)
```

When Express enters error-handling mode, it skips normal middleware and routes and searches for an applicable error handler.

If no custom error handler handles the error, Express's default error handler takes over.

### 5. Understanding `next('router')`

This is less commonly used, but useful when working with mounted routers.

It tells Express to exit the current router and pass control back to the parent application.

```javascript
const router = express.Router();

router.use((req, res, next) => {
    if (!req.headers['x-api-key']) {
        return next('router');
    }

    next();
});

router.get('/users', (req, res) => {
    res.send('Users');
});

app.use('/api', router);

app.use('/api', (req, res) => {
    res.status(401).send('Access denied');
});
```

If the API key is missing, the router is exited and the parent application's next matching layer can handle the request.

### 6. Important production mistake: calling `next()` after sending a response

Consider:

```javascript
app.get('/users', (req, res, next) => {
    res.json({ message: 'Success' });

    next();
});
```

The response has already been sent, but Express continues processing the stack.

A later handler might attempt another response, causing:

```javascript
Error: Cannot set headers after they are sent to the client
```

A safer approach:

```javascript
app.get('/users', (req, res) => {
    return res.json({ message: 'Success' });
});
```

Use `next()` to pass control, not after completing a response. Passing an error after a response has been sent is a special case that may be necessary for error handling, but it must be handled carefully.

### 7. Mounted routers: understanding request paths

This is especially useful in modular Express applications.

```javascript
const userRouter = express.Router();

userRouter.get('/users', (req, res) => {
    console.log(req.baseUrl);
    console.log(req.url);
    console.log(req.originalUrl);

    res.send('Users');
});

app.use('/api/v1', userRouter);
```

For a request to `/api/v1/users?active=true`:

| Property          | Value                       |
| ----------------- | --------------------------- |
| `req.baseUrl`     | `/api/v1`                   |
| `req.url`         | `/users?active=true`        |
| `req.originalUrl` | `/api/v1/users?active=true` |

- `req.baseUrl`: The path on which the router is mounted.
- `req.url`: The remaining URL visible inside the mounted router.
- `req.originalUrl`: The original request URL, including the mount path.

This distinction is useful when debugging routing, logging requests, and implementing middleware across multiple routers.

### Senior-level takeaways

1. Middleware execution is ordered; registration order can affect security and behavior.
2. `next()` continues normal execution.
3. `next('route')` skips the remaining handlers of the current route.
4. `next('router')` exits the current router.
5. `next(error)` switches to error handling.
6. Sending a response and then continuing normal execution can cause duplicate-response errors.
7. Mounted routers change the path visible through `req.url`, while `req.originalUrl` preserves the original URL.

## 6.4.3 — Express 4 vs Express 5

This is an important topic for a senior Node.js developer because many production applications still use Express 4, while newer applications may use Express 5.

The biggest practical difference is how Express handles asynchronous errors.

### 1. Async error handling

Consider this route:

```javascript
app.get('/users', async (req, res) => {
    const users = await userService.getUsers();

    res.json(users);
});
```

Suppose `userService.getUsers()` rejects its Promise because the database is unavailable.

Express 4:

Express 4 does not automatically forward rejected Promises from async route handlers to error-handling middleware.

You generally need to catch and forward the error:

```javascript
app.get('/users', async (req, res, next) => {
    try {
        const users = await userService.getUsers();
        res.json(users);
    } catch (error) {
        next(error);
    }
});
```

Express 5:

Express 5 automatically forwards rejected Promises returned by route handlers and middleware to `next(error)`.

```javascript
app.get('/users', async (req, res) => {
    const users = await userService.getUsers();

    res.json(users);
});
```

If the Promise rejects, Express forwards the error to your error-handling middleware.



Key difference

Express 5 reduces the need for repetitive `try/catch` blocks in async handlers.


### 2. Why async error handling matters

Imagine an application with 50 API endpoints.

In Express 4, developers often write repetitive error-handling code:

```javascript
app.get('/users', async (req, res, next) => {
    try {
        const data = await service.getUsers();
        res.json(data);
    } catch (error) {
        next(error);
    }
});

app.get('/orders', async (req, res, next) => {
    try {
        const data = await service.getOrders();
        res.json(data);
    } catch (error) {
        next(error);
    }
});
```

A common solution is a reusable async wrapper:

```javascript
const asyncHandler = (fn) => {
    return (req, res, next) => {
        Promise.resolve(fn(req, res, next))
            .catch(next);
    };
};
```

Usage:

```javascript
app.get('/users', asyncHandler(async (req, res) => {
    const users = await service.getUsers();
    res.json(users);
}));
```

This approach was widely used in Express 4 applications.

In Express 5, this wrapper is generally unnecessary for returned Promise rejections.

### 3. Important limitation: Express 5 does not catch every asynchronous error

This is a common misunderstanding.

Consider:

```javascript
app.get('/users', async (req, res) => {
    setTimeout(() => {
        throw new Error('Something went wrong');
    }, 1000);

    res.json({ message: 'Success' });
});
```

The error occurs inside a callback that runs later. It is not part of the Promise returned by the route handler.

Express 5 cannot automatically catch this error.

You need to explicitly forward it:

```javascript
app.get('/users', (req, res, next) => {
    setTimeout(() => {
        try {
            throw new Error('Something went wrong');
        } catch (error) {
            next(error);
        }
    }, 1000);
});
```

The same principle applies to callbacks from certain third-party libraries: errors outside the returned Promise chain need explicit handling.

### 4. Route path matching changes

Express 5 updated its route path matching behavior through a newer version of `path-to-regexp`.

Some route patterns accepted in Express 4 may need changes when upgrading.

For example, optional and wildcard route syntax has changed.

Rather than relying on older patterns such as:

```javascript
app.get('/users/:id?', handler);
```

Express 5 expects the newer optional-parameter syntax:

```javascript
app.get('/users{/:id}', handler);
```

This matters when upgrading applications with many existing routes.

### 5. Other relevant changes

| Area                               | Express 4                            | Express 5               |
| ---------------------------------- | ------------------------------------ | ----------------------- |
| Async rejected Promises            | Not automatically forwarded          | Automatically forwarded |
| Async error wrapper                | Commonly needed                      | Usually unnecessary     |
| Route path matching                | Older syntax                         | Updated syntax          |
| `req.body` when no body parser ran | Often `undefined` assumptions differ | `undefined`             |
| `res.status()`                     | Supported                            | Supported               |
| Middleware architecture            | Same general model                   | Same general model      |

One additional detail: Express 5 also changed some request and response API behavior. Review the official migration guide before upgrading rather than assuming complete backward compatibility.

### 6. Production upgrade considerations

If you're upgrading an existing Express 4 application:

1. Check your Node.js version and dependency compatibility.
2. Review route patterns, especially optional and wildcard parameters.
3. Review existing async wrappers and error-handling middleware.
4. Test authentication, validation, and error paths.
5. Test third-party middleware and libraries.
6. Run integration tests before deploying.

Don't simply remove every `try/catch` after upgrading. Some are still necessary for local recovery, cleanup, or translating errors into domain-specific errors.

### Interview takeaway

If asked, "What is the biggest difference between Express 4 and Express 5?"

A good senior-level answer:

> One of the biggest differences is asynchronous error handling. Express 4 does not automatically forward rejected Promises from async route handlers, so we typically use try/catch with next(error) or a reusable async wrapper. Express 5 handles rejected Promises automatically and forwards them to error middleware. However, errors occurring in independent callbacks, timers, or other asynchronous operations outside the returned Promise chain still need explicit handling.

## 6.4.4 — Centralized Error Handling in Express

This is an important senior-level backend topic. In production applications, errors can originate from controllers, services, repositories, databases, external APIs, authentication, and validation.

The goal is to handle them consistently without writing repetitive error-handling logic in every API.

### 1. Why centralized error handling?

Consider an application with multiple endpoints:

```javascript
app.get('/users', async (req, res) => {
    // Fetch users
});

app.get('/orders', async (req, res) => {
    // Fetch orders
});

app.post('/payments', async (req, res) => {
    // Process payment
});
```

Without centralized error handling, each endpoint might return errors differently:

```javascript
res.status(500).json({ message: 'Something went wrong' });
```

Another endpoint might return:

```javascript
res.status(500).json({ error: 'Internal error' });
```

This creates inconsistent API responses and makes error logging and debugging difficult.

Centralized error handling gives us:

- Consistent error responses.
- One place to log unexpected errors.
- Separation of business logic and HTTP error handling.
- Better control over which errors are exposed to clients.

### 2. Understanding the error-handling flow

<img width="936" height="608" alt="Screenshot 2026-11-07 221915" src="https://github.com/user-attachments/assets/38f478cc-8cf7-40a9-96f7-0aa4f7f4e74c" />


The important idea is that lower layers can throw meaningful errors, while the centralized middleware decides how to convert them into HTTP responses.

### 3. Create a custom application error class

Instead of throwing generic JavaScript errors everywhere, create a reusable error class.

```javascript
class AppError extends Error {
    constructor(message, statusCode = 500, code = 'INTERNAL_ERROR') {
        super(message);

        this.statusCode = statusCode;
        this.code = code;
        this.isOperational = true;

        Error.captureStackTrace(this, this.constructor);
    }
}

module.exports = AppError;
```

Now we can throw meaningful errors from services.

```javascript
const AppError = require('./AppError');

async function getUserById(userId) {
    const user = await User.findById(userId);

    if (!user) {
        throw new AppError(
            'User not found',
            404,
            'USER_NOT_FOUND'
        );
    }

    return user;
}
```

Notice that the service doesn't need to know how Express sends the response.

It simply reports the application error.

### 4. Centralized error middleware

Now create a global error handler:

```javascript
function errorHandler(err, req, res, next) {
    const statusCode = err.statusCode || 500;

    console.error({
        message: err.message,
        stack: err.stack,
        path: req.originalUrl
    });

    res.status(statusCode).json({
        success: false,
        code: err.code || 'INTERNAL_ERROR',
        message: err.isOperational
            ? err.message
            : 'Internal server error'
    });
}

module.exports = errorHandler;
```

Register it after all routes:

```javascript
app.use('/api/users', userRouter);
app.use('/api/orders', orderRouter);

app.use(errorHandler);
```

In Express, error-handling middleware should be registered after the routes and middleware whose errors it needs to handle.

### 5. Operational errors vs programming errors

This distinction is particularly important for senior developers.

Operational errors are expected failures that can happen during normal application operation.

Examples:

- User not found.
- Invalid request data.
- Insufficient wallet balance.
- Database temporarily unavailable.
- External payment provider timeout.

Programming errors are unexpected defects in the code.

Examples:

- Accessing a property of `undefined`.
- Calling a function that doesn't exist.
- Incorrect assumptions in application logic.
- Unexpected type errors.

| Operational errors                     | Programming errors                   |
| -------------------------------------- | ------------------------------------ |
| Expected failure scenarios             | Unexpected code defects              |
| Usually handled and returned to client | Usually treated as internal failures |
| Often have known status codes          | Usually return generic 500           |
| Should be logged appropriately         | Require investigation and fixing     |

For example:

```javascript
throw new AppError('Insufficient balance', 400);
```

This is an expected business failure.

But:

```javascript
user.profile.address.city
```

If `profile` is unexpectedly undefined, that may indicate a programming defect. Don't expose its internal details to the client.

### 6. Important production considerations

A. Don't expose internal error details

Avoid returning:

```javascript
res.status(500).json({
    message: err.message,
    stack: err.stack
});
```

This can expose internal implementation details, database information, or sensitive data.

Return a generic message for unexpected errors, and retain detailed diagnostics in protected logs.

B. Don't log every error at the same severity

For example:

- 400 validation failure: usually warn or info.
- 404 resource missing: often info or warn, depending on context.
- 500 unexpected error: error.
- Database outage: error, with suitable alerting.

Avoid logging sensitive information such as passwords, tokens, payment credentials, or unnecessary personal data.

C. Handle known database errors

Database errors may need translation into application-level errors.

For example, a MongoDB duplicate-key error could become:

```javascript
throw new AppError(
    'Email already exists',
    409,
    'EMAIL_ALREADY_EXISTS'
);
```

This keeps database-specific implementation details out of your public API contract.

D. Respect the response lifecycle

If headers have already been sent, don't attempt to send another response.

```javascript
function errorHandler(err, req, res, next) {
    if (res.headersSent) {
        return next(err);
    }

    res.status(500).json({
        message: 'Internal server error'
    });
}
```

This allows Express's default error handler to deal with errors that occur after the response has started.

### 7. A senior-level architectural recommendation

Keep these responsibilities separate:

| Layer                | Responsibility                        |
| -------------------- | ------------------------------------- |
| Controller           | Handles HTTP request and response     |
| Service              | Business logic and application errors |
| Repository           | Database operations                   |
| Custom error classes | Represent known application failures  |
| Error middleware     | Converts errors into HTTP responses   |
| Logger / monitoring  | Captures diagnostics and alerts       |

One important distinction: don't convert every error into a generic `AppError` too early. Preserve the original error as `cause` where appropriate, so debugging and observability retain the underlying reason.

### Interview questions

Q1. Why do we need centralized error handling in Express?

To maintain consistent error responses, separate error handling from business logic, and centralize logging and monitoring.

Q2. Should we handle errors in controllers or services?

Services should handle business-specific decisions and throw meaningful application errors. Controllers can pass errors to Express, while centralized middleware handles HTTP error responses.

Q3. What is the difference between operational and programming errors?

Operational errors are expected failures during normal execution. Programming errors indicate defects or unexpected conditions in the code.

Q4. What happens if an error occurs after response headers have been sent?

The error middleware should check `res.headersSent` and delegate using `next(err)` instead of attempting another response.

### Key takeaway

A good production error-handling architecture should have:

1. Meaningful custom application errors.
2. Centralized Express error middleware.
3. Consistent API error responses.
4. Proper classification of expected and unexpected failures.
5. Secure logging without exposing internal details.
