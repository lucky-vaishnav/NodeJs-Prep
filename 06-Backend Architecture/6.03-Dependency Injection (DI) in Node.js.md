# Phase 6.3 — Dependency Injection (DI) in Node.js

Let's understand Dependency Injection from a practical Node.js perspective, especially how it works in Express and NestJS.

This is an important senior-level topic because it directly affects maintainability, testability, loose coupling, and application flexibility.

## 1. What is Dependency Injection?

First, understand what a dependency is.

Suppose an `OrderService` needs an `OrderRepository` to save orders.

The repository is a dependency of the service because the service relies on it to perform its work.

There are two ways to establish this relationship.

Without Dependency Injection:

The service creates its own dependency.

```javascript
const OrderRepository = require('./order.repository');

class OrderService {
  constructor() {
    this.orderRepository = new OrderRepository();
  }

  async createOrder(data) {
    return this.orderRepository.create(data);
  }
}
```

Here, `OrderService` controls the creation of `OrderRepository`.

With Dependency Injection:

The dependency is provided from outside.

```javascript
class OrderService {
  constructor(orderRepository) {
    this.orderRepository = orderRepository;
  }

  async createOrder(data) {
    return this.orderRepository.create(data);
  }
}
```

Now the service doesn't know how the repository is created. It only knows that it receives an object capable of performing the required operation.

That's Dependency Injection.

In simple words: Instead of a class creating the objects it depends on, those objects are provided to it from outside.

## 2. Why do we need Dependency Injection?

Consider a real-world scenario.

Your application initially uses MongoDB through Mongoose. Later, you want to test the service without connecting to MongoDB.

Or perhaps you want to replace an external payment provider with another provider.

If your service creates its own dependencies, changing implementations becomes difficult.

With DI, the service depends on an abstraction or expected interface rather than a specific implementation.

For example:

```javascript
class OrderService {
  constructor(orderRepository) {
    this.orderRepository = orderRepository;
  }

  async createOrder(data) {
    return this.orderRepository.create(data);
  }
}
```

We can provide different implementations:

```javascript
const mongoRepository = new MongoOrderRepository();
const orderService = new OrderService(mongoRepository);
```

Or:

```javascript
const mockRepository = {
  create: async (data) => ({
    id: 101,
    ...data
  })
};

const orderService = new OrderService(mockRepository);
```

The service remains unchanged.

### Main benefits

| Benefit         | Explanation                                       |
| --------------- | ------------------------------------------------- |
| Loose coupling  | Service isn't tied to a specific implementation   |
| Testability     | Easily inject mocks or test doubles               |
| Maintainability | Implementations can be replaced independently     |
| Reusability     | Same service can work with different dependencies |
| Flexibility     | Easier to configure different implementations     |

## 3. Types of Dependency Injection

There are three commonly discussed approaches.

### A. Constructor Injection

Dependencies are passed through the constructor.

```javascript
class OrderService {
  constructor(orderRepository, paymentService) {
    this.orderRepository = orderRepository;
    this.paymentService = paymentService;
  }
}
```

Recommended default

Why?

- Dependencies are explicit.
- The object receives everything it needs during creation.
- Easier to test.
- The object cannot be created without its required dependencies if you enforce that in the constructor.

### B. Setter Injection

Dependencies are provided through a method after object creation.

```javascript
class OrderService {
  setRepository(repository) {
    this.repository = repository;
  }

  async createOrder(data) {
    return this.repository.create(data);
  }
}

const service = new OrderService();
service.setRepository(orderRepository);
```

Useful when a dependency is genuinely optional or needs to be configured later.

However, it introduces the possibility of using the service before its dependency has been initialized.

### C. Property Injection

Dependencies are assigned directly to object properties.

```javascript
class OrderService {
  async createOrder(data) {
    return this.orderRepository.create(data);
  }
}

const service = new OrderService();
service.orderRepository = orderRepository;
```

This is less explicit and makes it easier to create incorrectly configured objects.

For most application services, constructor injection is the best default.

## 4. How to implement DI manually in Express

This is especially important because Express doesn't provide a built-in dependency injection container.

We can implement DI ourselves.

Let's use a practical project structure:

```
src/
├── modules/
│   └── order/
│       ├── order.routes.js
│       ├── order.controller.js
│       ├── order.service.js
│       └── order.repository.js
│
├── container/
│   └── dependencies.js
│
├── app.js
└── server.js
```

### Step 1: Repository

`order.repository.js`

```javascript
class OrderRepository {
  async create(data) {
    // Database operation
    return {
      id: 101,
      ...data
    };
  }
}

module.exports = OrderRepository;
```

### Step 2: Service

`order.service.js`

```javascript
class OrderService {
  constructor(orderRepository) {
    this.orderRepository = orderRepository;
  }

  async createOrder(data) {
    if (!data.items || data.items.length === 0) {
      throw new Error('Order items are required');
    }

    return this.orderRepository.create(data);
  }
}

module.exports = OrderService;
```

Notice that the service doesn't import or create the repository.

### Step 3: Controller

`order.controller.js`

```javascript
class OrderController {
  constructor(orderService) {
    this.orderService = orderService;
  }

  createOrder = async (req, res, next) => {
    try {
      const result = await this.orderService.createOrder(req.body);

      res.status(201).json({
        success: true,
        data: result
      });
    } catch (error) {
      next(error);
    }
  };
}

module.exports = OrderController;
```

### Step 4: Dependency composition

`dependencies.js`

```javascript
const OrderRepository = require('../modules/order/order.repository');
const OrderService = require('../modules/order/order.service');
const OrderController = require('../modules/order/order.controller');

const orderRepository = new OrderRepository();

const orderService = new OrderService(
  orderRepository
);

const orderController = new OrderController(
  orderService
);

module.exports = {
  orderController
};
```

This file is responsible for creating objects and connecting their dependencies.

This is often called the Composition Root.

### Step 5: Routes

`order.routes.js`

```javascript
const express = require('express');
const router = express.Router();

const { orderController } = require('../../container/dependencies');

router.post('/', orderController.createOrder);

module.exports = router;
```

Now our route uses the already configured controller.

### What have we achieved?

Each component receives its dependency instead of creating it internally.

This also makes unit testing easier because we can construct an `OrderService` with a mock repository without initializing a database.

## 5. How does DI help with unit testing?

This is one of its biggest advantages.

Suppose we want to test `OrderService` without connecting to MongoDB.

We can inject a mock repository.

```javascript
const OrderService = require('./order.service');

describe('OrderService', () => {
  it('should create an order', async () => {
    const mockRepository = {
      create: async (data) => ({
        id: 101,
        ...data
      })
    };

    const orderService = new OrderService(mockRepository);

    const result = await orderService.createOrder({
      items: [{ productId: 1, quantity: 2 }]
    });

    console.log(result.id); // 101
  });
});
```

We don't need:

- A running MongoDB instance.
- A real repository implementation.
- External services.
- Actual database records.

We test the service independently.

This is called dependency isolation.

In production, we inject real dependencies. During testing, we inject mocks or fakes.

## 6. How does NestJS implement Dependency Injection?

Now let's connect this to NestJS, since you have experience with it.

NestJS provides a built-in Dependency Injection Container.

Instead of manually creating and wiring dependencies, we register providers and NestJS manages their creation and injection.

### Example

`order.service.ts`

```javascript
import { Injectable } from '@nestjs/common';

@Injectable()
export class OrderService {
  constructor(
    private readonly orderRepository: OrderRepository
  ) {}

  async createOrder(data: any) {
    return this.orderRepository.create(data);
  }
}
```

`order.module.ts`

```javascript
import { Module } from '@nestjs/common';

@Module({
  controllers: [OrderController],
  providers: [
    OrderService,
    OrderRepository
  ]
})
export class OrderModule {}
```

NestJS sees that `OrderService` requires `OrderRepository`.

Because both are registered as providers, the DI container resolves the dependency and injects it.

### What does `@Injectable()` do?

It marks a class as available for NestJS dependency injection and enables the framework to use its constructor dependency metadata.

However, simply adding `@Injectable()` doesn't register a provider automatically. The provider must be available in the relevant module scope.

### Different provider configurations

NestJS also supports different ways to provide dependencies.

Class provider:

```
providers: [OrderRepository]
```

Value provider:

```javascript
providers: [
  {
    provide: 'APP_CONFIG',
    useValue: {
      environment: 'production'
    }
  }
]
```

Factory provider:

```javascript
providers: [
  {
    provide: 'PAYMENT_SERVICE',
    useFactory: (config) => {
      return new PaymentService(config);
    },
    inject: ['APP_CONFIG']
  }
]
```

Token-based injection:

```javascript
constructor(
  @Inject('PAYMENT_SERVICE')
  private readonly paymentService: PaymentService
) {}
```

These approaches are useful when we need to inject configuration, external clients, interface implementations, or dynamically created objects.

## 7. Important production considerations

### A. Dependency lifecycle

Creating an object once and reusing it is different from creating a new instance for every request.

NestJS supports three common provider scopes:

| Scope     | Behavior                              |
| --------- | ------------------------------------- |
| DEFAULT   | Shared singleton instance             |
| REQUEST   | New instance for each request context |
| TRANSIENT | New instance for each injection       |

In Express, our manually created dependencies are typically instantiated once when the application starts and reused.

Be careful: a singleton service should not store request-specific user data in instance properties.

For example, this is dangerous:

```javascript
class OrderService {
  async createOrder(userId, data) {
    this.currentUserId = userId;

    // Other asynchronous operations
  }
}
```

Concurrent requests can overwrite `currentUserId`.

Prefer passing request-specific values as method arguments.

### B. Avoid circular dependencies

Consider:

```
OrderService → PaymentService
PaymentService → OrderService
```

Both services depend on each other.

This creates tight coupling and can cause dependency resolution problems.

Better approaches include:

- Moving shared responsibilities into a third service.
- Introducing events for decoupled communication.
- Redesigning module ownership.

NestJS supports `forwardRef()` for certain circular dependency cases, but it should not be the default solution.

### C. Don't introduce DI unnecessarily

For example:

```javascript
function calculateTotal(items) {
  return items.reduce(
    (sum, item) => sum + item.price,
    0
  );
}
```

This is a simple pure function. It doesn't need a DI container or an injected dependency.

Use DI when an object depends on other objects or services whose implementation, lifecycle, or behavior needs to be managed.

## 8. Common interview questions and senior-level answers

Q1. What is Dependency Injection?

DI is a design technique where a class receives its dependencies externally instead of creating them internally. It reduces coupling and improves testability and maintainability.

Q2. Is Dependency Injection the same as Dependency Inversion?

No.

- Dependency Injection is a technique for providing dependencies.
- Dependency Inversion is a SOLID principle that encourages high-level modules to depend on abstractions rather than concrete implementations.

DI can help implement Dependency Inversion, but they are not the same thing.

Q3. Does Express support Dependency Injection?

Express doesn't provide a built-in DI container. We can implement DI manually using constructor injection and a composition root, or use a third-party DI container.

Q4. Why is constructor injection generally preferred?

Because dependencies are explicit, required dependencies can be validated during construction, and unit testing becomes easier.

Q5. Does using DI automatically make an application loosely coupled?

No. If a service receives a concrete implementation and depends heavily on its internal details, coupling can still exist. Good dependency boundaries and abstractions matter.

## 9. What you should remember

The five important points

1. A dependency is an object or service another component needs.
2. DI means providing that dependency externally.
3. Constructor injection is generally the preferred approach.
4. Express can use manual DI; NestJS provides a DI container.
5. DI improves testing and flexibility, but unnecessary abstractions should be avoided.
