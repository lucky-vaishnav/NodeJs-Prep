# Phase 6.2 — Project Structure: Feature-Based vs Layer-Based Architecture

In the previous topic, we introduced routes, controllers, services, and repositories. Now let's go deeper into an important architectural decision:

How should we organize a growing Node.js application?

Imagine you are working on a backend with:

- User management
- Authentication
- Payments
- Orders
- Notifications
- Reports

There are two common approaches.

## 1. Layer-based project structure

In this approach, files are organized according to their technical responsibility.

```
src/
├── controllers/
│   ├── user.controller.js
│   ├── order.controller.js
│   └── payment.controller.js
│
├── services/
│   ├── user.service.js
│   ├── order.service.js
│   └── payment.service.js
│
├── repositories/
│   ├── user.repository.js
│   ├── order.repository.js
│   └── payment.repository.js
│
├── routes/
│   ├── user.routes.js
│   ├── order.routes.js
│   └── payment.routes.js
│
└── app.js
```

Advantages

- Simple to understand initially.
- Easy to locate files by technical responsibility.
- Works well for small applications.

Disadvantages

- As the application grows, each folder contains many unrelated files.
- A single feature requires navigating multiple folders.
- Changes to one feature can become difficult to manage independently.

## 2. Feature-based (module-based) project structure

Here, we organize files around business features.

```
src/
├── modules/
│   ├── user/
│   │   ├── user.routes.js
│   │   ├── user.controller.js
│   │   ├── user.service.js
│   │   └── user.repository.js
│   │
│   ├── order/
│   │   ├── order.routes.js
│   │   ├── order.controller.js
│   │   ├── order.service.js
│   │   └── order.repository.js
│   │
│   └── payment/
│       ├── payment.routes.js
│       ├── payment.controller.js
│       ├── payment.service.js
│       └── payment.repository.js
│
├── middleware/
├── config/
├── common/
├── app.js
└── server.js
```

Each module contains the files required for that feature.

Advantages

- Related functionality stays together.
- Easier to maintain and extend individual features.
- Better ownership boundaries when multiple developers work on the application.
- Easier to identify dependencies between features.

Disadvantages

- Requires discipline around module boundaries.
- Shared functionality needs careful organization.
- Poorly designed modules can still become tightly coupled.

## 3. Practical example: Order and Payment modules

Suppose an order needs payment processing.

A reasonable dependency flow could be:

```
Order Controller
      |
      v
Order Service
      |
      v
Payment Service
      |
      v
Payment Provider
```

The Order Service coordinates the operation, while the Payment Service owns payment-specific logic.

For example:

`order.service.js`

```
const paymentService = require('../payment/payment.service');
const orderRepository = require('./order.repository');

exports.createOrder = async (orderData) => {
  const order = await orderRepository.create({
    ...orderData,
    status: 'PENDING_PAYMENT'
  });

  const payment = await paymentService.createPayment({
    orderId: order.id,
    amount: order.totalAmount
  });

  return {
    order,
    payment
  };
};
```

Notice something important:

The Order Service does not need to know how the payment provider's API works. It delegates that responsibility to the Payment Service.

This is an example of separating responsibilities and managing dependencies.

Production note: This simplified example doesn't handle payment failures, retries, or transaction consistency. We'll study those implementation concerns separately.

## 4. Where should shared functionality go?

Not everything belongs inside a feature module.

For example:

```
src/
├── modules/
│   ├── user/
│   ├── order/
│   └── payment/
│
├── common/
│   ├── errors/
│   ├── constants/
│   ├── validators/
│   └── helpers/
│
├── middleware/
├── config/
└── app.js
```

Use `common` for genuinely reusable functionality.

Avoid turning it into a dumping ground for code whose ownership is unclear.

A useful principle:

Keep feature-specific logic inside its module. Move functionality into shared code only when there is a genuine reuse or ownership reason.

## 5. How does NestJS approach this?

NestJS naturally encourages feature-based modules.

For example:

```
src/
├── order/
│   ├── order.module.ts
│   ├── order.controller.ts
│   ├── order.service.ts
│   └── order.repository.ts
│
├── payment/
│   ├── payment.module.ts
│   ├── payment.controller.ts
│   └── payment.service.ts
│
└── app.module.ts
```

NestJS modules also provide dependency registration and encapsulation through its dependency injection system.

Express doesn't enforce this structure. You establish and maintain the boundaries yourself.

## 6. Senior-level takeaways

- Feature-based organization is often a good default for growing backend applications.
- Layer-based organization is perfectly reasonable for small applications.
- Folder structure alone does not guarantee good architecture.
- Avoid circular dependencies between feature modules.
- Keep module interfaces clear and avoid importing internal implementation details unnecessarily.
- Don't create abstractions simply to follow a pattern.
