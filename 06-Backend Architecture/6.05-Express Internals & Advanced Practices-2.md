## 6.4.5 — Async Error Handling Patterns & Production Pitfalls

We've covered Express 4 vs 5 and centralized error handling. Now let's connect them to real production scenarios.

In Node.js applications, many failures happen asynchronously:

- Database queries reject.
- Third-party APIs time out.
- Payment providers return errors.
- Background operations fail.
- Client connections close before processing finishes.

A senior developer should understand not only how to catch these errors, but also where they should be handled.

### 1. Errors in async service calls

Consider a typical Express architecture:

```
Route → Controller → Service → Repository → Database
```

Example:

```javascript
// Controller
async function getUser(req, res) {
    const user = await userService.getUser(req.params.id);

    res.json(user);
}

// Service
async function getUser(id) {
    return await userRepository.findById(id);
}

// Repository
async function findById(id) {
    return User.findById(id);
}
```

Suppose the database query fails.

The repository returns a rejected Promise, which propagates through the service and controller.

- Express 4: You need to catch and forward the rejection, usually through an async wrapper.
- Express 5: Express automatically forwards the rejected Promise returned by the controller to error middleware.

The important concept is that you don't need to catch an error at every layer if that layer cannot meaningfully handle it.

Catch errors when you need to recover, translate, clean up, or add useful context. Otherwise, let them propagate.

### 2. When should we catch errors inside a service?

Consider a payment service calling an external payment provider.

```javascript
async function processPayment(paymentData) {
    try {
        return await paymentProvider.charge(paymentData);
    } catch (error) {
        throw new AppError(
            'Payment processing failed',
            502,
            'PAYMENT_PROVIDER_ERROR',
            { cause: error }
        );
    }
}
```

Here, catching the error makes sense because the service translates a provider-specific failure into an application-level error.

However, there is an important payment-specific consideration:

A failed API call does not always mean the payment failed.

For example:

1. Your backend sends a payment request.
2. The payment provider processes the payment.
3. The response gets lost because of a network timeout.
4. Your backend receives a timeout error.

The payment may actually have succeeded.

Therefore, blindly retrying the payment can result in duplicate charges.

A production implementation should use an idempotency key and reconcile the payment status with the provider before deciding whether to retry.

### 3. Errors in callbacks and timers

Express 5 automatically forwards rejected Promises returned by route handlers and middleware. But it cannot automatically catch every asynchronous error.

Example:

```javascript
app.get('/report', (req, res, next) => {
    setTimeout(() => {
        try {
            throw new Error('Report generation failed');
        } catch (error) {
            next(error);
        }
    }, 1000);
});
```

Why do we need `try/catch` here?

Because the timer callback executes independently, after the route handler has returned. Its error is not part of a Promise returned by the route handler.

For callback-based APIs, use their error-first callback convention and explicitly pass errors to `next()` where appropriate.

### 4. `Promise.all()` and partial failures

This is a common production scenario.

Suppose an API fetches data from three services:

```javascript
const [user, orders, recommendations] = await Promise.all([
    userService.getUser(id),
    orderService.getOrders(id),
    recommendationService.getRecommendations(id)
]);
```

What happens if one Promise rejects?

`Promise.all()` rejects as soon as one input rejects.

However, the other operations are not automatically cancelled. They may continue running.

This can be a problem when some operations are optional.

For example:

- User details are mandatory.
- Orders are mandatory.
- Recommendations are optional.

A better approach is to handle the optional operation independently:

```javascript
const [user, orders, recommendations] = await Promise.all([
    userService.getUser(id),
    orderService.getOrders(id),
    recommendationService.getRecommendations(id)
        .catch(error => {
            logger.warn('Recommendations unavailable', error);
            return [];
        })
]);
```

Now, a recommendation-service failure doesn't fail the entire API.

Senior-level consideration: Use `Promise.allSettled()` when you need the outcome of every operation, or when you want to inspect individual failures and decide what to do. Don't use it automatically for every parallel operation.

### 5. Request timeout and client disconnection

Imagine a client requests a report that takes 30 seconds to generate.

Meanwhile, the user closes the browser or the mobile app cancels the request.

Your backend may still be processing the report.

This can waste:

- Database connections.
- CPU resources.
- External API calls.
- Memory.

You can listen for request/response lifecycle events:

```javascript
app.get('/report', async (req, res, next) => {
    try {
        const report = await reportService.generateReport();

        if (res.destroyed) {
            return;
        }

        res.json(report);
    } catch (error) {
        if (res.destroyed) {
            return;
        }

        next(error);
    }
});
```

This prevents attempting to send a response after the connection is gone.

But notice something important: it does not cancel the report generation itself.

For expensive operations, propagate an `AbortSignal` to supported database or HTTP operations, or implement explicit cancellation where supported.

Also distinguish:

- `req.aborted`: the incoming request was aborted before it was fully received.
- `res.destroyed`: the response stream or underlying connection has been destroyed.

A client disconnect is not necessarily an application error that should be returned as HTTP 500.

### 6. Avoid unhandled Promise rejections

Consider:

```javascript
app.get('/users', (req, res) => {
    userService.getUsers();

    res.json({ message: 'Request completed' });
});
```

The Promise is not awaited or returned.

If `getUsers()` rejects, Express cannot associate that rejection with this route's request.

Correct:

```javascript
app.get('/users', async (req, res) => {
    const users = await userService.getUsers();

    res.json(users);
});
```

Or:

```javascript
app.get('/users', (req, res, next) => {
    return userService.getUsers()
        .then(users => res.json(users))
        .catch(next);
});
```

The key rule:

Always await or return asynchronous operations whose failures must affect the current request.

For detached background work, handle its rejection explicitly.

### 7. Unhandled errors and process-level handlers

Node.js provides process-level events:

```javascript
process.on('unhandledRejection', (reason, promise) => {
    logger.error('Unhandled rejection', { reason });
});

process.on('uncaughtException', error => {
    logger.fatal('Uncaught exception', error);

    // Initiate controlled shutdown.
});
```

These are useful for last-resort diagnostics, but they are not replacements for request-level error handling.

An `uncaughtException` may leave the application in an inconsistent state. The safer production approach is generally:

1. Log the fatal error.
2. Stop accepting new requests.
3. Allow a short, bounded period for in-flight work to finish.
4. Close database and other resources.
5. Exit the process.
6. Let PM2, Kubernetes, or another process manager restart it.

Do not simply catch an uncaught exception and continue normal operation.

### 8. Production scenario: How would you debug this?

Suppose your API has the following behavior:

- It works normally most of the time.
- Occasionally, the API returns HTTP 500.
- New Relic shows that response time increases during these failures.
- The API calls two external services and one database query.

A senior-level investigation would look like this:

| Step | What to investigate |
| --- | --- |
| 1 | Check error logs and stack traces |
| 2 | Identify which dependency failed |
| 3 | Compare external API and DB latency |
| 4 | Check timeout and retry configuration |
| 5 | Check whether requests are being duplicated |
| 6 | Review Promise handling and unhandled rejections |
| 7 | Correlate failures using request/trace IDs |

Don't immediately increase the API timeout or add retries. First identify the source of the failure.

### Interview questions

Q1. Does Express 5 catch all asynchronous errors?

No. It automatically forwards rejected Promises returned by route handlers and middleware. Errors in independent callbacks, timers, and detached asynchronous operations still require explicit handling.

Q2. Should we catch errors at every layer?

No. Catch errors where recovery, translation, cleanup, or additional context is needed. Otherwise, allow them to propagate to centralized error handling.

Q3. What happens if an async operation is started but not awaited or returned?

Express cannot associate its rejection with the request. It may become an unhandled rejection.

Q4. Does `Promise.all()` cancel other operations when one Promise rejects?

No. It rejects as soon as one input rejects, but the remaining operations continue unless explicitly cancelled.

Q5. Should an application continue running after an uncaught exception?

Generally, no. Log the failure, perform controlled shutdown, and allow the process manager to restart the application.

### Key takeaways

- Don't catch errors unnecessarily at every layer.
- Translate third-party errors into meaningful application errors.
- Understand the difference between Promise-chain errors and callback errors.
- Handle optional parallel operations separately.
- Consider client disconnections and cancellation for long-running requests.
- Never use process-level error handlers as a substitute for proper application error handling.

## 6.4.6 — Express Performance & Production Best Practices

Let's focus on practical improvements that matter in production applications rather than basic Express optimization tips.

### 1. Middleware execution overhead

Every middleware adds some processing overhead to a request.

Consider:

```javascript
app.use(requestLogger);
app.use(cors());
app.use(authentication);
app.use(requestValidator);
app.use(rateLimiter);
app.use('/api', apiRouter);
```

Every applicable middleware executes in registration order.

For a high-traffic application, consider:

- Avoid unnecessary middleware on routes that don't need it.
- Don't perform expensive database queries inside global middleware.
- Avoid repeatedly parsing or transforming the same request data.
- Keep middleware responsibilities focused.

Example: If an endpoint is public, don't run database-backed authentication middleware unnecessarily.

You can scope middleware to specific routes:

```javascript
app.use('/api/private', authentication);
app.use('/api/public', publicRouter);
```

### 2. Avoid synchronous CPU-intensive operations

This is one of the most important Node.js performance considerations.

Consider:

```javascript
app.get('/report', (req, res) => {
    const report = generateLargeReportSync();

    res.json(report);
});
```

If `generateLargeReportSync()` takes 5 seconds, the event loop is blocked during that time.

Other requests handled by the same Node.js event loop are delayed too.

Better approaches depend on the workload:

- Use asynchronous I/O for database and network operations.
- Use Worker Threads for CPU-intensive JavaScript computation.
- Use background jobs for long-running report generation.
- Cache expensive results when appropriate.

Remember: making a function `async` does not automatically make CPU-intensive work non-blocking.

### 3. Request payload size limits

Large request bodies consume memory and can affect application performance.

For example:

```javascript
app.use(express.json({
    limit: '1mb'
}));
```

This limits JSON request bodies to approximately 1 MB.

Why does this matter?

Imagine an API receiving a 100 MB JSON payload. Express may need to buffer and parse that payload, consuming significant memory.

Production recommendations:

- Set appropriate body-size limits.
- Validate uploaded file sizes.
- Use streaming for large file uploads.
- Configure reverse-proxy limits as well.
- Reject unexpectedly large requests with HTTP 413.

Don't use an unnecessarily large global limit just because one endpoint accepts large files.

### 4. Compression

Response compression can reduce network transfer size.

For example, JSON responses may become significantly smaller when compressed.

Using Express compression middleware:

```javascript
const compression = require('compression');

app.use(compression());
```

However, compression has a trade-off:

| Benefit | Cost |
| --- | --- |
| Smaller response payload | CPU overhead |
| Reduced network transfer | Additional compression time |
| Better performance on slower networks | Potentially unnecessary for already compressed content |

For production, consider whether compression should be handled by Express or by Nginx/load balancers.

If Nginx already handles compression, avoid duplicating the same work unnecessarily.

### 5. Database connection pooling

This is especially important for applications using MongoDB or PostgreSQL.

Avoid opening a new database connection for every incoming request.

Instead, establish connections during application startup and reuse them through a connection pool or shared database client.

Conceptually:

```
Application Startup
       |
       v
Database Connection Pool
       |
       +---- Request 1
       |
       +---- Request 2
       |
       +---- Request 3
```

Why?

- Reduces connection-establishment overhead.
- Controls the number of concurrent database connections.
- Improves resource utilization.
- Avoids overwhelming the database.

A senior developer should also understand pool sizing, connection timeouts, idle connections, and how total pool size multiplies across application instances.

### 6. Response handling and caching

For frequently requested data, caching can reduce database load and response latency.

Example:

```javascript
app.get('/config', async (req, res) => {
    const config = await configService.getConfig();

    res.set('Cache-Control', 'public, max-age=300');

    res.json(config);
});
```

This allows suitable HTTP caches to reuse the response for five minutes.

But be careful:

- Don't publicly cache user-specific or sensitive responses.
- Choose cache duration based on how frequently data changes.
- Use correct cache invalidation strategies.
- Consider `private` or `no-store` for sensitive responses.

For backend-to-backend caching, Redis may be more suitable than relying on HTTP caching alone.

### 7. Production checklist

| Area | Recommendation |
| --- | --- |
| Middleware | Keep the stack lean and ordered correctly |
| CPU | Avoid blocking the event loop |
| Payload | Configure request-size limits |
| Compression | Apply where it provides a net benefit |
| Database | Reuse connections and configure pools |
| Caching | Cache suitable frequently accessed data |
| Logging | Use structured logs and request IDs |
| Security | Configure Helmet, CORS, and input validation appropriately |
| Monitoring | Track latency, error rates, CPU, memory and event-loop delay |
| Deployment | Use graceful shutdown and health checks |

### 8. Senior-level interview scenario

Question: Your Express application is experiencing increased response times under high traffic. How would you investigate and optimize it?

A good answer:

> First, I would identify where the latency is coming from rather than immediately optimizing Express middleware. I would inspect application metrics, request latency, event-loop delay, CPU and memory utilization, database query latency, and external API response times.
> 
> 
> If the event loop is blocked, I would investigate synchronous operations and CPU-intensive processing. If database latency is high, I would review query performance, indexes, and connection-pool configuration.
> 
> I would also review middleware overhead, payload sizes, caching opportunities, and response compression. Finally, I would validate improvements through load testing and monitor p95 and p99 latency.
>
