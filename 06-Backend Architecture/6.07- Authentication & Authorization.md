# 6.6 — Authentication & Authorization

This is an important area for senior backend interviews because authentication and authorization are not just about implementing login APIs. They involve security, identity management, access control, multi-tenancy, and protecting business resources.

We'll cover the complete architecture here. JWT and session internals will be covered separately in 6.7.

## 1. Authentication vs Authorization

These are two different security responsibilities.

Authentication — Who are you?

Authentication verifies the identity of a user or system.

Examples:

- Email and password login.
- Google login.
- API key authentication.
- Service-to-service authentication.
- Multi-factor authentication (MFA).

Authorization — What are you allowed to do?

Authorization determines whether an authenticated user can access a resource or perform an operation.

Examples:

- Can this user view a report?
- Can this user delete another user?
- Can this employee access an admin dashboard?
- Can this organization access a particular parking reservation?

| Authentication | Authorization |
| --- | --- |
| Verifies identity | Checks permissions |
| Happens before protected access | Happens after identity is established |
| Usually returns an identity | Allows or denies an action |
| Example: Login | Example: Delete user permission |

Typical HTTP responses:

- `401`: Missing or invalid authentication credentials.
- `403`: Authenticated user does not have permission.

### 3. Password storage and verification

One of the most important security rules:

Never store passwords in plain text or using reversible encryption.

Instead, store a password hash generated using a password-hashing algorithm.

Recommended choices:

- Argon2id.
- bcrypt.
- scrypt.

Argon2id is a strong default for new applications when supported by your infrastructure.

Example using bcrypt:

```jsx
const bcrypt = require('bcrypt');

async function registerUser(password) {
    const passwordHash = await bcrypt.hash(password, 12);

    await User.create({
        passwordHash
    });
}
```

During login:

```jsx
async function verifyPassword(password, passwordHash) {
    return bcrypt.compare(password, passwordHash);
}
```

Why not use SHA-256 directly?

SHA-256 is a fast general-purpose hash function. Attackers can test enormous numbers of password guesses quickly if they obtain the database.

Password-hashing algorithms are intentionally more expensive and support parameters that make brute-force attacks harder.

Also remember:

- Use unique salts; modern password-hashing libraries handle this automatically.
- Never log passwords.
- Use a secure password-reset process.
- Consider MFA for sensitive accounts.
- Apply login rate limiting and monitoring.

### 4. Authentication middleware architecture

After login, protected APIs need to identify the user.

In Express, authentication middleware can perform this responsibility.

Conceptually:

```jsx
async function authenticate(req, res, next) {
    try {
        const credentials = extractCredentials(req);

        const user = await authenticationService
            .authenticate(credentials);

        if (!user) {
            return res.status(401).json({
                message: 'Authentication required'
            });
        }

        req.user = {
            id: user.id,
            role: user.role,
            permissions: user.permissions
        };

        next();
    } catch (error) {
        next(error);
    }
}
```

This is an architectural example; the actual credential verification depends on whether you use sessions, JWT, or another authentication mechanism.

The important design decision is that downstream controllers should receive an established user identity instead of independently verifying credentials.

### 5. Role-Based Access Control (RBAC)

RBAC is one of the most common authorization models.

Permissions are assigned to roles, and users receive roles.

For example:

| Role | Permissions |
| --- | --- |
| Admin | Create, read, update, delete users |
| Manager | Read, update users |
| Employee | Read own profile |
| Guest | Access public resources |

A simple implementation:

```jsx
const rolePermissions = {
    ADMIN: ['USER_READ', 'USER_CREATE', 'USER_UPDATE', 'USER_DELETE'],
    MANAGER: ['USER_READ', 'USER_UPDATE'],
    EMPLOYEE: ['USER_READ']
};
```

Authorization middleware:

```jsx
function authorize(permission) {
    return (req, res, next) => {
        const permissions = rolePermissions[req.user.role] || [];

        if (!permissions.includes(permission)) {
            return res.status(403).json({
                message: 'Access denied'
            });
        }

        next();
    };
}
```

Usage:

```jsx
router.delete(
    '/users/:id',
    authenticate,
    authorize('USER_DELETE'),
    deleteUser
);
```

This is simple and works for smaller applications.

However, in larger systems, roles and permissions are usually stored in a database or managed through a dedicated authorization service.

### 6. RBAC vs ABAC

This is an important senior-level interview topic.

RBAC — Role-Based Access Control

Access depends on the user's role.

Example:

- Admin can manage users.
- Manager can view reports.
- Employee can view their own profile.

ABAC — Attribute-Based Access Control

Access depends on attributes of the user, resource, action, and sometimes the environment.

Example:

An employee can access a parking reservation only if:

- The reservation belongs to their organization.
- The employee is the reservation owner or has an authorized administrative role.
- The reservation is within the permitted scope.

| RBAC | ABAC |
| --- | --- |
| Role-based rules | Attribute-based rules |
| Easier to implement | More flexible |
| Good for standard role permissions | Good for contextual decisions |
| Can become complex with many roles | Requires careful policy design |

In production applications, both can be combined.

For example, RBAC determines whether a user can manage reservations, while ABAC determines which organization's reservations they can manage.

### 7. Resource-level authorization

This is where many backend security vulnerabilities occur.

Consider this endpoint:

```jsx
GET /api/reservations/123
```

The user is authenticated and has permission to view reservations.

But does that mean they can view reservation `123`?

Not necessarily.

Suppose:

- User A belongs to Organization A.
- User B belongs to Organization B.
- Reservation 123 belongs to Organization B.

If User A can access reservation 123 just by changing the ID in the URL, the application has an authorization vulnerability.

This is commonly associated with Broken Object Level Authorization (BOLA), also known as an IDOR-style vulnerability.

A safer approach:

```jsx
async function getReservation(reservationId, user) {
    const reservation = await Reservation.findOne({
        _id: reservationId,
        organizationId: user.organizationId
    });

    if (!reservation) {
        throw new AppError(
            'Reservation not found',
            404,
            'RESERVATION_NOT_FOUND'
        );
    }

    return reservation;
}
```

The important part is that resource ownership or organization scope is enforced during the data-access operation, not just by checking whether the user is authenticated.

Depending on the application, you might return 403 instead of 404. Returning 404 can avoid revealing whether another organization's resource exists.

Senior-level rule: Authorization must be checked at the resource level, not just at the route level.

### 8. Multi-tenant authorization

This is particularly important in SaaS applications.

Imagine one backend serves multiple organizations.

```
Application
   |
   +--- Organization A
   |       +--- Users
   |       +--- Reservations
   |
   +--- Organization B
   |       +--- Users
   |       +--- Reservations
   |
   +--- Organization C
           +--- Users
           +--- Reservations
```

Every tenant should only access its own resources unless an explicit cross-tenant permission exists.

A common approach:

1. Authenticate the user.
2. Determine their organization from trusted identity or server-side membership data.
3. Establish the tenant context.
4. Apply tenant filtering to database operations.
5. Check resource-level permissions.

Example:

```jsx
async function getUserOrders(req, res) {
    const orders = await Order.find({
        organizationId: req.user.organizationId,
        userId: req.user.id
    });

    res.json(orders);
}
```

Do not blindly trust an `organizationId` supplied by the client.

Also, be careful with background jobs and database queries that run outside HTTP middleware. Tenant isolation must be enforced there too.

### 9. Authentication strategies

There are several ways to authenticate users and systems.

| Strategy | Typical use |
| --- | --- |
| Session-based authentication | Traditional web applications |
| JWT-based authentication | APIs and distributed applications |
| API keys | Identifying and controlling API clients |
| OAuth 2.0 / OpenID Connect | Delegated access and identity |
| Mutual TLS | Service-to-service authentication |
| SSO / SAML | Enterprise identity integration |

A few important distinctions:

OAuth 2.0 is primarily an authorization framework for delegated access.

OpenID Connect (OIDC) builds on OAuth 2.0 and adds an identity layer for authentication.

SAML is commonly used for enterprise single sign-on.

API keys identify a client or application, but should not automatically be treated as proof of an individual user's identity.

We'll study JWT and sessions in depth in 6.7 instead of repeating their internals here.

### 10. Common authentication and authorization vulnerabilities

These are worth knowing for production development and interviews.

| Vulnerability | Example | Prevention |
| --- | --- | --- |
| Broken authentication | Weak password verification | Secure password hashing, MFA |
| BOLA / IDOR | Accessing another user's record by changing ID | Resource-level authorization |
| Brute-force attacks | Repeated login attempts | Rate limiting, monitoring |
| Privilege escalation | Employee gaining admin access | Server-side permission checks |
| Sensitive data exposure | Password or token in logs | Redaction and secure logging |
| Token theft | Stolen access credentials | Secure storage, TLS, short lifetimes |
| Session fixation | Reusing an attacker-known session ID | Regenerate session ID after login |
| Account enumeration | Revealing whether an email exists | Consistent responses and careful timing |

A key point: hiding buttons in the frontend is not authorization. Every protected operation must be checked on the backend.

### 11. Production authentication architecture

For a mature application, I would separate responsibilities like this:

| Component | Responsibility |
| --- | --- |
| Authentication controller | Login, logout, registration endpoints |
| Authentication service | Credential verification and identity establishment |
| Password service | Hashing and password verification |
| Authentication middleware | Validate incoming credentials |
| Authorization middleware / policy service | Check roles and permissions |
| User repository | User lookup and persistence |
| Audit service | Record security-sensitive actions |

Additional production considerations:

- Enforce HTTPS.
- Apply login and password-reset rate limits.
- Use secure account recovery workflows.
- Avoid revealing whether an account exists.
- Implement MFA for sensitive operations.
- Maintain audit logs for privileged actions.
- Revoke credentials when accounts are disabled or compromised.
- Keep authorization checks close to the resource being accessed.
- Review permissions whenever roles or organization memberships change.

## 12. Interview questions

Q1. What is the difference between authentication and authorization?

Authentication verifies a user's identity, whereas authorization determines whether that user has permission to perform a specific action.

Q2. Why should passwords be hashed instead of encrypted?

Password hashing is one-way, so the original password cannot be directly recovered. Encryption is reversible if the decryption key is available. Passwords should be stored using dedicated, slow password-hashing algorithms.

Q3. What is the difference between RBAC and ABAC?

RBAC grants access based on roles. ABAC evaluates attributes such as user identity, resource ownership, organization, action, and environmental conditions.

Q4. What is BOLA?

Broken Object Level Authorization occurs when a user can access another user's or tenant's resource by manipulating an object identifier without proper server-side authorization checks.

Q5. Is JWT authentication the same as authorization?

No. JWT is a token format commonly used to carry identity and claims. Authentication validates the token and establishes identity; authorization checks whether that identity can perform the requested action.

Q6. Should authorization be implemented only in middleware?

No. Middleware can enforce broad route-level permissions, but resource ownership and tenant-level access often need to be enforced in services or data-access queries as well.

Q7. What is the difference between OAuth 2.0 and OpenID Connect?

OAuth 2.0 provides delegated authorization. OpenID Connect adds authentication and identity information on top of OAuth 2.0.

## 13. What you should remember

For senior backend interviews, these are the most important points:

1. Authentication establishes identity; authorization controls access.
2. Never store plain-text passwords.
3. Use secure password hashing such as Argon2id or bcrypt.
4. Understand RBAC and ABAC.
5. Enforce resource-level authorization.
6. Protect tenant boundaries in multi-tenant applications.
7. Don't trust frontend permission checks.
8. Understand OAuth 2.0, OIDC, and SAML at an architectural level.
9. Treat API keys and user authentication as different concepts.
