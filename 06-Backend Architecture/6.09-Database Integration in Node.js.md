# Phase 6.9 — Database Integration in Node.js

This topic is not about database architecture or database design. We'll focus on how Node.js applications communicate with databases efficiently and safely.

Since you've worked with both PostgreSQL and MongoDB, I'll use both in the examples.

## 2. Database drivers and connection management

A database driver is the library that allows your Node.js application to communicate with a database.

Some common examples:

| Database | Node.js library |
| --- | --- |
| PostgreSQL | `pg` |
| MongoDB | `mongodb` |
| MongoDB ODM | `mongoose` |
| PostgreSQL ORM | `Prisma`, `Sequelize`, `TypeORM` |

For example, using PostgreSQL:

```jsx
const { Pool } = require('pg');

const pool = new Pool({
  host: process.env.DB_HOST,
  port: 5432,
  database: process.env.DB_NAME,
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  max: 20,
  idleTimeoutMillis: 30000,
  connectionTimeoutMillis: 5000
});

module.exports = pool;
```

Here, we're creating a connection pool instead of establishing a new database connection for every request.

Let's understand why.

## 3. Connection pooling — very important

Imagine your Express application receives 100 concurrent HTTP requests.

All 100 requests need to execute database queries.

Without connection pooling, an application that creates a new database connection for every request could attempt to establish 100 connections.

This is inefficient because:

- Creating database connections has overhead.
- Database servers have connection limits.
- Too many connections consume memory and other resources.
- Connection establishment adds latency.

A connection pool maintains a reusable collection of database connections.

![DB Connection Pool](https://images.openai.com/static-rsc-4/9j_qRL-c-2DxVDxsheqcGJAYsetJ_SxwIA3g3Snd0jY0c9t584znHvH7NajqJYrTEhFIheekt4o_KY9mZQsbbEju0Pq3g3DpM8KRBiPGaHmEUI42J_KWav-35S6NMrFyZlNxZrvM7HmIMF6edtDOqbpJKa-GKUlA7LxvvbmWaqY?purpose=inline)

### How it works

Suppose your pool has a maximum of five connections.

1. Request A acquires connection 1.
2. Request B acquires connection 2.
3. Request C acquires connection 3.
4. Request D acquires connection 4.
5. Request E acquires connection 5.
6. Request F arrives, but all connections are busy.
7. Request F waits until a connection becomes available.
8. When Request A finishes, its connection is released.
9. Request F can now use that connection.

The important point is that the connection is released back to the pool, not permanently closed after every request.

### What happens when the pool is exhausted?

Suppose:

- Pool maximum = 20 connections.
- 20 queries are running.
- Another 50 requests arrive and need the database.

Those additional requests may wait in the pool's acquisition queue.

If connections aren't released quickly enough, the queue grows, requests become slow, and eventually acquisition timeouts can occur.

This is a common production problem.

### Important pool configuration options

For PostgreSQL using `pg`:

| Option | Meaning |
| --- | --- |
| `max` | Maximum number of connections |
| `min` | Minimum number, where supported by the driver |
| `idleTimeoutMillis` | How long an idle connection can remain before removal |
| `connectionTimeoutMillis` | Maximum time to wait for a connection |
| `maxUses` | Maximum uses before a connection is replaced |

Don't assume that increasing `max` always improves performance.

For example:

- Application instance 1: 20 connections.
- Application instance 2: 20 connections.
- Application instance 3: 20 connections.

Total potential connections = 60.

If you deploy 10 instances, each configured for 20 connections, that's potentially 200 database connections.

You need to consider the combined connection demand of all application processes.

This is especially important when using PM2 cluster mode or horizontally scaling Node.js instances.

## 4. Connection leaks in Node.js

A connection leak happens when your application acquires a database connection but fails to release it.

Consider this example:

```jsx
const client = await pool.connect();

const result = await client.query(
  'SELECT * FROM users'
);

return result.rows;
```

What's wrong?

We acquired a connection using `pool.connect()`, but never released it.

After enough requests, the pool can become exhausted.

### Correct implementation

```jsx
async function getUsers() {
  const client = await pool.connect();

  try {
    const result = await client.query(
      'SELECT * FROM users'
    );

    return result.rows;
  } finally {
    client.release();
  }
}
```

The `finally` block is important.

It runs whether:

- The query succeeds.
- The query throws an error.
- The function returns early.
- An exception occurs during processing.

Therefore, the connection is returned to the pool.

Senior-level distinction: `pool.query()` automatically manages acquiring and releasing a connection for a single query. Use `pool.connect()` when you need to execute multiple queries on the same connection, especially inside a transaction.

## 5. How MongoDB connection pooling works

MongoDB's Node.js driver also manages connection pools.

Example using Mongoose:

```jsx
const mongoose = require('mongoose');

async function connectDatabase() {
  await mongoose.connect(process.env.MONGO_URI, {
    maxPoolSize: 20,
    minPoolSize: 5,
    serverSelectionTimeoutMS: 5000,
    socketTimeoutMS: 45000
  });
}
```

Important options:

| Option | Meaning |
| --- | --- |
| `maxPoolSize` | Maximum connections in a pool |
| `minPoolSize` | Minimum connections to maintain |
| `serverSelectionTimeoutMS` | How long to wait to find a suitable MongoDB server |
| `socketTimeoutMS` | Socket inactivity timeout |

Unlike PostgreSQL's `pg` pool, MongoDB driver pools are associated with server connections and topology. In a replica set or sharded deployment, there can be pools for multiple servers.

Don't assume `maxPoolSize: 20` means only 20 total connections across every MongoDB server in every topology.

### Important mistake

Don't connect to MongoDB inside every request:

```jsx
app.get('/users', async (req, res) => {
  await mongoose.connect(process.env.MONGO_URI);

  // Query database...
});
```

This is incorrect because you're repeatedly invoking connection setup during request processing.

Instead:

- Connect once during application startup.
- Reuse the connection throughout the application.
- Handle connection failures.
- Close the connection during graceful shutdown.

The same principle applies to PostgreSQL pools.

## 6. Transactions in Node.js

A transaction allows multiple database operations to execute as one logical unit.

For example, imagine a payment operation:

1. Deduct money from Account A.
2. Add money to Account B.
3. Save the transaction record.

If step 1 succeeds but step 2 fails, we don't want the database to remain in a partially updated state.

We use a transaction to ensure that either all operations commit or the transaction rolls back.

This is a database concept, but the important Node.js-specific part is how we manage the same connection and transaction lifecycle across asynchronous operations.

### PostgreSQL transaction using `pg`

```jsx
async function transferMoney(fromId, toId, amount) {
  const client = await pool.connect();

  try {
    await client.query('BEGIN');

    await client.query(
      `UPDATE accounts
       SET balance = balance - $1
       WHERE id = $2`,
      [amount, fromId]
    );

    await client.query(
      `UPDATE accounts
       SET balance = balance + $1
       WHERE id = $2`,
      [amount, toId]
    );

    await client.query(
      `INSERT INTO transactions
       (from_account, to_account, amount)
       VALUES ($1, $2, $3)`,
      [fromId, toId, amount]
    );

    await client.query('COMMIT');

  } catch (error) {
    await client.query('ROLLBACK');
    throw error;

  } finally {
    client.release();
  }
}
```

There are three important things here.

1. All queries use the same client.

A PostgreSQL transaction belongs to a specific connection.

If you execute `BEGIN` using one client and then execute subsequent queries using `pool.query()`, those queries might run on different connections. They won't automatically participate in the same transaction.

2. Always release the connection.

Even if the transaction fails, release the connection in `finally`.

3. Roll back on failure.

If an operation fails, roll back the transaction instead of leaving it partially completed.

For production code, also consider what happens if `ROLLBACK` itself fails: log that failure, preserve the original error, and ensure the connection is not reused in an uncertain state. A connection with an uncertain transaction state may need to be discarded rather than returned as healthy.

### Important: Don't use `Promise.all()` carelessly inside a transaction

Consider:

```jsx
await client.query('BEGIN');

await Promise.all([
  client.query('UPDATE accounts ...'),
  client.query('INSERT INTO transactions ...')
]);

await client.query('COMMIT');
```

This is generally a bad pattern with a single PostgreSQL client.

Why?

- A transaction is scoped to one connection.
- Queries on one connection need predictable ordering.
- Concurrently issuing commands can create confusing sequencing and error behavior.
- One operation might fail while another is still executing.

Prefer sequential queries inside a transaction unless your specific database library explicitly documents safe transaction concurrency.

```jsx
await client.query('BEGIN');

await client.query('UPDATE accounts ...');
await client.query('INSERT INTO transactions ...');

await client.query('COMMIT');
```

This makes the transaction lifecycle easier to reason about.

## 7. Transactions in MongoDB using Mongoose

MongoDB supports transactions as well, provided the deployment supports them (for example, a replica set or sharded cluster).

Example:

```jsx
async function transferMoney(fromId, toId, amount) {
  const session = await mongoose.startSession();

  try {
    await session.withTransaction(async () => {
      await Account.updateOne(
        { _id: fromId },
        { $inc: { balance: -amount } },
        { session }
      );

      await Account.updateOne(
        { _id: toId },
        { $inc: { balance: amount } },
        { session }
      );

      await Transaction.create(
        [{
          fromAccount: fromId,
          toAccount: toId,
          amount
        }],
        { session }
      );
    });

  } finally {
    await session.endSession();
  }
}
```

Notice that we pass the same `session` to every database operation.

If we forget to pass the session to one operation, that operation may execute outside the transaction.

### Important MongoDB consideration

MongoDB's transaction API may retry certain transient transaction failures.

Therefore, don't put unrelated side effects inside the transaction callback.

For example, avoid:

```jsx
await session.withTransaction(async () => {
  await Account.updateOne(...);

  await sendEmail(); // Avoid this here.
});
```

If the transaction callback is retried, the email could be sent multiple times.

Instead:

- Commit the database transaction.
- Trigger external side effects after successful commit.
- Use an outbox or durable job mechanism when reliable delivery is required.

## 8. ORM vs ODM vs native database drivers

This is an important area for a senior Node.js developer.

| Type | Meaning | Examples |
| --- | --- | --- |
| Native driver | Direct database communication | `pg`, `mongodb` |
| ORM | Maps relational database data to application objects | Prisma, Sequelize, TypeORM |
| ODM | Maps document database data to application objects | Mongoose |

### Native driver

Example:

```jsx
const result = await pool.query(
  'SELECT * FROM users WHERE id = $1',
  [userId]
);
```

Advantages:

- More direct control over queries.
- Less abstraction.
- Useful for complex SQL and performance-sensitive operations.

Disadvantages:

- More manual query and mapping work.
- You manage more database interaction details yourself.

### ORM

Example using Prisma:

```jsx
const user = await prisma.user.findUnique({
  where: {
    id: userId
  }
});
```

Advantages:

- Convenient query APIs.
- Type safety, depending on the ORM.
- Schema and migration tooling.
- Less repetitive database access code.

Disadvantages:

- Abstraction can hide query complexity.
- Generated queries may not always be optimal.
- Complex queries sometimes require raw SQL.

### ODM

Example using Mongoose:

```jsx
const user = await User.findById(userId);
```

Mongoose provides:

- Schema definitions.
- Validation.
- Middleware/hooks.
- Query helpers.
- Population.
- Document lifecycle management.

But remember: Mongoose is not the MongoDB database itself. It is an abstraction layer over the MongoDB driver.

### What should a senior developer understand?

You should be able to:

- Understand the actual query generated by an ORM.
- Identify when an abstraction creates inefficient queries.
- Use raw queries when necessary.
- Understand transaction behavior in your selected library.
- Avoid relying blindly on ORM defaults.

## 9. Common database integration problems in Node.js

These are particularly relevant to production debugging.

| Problem | Possible cause | What to investigate |
| --- | --- | --- |
| Requests become slow | Pool exhaustion | Active/idle connections, waiting requests |
| Connection timeout | Database overloaded or pool too small | Connection limits, query duration |
| Memory usage increases | Large result sets retained in memory | Query result size, pagination, streaming |
| Duplicate database operations | Retry without idempotency | Retry logic and request identifiers |
| Queries become slow | N+1 queries or inefficient ORM queries | Query logs and execution plans |
| Database connection leaks | Missing `release()` | Connection acquisition/release paths |
| Application fails after DB restart | Stale connections or failed reconnection handling | Driver pool and topology recovery behavior |
| Transaction hangs or fails | Long-running transaction or lock contention | Transaction duration and database locks |

### A. N+1 query problem

Imagine you fetch 100 orders and then execute another query for each order to fetch its customer.

```jsx
const orders = await Order.find();

for (const order of orders) {
  order.customer = await User.findById(order.customerId);
}
```

This produces:

- 1 query to fetch orders.
- 100 additional queries to fetch customers.

Total: 101 queries.

For a Node.js application, this also means more asynchronous operations and database round trips.

Possible solutions:

- Use SQL joins.
- Use MongoDB `populate()` where appropriate.
- Fetch related records in batches.
- Use a suitable aggregation pipeline.
- Avoid unnecessary relationship fetching.

### B. Fetching too much data

This is risky:

```jsx
const users = await User.find();
```

If the collection contains millions of records, you could load a huge amount of data into application memory.

Prefer pagination and projection:

```jsx
const users = await User.find(
  { active: true },
  { name: 1, email: 1 }
)
.limit(100);
```

The important Node.js concern is that database results are materialized into application memory. Large result sets can increase heap usage and garbage-collection pressure.

### C. Not handling database disconnection

For example, your MongoDB server restarts.

A production application should:

- Detect connection state changes.
- Log the failure.
- Allow the driver to perform its documented recovery behavior.
- Avoid creating a new connection on every failed request.
- Fail requests within reasonable time limits.
- Expose useful health information.

Don't write uncontrolled reconnect loops that create multiple pools or connections.

## 10. Database operations and the Node.js event loop

A common interview question:

If Node.js is single-threaded, how can it handle database operations asynchronously?

Consider:

```jsx
app.get('/users', async (req, res) => {
  const users = await User.find();

  res.json(users);
});
```

When the database query is executing:

- Node.js sends the request through the database driver.
- The driver waits for the database response using asynchronous I/O.
- Node.js can continue processing other requests.
- When the query completes, the Promise is resolved.
- The continuation after `await` runs when scheduled by the JavaScript runtime.

The important point is that waiting for an asynchronous database operation does not mean the JavaScript thread is blocked for the entire duration.

However, processing a very large result set synchronously or performing expensive JavaScript transformations after the query can still block the event loop.

This connects directly to the event-loop concepts we covered in Phase 1.

## 11. Database connection lifecycle in a Node.js application

A good production lifecycle looks like this:

Application startup

1. Load and validate configuration.
2. Initialize the database connection or pool.
3. Verify database connectivity.
4. Start accepting HTTP traffic only when required dependencies are ready.

During application execution

1. Reuse the shared pool.
2. Acquire and release connections correctly.
3. Monitor query duration and pool utilization.
4. Handle database errors appropriately.

Application shutdown

1. Stop accepting new HTTP requests.
2. Allow ongoing requests to finish within a deadline.
3. Close the database pool or client.
4. Exit the process.

For example, PostgreSQL:

```jsx
async function shutdown() {
  try {
    await pool.end();
    console.log('Database pool closed');
  } catch (error) {
    console.error('Error closing database pool', error);
  }
}
```

For Mongoose:

```jsx
await mongoose.disconnect();
```

The full application shutdown process is a general production concern, so we won't create a separate lesson for it. The Node.js-specific connection cleanup belongs here.

## 13. Key takeaways for your notes

- Use a shared database connection pool instead of creating a connection per request.
- Understand the pool's maximum connections, waiting behavior, and timeouts.
- Always release manually acquired PostgreSQL clients using `finally`.
- Use the same PostgreSQL client for all queries in a transaction.
- Pass the same MongoDB session to every operation in a transaction.
- Avoid external side effects inside retryable transaction callbacks.
- Understand the SQL or MongoDB operations generated by your ORM/ODM.
- Avoid N+1 queries and unnecessarily large result sets.
- Remember that asynchronous database I/O does not block the event loop while waiting.
- Close database connections during application shutdown.
