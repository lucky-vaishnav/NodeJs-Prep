## 6.5 — Middleware Architecture

You've already worked with Express middleware in daily development. Here, we'll focus on how to design middleware as a reusable backend architecture, rather than simply how to write middleware functions.

### 1. What is middleware architecture?

Middleware is a function that executes during the HTTP request-response lifecycle.

It can:

- Read and modify the request.
- Validate incoming data.
- Authenticate users.
- Check permissions.
- Log requests.
- Apply rate limits.
- Handle errors.
- Pass control to the next middleware.

### 2. Types of middleware

Express middleware can be categorized by its responsibility.

| Middleware type | Responsibility | Example |
| --- | --- | --- |
| Application-level | Applied across the application | Request logging |
| Router-level | Applied to a particular router | User authentication |
| Route-level | Applied to a specific route | Permission checks |
| Built-in | Provided by Express | `express.json()` |
| Third-party | Provided by packages | `cors`, `helmet` |
| Error-handling | Processes errors | Global error handler |

Let's look at the architectural differences.

Application-level middleware

```jsx
app.use(requestLogger);
app.use(express.json());
```

Used for functionality needed by most or all application routes.

Router-level middleware

```jsx
const userRouter = express.Router();

userRouter.use(authenticate);

userRouter.get('/', getUsers);
userRouter.get('/:id', getUser);

app.use('/api/users', userRouter);
```

Authentication applies to all routes inside this router.

Route-level middleware

```jsx
router.post(
    '/',
    authenticate,
    authorize('USER_CREATE'),
    validate(createUserSchema),
    createUser
);
```

This gives precise control over which middleware applies to each endpoint.

### 3. Middleware composition and reusability

One of the most important middleware design principles is to create small middleware functions with a single responsibility.

For example, avoid creating one large middleware that handles authentication, authorization, validation, and logging.

Instead:

```jsx
router.post(
    '/users',
    authenticate,
    authorize('USER_CREATE'),
    validate(createUserSchema),
    userController.create
);
```

Each middleware has a separate responsibility.

Benefits:

- Easier testing.
- Reusable across routes.
- Easier debugging.
- Clear execution flow.
- Less duplicated logic.

You can also create middleware factories.

For example, authorization middleware:

```jsx
function authorize(requiredPermission) {
    return (req, res, next) => {
        const permissions = req.user?.permissions || [];

        if (!permissions.includes(requiredPermission)) {
            return res.status(403).json({
                message: 'Access denied'
            });
        }

        next();
    };
}
```

Usage:

```jsx
router.delete(
    '/users/:id',
    authenticate,
    authorize('USER_DELETE'),
    userController.delete
);
```

Here, `authorize()` returns a middleware function configured with the required permission.

This is called a middleware factory.

It is particularly useful when the same middleware logic needs different configurations for different routes.

### 4. Authentication vs authorization middleware

These two responsibilities should remain separate.

Authentication: Who are you?

Authentication verifies the user's identity.

Example:

```jsx
async function authenticate(req, res, next) {
    try {
        const token = req.headers.authorization?.split(' ')[1];

        if (!token) {
            return res.status(401).json({
                message: 'Authentication required'
            });
        }

        const decoded = jwt.verify(token, process.env.JWT_SECRET);

        req.user = {
            id: decoded.sub,
            role: decoded.role
        };

        next();
    } catch (error) {
        next(error);
    }
}
```

After successful authentication, user information becomes available through `req.user`.

Authorization: What are you allowed to do?

```jsx
function authorize(requiredRole) {
    return (req, res, next) => {
        if (req.user?.role !== requiredRole) {
            return res.status(403).json({
                message: 'Insufficient permissions'
            });
        }

        next();
    };
}
```

Example:

```jsx
router.delete(
    '/users/:id',
    authenticate,
    authorize('ADMIN'),
    deleteUser
);
```

The distinction:

| HTTP status | Meaning |
| --- | --- |
| 401 Unauthorized | Authentication is missing or invalid |
| 403 Forbidden | Identity is known, but permission is insufficient |

Strictly speaking, HTTP 401 means the request lacks valid authentication credentials, while 403 means the server refuses the action.

### 5. Middleware should not contain business logic

This is an important architectural boundary.

Suppose you have an API for creating a parking reservation.

A poor design would be to put the complete reservation process inside middleware:

```jsx
async function reservationMiddleware(req, res, next) {
    // Validate parking availability
    // Calculate price
    // Create reservation
    // Process payment
    // Send confirmation
}
```

This makes the middleware difficult to reuse, test, and maintain.

A better design:

```jsx
router.post(
    '/reservations',
    authenticate,
    validate(reservationSchema),
    reservationController.create
);
```

Then:

```jsx
async function create(req, res) {
    const reservation = await reservationService.create(req.body, req.user);

    res.status(201).json(reservation);
}
```

The service handles the actual business operation.

Rule of thumb:

- Middleware handles cross-cutting concerns.
- Controllers handle HTTP request/response coordination.
- Services handle business logic.
- Repositories handle data access.

Not every concern belongs in middleware just because it runs before a controller.

### 6. Request context and `req` mutation

Middleware often attaches information to the request object.

For example:

```jsx
function requestContext(req, res, next) {
    req.context = {
        requestId: crypto.randomUUID(),
        receivedAt: Date.now()
    };

    next();
}
```

Later middleware and controllers can access:

```jsx
console.log(req.context.requestId);
```

Common examples include:

- Authenticated user.
- Request ID.
- Tenant ID.
- Correlation ID.
- Validated request data.

However, follow some rules:

1. Use consistent property names.
2. Avoid overwriting Express properties.
3. Don't store unnecessary large objects on `req`.
4. Don't store request-specific data in global variables.
5. Treat client-provided values as untrusted until validated.

For example, never assume a client-provided `tenantId` is authorized simply because it exists in a request header.

### 7. Request validation middleware

Validation is another common cross-cutting concern.

Instead of validating input separately inside every controller, create reusable validation middleware.

Example using Zod:

```jsx
const { z } = require('zod');

const createUserSchema = z.object({
    body: z.object({
        name: z.string().min(2),
        email: z.string().email()
    })
});

function validate(schema) {
    return (req, res, next) => {
        const result = schema.safeParse({
            body: req.body,
            params: req.params,
            query: req.query
        });

        if (!result.success) {
            return res.status(400).json({
                message: 'Validation failed',
                errors: result.error.issues
            });
        }

        req.validated = result.data;

        next();
    };
}
```

Usage:

```jsx
router.post(
    '/users',
    validate(createUserSchema),
    createUser
);
```

Controller:

```jsx
async function createUser(req, res) {
    const { name, email } = req.validated.body;

    const user = await userService.create({ name, email });

    res.status(201).json(user);
}
```

This creates a clean boundary: the controller works with validated input instead of trusting raw request data.

In production, make sure validation errors are formatted consistently and don't accidentally expose sensitive input values.

### 8. Middleware ordering — a real production concern

Middleware ordering can affect security and application behavior.

Consider:

```jsx
app.use('/api', userRouter);

app.use(express.json());
```

This is problematic if your routes expect parsed JSON request bodies.

The JSON parser was registered after the router, so it won't run before the route handlers.

A better arrangement:

```jsx
app.use(helmet());
app.use(cors());

app.use(express.json({ limit: '1mb' }));

app.use(requestLogger);

app.use('/api/auth', authRouter);
app.use('/api/users', userRouter);
app.use('/api/orders', orderRouter);

app.use(notFoundHandler);
app.use(errorHandler);
```

Also remember:

- Authentication should run before authorization.
- Body parsing should run before middleware that reads `req.body`.
- Routes should run before the not-found handler.
- Error middleware should run after routes and other relevant middleware.

There isn't one universal ordering for every middleware. For example, logging may need to run before rate limiting to capture rejected requests too.

### 9. Common middleware mistakes

| Mistake | Why it is problematic | Better approach |
| --- | --- | --- |
| Forgetting `next()` | Request hangs | Pass control or send response |
| Calling `next()` twice | Can trigger duplicate execution/errors | Ensure one control-flow path |
| Sending response then calling `next()` | Can cause duplicate response errors | Return after sending |
| Heavy DB operations in global middleware | Adds unnecessary latency | Scope it to required routes |
| Business logic in middleware | Creates tight coupling | Move it to services |
| Trusting request headers | Security vulnerability | Validate and authorize |
| Storing user data globally | Cross-request data leakage | Keep it request-scoped |
| Logging tokens/passwords | Sensitive data exposure | Redact sensitive fields |

### 10. How to test middleware independently

Middleware should be testable without starting the entire Express application.

For example, with Jest:

```jsx
describe('authorize middleware', () => {
    it('should reject users without permission', () => {
        const req = {
            user: {
                permissions: []
            }
        };

        const res = {
            status: jest.fn().mockReturnThis(),
            json: jest.fn()
        };

        const next = jest.fn();

        authorize('USER_DELETE')(req, res, next);

        expect(res.status).toHaveBeenCalledWith(403);
        expect(next).not.toHaveBeenCalled();
    });
});
```

Test at least:

- Successful execution.
- Missing authentication.
- Insufficient permissions.
- Invalid request data.
- Errors passed to `next(error)`.
- Correct behavior when middleware is composed.

## 11. Express middleware vs NestJS guards, interceptors and pipes

Since you work with both Express and NestJS, this distinction is useful.

| Express | NestJS equivalent / related concept |
| --- | --- |
| Middleware | Middleware |
| Authentication middleware | Often Guard |
| Authorization middleware | Guard |
| Validation middleware | Pipe |
| Request/response transformation | Interceptor |
| Centralized error middleware | Exception Filter |

These are conceptual mappings, not exact one-to-one replacements.

For example:

- Express middleware is commonly used for authentication.
- NestJS Guards are specifically designed for authorization decisions.
- NestJS Pipes handle transformation and validation.
- NestJS Interceptors can wrap handler execution and transform results.

NestJS builds a more structured request lifecycle around these components.

## 12. Senior-level interview questions

Q1. What is middleware composition?

Combining small, independent middleware functions into a request-processing pipeline, where each function handles a specific responsibility.

Q2. What is the difference between application-level and router-level middleware?

Application-level middleware is registered on the Express application, while router-level middleware is registered on a particular router and generally applies only to that router's routes.

Q3. Why should authentication and authorization be separate?

Authentication establishes identity; authorization determines whether that identity has permission to perform a particular action.

Q4. Why should business logic not be placed in middleware?

Middleware should handle cross-cutting request-processing concerns. Business logic belongs in services, where it can be reused independently of HTTP.

Q5. How would you design reusable authorization middleware?

Use a middleware factory that accepts a required role or permission and returns a middleware function that checks the authenticated user's permissions.

Q6. What happens if middleware neither sends a response nor calls `next()`?

The request remains pending because Express has no instruction to continue or finish processing.

Q7. How would you prevent sensitive data from leaking between requests?

Keep request-specific information on the request context, avoid mutable global state, and ensure asynchronous operations don't share request-specific objects incorrectly.

## 13. What you should remember

For senior-level interviews, focus on these architectural principles:

1. Middleware should have a single responsibility.
2. Middleware should be reusable and composable.
3. Authentication and authorization should be separate.
4. Business logic belongs in services.
5. Middleware ordering is important.
6. Validate untrusted input before using it.
7. Avoid expensive global middleware.
8. Middleware should be independently testable.
